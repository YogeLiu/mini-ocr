# 第 27 章　回答的对数概率

## 本章在全景图中的位置

从第 16 章起，我们一直在用交叉熵训练模型。交叉熵的本质是**"正确 token 的对数概率"取负**。本章把这个量单独拿出来，当作一个工具来研究，因为后面几章全都建立在它上面：

| 用法 | 怎么用回答的对数概率 | 章 |
|---|---|---|
| SFT 损失 | 回答每个 token 的对数概率，取负、求平均 | 26 |
| 困惑度 | exp(−平均对数概率) | 14、16 |
| 选择题评测 | 比较几个候选答案的对数概率，选最大的 | 本章 |
| 置信度 | 用对数概率判断"模型有多大把握" | 本章、33 |
| DPO | 好回答与坏回答的对数概率之差，再和参考模型比 | 30 |
| GRPO | 新旧模型对同一个回答的对数概率之比 | 31 |

本章回答四个问题：

1. **怎样正确地算出每个 token 的对数概率？** 错位一格不会报错，但结果完全是错的；
2. **一个回答的对数概率是求和还是求平均？** 两种做法会选出不同的答案；
3. **能不能用对数概率代替生成来做评测？** 让模型在几个候选里"挑一个"，而不是自由地写；
4. **对数概率能当置信度用吗？** 模型说"我有 90% 的把握"时，它真的有 90% 的时候是对的吗？能不能靠它发现 OCR 读错的行？

第 3、4 个问题用第 24 章的 Qwen3.5-0.8B 实测（只推理，CPU 上可以跑）。

## 学习目标

1. 写出 `token_logprobs`，说清每一维、每一次错位的含义；验证它的 −平均值等于模型的损失；
2. 在两种标签约定（−100 标签、显式 mask）之间互相转换；
3. 解释求和与求平均分别偏向什么样的回答，并用实例说明；
4. 用似然对候选答案打分做选择题，知道它与生成式评测的区别；
5. 实现熵、ECE、AUROC，用它们评价置信度是否可信。

## 27.1 定义

序列 s = (s₀, s₁, …, s_{T−1})，模型在位置 t 看到 s₀ … s_t，输出一个下一个 token 的分布。第 t + 1 个 token 的对数概率是

```
ℓ_{t+1} = log π(s_{t+1} | s₀, …, s_t)
```

一个回答（序列里位置集合为 R 的一段）的对数概率是它每个 token 的对数概率之和：

```
log π(回答 | 提示) = Σ_{t ∈ R} ℓ_t
```

这正是"回答的概率"取对数：概率的链式法则把一个序列的概率拆成每个 token 的条件概率之积（第 6 章），取对数后乘积变成求和。

### 练习 27.1：`token_logprobs`

```python
def token_logprobs(logits, ids):
    lp = F.log_softmax(logits[:, :-1].float(), dim=-1)          # (B, T−1, V)
    return lp.gather(-1, ids[:, 1:, None]).squeeze(-1)           # (B, T−1)
```

逐行：

1. `logits[:, :-1]`：最后一个位置的 logits 预测的是序列之外的 token，没有对应的答案，丢掉；
2. `ids[:, 1:]`：第 0 个 token（通常是 `<bos>`）前面没有东西，它不被预测，丢掉；
3. 这两个"丢掉"让 logits 的第 t 行和 ids 的第 t + 1 个对齐。**返回值的第 t 列是第 t + 1 个 token 的对数概率**；
4. `log_softmax` 而不是 `torch.log(torch.softmax(...))`：后者在概率很小时会得到 log(0) = −∞（第 6 章的数值稳定性）；
5. `.float()`：即使模型用 bf16 计算，log_softmax 也用 fp32；
6. `gather(-1, ids[:, 1:, None])`：在最后一维（词表）上，按目标 token 的编号取出一个数。`ids[:, 1:, None]` 的形状是 (B, T−1, 1)，取出来也是 (B, T−1, 1)，`squeeze(-1)` 去掉最后一维。

手算（测试 `test_token_logprobs_by_hand`）：3 个位置、词表 3 个词，各位置的概率分别是 [0.5, 0.25, 0.25]、[0.1, 0.8, 0.1]、[1/3, 1/3, 1/3]，ids = [2, 0, 1]。位置 0 预测 ids[1] = 0，概率 0.5；位置 1 预测 ids[2] = 1，概率 0.8；位置 2 的分布被丢掉。结果是 [log 0.5, log 0.8]。

### 在真实模型上核对

第 1 部分用第 16 章训练好的字符级 GPT，在验证集的一段 300 个字符的文字上：

```
300 个字符；−平均对数概率 1.1564，模型自己算的损失 1.1564（应该相同）
平均每个字符 1.67 比特；困惑度 3.18（字符表 100 个）
```

**语言模型的损失就是 −平均对数概率**，这是检查 `token_logprobs` 有没有写对的第一道关。困惑度 3.18 的意思是：平均来说，模型在每个位置的不确定程度相当于在 3.18 个字符里均匀地猜，而字符表有 100 个。

### 每个 token 读出了什么

第一行文字的前 40 个字符（数字是对数概率，括号里是模型在预测这个字符时的熵，27.5 节讲）：

```
'T':-12.21(0.0)  'a':-4.71(2.6)  'b':-1.85(1.3)  'l':-0.00(0.0)  'e':-0.00(0.0)  ' ':-0.39(0.8)  'c':-3.39(3.3)  'o':-1.01(1.8)
'n':-2.28(1.8)  't':-0.00(0.0)  'a':-0.00(0.0)  'i':-0.00(0.0)  'n':-0.00(0.0)  ' ':-0.31(0.8)  'r':-3.36(3.1)  ...
```

- `Table` 的 `l`、`e`，`contain` 的 `tain`：对数概率 −0.00，模型几乎 100% 确定。读到 `Tab` 时，后面是 `le` 几乎没有悬念；
- 每个词的**第一个字母**（`c`、`r`、`b`）对数概率在 −3 左右，熵也最大：下一个词是什么，模型拿不准；
- 第一个字符 `T` 的对数概率是 **−12.21**，而熵是 **0.0**。熵为 0 说明模型非常确定，对数概率极低说明它确定的不是 `T`。原因：第 16 章的预训练数据是首尾相接的文字，**从来没有出现过 `<bos>`**。模型在 `<bos>` 之后预测的是换行符（实测概率 99.5%），它对一个从没见过的输入给出了一个自信但错误的回答。这一个字符就贡献了整段总和的 3.5%。

按字符的类别平均（"下一个字符是这一类"时）：

| 类别 | 个数 | 平均对数概率 | 对应的概率 | 平均熵 |
|---|---|---|---|---|
| 空格、换行 | 48 | −0.22 | 80.4% | 0.45 |
| 标点 | 19 | −0.68 | 50.9% | 0.44 |
| 词内字母 | 146 | −0.80 | 45.2% | 0.82 |
| 公式（`$$` 之间） | 45 | −1.21 | 29.9% | 1.20 |
| 数字 | 5 | −3.46 | 3.2% | 2.43 |
| 词首字母 | 37 | −3.67 | 2.5% | 2.92 |

困难集中在两类地方：**新词的开头**、**随机的数字**。语言模型的大部分损失来自少数几个"信息量大"的位置：词首字母和数字只占 42 个字符（14%），却贡献了总和的约 44%。这个模式对 OCR 也很重要：一个 VLM 读一行字时，它的语言先验在词内很强（读出 `Tab` 就会写 `le`），在词首和数字上很弱，必须依赖图像。第 24 章看到的幻觉，大多发生在语言先验和图像冲突的地方。

## 27.2 错位：不报错的 bug

第 2 部分故意把对齐写错：

```
正确（位置 t 预测 ids[t + 1]）：平均对数概率  -1.16
错成 ids[t]（没错位）：        平均对数概率 -10.38
错成 ids[t + 2]（多错一位）：  平均对数概率  -9.64
均匀猜测：                     平均对数概率  -4.61
```

两种错误都不会报错：形状对得上（或者只差一列），代码照样跑完，得到一个负数。只有和"均匀猜测"（−ln 100 = −4.61）比较，才会发现结果比瞎猜还差得多。

"没错位"时为什么特别差？位置 t 的输出是"下一个字符"的分布，用它去取"当前字符"的概率：模型刚读到 `a`，它预测下一个字符几乎不会还是 `a`，所以这个概率很低。

**检查对齐的三个办法**：

1. 和模型自己算的损失比较（第 1 部分）：−平均对数概率应该等于损失；
2. 和均匀猜测比较：训练过的模型的平均对数概率应该远高于 −ln V；
3. 在一个手算的小例子上核对（测试 `test_token_logprobs_by_hand`）。

真实的后训练代码里，这个错误常常以更隐蔽的形式出现：logits 已经被框架错位过一次（有的实现返回的 logits 已经去掉了最后一个位置），你又错位一次。**每次换框架、换模型，都要重新做一次这三个检查**。

## 27.3 只算回答：两种约定

前面几章用的是**约定一**：标签和 ids 一样长，不算的位置是 −100（第 22、26 章）。强化学习的代码里更常见的是**约定二**：先算出每个位置的对数概率 (B, T−1)，再乘一个显式的 0/1 mask。

| | 约定一：−100 标签 | 约定二：显式 mask |
|---|---|---|
| 形状 | targets (B, T)，最后一列总是 −100 | mask (B, T−1) |
| 第 t 列的含义 | 位置 t 要预测的 token（= ids[t + 1]），或 −100 | 第 t + 1 个 token 是否属于回答 |
| 用在 | `cross_entropy(ignore_index=-100)` | `(token_logprobs * mask).sum()` |
| 能拿到每个 token 的值吗 | 不能（直接得到平均损失） | 能 |

两者描述的是同一件事，只是存储方式不同。

### 练习 27.2、27.3：mask 与互相转换

```python
def response_mask(roles):
    return torch.tensor([1.0 if r == ROLE_ANSWER else 0.0 for r in roles[1:]])

def labels_to_mask(targets):
    return (targets[:, :-1] != -100).float()

def mask_to_labels(ids, mask):
    tg = torch.where(mask.bool(), ids[:, 1:], torch.full_like(ids[:, 1:], -100))
    return torch.cat([tg, torch.full_like(ids[:, :1], -100)], 1)
```

- `response_mask` 看 `roles[1:]`：第 t 列对应第 t + 1 个 token，和 `token_logprobs` 的对齐方式一致；
- `labels_to_mask` 丢掉最后一列（它总是 −100）；
- `mask_to_labels` 是反过来：mask 为 1 的位置填目标 token，其余 −100，最后补一列 −100。

另一个常用的版本 `mask_from_lengths`：已知提示长 3、总长 7、补齐到 10 时，目标位置 j = 1 … 9 中 3 ≤ j < 7 的为 1，得到 `[0, 0, 1, 1, 1, 1, 0, 0, 0]`。

测试 `test_masks_and_conventions` 检查三件事：两种约定互相转换不丢信息；回答的 −平均对数概率等于第 26 章的 `sft_loss`；`seq_logprob` 的求和与手动求和一致。**SFT 的损失不是另一个东西，它就是回答 token 对数概率的负平均**。

## 27.4 求和还是平均

### 两种汇总

```python
def seq_logprob(lp, mask, reduce="sum"):
    s = (lp * mask).sum(-1)
    return s if reduce == "sum" else s / mask.sum(-1).clamp(min=1)
```

- **求和**：回答的概率的对数。这是"严格"的定义，回答越长，乘的概率越多，总和越负；
- **平均**：每个 token 平均的对数概率。和长度无关，衡量的是"每个 token 写得有多顺"。

### 它们会选出不同的答案

第 2 部分给字符级 GPT 一个开头，比较五种接法（每种接法后面加一个换行，表示"说完了"）：

```
开头 'Every that fire word just thought '
'it.'                                4 个字符  总和   -7.79  平均  -1.95
'state.'                             7 个字符  总和   -7.83  平均  -1.12
'a.'                                 3 个字符  总和  -15.19  平均  -5.06
'state state state state.'          25 个字符  总和  -28.72  平均  -1.15
'thought thought thought.'          25 个字符  总和  -19.97  平均  -0.80
按总和最好：'it.'；按平均最好：'thought thought thought.'
```

- **按总和**，最短的 `it.` 胜出（虽然它每个字符写得并不顺，平均 −1.95）：短回答乘的概率少，天然占便宜；
- **按平均**，`thought thought thought.` 胜出：重复前文的词，每个字符都很好预测（语言模型很擅长"抄前面的"），平均只有 −0.80。但它显然不是一个好的接法。

这就是**长度偏差**：

- 用求和比较，偏向**短**回答；
- 用平均比较，偏向**长而啰嗦、容易预测**的回答（包括重复）。

两种都不完美，关键是知道自己用的是哪一种、它鼓励什么。原始的 DPO（第 30 章）用求和；有的变体（SimPO 等）改用平均来消除对短回答的偏好，代价是可能鼓励啰嗦。原始的 GRPO（第 31 章）先在每个回答内部按 token 平均、再在回答之间平均（相当于第 26 章的"按样本平均"）；DAPO 改成在所有回答的所有 token 上一起平均，理由是长回答里的每个 token 不应该被稀释。

在选择题里（27.6 节），候选答案的长度如果差别很大，这个偏差会直接决定结果。

## 27.5 熵：模型有多拿不准

### 定义

位置 t 的预测分布 p 的熵：

```
H_t = −Σ_v p(v) log p(v)
```

- 范围是 [0, ln V]：0 表示所有概率都在一个 token 上；ln V 表示 V 个 token 均匀分布；
- 熵和"正确 token 的对数概率"是两个不同的量：熵只看分布本身，不看答案。第 1 部分的第一个字符 `T` 就是一个例子：熵 0.0（模型很确定），对数概率 −12.21（它确定的东西是错的）。

### 练习 27.4：`token_entropy`

```python
def token_entropy(logits):
    lp = F.log_softmax(logits[:, :-1].float(), dim=-1)
    return -(lp.exp() * lp).sum(-1)
```

用 `log_softmax` 先得到 log p，再 `exp` 得到 p。直接 `p * torch.log(p)` 在 p = 0 时是 0 × (−∞) = NaN；用 log_softmax 时 log p 是一个很大的负数（不是 −∞），乘以几乎为 0 的 p 得到 0。

第 1 部分里熵最大的 5 个位置都在 `54 numeral look King Plan` 这一行：它是一个随机生成的单词序列，每个词的开头都无法预测，熵约 3.7（相当于在 e^3.7 ≈ 40 个字符里均匀地猜）。

熵在强化学习里是一个重要的监控量（第 31 章）：训练中如果熵迅速降到接近 0，说明模型的输出越来越单一，不再"探索"别的回答，这叫**熵坍缩**。

### 补齐和精度

第 1 部分还检查了两件事：

```
右侧补齐 8 个 <pad>：前面位置的对数概率最大差 6.3e-06
模型改用 bf16：每个字符的对数概率平均差 0.0067，最大差 0.272；整段的总和 -346.91（fp32） vs -347.02（bf16）
```

- 右侧补齐不改变前面位置的结果：因果注意力里，前面的位置看不到后面（差 6.3 × 10⁻⁶ 是浮点舍入）。所以批量计算时可以放心补齐，只要 mask 把补齐的位置排除；
- bf16 下单个字符的对数概率最多差 0.27。这对训练损失无所谓，但在 DPO、GRPO 里，我们要比较**两个很接近的对数概率之差**（新旧模型对同一个回答），0.1 量级的误差可能和信号本身一样大。所以后训练代码通常让 log_softmax 在 fp32 里算（`token_logprobs` 里的 `.float()`），有的实现甚至让最后一层也用 fp32。

## 27.6 用似然做选择题

### 两种评测方式

问一个 VLM "图里有几个物体？"，有两种方式拿到它的答案：

1. **生成**：让它自由地写，再把写出来的文字和真值比较（第 24 章）。要处理大小写、多余的句号、"There are 3 shapes." 这样的完整句子；
2. **打分**：给出候选答案（"1"、"2"、"3"），分别算 log π(候选 | 图, 问题)，选最大的。模型不需要写，只需要"认"。

打分的好处：没有格式问题，结果确定（不依赖解码策略），还能得到每个候选的概率。SEED-Bench 最初的评测方式，以及很多语言模型的多选基准（HellaSwag、ARC 等，lm-evaluation-harness 的默认做法）用的就是这样的似然打分；MMBench 则是让模型生成、再把回答匹配到选项上。坏处：只能用于答案空间是有限集合的任务；而且它测的是"认"的能力，不是"写"的能力，两者可能不一致。

### Qwen3.5 的结果

第 3 部分用第 24 章第 5 部分同样的 50 张图、同样的问题，对每个候选算"候选 + `<|im_end|>`"的总对数概率。每个候选试两种写法：直接写（`1`、`red`、`yes`），和前面加一个空格（` 1`、` red`、` yes`）。

| 任务 | 候选 | 无空格：按似然选 | 无空格：候选的概率之和 | 加空格：按似然选 | 加空格：候选的概率之和 | 第 24 章：生成后比较 |
|---|---|---|---|---|---|---|
| count | 1、2、3 | 98% | 99.3% | 96% | 0.0% | 98% |
| left | 四种颜色 | 86% | 72.3% | 88% | 27.4% | 86% |
| exists | yes、no | 98% | 0.1% | 98% | 0.2% | 98% |

（"候选的概率之和"是每道题里所有候选的概率加起来，取 50 道题的中位数：模型把多少概率给了我们写出的这几种回答。）

三个观察：

**一、按似然选和生成后比较的准确率几乎相同。** 候选都是一两个 token 时，打分和贪心生成在做几乎同一件事（27.12 节）。

**二、写法很重要，而且不同任务不一样。** 数数时，模型把 99.3% 的概率给了不带空格的 `1`、`2`、`3`；带空格的写法 ` 1` 被分词成 `Ġ` + `1` 两个 token，几乎没有概率。颜色则分成两半：不带空格 72.3%、带空格 27.4%——模型自己生成颜色时也会在两种写法之间摇摆。这是 Qwen 的分词器（BPE，第 14 章）的特点：`Ġred`（带空格的 red）和 `red` 是两个不同的 token。

**三、exists 的两种写法都只拿到 0.1–0.2% 的概率，准确率却仍然是 98%。** 模型真正想写的是首字母大写的 `Yes` / `No`（第 24 章第 5 部分的例子里，回答都是 `Yes`）。我们的候选几乎都不是它会写的东西，但在 `yes` 和 `no` 之间，正确的那个仍然更可能。所以**似然打分只看候选之间的相对大小**，候选的写法不自然时，绝对概率没有意义，相对排名有时仍然可用——但这不可靠，应该先看模型自己生成时用什么写法。

用候选之间 softmax 后的最大概率作为置信度（加空格的写法），150 道题的 ECE 是 0.067：

| 置信度段 | 平均置信度 | 准确率 | 题数 |
|---|---|---|---|
| [0.4, 0.5) | 49.5% | 50.0% | 2 |
| [0.5, 0.6) | 55.9% | 66.7% | 3 |
| [0.6, 0.7) | 68.0% | 75.0% | 4 |
| [0.7, 0.8) | 74.8% | 100.0% | 7 |
| [0.8, 0.9) | 85.6% | 100.0% | 26 |
| [0.9, 1.0) | 98.1% | 94.4% | 108 |

大部分题目置信度在 0.9 以上，那一段的准确率 94.4%，略低于平均置信度 98.1%（轻微的过度自信）；0.7–0.9 的两段反而全对（略微不够自信）。整体校准得相当好。注意每段的题数：0.4–0.7 的三段一共只有 9 道题，那里的"准确率"几乎没有统计意义（第 25 章）。

## 27.7 置信度与校准

### 两个问题

把对数概率当成"置信度"时，要分开问两个问题：

1. **区分**：读错的行，置信度是不是普遍更低？用 **AUROC** 衡量：随机抽一行读错的、一行读对的，读错的那行分数更"可疑"的概率。1 表示完美区分，0.5 表示和瞎猜一样；
2. **校准**：模型说"这一行有 80% 的概率完全正确"时，这样的行里是不是真有 80% 是对的？用**可靠性图**和 **ECE** 衡量。

两者是不同的性质：把所有置信度都乘以 0.5，排名不变（AUROC 不变），但数值全错了（ECE 变大）。

### 练习 27.5：ECE

```python
def ece(conf, correct, n_bins=10):
    n = len(conf)
    return float(sum(cnt / n * abs(acc - c) for _, _, c, acc, cnt in reliability(conf, correct, n_bins)))
```

`reliability` 把 [0, 1] 等分成 10 段，统计每段的样本数、平均置信度、准确率。ECE 是各段 |准确率 − 置信度| 按样本数加权的平均。测试里两个手算的例子：10 个样本都说 90%、对了 9 个，ECE = 0；4 个样本都说 100%、对了 2 个，ECE = 0.5。

### 练习 27.6：AUROC

```python
def auroc(scores, labels):
    ...                              # 排序，并列取平均名次（从 1 开始）
    return (R - npos * (npos + 1) / 2) / (npos * nneg)
```

R 是正例的名次之和（推导见 27.12 节）。测试把它和"枚举所有正负配对、逐对比较"的结果对比，200 个随机样本上完全相同。

### 第 4 部分：Qwen3.5 读文字行，它知道自己读错了吗

第 24 章第 6 部分的设置（50 行，放大 2 倍）：CER 12.80%，整行正确 60%，与第 24 章完全相同。对每一行，用模型**生成时的 token 编号**再做一次前向，得到每个 token 的对数概率。

**先说一个作者自己犯的错误。** 第一版代码把生成的文字（解码、去掉首尾空格之后）重新分词，再算对数概率。结果读对的单词 `went` 的对数概率是 −4.28。贪心生成选的是概率最大的 token，怎么可能只有 e^−4.28 ≈ 1.4%？打印生成时的 token 才发现：

```
生成：      ['Ġwent', '<|im_end|>']            第一个 token 的对数概率 −0.06
重新分词：  ['went', '<|im_end|>']             第一个 token 的对数概率 −4.28
```

Qwen3.5 回答时总是先写一个带前导空格的 token（`Ġ` 表示空格）。`strip()` 去掉了这个空格，重新分词就得到了另一个 token `went`，模型几乎不会写它。修正后的第 4 部分统计：

```
重新分词后与生成时的 token 完全相同的行：20%
整行的对数概率（中位数）：用生成时的编号 -0.80，用重新分词的编号 -3.08
```

80% 的行重新分词后变了样，对数概率被系统性地低估了约 2.3 nat。**永远直接用生成时的 token 编号打分**；如果只有文字，先确认重新分词能不能还原生成时的 token。

### 区分：AUROC

50 行里，NED > 0.5 的"严重读错"有 4 行，"不完全对"有 20 行。用几种分数把它们挑出来：

| 分数（越大越可疑） | 严重读错 | 不完全对 |
|---|---|---|
| −平均对数概率 | 0.978 | 0.810 |
| −最低的 token 对数概率 | 0.984 | 0.820 |
| −总对数概率 | **1.000** | **0.855** |
| −总对数概率（重新分词，错误的做法） | 0.995 | 0.803 |
| 输出的 token 数（对照：只看长度） | 0.742 | 0.615 |

- **总对数概率最好**：4 行严重读错全部排在最可疑的位置，AUROC 1.000；
- 但"严重读错"只有 4 行，AUROC 的不确定性很大：多一行、少一行，数字就可能变化好几个百分点。"不完全对"的 20 行更可靠：0.81–0.86；
- **长度对照**：严重读错的输出往往更长（`3205.16500000` 比 `$225.24 story was` 多出一串数字），而总对数概率随长度变负，所以总和的区分能力里有一部分是长度。只看长度的 AUROC 是 0.742、0.615，明显低于对数概率：**对数概率提供了长度之外的信息**。平均对数概率（已经除掉了长度）仍然有 0.978、0.810，也说明了这一点；
- 错误的做法（重新分词）在这里只差了一点，因为重新分词对每一行的低估差不多是同一个量。但它的数值是错的，后面的校准就全错了。

NED 最大的 6 行：

| 真值 | 读出 | NED | 总对数概率 | 最低的 token |
|---|---|---|---|---|
| `$225.24 story was` | `3205.16500000` | 0.82 | −12.32 | −2.18 |
| `listen money minute` | `after recession methods` | 0.78 | −7.21 | −3.14 |
| `even 649 20 keep top` | `ени 040 20 кгр тп.` | 0.65 | −15.69 | −3.22 |
| `first $198.50` | `test $ 1.00000` | 0.64 | −7.38 | −1.38 |
| `COUNTRY right.` | `country right.` | 0.50 | −1.10 | −0.85 |
| `rule less` | `rule of` | 0.44 | −6.01 | −2.15 |

完全读对的行里总对数概率最低的 3 行：

| 行 | 总对数概率 | 最低的 token |
|---|---|---|
| `learn 1028` | −1.57 | −1.49 |
| `22-04-2025 got Keep` | −1.33 | −0.98 |
| `in` | −1.29 | −1.27 |

第 24 章那几行"幻觉"（换成俄文、凭空写出数字），总对数概率都在 −7 以下，远低于任何一行读对的（最低 −1.57）。**模型在幻觉时是"知道"自己不确定的**，只是贪心解码仍然要选一个 token 写下去。唯一的例外是 `COUNTRY right.` → `country right.`：大小写错了，但模型很确定（−1.10）——它不认为大小写是需要注意的事。

这对 OCR 的实际用途是：用总对数概率给每一行打一个分，把最可疑的 10–20% 交给人检查或者换一个模型重读，能抓住大部分严重的错误。第 33 章的数据工程会用这个办法挑难例。

### 校准：可靠性图

把 exp(总对数概率)——整行被这样写出来的概率——当作"这一行完全正确"的置信度：

| 置信度段 | 平均置信度 | 准确率 | 行数 |
|---|---|---|---|
| [0.0, 0.1) | 1.2% | 0.0% | 8 |
| [0.1, 0.2) | 14.7% | 0.0% | 1 |
| [0.2, 0.3) | 25.0% | 60.0% | 5 |
| [0.3, 0.4) | 35.0% | 50.0% | 8 |
| [0.4, 0.5) | 45.9% | 50.0% | 6 |
| [0.5, 0.6) | 56.1% | 100.0% | 4 |
| [0.6, 0.7) | 66.0% | 100.0% | 4 |
| [0.7, 0.8) | 75.3% | 50.0% | 2 |
| [0.8, 0.9) | 84.3% | 80.0% | 5 |
| [0.9, 1.0) | 95.3% | 100.0% | 7 |

ECE 0.152。中间几段（0.2–0.7）准确率明显高于置信度：模型**不够自信**。原因之一：整行的概率是所有 token 概率的乘积，一行 6 个 token 每个 0.9，整行只有 0.53；但"整行正确"并不要求模型在每个 token 上都很确定，只要求最大概率的那个是对的。另外，模型的一部分概率分给了"等价但不同"的写法（比如前导空格、大小写），这些写法我们评测时算错，但不一定是读错。

## 27.10 常见错误

| 现象 | 原因 | 怎么查 |
|---|---|---|
| 对数概率比均匀猜测还低很多 | 错位：logits 和 ids 没有错开一位，或者错开了两次 | 和模型的损失比较；和 −ln V 比较 |
| 生成的回答，算出来的概率却很低 | 把生成的文字重新分词，得到了不同的 token（比如丢了前导空格） | 直接用生成时的 token 编号打分（27.7 节） |
| 选择题的结果偏向某个候选 | 候选的 token 数不同（求和偏向短的）；或者写法和模型习惯的不一样（有没有空格） | 打印每个候选的 token；用模型自己生成时的写法 |
| bf16 下 DPO/GRPO 的比值很抖 | 对数概率的精度不够，两个接近的数相减 | log_softmax 用 fp32 |
| 熵出现 NaN | 用 p · log p，p = 0 时得到 0 × (−∞) | 用 log_softmax 得到 log p |
| 补齐后结果变了 | 左侧补齐（因果模型的前面位置能看到补齐的 token），或者 mask 没有排除补齐的位置 | 右侧补齐；mask 只覆盖回答 |
| 置信度很高但经常错 | 模型过度自信（SFT 后常见），或者用的分数和长度有关 | 画可靠性图、算 ECE；温度缩放 |
| 用总对数概率挑读错的行，效果特别好 | 读错的输出往往更长，总和越长越负：分数里混进了长度 | 加一个"只看长度"的对照分数 |

## 27.11 真实世界对照

- **TRL、OpenRLHF、verl** 的 DPO/GRPO 实现里，都有一个 `selective_log_softmax` / `get_batch_logps` 一类的函数，做的就是 `token_logprobs` + mask 求和。读它们的代码时，先找到"在哪里错位"、"mask 从哪来"；
- **多选基准的似然评测**：lm-evaluation-harness 对每个选项算 `loglikelihood`，同时报告 `acc`（按总和选）和 `acc_norm`（按字节长度归一化后选），就是 27.4 节的两种汇总；
- **OCR 的置信度**：传统 OCR 引擎（Tesseract、PaddleOCR）都会输出每个字符或每行的置信度；VLM 的 OCR 一般不直接给，需要像第 4 部分这样从对数概率里算。第 33 章用它挑选需要人工检查或重新标注的样本；
- **校准**：Guo 等人（2017）发现现代神经网络普遍过度自信，提出温度缩放；大语言模型经过 RLHF 之后，校准往往比预训练模型差（GPT-4 技术报告里有这样的图）；
- **分词的边界问题**：很多框架在评测和后训练里处理"提示和回答的分界处的 token"时都出过 bug：回答开头的空格应该算在提示里还是回答里，会改变 token 的切分。正确的做法是先拼好整个字符串再分词，再找回答的起点；或者像本章一样，直接使用生成时的编号。

## 27.12 深入一步

### 为什么 SFT 之后的模型会过度自信

交叉熵 −log p(正确) 在 p → 1 时才趋于 0，所以即使模型已经全部答对，损失还在推动 p 继续变大，logits 的尺度不断增大。验证集上答错的那些题，模型也会用很大的 logits 给出错误的答案，于是"置信度 95%、实际准确率 85%"。温度缩放（logits 除以 τ > 1）把所有的置信度压低一点，往往就能把 ECE 降下来，而且不改变 argmax，不影响准确率。

### AUROC 和排名

AUROC = P(正例分数 > 负例分数)。把 n₊ 个正例和 n₋ 个负例的分数放在一起排序，正例的名次之和 R 里包含了"正例之间互相比较"的部分 n₊(n₊ + 1)/2，减掉之后剩下的就是"正例排在负例上面"的对数，除以所有正负配对的数量 n₊ · n₋ 即为 AUROC。并列时取平均名次，相当于并列的配对各算一半。这个公式让 AUROC 的计算从 O(n₊ n₋) 降到 O(n log n)（排序）。

AUROC 只看排名，不看分数的绝对值，所以它和校准无关：一个极度不校准的模型（所有置信度都乘以 0.1）AUROC 不变。**挑难例看 AUROC，报置信度看 ECE**，两者回答的是不同的问题。

### 选择题打分和生成的关系

贪心生成在每一步取 argmax，选择题打分比较整条候选的概率。两者在候选都只有一个 token 时完全等价（只要候选包括了模型的 argmax）；候选更长时可能不同：贪心在第一步选了 A 的开头，但 B 作为整体的概率可能更大。这也是束搜索（第 17 章）要解决的问题。

| 几个候选里选一个 | 每个候选的总对数概率 | 候选的 token 数不同时有长度偏差；写法要和模型习惯一致 |
| 模型有多拿不准 | 熵 | 不需要知道正确答案 |
| 一个回答可信吗 | 总对数概率 / 最低的 token 对数概率 | 混有长度；用 AUROC 评价，用 ECE 评价校准 |
| 两个模型对同一个回答的看法差多少 | 对数概率之差 | DPO、GRPO、KL 的基础；fp32 |

## 27.14 本章小结

- 每个 token 的对数概率：logits 去掉最后一个位置，ids 去掉第一个，log_softmax 后 gather。返回的第 t 列是第 t + 1 个 token；
- 语言模型的损失、SFT 的损失都是"回答 token 对数概率的负平均"；检查实现的方法：与模型损失比较、与 −ln V 比较、手算小例子；
- 两种标签约定（−100 和显式 mask）可以互相转换；后训练代码多用显式 mask，因为要用每个 token 的值；
- 求和偏向短回答，平均偏向长而容易预测的回答（包括重复）；
- 熵衡量"拿不准"，与正确答案无关；用 log_softmax 计算避免 NaN；bf16 的对数概率误差在后训练里不可忽略；
- 用似然对候选打分可以代替生成做选择题；候选的写法（有没有前导空格）要和模型生成时的一致；
- 置信度要用两个量评价：能不能区分对错（AUROC），数值是否可信（ECE）；评价一个分数时，要用"只看长度"之类的对照排除混杂因素；
- 用生成的 token 编号打分，不要把文字重新分词。

## 参考答案

1. logits 的最后一个位置预测的是序列之外的 token，没有对应的目标；ids 的第一个 token 前面没有上下文，不被预测。去掉两头之后，logits 的第 t 行正好预测 ids 的第 t + 1 个。
2. 和模型自己算的损失比较（−平均对数概率应该等于损失）；和均匀猜测 −ln V 比较（训练过的模型应该远高于它）；在手算的小例子上核对。
3. 求和偏向短回答（乘的概率少），例如第 2 部分的 `it.`；平均偏向长而容易预测的回答，例如重复前文的 `thought thought thought.`。
4. 熵只看分布本身，不需要正确答案；对数概率看的是正确 token 的概率。模型非常确定、但确定的是一个错误的 token 时，熵低、对数概率也低，例如第 1 部分的第一个字符 `T`（熵 0.0，对数概率 −12.21）。
5. 打分：没有格式问题、结果确定、能得到每个候选的概率；但只能用于有限的候选集合，测的是"认"而不是"写"，而且候选的写法、长度会影响结果。生成：测的是真实的使用方式，但要处理格式，结果依赖解码策略。
6. 重新分词可能得到和生成时不同的 token 序列（比如丢掉前导空格、不同的切分方式）。模型对这些"不自然"的序列给出很低的概率，算出来的置信度就不是模型实际生成时的置信度。第 4 部分里，生成时的 `Ġwent` 对数概率 −0.06，重新分词后的 `went` 是 −4.28。
7. 可能。AUROC 只看排名，ECE 看数值。一个模型可以把对的和错的排得很好（AUROC 高），但所有置信度都偏低或偏高（ECE 高）。这时用它挑难例没问题，但不能直接把它的置信度当成准确率；温度缩放可以修正数值而不改变排名。
8. 总对数概率随长度变负，而读错的输出（尤其是幻觉）往往更长。分数的区分能力可能有一部分只是在"量长度"。加一个只看长度的分数，就能知道对数概率在长度之外还提供了多少信息。
9. 总和 ln 0.8 + ln 0.5 + ln 0.25 = −0.223 − 0.693 − 1.386 = −2.303；平均 −0.768；困惑度 e^0.768 ≈ 2.15（等于概率的几何平均的倒数，(0.8 × 0.5 × 0.25)^(−1/3) = 0.1^(−1/3) ≈ 2.15）。
10. 总和：A = −2，B = −3，选 A；平均：A = −1，B = −0.5，选 B。
11. 对数概率 −ln 100 ≈ −4.61；熵 ln 100 ≈ 4.61；困惑度 100。
12. `log(softmax)` 在概率很小时会下溢成 log(0) = −∞，应该用 `log_softmax`；没有错位（logits 的第 t 行在取 ids 的第 t 个，应该取第 t + 1 个）；没有转成 fp32。
13. p 为 0 时 `torch.log(p)` 是 −∞，0 × (−∞) = NaN。应该用 `lp = log_softmax(logits)`，`H = -(lp.exp() * lp).sum(-1)`。另外如果要和 `token_logprobs` 对齐，还要去掉最后一个位置。
