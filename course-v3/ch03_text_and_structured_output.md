## 3.1 字符就是整数

### 码位

计算机只会存数字。要存文字，就得给每个字符**编一个号**。全世界通用的编号表叫 **Unicode**，它给每个字符一个唯一的整数，叫**码位**（code point），习惯写成 `U+` 加十六进制，比如 `A` 是 `U+0041`（十进制 65）。

Python 里 `ord(字符)` 给出码位，`chr(整数)` 反过来：

```python
ord("A")      # 65
chr(65)       # 'A'
ord("∑")      # 8721
```

运行 `python -m labs.ch03.latex_tour`，第 1 部分的输出：

```
'A'    码位 U+0041（十进制    65）  UTF-8 字节 [65]（1 个字节）
'a'    码位 U+0061（十进制    97）  UTF-8 字节 [97]（1 个字节）
'7'    码位 U+0037（十进制    55）  UTF-8 字节 [55]（1 个字节）
'+'    码位 U+002B（十进制    43）  UTF-8 字节 [43]（1 个字节）
'\\'   码位 U+005C（十进制    92）  UTF-8 字节 [92]（1 个字节）
'{'    码位 U+007B（十进制   123）  UTF-8 字节 [123]（1 个字节）
'é'    码位 U+00E9（十进制   233）  UTF-8 字节 [195, 169]（2 个字节）
'∑'    码位 U+2211（十进制  8721）  UTF-8 字节 [226, 136, 145]（3 个字节）

字符串 'x^{2}' 有 5 个字符：['x', '^', '{', '2', '}']
对应的码位： [120, 94, 123, 50, 125]
```

注意第 5 行：Python 显示 `'\\'`，但这是**一个**字符——反斜杠。在 Python 字符串里，反斜杠本身是"转义符"（`"\n"` 表示换行），所以要表示一个真正的反斜杠，源代码里得写两个：`"\\"`。LaTeX 的命令都以反斜杠开头，所以本章的代码里会看到大量 `"\\frac"`——它实际上只有 5 个字符 `\frac`。另一种写法是**原始字符串** `r"\frac"`，前缀 `r` 让反斜杠不再转义。

### 编码：从码位到字节

码位是"编号"，但存到文件里、在网络上传输时，需要变成字节。把码位变成字节的规则叫**编码**（encoding）。今天几乎一切文本都用 **UTF-8**：

| 码位范围 | 字节数 | 例子 |
|---|---|---|
| U+0000 – U+007F（ASCII：英文字母、数字、常用符号） | 1 | `A` → `[65]` |
| U+0080 – U+07FF（带重音的拉丁字母、希腊字母等） | 2 | `é` → `[195, 169]` |
| U+0800 – U+FFFF（大多数中文、数学符号等） | 3 | `∑` → `[226, 136, 145]` |
| U+10000 以上（表情符号、罕用字） | 4 | 😀 → 4 个字节 |

UTF-8 是**变长**的：常用的英文字符只占 1 个字节，和几十年前的 ASCII 编码完全兼容。这一点在第 14 章会很重要：有一类分词器（byte-level BPE）是在**字节**而不是字符上工作的，所以一个中文字在它眼里是 3 个"字节 token"。

Python 里：

```python
"∑".encode("utf-8")              # b'\xe2\x88\x91'，一个 bytes 对象
b'\xe2\x88\x91'.decode("utf-8")  # '∑'
len("∑"), len("∑".encode())      # (1, 3)：1 个字符，3 个字节
```

> **常见错误**：用错误的编码读文件，会得到乱码（比如把 UTF-8 的中文当成 GBK 读）。Python 3 里打开文本文件时，**总是写明** `open(path, encoding="utf-8")`。

### 字符集：模型能写出哪些字符

对 OCR 模型来说，**字符集**（charset，或叫词表 vocabulary）是它能输出的所有符号的集合。第 2 章的模板分类器用了 62 个字符（数字 + 大小写字母）。本书的 MiniDoc 只包含英文和数学符号（这是第 0 章定下的范围），真实的多语言 OCR 模型字符集可达几万。

字符集的设计有几个实际问题：

1. **长得像的字符**：`O`（字母）和 `0`（数字），`l`（小写 L）、`I`（大写 i）和 `1`，在很多字体里几乎一模一样。第 2 章的实验中 `I→l` 就是常见混淆。模型需要上下文（"l0ve" 应该是 "love"），或者评测时要考虑这种歧义；
2. **同一个字符有多种码位**：全角的 `ｘ`（U+FF58）和半角的 `x`（U+0078）看起来差不多，码位却不同；`é` 既可以是一个码位 U+00E9，也可以是 `e` 加上一个"组合重音符" U+0301，两种写法显示完全一样。Unicode 定义了**归一化形式**来处理这个问题：`unicodedata.normalize("NFC", s)` 把可以合并的组合合并成一个码位，`"NFKC"` 更进一步，把全角字符、连字（`ﬁ` → `fi`）等"兼容字符"也换成标准形式；
3. **归一化会丢信息**：NFKC 会把上标 `²`（U+00B2）变成普通的 `2`，于是 `x²` 变成了 `x2`——**含义变了**。所以对数学内容，不能随便套用 NFKC。

这引出了本章的主题：**归一化要保留含义、消除写法差异，而什么算"含义"，要根据任务来定义。**

## 3.2 结构化输出：OCR 要写出的三种文本

一份文档不只是一串字。它有标题、段落、表格、公式，这些**结构**也是 OCR 要还原的。现代 OCR 模型用几种通用的文本格式来表达结构。第 2 部分的输出：

```
--- Markdown（62 个字符）
# Title

Some **bold** text and an inline formula \( x^{2} \).
--- HTML 表格（73 个字符）
<table><tr><td>a</td><td>1</td></tr><tr><td>b</td><td>2</td></tr></table>
--- LaTeX 公式（23 个字符）
\frac{a+1}{b}=x_{n}^{2}
```

### Markdown：文档的骨架

Markdown 是一种"用普通字符表示格式"的写法：

| 写法 | 含义 |
|---|---|
| `# 标题`、`## 小标题` | 一级、二级标题（`#` 的个数是级别） |
| 空一行 | 分段 |
| `**粗体**`、`*斜体*` | 强调 |
| `- 项目` | 无序列表 |
| `\( x^{2} \)` 或 `$x^{2}$` | 行内公式（里面是 LaTeX） |
| `\[ ... \]` 或 `$$ ... $$` | 独立成行的公式 |
| `\| a \| b \|` 加一行 `\|---\|---\|` | 简单表格 |

文档解析模型（第 33 章）最常见的输出就是 Markdown：标题、段落按阅读顺序排列，公式嵌 LaTeX，表格嵌 HTML。

### HTML 表格：二维结构写成一维文本

表格是二维的，但文本是一维的。HTML 用**嵌套的标签**把二维结构"拉平"：

```html
<table>
  <tr> <td>a</td> <td>1</td> </tr>      ← 第一行（tr = table row），两个单元格（td = table data）
  <tr> <td>b</td> <td>2</td> </tr>      ← 第二行
</table>
```

每个 `<xxx>` 是**开始标签**，`</xxx>` 是对应的**结束标签**，两者之间是内容。标签必须**正确嵌套**：`<tr><td></tr></td>` 是错的，就像括号 `([)]` 是错的一样。

HTML 表格能表达 Markdown 表格表达不了的东西——**合并单元格**：

```html
<table>
  <tr> <td rowspan="2">合计</td> <td>3</td> </tr>     ← 第一个单元格竖着跨 2 行
  <tr> <td>4</td> </tr>                                ← 这一行只写 1 个单元格，因为第 1 列被上面占了
</table>
```

`rowspan="2"` 表示竖跨两行，`colspan="3"` 表示横跨三列。真实文档（财报、论文）里合并单元格很常见，所以表格识别模型几乎都输出 HTML 而不是 Markdown。

从结构上看，HTML 表格是一棵**树**：`table` 下面有若干 `tr`，每个 `tr` 下面有若干 `td`，每个 `td` 下面是文字。第 25 章的表格指标 **TEDS** 就是比较两棵这样的树有多像（用"树编辑距离"），而不是比较字符串。

### LaTeX：公式的写法

LaTeX 是数学排版的标准语言。本书只用它的一个小子集：

| 写法 | 含义 | 显示 |
|---|---|---|
| `x^{2}` | 上标 | x² |
| `x_{n}` | 下标 | xₙ |
| `x_{n}^{2}` | 上下标同时有 | xₙ² |
| `\frac{a}{b}` | 分数：分子 a，分母 b | a/b 上下排列 |
| `\sqrt{x}` | 根号 | √x |
| `{...}` | 花括号：把几个东西**组成一组**，本身不显示 | — |
| `+ - =`、`( )` | 运算符、括号 | 原样 |

规则：

- `^` 和 `_` 只作用于**紧跟着的一个东西**：`x^23` 是 x² 后面跟一个 3，要写 `x^{23}` 才是 x²³；
- `\frac` 后面必须跟**两组**花括号：`\frac{a+1}{b}`；
- 花括号只用来分组：`{x}^2` 和 `x^2` 显示一样。

**三种格式的共同点**：它们都是**纯文本**，但文本里藏着**结构**（层级、行列、分子分母）。OCR 模型的输出就是这样的文本。这有两个后果：

1. **模型必须写出语法正确的文本**。少一个 `}` 或 `</td>`，整个结构就坏了，可能连渲染都渲染不出来。第 31 章的强化学习里，"格式是否合法"本身就是一项奖励；
2. **同一个结构有很多种写法**。这是下面几节的主题。

## 3.3 语法树

### 从字符串到树

看这个公式：`\frac{a+1}{b}=x_{n}^{2}`。它的结构是：

- 整个公式是一行，从左到右有三样东西：一个分数、一个等号、一个带上下标的 x；
- 分数有分子（`a + 1`，一行三个东西）和分母（`b`）；
- 带上下标的 x 有底（`x`）、下标（`n`）、上标（`2`）。

这种"一个东西由几个部分组成，每个部分又由更小的部分组成"的结构，画出来是一棵倒着长的**树**：

```
                       row
          ┌─────────────┼──────────────┐
         frac          op '='         script
       ┌───┴───┐                ┌───────┼───────┐
      row     row             sym 'x'  row      row
    ┌──┼──┐    │                        │        │
  'a' '+' '1' 'b'                     'n'      '2'
              [分子] [分母]              [底] [下标] [上标]
```

树的术语：最上面的叫**根**（root），没有子节点的叫**叶子**（leaf），中间的叫**内部节点**。叶子是具体的符号，内部节点是结构。

### 用元组表示树

`miniocr/data/latex.py` 用 Python 元组表示树的节点，**第 0 个元素是节点类型**：

| 节点 | 写法 | 含义 |
|---|---|---|
| 符号 | `("sym", "x")` | 字母、数字、括号 |
| 运算符 | `("op", "+")` | `+`、`-`、`=` |
| 行 | `("row", [节点, ...])` | 若干节点从左到右排成一行 |
| 上下标 | `("script", 底, 下标, 上标)` | 下标或上标可以是 `None`；下标、上标都是 row |
| 分数 | `("frac", 分子, 分母)` | 分子、分母都是 row |
| 根号 | `("sqrt", 内容)` | 内容是 row |

第 3 部分的输出：

```

记号: ['\\frac', '{', 'a', '+', '1', '}', '{', 'b', '}', '=', 'x', '_', '{', 'n', '}', '^', '{', '2', '}']
语法树（元组写法）: ('row', [('frac', ('row', [('sym', 'a'), ('op', '+'), ('sym', '1')]), ('row', [('sym', 'b')])), ('op', '='), ('script', ('sym', 'x'), ('row', [('sym', 'n')]), ('row', [('sym', '2')]))])

  frac
    [分子]

        sym 'a'
        op '+'
        sym '1'
    [分母]
      row
        sym 'b'
  op '='

      row

```

元组写法挤在一行，很难读；`print_tree` 用缩进表示层级，每深一层多缩进两格——和 Python 代码的缩进是一个道理。**先在纸上把这棵树画出来，再和输出对照。**

为什么用元组而不是定义一个类？元组可以直接用 `==` 比较（两棵树的所有节点都相同才相等），可以打印，可以当字典的键，不需要额外的代码。对一个只有 6 种节点的小语言，这是最简单的选择。

### 遍历：叶子和结构

很多操作都是"把树走一遍"，叫**遍历**（traversal）。`leaves` 按从左到右的顺序收集所有叶子：

```python
def leaves(node):
    kind = node[0]
    if kind in ("sym", "op"):
        return [node[1]]                                   # 叶子：返回它自己
    if kind == "row":
        return [x for c in node[1] for x in leaves(c)]     # 行：依次收集每个子节点的叶子
    if kind == "script":
        out = leaves(node[1])                              # 先底
        for part in node[2:]:                              # 再下标、上标（按这个顺序）
            if part is not None:
                out += leaves(part)
        return out
    if kind == "frac":
        return leaves(node[1]) + leaves(node[2])           # 先分子，再分母
    if kind == "sqrt":
        return leaves(node[1])
```

这是**递归**的典型写法：对每种节点，说清楚"我的结果怎样由孩子们的结果组成"，剩下的交给递归。

`leaves` 的顺序非常重要：第 2 章的渲染器给每个符号画框时，框的顺序**必须**和 `leaves` 一致，这样"第 k 个框"和"第 k 个符号"才对得上。测试 `test_leaves_order` 和 `test_formula_boxes_follow_leaves_and_stay_inside` 一起保证了这一点。

`structure_of` 收集公式里出现了哪些**结构**：`script`、`frac`、`sqrt`、`paren`（括号），以及 `nested`（结构里还套着结构，比如分母里有上标）。它用来给公式分难度等级，评测时按难度**分桶**统计（第 25 章）。

## 3.4 生成：从树写出 LaTeX

### 规范写法

把树写成字符串的函数是 `to_latex`。不给随机数生成器（`rng=None`）时，它输出唯一的**规范写法**（canonical form）：

- 上下标**总是**带花括号：`x^{2}`，而不是 `x^2`；
- 同时有上下标时，**先下标后上标**：`x_{n}^{2}`；
- 分数总是用 `\frac{}{}`；
- 不加任何空格。

```python
def to_latex(node, rng=None):
    kind = node[0]
    if kind in ("sym", "op"):
        if rng is not None and kind == "op" and rng.random() < 0.2:
            return " " + node[1] + " "                     # 随机写法：运算符两边加空格
        return node[1]
    if kind == "row":
        return "".join(to_latex(c, rng) for c in node[1])  # 行：子节点依次写出，拼起来
    if kind == "script":
        _, base, sub, sup = node
        b = to_latex(base, rng)
        if base[0] == "row":
            b = "{" + b + "}"                              # 底是一组时要加花括号：{a+b}^{2}
        parts = []
        if sub is not None:
            parts.append("_" + _script_arg(sub, rng))
        if sup is not None:
            parts.append("^" + _script_arg(sup, rng))
        if rng is not None and len(parts) == 2 and rng.random() < 0.5:
            parts.reverse()                                # 随机写法：先上标后下标
        return b + "".join(parts)
    if kind == "frac":
        n, d = to_latex(node[1], rng), to_latex(node[2], rng)
        if rng is not None and rng.random() < 0.15:
            return "{" + n + " \\over " + d + "}"         # 随机写法：老式的 \over
        return "\\frac{" + n + "}{" + d + "}"
    if kind == "sqrt":
        return "\\sqrt{" + to_latex(node[1], rng) + "}"
```

`_script_arg` 处理上下标的内容：规范写法总加花括号；随机写法下，如果内容只有一个字符，有一半概率省略花括号（`x^2`）。

### 随机写法：模拟真实数据集

给了 `rng` 时，`to_latex` 在每个"可以有多种写法"的地方随机选一种。这四种变化都**不改变含义**：

| 变化 | 规范 | 等价写法 | 概率 |
|---|---|---|---|
| 运算符两边的空格 | `a+b` | `a + b` | 每个运算符 0.2 |
| 单字符上下标省略花括号 | `x^{2}` | `x^2` | 0.5 |
| 上下标的先后 | `x_{n}^{2}` | `x^{2}_{n}` | 0.5 |
| 分数的写法 | `\frac{a}{b}` | `{a \over b}` | 0.15 |

为什么要故意制造写法差异？因为**真实的数据集就是这样的**。公式识别的训练数据通常从论文的 LaTeX 源码里提取，不同作者有不同的习惯，同一个作者前后也不一致。我们的模拟数据加入这些差异，是为了让第 25 章的评测实验和真实情况一样"麻烦"。

第 4 部分对一棵树随机写 200 次：

```
规范写法: \frac{a}{b}+x_{n}^{2}-3y
随机写 200 次，得到 41 种不同的字符串，出现最多的 8 种：
   22 次  '\\frac{a}{b}+x_{n}^2-3y'                归一化 → \frac{a}{b}+x_{n}^{2}-3y
   20 次  '\\frac{a}{b}+x^{2}_n-3y'                归一化 → \frac{a}{b}+x_{n}^{2}-3y
   14 次  '\\frac{a}{b}+x_n^2-3y'                  归一化 → \frac{a}{b}+x_{n}^{2}-3y
   14 次  '\\frac{a}{b}+x^{2}_{n}-3y'              归一化 → \frac{a}{b}+x_{n}^{2}-3y
   12 次  '\\frac{a}{b}+x_{n}^{2}-3y'              归一化 → \frac{a}{b}+x_{n}^{2}-3y
   10 次  '\\frac{a}{b}+x^2_{n}-3y'                归一化 → \frac{a}{b}+x_{n}^{2}-3y
    9 次  '\\frac{a}{b}+x_n^{2}-3y'                归一化 → \frac{a}{b}+x_{n}^{2}-3y
    8 次  '\\frac{a}{b}+x_{n}^{2} - 3y'            归一化 → \frac{a}{b}+x_{n}^{2}-3y
```

一个只有 9 个符号的公式，就有 41 种写法。**手算一下最多能有多少种**：上下标先后 2 种 × 下标是否带花括号 2 × 上标是否带花括号 2 = 8 种；分数 2 种；两个运算符各自是否加空格 2 × 2 = 4 种。总共 8 × 2 × 4 = 64 种。200 次随机抽样见到了其中 41 种（`\over` 只有 15% 的概率，所以带 `\over` 的那一半很少见，前 8 名里一个都没有）。

## 3.5 解析：从 LaTeX 回到树

**解析**（parsing）是生成的逆过程：给一个字符串，找出它的语法树。它分两步。

### 第一步：切成记号

**记号**（token）是语法上不可再分的最小单位。在我们的 LaTeX 子集里，记号有两种：以反斜杠开头的**命令**（`\frac`、`\sqrt`、`\over`），和**单个字符**。空格不是记号，直接丢掉。

```python
def tokenize(s):
    toks, i = [], 0
    while i < len(s):
        c = s[i]
        if c == " ":
            i += 1                                        # 空格：跳过
        elif c == "\\":
            j = i + 1
            while j < len(s) and s[j].isalpha():          # 反斜杠后面连续的字母，组成命令名
                j += 1
            if j == i + 1:
                raise LatexError(f"第 {i} 个字符的反斜杠后面没有命令名")
            toks.append(s[i:j])
            i = j
        else:
            toks.append(c)                                # 其他：单个字符
            i += 1
    return toks
```

这里用一个下标 `i` 从左往右扫描字符串，每次"吃掉"一个记号。**手算** `tokenize("\frac{a}{b} + x^2")`：

```
i=0  '\'   → 往后找字母 f,r,a,c，到 i=5 的 '{' 停 → 记号 '\frac'，i=5
i=5  '{'   → 记号 '{'
i=6  'a'   → 记号 'a'
...
i=11 ' '   → 跳过
i=12 '+'   → 记号 '+'
...
结果：['\frac', '{', 'a', '}', '{', 'b', '}', '+', 'x', '^', '2']
```

和测试 `test_tokenize` 期望的完全一样。

### 第二步：按文法组装成树

**文法**（grammar）是描述"什么样的记号序列是合法的、它的结构是什么"的规则。我们的文法可以写成下面几条（`*` 表示"重复零次或多次"，`|` 表示"或者"）：

```
行（row）      := 项*
项（item）     := 原子 ( ('_' | '^') 上下标参数 )*
原子（atom）   := 组 | '\frac' 组 组 | '\sqrt' 组 | 运算符 | 符号
组（group）    := '{' 行 '}'          （组内可以有一个 \over，把它分成分子和分母）
上下标参数     := 组 | 符号
```

读法：一行由若干个项组成；一个项是一个原子，后面可能跟着若干个 `_xxx` 或 `^xxx`；一个原子要么是花括号组，要么是分数、根号、运算符或单个符号……

**递归下降**（recursive descent）是最直接的解析方法：**文法里的每一条规则，写成一个函数**。函数从当前位置开始读记号，读到自己负责的结构结束为止，返回那一部分的树。规则里提到别的规则，函数就调用别的函数。"行"里有"项"，"项"里有"原子"，"原子"里可能有"组"，"组"里又有"行"——这就是"递归"的来源，而 `\frac{\frac{a}{b}}{c}` 这样的嵌套也就自然被处理了。

`_Parser` 类保存记号列表和当前位置，提供两个基本操作：

```python
def peek(self):                         # 看一眼当前记号，不移动
    return self.toks[self.i] if self.i < len(self.toks) else None

def take(self, expect=None):            # 取走当前记号，位置后移一格
    t = self.peek()
    if t is None:
        raise LatexError("公式意外结束")
    if expect is not None and t != expect:
        raise LatexError(f"期望 {expect!r}，实际是 {t!r}")
    self.i += 1
    return t
```

然后是每条规则对应的函数。**原子**：看第一个记号是什么，决定是哪种结构：

```python
def atom(self):
    t = self.peek()
    if t is None:
        raise LatexError("公式意外结束")
    if t == "{":
        return self.group()                                # 花括号组
    if t == "\\frac":
        self.take()
        return ("frac", self.group(), self.group())        # \frac 后面必须是两个组
    if t == "\\sqrt":
        self.take()
        return ("sqrt", self.group())
    if t in OPS:
        self.take()
        return ("op", t)
    if len(t) == 1 and t in SYMBOLS:
        self.take()
        return ("sym", t)
    raise LatexError(f"不认识的记号 {t!r}")
```

**组**：读一个 `{`、一行、一个 `}`：

```python
def group(self):
    self.take("{")
    r = self.row(inside_group=True)
    self.take("}")
    if r[0] == "over":                                     # {a \over b}：变成分数
        return ("row", [("frac", r[1], r[2])])
    return r
```

**行**：不断读项，直到遇到 `}`（组结束）或字符串结束：

```python
def row(self, inside_group=False):
    items = []
    while self.peek() is not None and self.peek() != "}":
        if self.peek() == "\\over":
            if not inside_group:
                raise LatexError("\\over 只能出现在花括号里")
            self.take()
            den = self.row(inside_group=True)              # \over 右边的部分是分母
            if den[0] == "over":
                raise LatexError("一组花括号里只能有一个 \\over")
            return ("over", ("row", items), den)           # 已经读到的部分是分子
        items.extend(self.item())
    return ("row", items)
```

`\over` 是这个文法里唯一"别扭"的地方：`\frac{a}{b}` 一开始就告诉你"这是个分数"，而 `{a \over b}` 要读到中间才知道前面的 `a` 是分子。处理方法是：`row` 在遇到 `\over` 时，把已经读到的部分作为分子、继续读到的部分作为分母，返回一个临时的 `("over", 分子, 分母)` 节点；调用它的 `group` 再把它变成真正的分数。这种"临时节点"只存在于解析过程中，不会出现在最终的树里。

### 练习 3.4：解析一个"项"

项 = 原子 + 若干个上下标。这是文法里最细致的一条规则，也是你要亲手写的：

```python
def item(self):
    base = self.atom()                                     # 1. 先读底
    sub = sup = None
    while self.peek() in ("_", "^"):                       # 2. 后面有 _ 或 ^ 就继续读
        mark = self.take()
        arg = self.script_arg()
        if mark == "_":
            if sub is not None:
                raise LatexError("同一个底有两个下标")      #    x_1_2 不合法
            sub = arg
        else:
            if sup is not None:
                raise LatexError("同一个底有两个上标")      #    x^2^3 不合法
            sup = arg
    if sub is None and sup is None:                        # 3. 没有上下标
        if base[0] == "row":
            return list(base[1])                           #    单独的 {a+b}：花括号不改变含义，展开
        return [base]
    if base[0] == "row" and len(base[1]) == 1:
        base = base[1][0]                                  # 4. {x}^2 与 x^2 相同
    return [("script", base, sub, sup)]
```

几个设计要点，写之前想清楚：

- **为什么返回列表？** 因为一个花括号组 `{a+b}`（后面没有上下标）里有 3 个节点，它们应该直接展开到外面的行里——`a{+}b` 和 `a+b` 是同一个公式。所以 `item` 返回"若干个节点"，`row` 用 `items.extend(...)` 把它们接上；
- **为什么 `x^2_n` 和 `x_n^2` 得到同一棵树？** 因为循环里不管先遇到哪个，都分别存进 `sub` 和 `sup`，最后组成的节点是 `("script", x, 下标, 上标)`，和读到的先后无关。**这正是"写法不同、含义相同"在解析器里被消除的地方**；
- **为什么要检查"两个上标"？** `x^2^3` 在 LaTeX 里是错误（Double superscript），因为它有歧义：是 x 的 2 次方再 3 次方，还是 x 的 2³ 次方？拒绝它，比猜一个意思更安全；
- **第 4 步**：`{x}^2` 读到的底是 `("row", [("sym", "x")])`，只有一个元素的行，把它"拆开"成 `("sym", "x")`，于是和 `x^2` 得到同一棵树。如果底有多个元素，比如 `{a+b}^2`，就保留为行。

`script_arg` 处理上下标的参数：要么是花括号组，要么是**紧跟着的单个符号**——这就是 `x^23` 只把 2 当上标的原因。

### 一个值得注意的例子：括号的上标

```
parse("(x+1)^{2}")
→ ('row', [('sym','('), ('sym','x'), ('op','+'), ('sym','1'), ('script', ('sym',')'), None, ('row',[('sym','2')]))])
```

上标挂在了**右括号**上，而不是整个 `(x+1)` 上！这不是我们解析器的 bug——真正的 LaTeX 也是这样处理的：圆括号在 LaTeX 里只是普通的符号，不是分组，`^` 作用于紧挨着的前一个东西，也就是 `)`。显示出来的效果是一样的（上标在右括号的右上方），但语法树的结构和数学含义不一致。这是一个很好的提醒：**LaTeX 描述的是"怎么排版"，不是"数学上是什么"**。两个排版效果相同的 LaTeX 字符串，语法树可以不同（`{(x+1)}^{2}` 的树就不一样）；两个数学上相同的公式（`a+b` 和 `b+a`），排版和树都不同。本章的归一化只能处理第一类中的一部分——3.8 节会讨论这个局限。

### 拒绝不合法的输入

第 5 部分：

```
'x^'           错误：公式意外结束
'\\frac{a}'    错误：公式意外结束
'a \\over b'   错误：\over 只能出现在花括号里
'x^2^3'        错误：同一个底有两个上标
'\\alpha+1'    错误：不认识的记号 '\\alpha'
'x}'           错误：多余的 '}'
```

最后一个错误来自 `parse` 本身：

```python
def parse(s):
    p = _Parser(tokenize(s))
    tree = p.row()
    if p.peek() is not None:                    # 顶层的 row 遇到 } 就停了，但字符串还没完
        raise LatexError(f"多余的 {p.peek()!r}")
    return _clean(tree)
```

`\alpha` 在真正的 LaTeX 里是合法的（希腊字母 α），但不在我们的子集里，所以也被拒绝。**解析器的"合法"总是相对于某个文法而言的。** 真实 OCR 模型的输出可能包含成百上千种 LaTeX 命令，评测工具必须有一个足够大的文法，否则会把正确的输出误判成"格式错误"。

`_clean` 是最后的整理：它把嵌套的 row 展平（`("row", [("row", [a, b]), c])` 变成 `("row", [a, b, c])`），保证解析出的树和生成器产生的树形状完全一致，这样 `parse(to_latex(tree)) == tree` 才能用 `==` 直接比较。

## 3.6 归一化

### 练习 3.5

有了解析和生成，归一化只有一行：

```python
def normalize(s):
    return to_latex(parse(s))
```

**解析成树，再按规范写法写回去。** 所有"写法上的差异"都在解析时被消除（它们对应同一棵树），而规范写法是唯一的，所以：

> 两个字符串**表示同一棵树**，当且仅当它们**归一化后相等**。

测试 `test_known_cases` 里的例子：

```
"x^2"            → "x^{2}"
"x^2_n"          → "x_{n}^{2}"        上下标的先后不影响含义
"{a \over b}+1"  → "\frac{a}{b}+1"
" 3x + y = 7 "   → "3x+y=7"           空格不影响含义
"{{a \over b}}"  → "\frac{a}{b}"      多余的花括号不影响含义
"{x}^2"          → "x^{2}"
"\sqrt{x_1+1}"   → "\sqrt{x_{1}+1}"
```

### 怎样测试一个归一化函数

`test_roundtrip_and_all_styles_normalize_to_canonical` 对每个难度等级随机生成 500 棵树，检查三条**性质**：

1. **往返**（round-trip）：`parse(to_latex(tree)) == tree`——规范写法解析回来是同一棵树；
2. **幂等**（idempotent）：`normalize(canon) == canon`——已经规范的字符串，再归一化不变。更一般地，`normalize(normalize(s)) == normalize(s)`；
3. **覆盖所有写法**：对每棵树的 3 种随机写法 `s`，`normalize(s) == to_latex(tree)`。

这种测试方式叫**基于性质的测试**（property-based testing）：不是写几个具体的"输入 → 期望输出"，而是说出"对所有输入都应该成立的规律"，再用大量随机输入去检验。对解析器、编码器、数据变换这类代码，它能发现手写例子想不到的边角情况。本章开发过程中，正是第 1 条性质发现了生成器产生的树里有嵌套的 row、和解析结果不一致的 bug（后来加了 `_clean`）。

还有一个**反向**的测试：`test_random_styles_really_differ` 检查随机写法**确实**和规范写法不同（300 个公式里超过 100 个不同）。为什么要测这个？如果 `to_latex` 的随机分支因为某个 bug 从不生效，前面的测试会全部通过（规范写法归一化当然等于规范写法），但整个"写法不唯一"的模拟就失效了，第 25 章的评测实验也就没有意义。**测试不仅要检查代码做了它该做的，还要检查它没有"什么都不做"。**

## 3.7 实验：为什么评测前必须归一化

### 实验设计

假设有一个**完美**的公式识别模型：它每次都认对了公式（语法树完全正确），只是写出来的写法是随机的——就像人类标注员一样。同时，数据集里的标准答案也是另一个人用随机写法写的。用"字符串完全相同"作为评测标准，这个完美模型能得多少分？

```python
for level in (1, 2, 3, 4):
    trees = [gen_formula(rng, level) for _ in range(1000)]
    refs = [to_latex(t, rng) for t in trees]          # 数据集里的标注：随机写法
    preds = [to_latex(t, rng) for t in trees]         # 模型的输出：另一种随机写法
    raw = np.mean([p == r for p, r in zip(preds, refs)])
    norm = np.mean([normalize(p) == normalize(r) for p, r in zip(preds, refs)])
```

**先写下你的预测**：level 1（只有字符和运算符）和 level 3（有分数）时，不归一化的完全匹配率大约多少？

### 结果

```
  level 1：不归一化的完全匹配  69.7%   归一化后 100.0%
  level 2：不归一化的完全匹配  24.9%   归一化后 100.0%
  level 3：不归一化的完全匹配  19.9%   归一化后 100.0%
  level 4：不归一化的完全匹配  22.3%   归一化后 100.0%
```

**一个完美的模型，在 level 3 上只得了 19.9 分。** 归一化之后，100 分。

### 怎么读

**为什么 level 1 是 69.7%？** level 1 的公式只有符号和运算符，唯一的随机性是"运算符两边加不加空格"（每个运算符 20% 概率加）。两种写法要完全一致，每个运算符必须"两边都加"或"两边都不加"：概率是 `0.8² + 0.2² = 0.68`。level 1 的公式平均约 1 个运算符（有些没有运算符，概率为 1；有些有 2 个，概率为 0.68² ≈ 0.46），平均下来约 70%，和实测吻合。

**为什么 level 2 以后掉到 20% 左右？** 每多一处可变的写法，匹配概率就再乘上一个小于 1 的数。一个单字符上标省不省花括号，两边一致的概率是 `0.5² + 0.5² = 0.5`；一个同时有上下标的项，先后顺序一致的概率也是 0.5。几处变化乘起来，很快就降到 20% 左右。level 4 比 level 3 略高，是因为 level 4 的公式里有一部分是根号、括号这类**没有写法变化**的结构，它们不降低匹配率。

**这个实验说明了什么？**

1. **评测协议必须写明归一化规则。** 同一个模型，用不同的比较方式，分数可以差几十个百分点。读论文时，如果两篇论文的公式识别分数差很多，先查它们是否用了同样的归一化；
2. **训练数据也需要归一化。** 如果训练数据的写法不统一，模型要额外学"什么时候写 `x^2`、什么时候写 `x^{2}`"——这是不可能学会的随机性，只会让训练损失降不下去、模型输出不稳定。所以第 13、26 章训练公式识别时，**训练标签统一用规范写法**；
3. **强化学习的奖励也一样。** 第 31 章用"预测是否正确"作为奖励，如果不归一化，模型会因为写法而不是内容被惩罚。

### 难度等级

第 7 部分统计了四个难度等级的公式：

```
level 1：LaTeX 平均   3.6 字符，最长   8；结构出现率 []
         例子：['8', 'y', 'x-k']
level 2：LaTeX 平均   9.7 字符，最长  25；结构出现率 [script 100%]
         例子：['3+b_{6}-5z', 'b_{9}=6c', '6n-z^{x}']
level 3：LaTeX 平均  24.0 字符，最长  65；结构出现率 [frac 100%, nested 65%, script 79%]
         例子：['\\frac{5c+4_{n}^{8}}{n_{z}^{8}}+n_{8}', '\\frac{2x-6}{7}+3a-5', 'y_{4}-c-\\frac{a^{z}}{7b}']
level 4：LaTeX 平均  22.1 字符，最长  76；结构出现率 [frac 49%, nested 58%, paren 29%, script 74%, sqrt 43%]
         例子：['\\sqrt{z^{y}}=2_{3}', 'c^{7}+c^{9+a}-\\frac{9-5a}{5c-k_{3}}', 'c_{y}=(c-n)']
```

`gen_formula` 按难度要求生成：

```python
_REQUIRED = {1: set(), 2: {"script"}, 3: {"frac"}, 4: {"sqrt", "paren", "nested"}}

def gen_formula(rng, level=3, max_terms=3):
    while True:
        ...                                            # 随机生成 1–3 个项，用运算符连起来
        tree = _clean(("row", items))
        need = _REQUIRED[level]
        if not need or structure_of(tree) & need:      # 满足这个等级的要求才返回，否则重来
            return tree
```

这种"不满足就重来"的写法叫**拒绝采样**（rejection sampling）：先按简单的规则随便生成，再丢掉不合要求的。它简单、不容易出错，代价是可能要试好几次。

注意几个细节：

- level 4 的平均长度（22.1）反而比 level 3（24.0）短。level 4 只要求出现根号、括号或嵌套**之一**，不再要求一定有分数（frac 只占 49%），而分数是最"长"的结构。"难度"不等于"长度"；
- 有些公式在数学上很奇怪，比如 `4_{n}^{8}`（数字带下标）、`2_{3}`。我们的生成器只保证**语法**合法，不保证数学上有意义。对训练识别模型来说这没关系——模型要学的是"看到什么就写什么"，而不是"写出有意义的数学"。但这也意味着 MiniDoc 上的语言模型**学不到数学常识**，它没法靠"上下文"猜出模糊的符号。真实数据中，上下文是很强的线索（第 14 章的语言模型和第 22 章的 VLM 都会利用它）。
- 打开 `outputs/ch03/levels.png` 看看四个等级的公式图（每行一个等级），感受一下第 2 章的渲染器怎样把树排成图。

## 3.8 归一化的局限

我们的归一化处理了**写法**上的差异，但有很多"含义相同"它处理不了：

| 例子 | 是否同一棵树 | 我们的归一化能否识别 |
|---|---|---|
| `x^2` 与 `x^{2}` | 是 | ✔ |
| `x_{n}^{2}` 与 `x^{2}_{n}` | 是 | ✔ |
| `(x+1)^{2}` 与 `{(x+1)}^{2}` | 否（上标挂的位置不同） | ✘，但它们**排版效果相同** |
| `a+b` 与 `b+a` | 否 | ✘，**数学上相等**，但排版不同 |
| `\frac{1}{2}` 与 `0.5` | 否 | ✘，数值相等，排版完全不同 |
| `\left( x \right)` 与 `(x)` | — | 不在我们的子集里；真实 LaTeX 里排版几乎相同 |

对 OCR 来说，"正确"的标准应该是：**模型写出的东西，排版出来和图上的一样。** `a+b` 和 `b+a` 排版不同，所以如果图上是 `a+b`，写 `b+a` 就是错的——这一点我们的归一化做对了。但 `(x+1)^{2}` 和 `{(x+1)}^{2}` 排版相同，却会被判错——这一点我们做错了。

**最彻底的办法是：直接比较渲染出来的图。** 把预测和标准答案都渲染成图，逐个符号比较位置和形状。这就是 **CDM**（Character Detection Matching）指标的思想，第 25 章会实现它的简化版。Xiaomi-OCR-0 的技术报告用 CDM 评公式，在 Mix-RL 阶段也用 CDM 作为公式任务的奖励（第 31、34 章）——原因正是本节所说的：字符串比较对公式太不公平。

## 3.11 真实世界对照

**真实的公式数据。** 最早的大规模公式识别数据集（如 im2latex-100k）从 arXiv 论文的 LaTeX 源码中提取公式，渲染成图片作为输入。它的作者就遇到了本章的问题，做法是：用一个真正的 LaTeX 解析器（基于 KaTeX）把所有公式解析后重新输出，统一空格、花括号等写法，再把公式切成记号。这和本章的 `normalize` 是同一个思想，只是文法大得多。

**真实的 LaTeX 远比我们的子集复杂**：几百个命令（`\alpha`、`\sum`、`\int`、`\mathbf`），可伸缩的括号（`\left( \right)`），矩阵环境（`\begin{matrix}...\end{matrix}`），各种空白命令（`\,`、`\quad`），以及很多"排版相同、写法不同"的情形（`\dfrac` 与 `\frac` 在行间公式里一样）。所以真实的评测往往同时报告多个指标：字符串级的编辑距离（第 25 章）、BLEU，以及基于渲染的 CDM。

**文档解析的输出格式。** 本书第 33 章会对比几个开源文档解析系统，它们的输出约定各有不同：大多数用 Markdown 组织整页、用 LaTeX 写公式、用 HTML 写表格；有的模型还会输出每个区块的类别和边界框（例如用 JSON 列出 `{"category": "Formula", "bbox": [...], "text": "..."}`）。Xiaomi-OCR-0 对不同任务用不同的提示词，输出对应的格式。**输出格式本身就是模型设计的一部分**：格式越统一、越规范，模型越容易学，评测也越公平。

**结构化输出与语言模型。** 第 14 章会讲分词。一个有意思的问题是：`\frac` 应该是 1 个 token 还是 5 个？`<td>` 呢？很多 OCR 模型会把常用的 LaTeX 命令和 HTML 标签加进词表作为单独的 token，让序列更短、结构更清楚。

## 3.12 深入一步

### 为什么递归下降能工作：每次只看一个记号就够了

我们的解析器有一个很好的性质：**在任何位置，只看当前这一个记号，就知道该走文法的哪个分支**。看到 `{` 就是组，看到 `\frac` 就是分数，看到 `_` 或 `^` 就是上下标。这样的文法叫 **LL(1)** 文法（从左往右读、最左推导、向前看 1 个记号）。LL(1) 文法可以用递归下降解析，**不需要回溯**，每个记号只读一次，解析时间和字符串长度成正比。

唯一的例外是 `\over`：读到它之前，不知道前面的内容是分子。我们的处理方法——先当作普通的行读，遇到 `\over` 再"改口"——是一种常见的技巧。TeX 本身对 `\over` 也是这样处理的，这也是为什么 LaTeX 推荐用 `\frac` 而不推荐 `\over`：`\frac` 是"先说结构、再给内容"的，对人对机器都更清楚。

**设计一种输出格式时，让它容易解析，是一个真实的考虑。** 第 23 章设计 VLM 的定位输出格式（比如 `<box>(x0,y0),(x1,y1)</box>`），也会遵循这个原则：用明确的开始和结束标记，让模型的输出能被简单可靠地解析出来。

### 为什么"规范写法"能保证归一化的正确性

归一化正确的条件可以严格表述为两条：

1. **生成是单射**：不同的树，规范写法不同。在我们的规范写法里，每种节点都有唯一的、带完整括号的写法（上下标总带花括号、分数总用 `\frac{}{}`），所以从字符串可以唯一地还原出树——这正是"往返"性质 `parse(to_latex(t)) == t` 所保证的；
2. **解析消除了所有写法差异**：任何一种合法写法，解析出的树都是它所表示的那棵树。

由 1 和 2：`normalize(s1) == normalize(s2)` ⟺ `to_latex(parse(s1)) == to_latex(parse(s2))` ⟺（由 1）`parse(s1) == parse(s2)`。也就是说，**归一化后相等，恰好等价于表示同一棵树**。幂等性也随之成立：`normalize(normalize(s)) = to_latex(parse(to_latex(parse(s)))) = to_latex(parse(s))`，中间一步用了往返性质。

这就是为什么测试里要检查往返性质：它不是一个"顺便的"检查，而是归一化正确的数学前提。

### 结构的复杂度：为什么写法数目指数增长

3.4 节手算出一个 9 符号的公式有 64 种写法。一般地，如果一个公式有 k 个"独立的可变点"，每个有 2 种写法，总写法数是 2^k——**指数增长**。而两种随机写法完全相同的概率是每个可变点"两边一致"的概率之积，同样是**指数下降**。这就是 3.7 节的实验中，公式一长、结构一多，字符串匹配率就迅速掉到 20% 的原因。第 25 章会看到，**编辑距离**这种"部分给分"的指标，对写法差异不那么敏感，但也不是零——空格、花括号都会被计入编辑次数。

## 3.13 横向对照：怎样判断两个结构化输出"一样"

| 方法 | 怎么比 | 对写法差异 | 对真正的错误 | 代表与本书位置 |
|---|---|---|---|---|
| 字符串完全匹配 | `pred == ref` | 极度敏感（3.7 节：完美模型 20 分） | 一个字符错就 0 分，没有部分分 | 最简单的基线 |
| 归一化后完全匹配 | `normalize(pred) == normalize(ref)` | 消除文法内的差异 | 没有部分分；文法外的命令无法处理 | 本章；第 25 章 |
| 编辑距离 / NED | 需要多少次插入、删除、替换才能把一个变成另一个，除以长度 | 部分敏感 | 有部分分 | 文字 OCR 的标准指标（CER）；第 25 章 |
| BLEU | 统计 n 个连续记号的重合程度 | 部分敏感 | 有部分分，但对顺序和结构不敏感 | 早期公式识别论文常用 |
| 树编辑距离（TEDS） | 两棵树之间需要多少次节点插入、删除、替换 | 消除了文本层面的差异 | 有部分分，并且理解结构 | 表格识别的标准指标；第 25 章 |
| 渲染后比较（CDM） | 把两边都渲染成图，匹配每个符号的位置和形状 | 排版相同就判相同，最公平 | 有部分分 | 公式识别；Xiaomi-OCR-0 的评测和奖励；第 25、31、34 章 |

一个普遍的规律：**越接近"人看到的效果"的比较方式越公平，但也越复杂、越慢。** 字符串比较一微秒，渲染比较可能要几十毫秒。在评测时可以用慢而准的方法；在强化学习里每一步都要给成千上万个样本打分，就要在准确和速度之间权衡（第 31 章）。

## 3.14 本章小结

- 字符在计算机里是整数（Unicode 码位）；存储和传输时编码成字节（UTF-8，变长：英文 1 字节，中文和多数数学符号 3 字节）；
- Unicode 归一化（NFC/NFKC）能消除码位层面的写法差异，但 NFKC 会改变数学含义（`x²` → `x2`）；
- OCR 的输出是**带结构的文本**：Markdown（文档骨架）、HTML（表格，支持合并单元格）、LaTeX（公式）；
- 结构用**语法树**表示；`leaves` 给出从左到右的符号，必须和渲染器的框顺序一致；
- **解析** = 切记号 + 递归下降（每条文法规则一个函数）；**生成**有唯一的规范写法和多种等价的随机写法；
- **归一化 = `to_latex(parse(s))`**；它的正确性依赖往返性质；用基于性质的测试检验；
- 不归一化时，一个完美的模型在 level 3 上只有 19.9% 的完全匹配；训练标签、评测、奖励都要归一化；
- 归一化只能消除"同一棵树"的写法差异；排版相同但树不同的情况，要靠渲染后比较（CDM）。

## 参考答案

1. 码位是字符的编号（一个整数），UTF-8 字节是这个编号在文件中存储时的字节序列。`"x∑"` 有 2 个字符；`x` 占 1 个字节，`∑`（U+2211）占 3 个字节，共 4 个字节。
2. 真实表格中经常有合并单元格（跨行、跨列），HTML 用 `rowspan`/`colspan` 可以表达，Markdown 表格不能。
3. 因为 `_Parser.item` 在循环里读上下标时，不管先读到哪个，都分别存进 `sub` 和 `sup` 变量，最后构造 `("script", 底, sub, sup)`，节点里的顺序是固定的，与读到的先后无关。然后 `to_latex` 按规范总是先写下标。
4. 在 LaTeX 中，圆括号只是普通符号，不起分组作用，`^` 只作用于紧挨着的前一个原子，也就是 `)`。这意味着 `(x+1)^{2}` 和 `{(x+1)}^{2}` 排版相同，但语法树不同，归一化后不相等——我们的归一化会把这两种写法判为不同，这是它的局限之一。
5. 它检查 `to_latex` 的随机分支确实产生了与规范写法不同的字符串。如果随机分支因为 bug 从不生效（比如概率写成了 0，或者 `rng` 没有传下去），所有其他测试仍然会通过，但"写法不唯一"的模拟就失效了，基于它的评测实验也就失去了意义。
6. 有 2 个运算符，每个两边一致的概率是 `0.8² + 0.2² = 0.68`，两者独立，总概率 `0.68² ≈ 0.462`。
7. 可变点：上下标先后（2 种）、下标是否带花括号（2 种）、上标是否带花括号（2 种），共 2³ = 8 种写法。每一处"两边一致"的概率都是 `0.5² + 0.5² = 0.5`，总概率 `0.5³ = 0.125`。
8. `tokenize`：`['x', '_', '{', 'n', '}', '\over', '2']`（空格被丢掉）。`parse("{x_{n} \over 2}")`：组内的行先读到项 `x_{n}`，遇到 `\over`，把它作为分子、继续读到 `2` 作为分母，返回 `over` 节点，`group` 把它变成分数，最终 `_clean` 展平后得到 `('row', [('frac', ('row', [('script', ('sym','x'), ('row',[('sym','n')]), None)]), ('row', [('sym','2')]))])`，归一化为 `\frac{x_{n}}{2}`。
9. 它只接受"先下标后上标"的顺序：输入 `x^2_n` 时，先检查 `_`（不是），再检查 `^`（是），读完上标后就返回了，剩下的 `_n` 留给外层的 `row`，外层会把 `_` 当作原子去解析，报"不认识的记号"错误。它也不会拒绝 `x_1_2`：读完第一个下标后不再检查，第二个 `_` 同样会让外层报一个不准确的错误信息。正确的做法是用 `while` 循环，并检查重复。
10. ```python
    def count_nodes(t):
        kind = t[0]
        if kind in ("sym", "op"):
            return 1
        if kind == "row":
            return 1 + sum(count_nodes(c) for c in t[1])
        return 1 + sum(count_nodes(c) for c in t[1:] if c is not None)
    ```
    `parse("x^{2}")` 是 `('row', [('script', ('sym','x'), None, ('row', [('sym','2')]))])`：外层 row 1 + script 1 + sym x 1 + 上标 row 1 + sym 2 1 = 5。
11. 一行代码依赖两个复杂的函数，任何一个出错都会让它出错。例如：(a) 解析器没有消除某种写法差异（比如没有把 `{x}^2` 的底拆开），导致两种写法归一化后不同；(b) 生成器的规范写法不唯一或者有歧义（比如单字符上标不加花括号时，`x^{23}` 和 `x^23` 会混淆），往返性质失败；(c) 解析器接受了不合法的输入（比如 `x^2^3`），给出一个"猜测"的树；(d) 解析出的树形状和生成器的不一致（嵌套的 row），导致 `==` 比较失败。
