## 18.1 计算量：6N

### 推导

一个线性层 y = W x，W 是 d_out × d_in。对一个 token：

- **前向**：每个输出元素是 d_in 次乘法和 d_in 次加法，共 d_out 个输出 → 2 · d_in · d_out = **2 × 参数量** 次浮点运算（FLOP）；
- **反向**要算两样东西：
  - 对输入的梯度 ∂L/∂x = Wᵀ (∂L/∂y)：又是一次同样大小的矩阵乘法，2 × 参数量；
  - 对权重的梯度 ∂L/∂W = (∂L/∂y) xᵀ：外积，也是 2 × 参数量。

合计每个 token **6 × 参数量**。Transformer 的参数几乎都在线性层里（注意力的 4 个投影、MLP 的 3 个矩阵），所以：

```
训练 FLOP ≈ 6 · N · D
```

N 是参数量（不含嵌入：嵌入是查表，不做乘法），D 是训练的 token 数。这是估算训练成本最常用的公式。

**注意力分数**的部分不在 N 里：QKᵀ 和 权重·V 各是 2 · T · d 次（每个 token，每层），乘 3 算上反向，每层 12 · T · d。T 远小于 d 的几倍时可以忽略；长序列时要算上。

### 练习 18.3

```python
def flops_per_token(n_params_non_emb, n_layer, d_model, T):
    return 6 * n_params_non_emb + 12 * n_layer * T * d_model
```

## 18.2 显存

训练时显存里有四样东西：

| | 大小 | 说明 |
|---|---|---|
| 参数 | N × 每个参数的字节数 | float32 是 4 字节，bf16 是 2 字节 |
| 梯度 | 与参数相同 | 每个参数一个梯度 |
| 优化器状态 | Adam：2 × N × 4 字节 | m 和 v，通常用 float32 存 |
| 激活 | 与 批 × 长 × 层数 × d 成正比 | 前向时保存、反向时使用的中间结果 |

前三项只和模型大小有关，float32 训练时是 4 + 4 + 8 = **16 字节/参数**。混合精度训练（第 11 章）时：bf16 参数 2 + bf16 梯度 2 + float32 主权重 4 + Adam 8 = 仍是 16 字节/参数。

**激活**为什么要存？反向传播计算 ∂L/∂W = (∂L/∂y) xᵀ 时需要前向的输入 x。每一层的输入、注意力的权重、激活函数的输入……都要保存到反向时使用。它和批大小、序列长度成正比，和参数量没有直接关系。

### 怎样测量激活

PyTorch 的 `torch.autograd.graph.saved_tensors_hooks` 可以拦截 autograd 为反向保存的每个张量：

```python
def saved_activation_bytes(fn):
    seen, total = set(), [0]

    def pack(t):
        key = (t.data_ptr(), t.numel(), t.dtype)
        if key not in seen:
            seen.add(key)
            total[0] += t.numel() * t.element_size()
        return t

    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        loss = fn()
    return total[0], loss
```

- 每当 autograd 要保存一个张量，就调用 `pack`；我们只是记下它的大小，原样返回；
- 同一块内存可能被多个运算保存（比如一层的输出既是下一层的输入，又被残差使用），按数据指针去重；
- 参数本身也会被"保存"（线性层的反向需要 W），所以这个数字包括了一份参数。小模型时这部分可以忽略。

这个方法在 CPU 上也能用，不需要 GPU 的 `torch.cuda.max_memory_allocated`。

### 激活检查点

**激活检查点**（activation checkpointing，也叫梯度检查点）用计算换内存：前向时只保存每个块的**输入**，块内部的中间结果都丢掉；反向经过这个块时，用保存的输入**重新做一遍前向**，得到中间结果，再算梯度。

```python
for b in m.blocks:
    h = checkpoint(b, h, cos, sin, use_reentrant=False)
```

代价：每个块的前向做两次，总计算量从 前向 + 反向（≈ 1 + 2）变成 前向 + 前向 + 反向（≈ 1 + 1 + 2），多算约 1/3。

## 18.3 梯度累积

### 问题

想用批大小 256 训练，但显存只够放 32 个样本的激活。

### 做法

把大批拆成 8 个小批，每个小批做前向和反向，梯度**累加**在 `.grad` 里（PyTorch 的 `backward()` 默认就是累加，这也是为什么每步要 `zero_grad()`）；8 个都做完后，再做一次参数更新。

### 练习 18.1

```python
def train_step(model, opt, micro_batches, clip=1.0):
    n = len(micro_batches)
    total = 0.0
    for x, y in micro_batches:
        loss = model(x, targets=y)[1] / n
        loss.backward()
        total += loss.item()
    torch.nn.utils.clip_grad_norm_(model.parameters(), clip)
    opt.step()
    opt.zero_grad(set_to_none=True)
    return total
```

**为什么除以 n**：每个小批的 loss 已经是"小批内所有 token 的平均"。大批的损失是"大批内所有 token 的平均"。当每个小批的 token 数相同时：

```
大批平均 = (1/n) Σ_k (第 k 个小批的平均)
```

所以每个小批的 loss 除以 n 再反向，累加起来的梯度就是大批的梯度。

**等价的前提**：每个小批的有效 token 数相同。如果有的小批里有很多被 mask 的位置（比如监督微调时提示部分不计损失，第 26 章），"平均的平均"就不等于"总的平均"：短的小批里每个 token 的权重被放大了。正确的做法是先数出整个大批的有效 token 总数，每个小批的损失用"总和 / 总数"而不是"小批内平均 / n"。

- `clip_grad_norm_` 要在所有小批累积**之后**做：裁剪的是大批的梯度；
- `set_to_none=True` 把 `.grad` 设为 None 而不是 0，省一次清零的运算，也省内存。测试检查了这一点。

测试 `test_grad_accumulation_equals_big_batch` 用 SGD 验证：批 16 一次和批 4 累积 4 次，更新后的参数一致（误差 < 10⁻⁶）。

## 18.4 检查点与续训

### 要保存什么

续训后的结果要和不中断完全一样，需要恢复**训练的全部状态**：

1. **模型参数**；
2. **优化器状态**：Adam 的 m、v，以及步数 t（偏差修正要用）；
3. **当前步数**：学习率调度要用；
4. **随机数状态**：决定下一批取哪些数据、dropout 丢哪些单元。

### 练习 18.2

```python
def save_checkpoint(path, model, opt, step, generator, extra=None):
    torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "step": step,
                "rng": generator.get_state(), "extra": extra}, path)


def load_checkpoint(path, model, opt, generator):
    ck = torch.load(path, map_location="cpu", weights_only=False)
    model.load_state_dict(ck["model"])
    opt.load_state_dict(ck["opt"])
    generator.set_state(ck["rng"])
    return ck["step"], ck["extra"]
```

- `opt.state_dict()` 包含每个参数的 m、v 和步数，以及学习率等超参数；
- 我们的数据采样用一个独立的 `torch.Generator`，保存它的状态就能精确复现之后的批。如果用全局随机数（`torch.manual_seed`），还要保存 `torch.get_rng_state()`，用 GPU 时还有 `torch.cuda.get_rng_state()`；
- `weights_only=False`：PyTorch 2.6 起 `torch.load` 默认只允许加载张量，而我们的检查点里有 Python 对象（步数、extra）。只对自己生成的文件这样做：加载来路不明的文件时 `weights_only=False` 可能执行任意代码。

测试 `test_checkpoint_resume_is_exact`：训练 6 步得到 6 个损失；另起一次，训练 3 步、保存、在一个全新的模型和优化器里恢复、再训练 3 步。两次的 6 个损失用 `==` 比较，**逐位相同**。

第 1 部分：

- 实测 656 GFLOP/秒。32 核 CPU 的 float32 峰值大约是几 TFLOP/秒，我们用到了其中的一部分；一块现代 GPU 的 bf16 峰值是它的几百倍；
- 第 16 章的预训练是 0.26 PFLOP（2.6 × 10¹⁴），Qwen3-0.6B 是 9.5 × 10²² FLOP，相差约 4 亿倍。这就是为什么第 24 章起我们直接使用别人预训练好的模型：从零预训练一个真实的语言模型，远超个人能负担的范围；
- **利用率**（MFU，model FLOPs utilization）= 实际达到的 FLOP/秒 ÷ 硬件峰值。大模型训练的 MFU 一般在 30%–60%。用 6ND 和 MFU 就能在开始训练之前估算需要的时间：时间 = 6ND ÷ (峰值 × MFU)。

第 2 部分：

  与参数量成正比的部分（float32）：参数 12.4 MB  梯度 12.4 MB  Adam m 12.4 MB  Adam v 12.4 MB  合计 49.4 MB = 16 字节/参数
       批 × 长        保存的激活     每个 token         用激活检查点

- **激活与批 × 长成正比**：每个 token 约 90 KB。批 64 × 256 时激活是 1.38 GB，而参数、梯度、优化器状态加起来只有 49 MB。**小模型、大批、长序列时，激活是显存的大头**；
- 每个 token 90 KB，4 层，每层约 22 KB，也就是约 22 个 d = 256 维的 float32 向量：每层的 RMSNorm 输入输出、q、k、v、注意力输出、SwiGLU 的 gate 和 up（各 2.75d）及其乘积……都要为反向保存。8 × 128 时每个 token 略多（99.9 KB），因为参数本身也被"保存"了一份，摊到的 token 少；
- **激活检查点**把激活降到约 1/12（99.9 → 7.6 MB）：只剩每个块的输入（每层 1 个 d 维向量）和最后的输出层。代价是每个块的前向要做两遍。

**估算真实模型**：全量微调 Qwen3-0.6B，16 字节/参数 × 0.6B ≈ 8.9 GB，还没算激活。这超过了作者实际能用的显存（作者的 GPU 上同时运行着别的服务，只剩不到 1 GB）。第 28 章用 LoRA：冻结原模型，只训练每层旁边很小的低秩矩阵，梯度和优化器状态几乎为 0，模型本身可以用 bf16（2 字节/参数）甚至 4 位量化存储。

    小批 32 × 累积  1：每步 0.12 秒，激活峰值  362.4 MB

第 4 部分：

```
  不中断训练 120 步 vs 训练 60 步、保存、在新进程里恢复、再训练 60 步：120 个损失逐位相同
  只恢复模型、忘了恢复优化器：第 61–65 步的损失 [2.54, 3.156, 3.022, 2.755, 2.658]

```

- 完整的检查点让续训和不中断**逐位相同**：120 个浮点数用 `==` 比较全部相等；
- 忘了恢复优化器（只加载了模型参数）：第 61 步的损失相同（它是在更新之前算的），第 62 步跳到 3.156，比正确的 2.514 高了 0.64，之后几步逐渐回落。

原因（第 11 章）：新的 Adam 的 m = v = 0，步数从 1 开始。第一步经过偏差修正后，更新量是 lr · m̂/√v̂ = lr · g/|g| = lr · sign(g)：**每个参数都被推了整整一个学习率**，不管它的梯度多小。训练到第 60 步时，正常的 Adam 更新量远小于 lr（v 记住了梯度的大小）；突然的满幅更新把模型推离了原来的位置。

真实训练中更常见的错误是忘了恢复学习率调度的步数：学习率从预热重新开始，或者停在错误的位置。所以检查点里要存步数。

## 18.6 迷你缩放定律

### 什么是缩放定律

2020 年 OpenAI 的研究（Kaplan 等）发现：语言模型的损失与参数量 N、数据量 D、计算量 C 之间存在惊人规律的**幂律**关系：

```
L(N) ≈ c + a · N^(−α)
```

c 是不可约的损失（语言本身的不确定性），a · N^(−α) 是"模型不够大"造成的额外损失。在双对数坐标上，L − c 和 N 是一条直线。这条规律跨越了好几个数量级，让人可以用小模型的实验预测大模型的效果。

### 实验

第 5 部分：固定 4 层，只改宽度 d，每个模型都训练 800 步 × 32 × 128 = 330 万个 token：

```
    d =  32  N =    65,824  验证 1.949 bits/字符  （17 秒，计算量 1.29 TFLOP）
    d =  64  N =   213,568  验证 1.838 bits/字符  （22 秒，计算量 4.20 TFLOP）
    d =  96  N =   443,232  验证 1.817 bits/字符  （33 秒，计算量 8.71 TFLOP）
    d = 128  N =   853,120  验证 1.816 bits/字符  （45 秒，计算量 16.77 TFLOP）
    d = 192  N = 1,771,200  验证 1.809 bits/字符  （72 秒，计算量 34.82 TFLOP）
    d = 256  N = 3,213,568  验证 1.814 bits/字符  （96 秒，计算量 63.18 TFLOP）
  拟合 L(N) = 1.773 + 7.32 · N^(−0.368)（bits/字符）
  外推：N = 10M 时 1.792，N = 100M 时 1.781——越来越接近 1.773
```

（`power_fit` 对 c 做网格搜索，每个 c 下对 log(L − c) 和 log N 做最小二乘直线拟合，选误差最小的。图存在 `outputs/ch18/scaling.png`。）

读法：

- **前几步的收益很大**：N 从 6.6 万到 21 万（3 倍），损失降了 0.11 bits；从 21 万到 44 万降了 0.02；之后几乎不降；
- **c = 1.773**：拟合出的"不可约损失"。第 16 章 16.9 节分析过，我们的语料由随机单词组成，本身就有约 1.5 bits/字符以上的熵，模型再大也降不下去。c 还包含了"只训练 330 万个 token"带来的限制；
- **最大的模型反而略差**（d = 256 是 1.814，d = 192 是 1.809）：大模型在同样的步数下**欠训练**——参数多，需要更多的数据和步数才能收敛。这也提醒我们：0.005 bits 的差别在这个实验的噪声范围内，不要过度解读；
- 指数 α = 0.368 只是在这个小实验上的拟合值。Kaplan 等人在真实语言上得到的 α 约 0.076（对参数量），Chinchilla 的拟合约 0.34——不同的实验设置、数据、拟合方法得到的数字差别很大。重要的是**幂律的形式**和**收益递减**的规律。

在我们的合成语料上，缩放定律的"好消息"（大模型更好）很快就被不可约损失淹没了。真实语言的 c 低得多，可学的结构多得多，所以模型越大越好的趋势能持续很多个数量级。

### Chinchilla：参数和数据怎样分配

计算量 C ≈ 6ND 固定时，该用大模型少数据，还是小模型多数据？DeepMind 2022 年的 Chinchilla 研究训练了 400 多个模型，结论是：**N 和 D 应该同比例增长**，最优点大约是**每个参数 20 个 token**。

```
  我们最大的模型 N = 3,213,568，按这个比例需要 64M token，实际只训练了 3.3M——它是"欠训练"的
```

Chinchilla 之前，GPT-3（1750 亿参数）只训练了 3000 亿 token（每个参数不到 2 个）。Chinchilla（700 亿参数、1.4 万亿 token）用更少的参数达到了更好的效果。

今天的小模型训练的数据远远超过 20 token/参数：Qwen3-0.6B 训练了约 36 万亿 token，每个参数 6 万个 token。为什么？Chinchilla 回答的是"**训练**计算量固定时怎样最优"，但模型训练一次、使用无数次，**推理**成本和参数量成正比。多花训练成本让小模型更强，部署时更便宜。这对 VLM 尤其重要：OCR 要处理海量文档，小而强的模型（0.5B–3B）才有实际价值。

## 18.7 吞吐与批大小

第 6 部分：

```
     批大小     训练 token/秒        推理（前向）token/秒
       1          8,981               58,644
       4         21,771               92,935
      16         31,713              131,103
      64         32,727              108,066
```

- **训练**：批 1 时每秒只有 9 千个 token，批 16 时 3.2 万，批 64 时几乎不再增加。批小的时候，矩阵乘法太小，大部分时间花在调度、启动运算、读写内存上；批大到一定程度后，算力被用满，再大的批只增加显存，不增加速度；
- **推理**：批 64 反而比批 16 慢。批大时中间结果太大，放不进 CPU 的缓存，频繁读写内存（第 15 章注意力计时的同一现象）。在 GPU 上也有类似的"最佳批大小"，需要实测；
- 这和第 17 章"解码比预填充慢 35 倍"是同一个道理的两面：硬件喜欢大块的计算。

**批大小还影响优化**：大批的梯度噪声小，可以用更大的学习率；但超过某个"临界批大小"后，增大批不再减少需要的步数，只是浪费计算。语言模型预训练的批大小通常是几百万个 token，并且在训练过程中逐渐增大。

## 18.8 训练监控：看什么、怎么判断

前面的实验都很短，出了问题一眼就能看出来。真实的训练动辄几小时到几周，需要在训练过程中持续记录几个量，及早发现问题。`train_lm` 每隔一段打印的正是其中最基本的几项。

### 该记录的量

| 量 | 正常的样子 | 异常时说明什么 |
|---|---|---|
| 训练损失 | 先快速下降，然后缓慢下降，有小幅波动 | 不降：学习率太小、数据或标签错位；突然变成 nan：数值溢出 |
| 验证损失 | 跟着训练损失下降，略高 | 训练降、验证升：过拟合（第 10 章） |
| 梯度范数（裁剪前） | 训练初期较大，之后稳定在某个范围 | 突然暴涨：损失尖峰的前兆；持续为 0：梯度断了 |
| 学习率 | 按调度变化（预热、余弦衰减） | 与预期不符：调度的步数没对上（比如续训没恢复步数） |
| 吞吐（token/秒） | 稳定 | 突然下降：数据加载成了瓶颈、显存不够开始交换 |
| 显存峰值 | 前几步后稳定 | 持续增长：某处保留了计算图（比如把带梯度的 loss 存进列表，而不是 `loss.item()`） |

最后一行是新手很常见的错误：`losses.append(loss)` 会把整个计算图留在内存里，每一步都多留一份，显存一路上涨直到溢出。应该写 `losses.append(loss.item())`。我们的 `train_step` 返回的 `total` 就是用 `loss.item()` 累加的浮点数。

### 损失尖峰

大模型训练中，损失有时会突然跳高几倍，然后（有时）慢慢恢复。常见的原因：

- **学习率过大**：训练后期本该稳定，但某一批数据的梯度特别大，一步走得太远；
- **坏数据**：某批数据异常（大量重复字符、极长的序列、乱码），模型对它的损失很大；
- **数值问题**：bf16/fp16 下某处溢出（第 11 章）、注意力的 logits 过大，softmax 饱和。

应对方法依次是：梯度裁剪（我们一直在用，`clip=1.0`）、降低学习率、跳过有问题的数据、从尖峰之前的检查点恢复后换一个数据顺序继续。这也是为什么要**定期**保存检查点：出了问题能回到不久之前。

### 怎样判断"训练够了没有"

- 验证损失已经不怎么降了，并且降幅小于你关心的精度——比如本章 d = 128 和 d = 192 的 0.007 bits 之差，已经接近随机波动；
- 下游任务的指标（OCR 的字符错误率、第 13 章的 CER）不再提高。损失和下游指标不总是同步：损失降了 0.01，CER 可能不变；
- 对照缩放曲线：如果同样大小的模型多训练一倍数据只降了一点点，再训练也不划算，不如换更大的模型或更好的数据。

**看曲线而不是看单个数**：一次评估的验证损失有随机误差（验证集有限）。判断趋势时看最近几次评估的变化，或者把评估用的批数加大。

## 18.10 常见错误

| 现象 | 原因 | 怎么查 |

| 梯度累积后训练发散 | 每个小批的损失没有除以累积次数，梯度大了 n 倍 | 和不累积的大批比较梯度 |

## 18.11 真实世界对照

- **大模型训练的规模**：Qwen3 用约 36 万亿 token 预训练；Llama 3 用约 15 万亿 token。训练用数千到上万块 GPU，持续数周到数月；
- **并行策略**：单块 GPU 放不下时，要把模型和数据分到多块 GPU 上：数据并行（每块 GPU 一份完整模型，处理不同的数据）、ZeRO / FSDP（把参数、梯度、优化器状态切分到各块 GPU）、张量并行（把一个矩阵乘法切开）、流水线并行（不同的层放在不同的 GPU）。本章的梯度累积可以看作单卡上的"数据并行"；
- **检查点**：大规模训练每隔几百到几千步保存一次检查点，一个检查点可能有几百 GB（参数 + 优化器状态）。训练中途机器故障是常态，自动从最近的检查点恢复是基本要求；
- **缩放定律的应用**：开始一次昂贵的训练之前，先用一系列小模型拟合缩放曲线，预测大模型的损失，选择超参数。GPT-4 的技术报告说，他们用计算量少 1 万倍的小模型拟合曲线，准确预测了最终损失；
- **微调的显存**：第 28 章逐项估算并实测显存的组成、实现 LoRA；第 35 章估算真实 VLM 全量微调与 LoRA 的显存，并在 CPU 上实测峰值内存。

## 18.12 深入一步

### 6N 的推导更细致一点

前向 2N 的说法忽略了一些小项：激活函数、归一化、softmax、残差相加，它们的计算量与 d（而不是 d²）成正比，相比矩阵乘法可以忽略。反向的 4N 也假设了每个参数都要计算梯度；冻结的参数（第 22 章冻结视觉编码器、第 28 章 LoRA）不需要对权重的梯度。如果冻结的层后面还有要训练的层、前面也有（比如 LoRA 中的每一层），梯度仍要穿过它，只省掉对权重的那一半，反向从 4N 降到 2N，合计 4N；如果冻结的部分在最底层、它之前没有要训练的东西（第 22 章冻结的视觉编码器），反向根本不必经过它，只剩前向的 2N。

### 激活检查点的最优策略

我们在每个块的边界设检查点。更一般地，设检查点的位置是一个优化问题：检查点越密，保存的越多、重算的越少；越稀，保存的越少、重算的越多。经典的结论是：对 L 层的网络，每隔 √L 层设一个检查点，内存降到 O(√L)，计算只多一次前向。还可以只对计算便宜、内存大的部分（比如注意力的 softmax）重算。

### 为什么累积的步数不能太多

梯度累积让我们用小显存模拟大批，但大批本身不总是好的。批越大，每个样本对参数的"推动"越平均，模型越容易停在平坦的区域；在相同的 token 数下，过大的批意味着更少的更新步数。批大小是一个需要调的超参数，梯度累积只是实现它的手段。

## 18.14 本章小结

- 训练计算量 ≈ 6ND：前向 2N、反向 4N；
- 训练显存 = 参数 + 梯度 + 优化器状态（16 字节/参数）+ 激活；小模型、长序列时激活是大头；
- `saved_tensors_hooks` 可以在 CPU 上实测激活；激活检查点用重算换内存，本例降到 1/12；
- 梯度累积等价于大批（前提是各小批的有效 token 数相同），激活降到 1/n；
- 完整的检查点 = 参数 + 优化器状态 + 步数 + 随机数状态，续训才能逐位一致；忘了优化器状态会让损失跳起来；
- 缩放定律：L(N) = c + a · N^(−α)，收益递减；在我们的随机语料上很快接近不可约损失；
- Chinchilla：训练计算量固定时约 20 token/参数最优；为了推理便宜，小模型常常训练得远超这个比例；
- 吞吐随批大小增长，直到算力用满。

## 参考答案

1. 每个线性层的前向是一次矩阵乘法（2 × 参数量次运算）；反向要算对输入的梯度和对权重的梯度，各是一次同样大小的矩阵乘法，所以是前向的两倍。合计 6N。
2. 参数、梯度、优化器状态、激活。只有激活与批大小（和序列长度）有关。
3. 用计算换内存：不保存块内部的激活，反向时重新做一遍前向，多算约 1/3，激活大幅减少。
4. 各个小批的有效 token 数不同时（比如有的位置被 mask 掉），"小批平均再平均"不等于"全部 token 平均"。
5. 模型参数、优化器状态（m、v、步数）、当前步数（学习率调度）、随机数状态（数据顺序、dropout）。缺了优化器状态，新 Adam 的第一步更新量是 lr · sign(g)，每个参数被推了满幅的学习率，损失跳起来。
6. 不可约损失：模型再大也降不下去的部分，包括数据本身的不确定性。我们的语料由均匀随机的单词组成，下一个单词本来就无法预测，熵很高。
7. 训练计算量固定时，参数和数据应同比例增长，约 20 token/参数最优。今天的小模型要大量部署，推理成本与参数量成正比，多花训练计算让小模型更强更划算。
8. 6 × 1.2 × 10⁹ × 10¹¹ = 7.2 × 10²⁰ FLOP。
9. 16 字节 × 7 × 10⁹ = 112 GB（约 104 GiB）。
10. 90 KB × 16 × 512 ≈ 737 MB；激活检查点后约 61 MB。
11. 10⁶^(−0.368) = 10^(−2.208) = 0.00619；7.32 × 0.00619 = 0.0453；L = 1.818。
12. 每个小批都做了 `opt.step()`，这是普通的小批训练而不是梯度累积；损失也没有除以累积次数。应该在所有小批 `backward()` 之后才 `step()` 和 `zero_grad()`，每个小批的损失除以 n。
13. `model`（参数）、`opt`（优化器状态：m、v、步数、超参数）、`step`（当前步数，学习率调度用）、`rng`（数据采样和 dropout 的随机数状态），可选的 `extra`（配置、最好的验证损失等）。
14. 用同样的初始条件训练 2k 步记录每步损失；另起一次训练 k 步、保存、在全新的模型和优化器里恢复、再训练 k 步；比较两组损失是否逐位相同（`==`）。
