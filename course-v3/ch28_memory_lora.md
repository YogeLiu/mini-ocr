# 第 28 章　显存、梯度检查点、LoRA 与冻结

## 本章在全景图中的位置

到第 27 章为止，我们的模型只有 420 万个参数，训练时从来不用担心内存。真实的 VLM 不一样：第 24 章看过的 Qwen3.5-0.8B 有 8.5 亿个参数，LLaVA-1.5 有 70 亿个。拿到一块 16 GB 的显卡，第一个问题往往不是"怎样训练得更好"，而是"**能不能训练起来**"。

本章回答这个问题，分三步：

1. **训练时内存里有什么？** 参数、梯度、优化器状态、激活值。前三样只和参数量有关，可以用一行公式**估算**；激活值和批大小、序列长度有关，我们在 CPU 上**精确地数出来**：PyTorch 允许截获每一个"前向时保存、反向时要用"的张量；
2. **激活值太多怎么办？** 梯度检查点：前向时少存一些，反向时重新算；
3. **参数相关的内存太多怎么办？** 冻结一部分模型、或者用 LoRA 只训练一个很小的增量。

第 35 章在真实模型上做 LoRA 微调时，用到的就是这里的估算方法和这三种手段。

本章的第 1–5 部分不训练，所有数字都是作者在 CPU 上实际测出来的（日志在 `outputs/ch28/`）；第 6 部分的训练对照由你自己跑。

## 学习目标

学完本章，你应该能够：

1. 对任意一个模型，估算全参训练（fp32、bf16 混合精度）和 LoRA 训练时参数、梯度、优化器状态各占多少内存，并解释为什么"bf16 混合精度"并不减少这部分内存；
2. 说出激活值是什么、为什么随"批大小 × 序列长度"线性增长；用 `saved_tensors_hooks` 在 CPU 上精确地数出一次前向保存了多少激活值，并能把一个 Transformer 块的激活值逐项对上；
3. 解释为什么冻结语言模型、只训练连接器时，语言模型的激活值仍然要保存；
4. 实现梯度检查点，说明它省了什么、多花了什么，并验证它不改变梯度；
5. 实现 LoRA：低秩分解、B = 0 的初始化、α/r 缩放、合并；数出 LoRA 的参数量，说出 LoRA 省了哪些内存、没省哪些；
6. 面对一个"显存不够"的情况，知道先查哪一项、用哪种手段。

## 28.1 训练时内存里有什么

训练一步时，内存里有五类东西：

| | 是什么 | 大小取决于 | 什么时候存在 |
|---|---|---|---|
| **参数** | 模型的权重 | 参数量 | 始终 |
| **梯度** | 每个可训练参数一个 | 可训练参数量 | 反向开始到优化器更新之后 |
| **优化器状态** | AdamW 的 m 和 v | 可训练参数量 | 始终 |
| **激活值** | 前向时算出、反向时还要用的中间结果 | 批大小 × 序列长度 × 模型宽度 × 层数 | 前向开始到反向用完 |
| **临时结果** | 某一步计算的输出，用完就丢 | 一般较小 | 一瞬间 |

前三类叫**静态内存**：模型和优化器一定，它们就固定了，和你喂多大的批无关。激活值是**动态内存**：批大一倍，它就大一倍。

为什么要分开讨论？因为它们的解决办法不同：

- 静态内存太大：用更少的字节存每个数（低精度）、冻结一部分参数、LoRA、把优化器状态分到多张卡上（ZeRO，28.11 节）；
- 激活值太大：减小批（配合梯度累积，第 18 章）、梯度检查点、更短的序列（对 VLM：更少的视觉 token）。

## 28.2 静态内存：估算

### 每个参数几个字节

全参训练、fp32、AdamW：

```
权重 4 字节 + 梯度 4 字节 + m 4 字节 + v 4 字节 = 16 字节/参数
```

一个 10 亿参数的模型，光静态内存就要 16 GB。

**bf16 混合精度**（第 11 章）：前向和反向用 bf16 计算，权重和梯度是 bf16（各 2 字节）；但优化器更新时要用 fp32，否则小的更新量会被舍掉（bf16 只有 7 位尾数，1 附近的间距是 2⁻⁷ ≈ 0.0078，1 + 0.001 在 bf16 里就是 1）。所以要再存一份 fp32 的"主权重"：

```
bf16 权重 2 + bf16 梯度 2 + fp32 的 m、v 各 4 + fp32 主权重 4 = 16 字节/参数
```

**和 fp32 一样多。** 混合精度省的不是静态内存，而是**激活值**（每个激活值从 4 字节变成 2 字节）和**计算时间**（GPU 的 bf16 矩阵乘法快得多）。很多初学者以为"换成 bf16 显存就减半"，这是最常见的误解之一。

**LoRA**（28.5 节）：底座冻结，用 bf16 存（2 字节/参数，没有梯度、没有优化器状态）；只有 LoRA 的小矩阵要梯度和优化器状态（16 字节/参数）。

### 练习 28.3：`static_memory`

```python
def static_memory(n_params, n_trainable, param_dtype="fp32", optimizer="adamw", master_fp32=False):
    b = BYTES[param_dtype]
    out = dict(params=n_params * b, grads=n_trainable * b,
               optim={"adamw": 8, "sgd": 0}[optimizer] * n_trainable,
               master=4 * n_trainable if master_fp32 and param_dtype != "fp32" else 0)
    out["total"] = sum(out.values())
    return out
```

注意 `params` 用的是**全部**参数，其余三项用的是**可训练**参数。冻结的参数仍然要在内存里（前向要用它），但不需要梯度和优化器状态。

### 第 1 部分：四个模型的估算

真实模型的参数量怎么数？下载整个模型太慢。`transformers` 可以只读配置文件、在 `meta` 设备上建模型：每个张量只有形状、没有数据，不占内存。这样几秒钟就能数出 70 亿参数模型的每一层。

```
模型                参数    LoRA 参数   全参 fp32 + AdamW  全参 bf16 混合精度  LoRA（bf16 底座）
我们的 VLM        4.2M     0.28M (6.79%)       63.54 MB            63.54 MB          12.26 MB
Qwen3.5-0.8B    853.0M     6.39M (0.75%)       12.71 GB            12.71 GB           1.68 GB
Qwen2.5-VL-3B  3754.6M    29.93M (0.80%)       55.95 GB            55.95 GB           7.44 GB
LLaVA-1.5-7B   7063.4M    39.98M (0.57%)      105.25 GB           105.25 GB          13.75 GB
```

（LoRA：r = 16，装在语言模型所有注意力和 MLP 的线性层上，28.5 节。）

手算核对 Qwen3.5-0.8B 的 LoRA 一栏：底座 853.0M × 2 字节 = 1.706 × 10⁹ 字节；LoRA 的参数 6.39M × 16 字节（bf16 权重 2 + 梯度 2 + m、v 8 + 主权重 4）= 0.102 × 10⁹ 字节；合计 1.808 × 10⁹ 字节 = 1.808 × 10⁹ / 2³⁰ GB = 1.68 GB。

读这张表：

- **一块 16 GB 的显卡全参训练不了 Qwen3.5-0.8B**：静态内存已经 12.7 GB，再加上激活值、CUDA 自己占的内存（28.7 节）就不够了。用 LoRA 只要 1.68 GB；
- **7B 模型的全参训练要 105 GB**，超过任何一张消费级显卡，甚至超过一张 80 GB 的 A100。这就是为什么大模型的微调几乎都用 LoRA 或者多卡；
- 我们的 VLM 上 LoRA 参数占比（6.79%）比真实模型（0.6–0.8%）高得多：r = 16 相对于宽度 256 很大，而真实模型的宽度是 1024–4096。LoRA 的参数量 ∝ r × (in + out)，原层 ∝ in × out，宽度越大，同样的 r 占比越小。

## 28.3 激活值

### 什么是激活值，为什么要保存

第 8 章写自动求导时，每个运算的 `backward` 都要用到前向时的某些量：

| 运算 | 反向要用的 |
|---|---|
| `y = x @ W.T`（线性层） | 对 W 的梯度 `gᵀ x` 要 **x**；对 x 的梯度 `g W` 要 W（参数，本来就在内存里） |
| `y = silu(x)` | silu 的导数要 **x** |
| `y = a * b` | 对 a 的梯度要 **b**，对 b 的梯度要 **a** |
| `y = x / rms(x) * w`（RMSNorm） | 要 **x** 或归一化后的结果，以及 **rms** |
| softmax / 注意力 | 要输出（或者能重新算出输出的量） |

这些被保存下来的张量就是**激活值**。它们的形状都带着 (批大小, 序列长度, …)，所以批大一倍、序列长一倍，激活值就大一倍。

### 练习 28.4：`SavedTensors`

PyTorch 在前向时把每个要保存的张量交给 autograd。`torch.autograd.graph.saved_tensors_hooks(pack, unpack)` 让我们在这一刻插一个函数：每保存一个张量，`pack(t)` 就被调用一次。我们在 `pack` 里记下它的大小，然后原样返回。

```python
def _pack(self, t):
    st = t.untyped_storage()
    ptr = st.data_ptr()
    if ptr not in self.skip and ptr not in self.seen:
        self.seen.add(ptr)
        self.bytes += st.nbytes()
        self.count += 1
    return t
```

两个细节：

- **按存储去重**。很多张量是同一块内存的不同视图（`view`、`transpose`、切片），比如 q、k、v 都是 qkv 输出的视图。按张量算会重复计数，按 `untyped_storage()` 算才是真实占用的内存；
- **跳过参数和 buffer**。线性层的反向要用 W，所以 W 也会被"保存"，但它本来就在内存里，不是额外的开销。`__init__` 里把模型所有参数和 buffer 的存储地址放进 `self.skip`。

为什么不用 GPU 的显存统计？一是这台机器的 GPU 被别的程序占着；二是 CUDA 的统计里混着内存分配器的缓存、临时结果、CUDA 上下文，很难对上"到底存了哪些张量"（28.7 节）。`SavedTensors` 数出来的是精确的、可以逐项核对的数字。

### 一个 Transformer 块保存了什么

用第 16 章的 GPT 的一个块（d = 256，d_ff = 704，4 个头），输入 100 个 token，记录每个被保存的张量来自哪个子模块。单位是"每个 token 几个 d 维的 fp32 向量"（一个 d 维向量 = 256 × 4 = 1 KB）：

| 子模块 | 保存的东西 | 每个 token |
|---|---|---|
| `n1`（RMSNorm） | 输入 x、归一化后的结果；rms（每个 token 一个数） | 2.0 |
| `attn.qkv` | 线性层的输入 | 1.0 |
| `attn`（RoPE、注意力） | qkv 的输出（q、k、v 共 3 份）、加了 RoPE 的 q 和 k（2 份）、注意力的输出（1 份）；logsumexp（每个头每个 token 一个数） | 6.0 |
| `n2`（RMSNorm） | 同 n1 | 2.0 |
| `mlp.gate`、`mlp.up` | 两个线性层共用的输入 | 1.0 |
| `mlp`（SwiGLU） | gate 的输出、up 的输出、silu(gate)，各 d_ff = 2.75 d | 8.25 |
| `mlp.down` | 线性层的输入 silu(gate) · up | 2.75 |
| **合计** | | **23.0** |

三点值得注意：

1. **MLP 占了一半多**（12 / 23）：它的中间层宽 2.75 d，有四个这么宽的张量；
2. **没有 T × T 的注意力矩阵**。朴素的注意力要保存 softmax 之后的 (头, T, T) 矩阵，T = 2048 时这一项比别的都大。`F.scaled_dot_product_attention` 用的是 Flash Attention 一类的算法：只存每行的 logsumexp（这里 0.016），反向时重新算注意力分数。这是现代模型能处理长序列的关键之一；
3. 加上最后的 RMSNorm、输出层和交叉熵（每个 token 3.4 个向量，均摊到 4 层是 0.85），每层每个 token 约 **23.9 个 d 维向量**。

### 用公式推到真实模型

对一个结构和我们相同的 Transformer（Pre-LN、SwiGLU、Flash 注意力），每层每个 token 的激活值约为（把上表里的 d_ff 单独写出来）：

```
2 + 1 + 6 + 2 + 1 = 12 个 d 维向量    +    4 个 d_ff 维向量
```

以 LLaMA-7B 的形状为例（d = 4096，d_ff = 11008，32 层，bf16 每个数 2 字节）：

```

```

### 第 2 部分：冻结哪一部分，激活值会怎样

批 8 条描述（每条约 163 个 token，其中 64 个视觉 token），在不同的冻结设置下数激活值、测一步（前向 + 反向）的时间：

| 设置 | 可训练参数 | 保存的激活值 | 张量数 | 每步 |
|---|---|---|---|---|
| 全部训练 | 4,164,224 | 139.57 MB | 138 | 54 毫秒 |
| 冻结 ViT | 3,337,984 | 122.87 MB | 82 | 47 毫秒 |
| 冻结语言模型（只训 ViT + 连接器） | 925,056 | 102.63 MB | 115 | 44 毫秒 |
| 只训连接器（第 22 章阶段 1） | 98,816 | 85.93 MB | 59 | 43 毫秒 |
| 只训 ViT | 826,240 | 101.88 MB | 113 | 42 毫秒 |
| LoRA r = 16（语言模型）+ 连接器 | 381,440 | 111.72 MB | 91 | 55 毫秒 |
| 全部冻结（只做前向） | 0 | 0 B | 0 | 15 毫秒 |

对照：参数本身（fp32）只有 15.89 MB。**这个批的激活值是参数的 8.8 倍。**

最值得想清楚的一行是**只训连接器**：可训练的参数只有 2.4%，激活值却还有全部训练时的 62%。为什么？

连接器在语言模型的**前面**。损失在语言模型的输出端，梯度要从输出端一路穿过语言模型的每一层，才能传到连接器。穿过一层，就要用到这一层的激活值（比如 silu 的导数要它的输入）。所以**冻结的语言模型照样要保存激活值**，只是少存了一些：冻结的线性层不需要算 W 的梯度，于是不需要保存它的输入 x（上面"线性层"那一行）；冻结的 RMSNorm 不需要算它的缩放权重的梯度，于是不需要保存归一化后的结果。用 28.3 节的方法数一个冻结的块：每个 token 16.27 个向量，比训练时的 23.02 少 6.75 个——qkv、gate/up、down 的输入（1 + 1 + 2.75）和两个 RMSNorm 的输出（1 + 1）。o 的输入就是注意力的输出（同一块内存），注意力反向要用它，所以照样要存。

核对：6.75 个向量 × 4 层 × 1304 个 token（8 条 × 163）× 1 KB = 34.4 MB，再加上最后的 RMSNorm 和输出层少存的两个向量（2 × 1304 KB = 2.5 MB），共 36.9 MB；测量的差是 139.57 − 102.63 = 36.94 MB。

反过来，**冻结 ViT** 时 ViT 的激活值全部不用存：ViT 在最前面，它的参数不训练，就没有任何梯度需要穿过它。

**全部冻结**时激活值是 0：损失不需要梯度，autograd 什么都不保存。这就是 `torch.no_grad()` 推理时内存小得多的原因。

时间：冻结只省了 20% 左右（54 → 43 毫秒）。反向的大部分工作是"把梯度往前传"，冻结只省掉了"算参数的梯度"那一半里的一部分。LoRA 在这个小模型上甚至没有变快（55 毫秒）：多出来的小矩阵乘法有固定的开销，在宽度 256 的模型上省下的计算抵不过这些开销。在真实的大模型上 LoRA 会快一些（28.5 节）。

（这些毫秒级的时间在 CPU 上有几毫秒的波动，只看大致的比例。）

## 28.4 梯度检查点

### 想法

激活值存下来，是为了反向时用。如果不存，反向时**重新算一遍前向**，也能得到它们。这就是梯度检查点（gradient checkpointing，也叫激活重计算）：

- 前向时，每个 Transformer 块只保存它的**输入**（每个 token 1 个向量），块内部的 23 个向量都不存；
- 反向传播到这个块时，用保存的输入把这个块的前向再跑一遍（这次保存内部的激活值），然后立刻对这个块做反向，用完就丢。

任何时刻，内存里只有"所有块的输入"加上"一个块的内部激活值"。代价是每个块的前向算了两次：一步的计算量从"前向 + 反向 ≈ 1 + 2 = 3 份前向"变成"4 份前向"，多 33%。

### 练习 28.5：`CheckpointBlock`

```python
class CheckpointBlock(nn.Module):
    def __init__(self, block):
        super().__init__()
        self.block = block

    def forward(self, *args, **kw):
        if torch.is_grad_enabled() and self.training:
            return checkpoint(self.block, *args, use_reentrant=False, **kw)
        return self.block(*args, **kw)
```

`torch.utils.checkpoint.checkpoint` 做了所有的工作。`use_reentrant=False` 是 PyTorch 推荐的新实现：旧的实现（`True`）在输入都不需要梯度时会出错（比如冻结了前面所有层），也不支持关键字参数。推理时（`no_grad` 或 `eval`）直接调用，不需要多算。

`checkpoint_blocks(blocks)` 把一个 `ModuleList` 里的每个块原地换成 `CheckpointBlock`。因为换的是 `blocks[i]`，模型的 `forward` 不用改：它照样 `for b in self.blocks: x = b(x, cos, sin)`。

### 第 4 部分：省了多少、多花了多少

同一批 8 条描述，全部训练：

```
检查点：不用             激活值  139.57 MB（138 个张量）  每步 50 毫秒
检查点：语言模型的块     激活值   27.38 MB（ 74 个张量）  每步 61 毫秒
检查点：语言模型 + ViT   激活值   12.32 MB（ 26 个张量）  每步 62 毫秒
两种方式的损失 4.672068 vs 4.672068，梯度最大差 0.0e+00
```

- 语言模型的块加检查点，激活值少了 80%（139.57 → 27.38 MB），时间多了 22%（理论上限是 33%：只有块内部被重算，嵌入、输出层、损失不重算）；
- 再加上 ViT 的块，只剩 12.32 MB，是原来的 9%。剩下的是每个块的输入、输出层和交叉熵、连接器；
- **梯度完全相同**（差 0）：检查点不改变数学，只改变"什么时候算"。如果你在模型里用了 dropout，重算时要用同样的随机数，`checkpoint` 默认会保存和恢复随机数生成器的状态，所以仍然一致。

核对一下语言模型那 112 MB：每层每个 token 23 个向量（1 KB），4 层，8 × 163 = 1304 个 token，是 23 × 4 × 1304 KB = 117 MB；检查点之后每层还要存 1 个向量（块的输入），5 MB。差 112 MB，和测量一致。

### 什么时候用

- 显存不够、而且激活值是大头时（批大、序列长、视觉 token 多），检查点几乎总是值得的：花 20–30% 的时间换 5 倍以上的批，通常比把批减小 5 倍、多跑 5 倍的梯度累积更划算；
- 激活值不是大头时（批很小、静态内存占了大部分）没有用，应该先看 LoRA 或冻结；
- HF 的模型用 `model.gradient_checkpointing_enable()` 打开，做的事和我们一样。

## 28.5 LoRA

### 想法

全参微调要为每个参数存梯度和两个优化器状态（28.2 节：每个参数 16 字节）。如果只想让模型学会一个新任务，真的需要改动所有参数吗？

LoRA（Low-Rank Adaptation，2021）的假设是：**微调时权重的变化量 ΔW 是低秩的**——一个 out × in 的矩阵，可以写成两个瘦矩阵的乘积：

```
ΔW = B · A          B: (out, r)   A: (r, in)   r ≪ min(in, out)
```

冻结原来的 W，只训练 A 和 B：

```
y = x Wᵀ + (α / r) · x Aᵀ Bᵀ
```

- **参数量**：原来 in × out 个，现在 r × (in + out) 个。我们的 GPT 的 qkv 层 256 → 768，原来 196,608 个参数；r = 16 时 LoRA 只有 16 × (256 + 768) = 16,384 个，是原来的 8.3%；
- **初始化**：A 随机，**B 全为 0**。所以刚装上 LoRA 时 ΔW = 0，模型的输出和原来完全相同，训练从原模型出发；
- **缩放 α / r**：r 变大时，ΔW 的元素个数多了，初始的更新幅度会变大。除以 r 让不同的 r 在同样的学习率下大致可比；α 是另一个超参数，常取 r 的 1–2 倍（我们的默认值是 α = 16）。

为什么不两个都随机、或者两个都为 0？两个都随机，ΔW 一开始就不是 0，模型一装上就变了样；两个都为 0，A 的梯度 ∝ B（= 0），B 的梯度 ∝ A（= 0），永远学不动。一个随机、一个为 0，既保证 ΔW = 0，又保证 B 的梯度不为 0：第一步更新 B，之后 A 也开始有梯度。

### 什么是"秩"

一个矩阵的秩是它的行（或列）里线性无关的最大个数（第 4 章）。ΔW = B · A 的每一列都是 B 的 r 列的线性组合，所以秩最多是 r。"低秩"的直觉是：微调只需要在少数几个"方向"上调整模型，比如"更倾向于输出短答案"、"更注意图像的左侧"，而不是独立地改动几十万个参数。

这个假设不总是成立。第 6 部分请你比较 r = 4、16、64：如果 r = 4 和全参差不多，说明这个任务需要的调整确实是低秩的；如果 r 越大越好、一直追不上全参，说明任务需要的变化更复杂。

### 练习 28.1：`LoRALinear.forward`

```python
def forward(self, x):
    return self.base(x) + (self.drop(x) @ self.A.T @ self.B.T) * self.scale
```

注意乘法的顺序：先 `x @ A.T`（(…, in) × (in, r) → (…, r)），再乘 `B.T`（(r, out)）。中间结果只有 r 维。如果先算 `B @ A` 得到 out × in 的矩阵再乘 x，计算量和普通的线性层一样大，就失去了"低秩"的好处（训练时如此；推理时可以合并，见下文）。

形状约定和 `nn.Linear` 一致：`weight` 是 (out, in)，所以 A 是 (r, in)、B 是 (out, r)，`B @ A` 是 (out, in)。peft 库的 `lora_A`、`lora_B` 是两个 `nn.Linear`，权重形状和这里相同。A 的初始化（`kaiming_uniform_(a=√5)`）也和 peft 的默认值一样，它就是 `nn.Linear` 默认的初始化。

### 练习 28.2：`apply_lora`

```python
def apply_lora(model, targets, r=8, alpha=16, dropout=0.0):
    for p in model.parameters():
        p.requires_grad_(False)
    replaced = []
    for name, module in list(model.named_modules()):
        if isinstance(module, LoRALinear):
            continue
        for child_name, child in list(module.named_children()):
            if isinstance(child, nn.Linear) and child_name in targets:
                setattr(module, child_name, LoRALinear(child, r, alpha, dropout))
                replaced.append(f"{name}.{child_name}" if name else child_name)
    for module in model.modules():
        if isinstance(module, LoRALinear):
            module.A.requires_grad_(True)
            module.B.requires_grad_(True)
    return replaced
```

三个细节：

- `list(model.named_modules())`：先复制一份列表。边遍历边 `setattr` 会改变正在遍历的结构；
- 跳过已经是 `LoRALinear` 的模块：否则它里面的 `base`（一个 `nn.Linear`，名字是 "base"）在 targets 里时会被再包一次。即使不在 targets 里，跳过也更安全；
- 最后一步让**所有** LoRA 的 A、B 可训练：第一步冻结了模型的所有参数，包括之前已经装好的 LoRA。作者第一次写的时候漏了这一步，测试 `test_apply_lora_counts_and_grads` 里"对同一个模型调用两次"的检查发现了它——第二次调用把第一次装的 LoRA 也冻结了，`backward()` 报错"没有任何张量需要梯度"。

`targets` 按**子模块的名字**匹配（`qkv`、`o`、`gate`、`up`、`down`），不是按完整路径。真实模型里的名字不同：Qwen、LLaMA 是 `q_proj`、`k_proj`、`v_proj`、`o_proj`、`gate_proj`、`up_proj`、`down_proj`。peft 的 `target_modules` 也是这样匹配的。注意：VLM 的视觉塔里也可能有同名的层，如果只想给语言模型装 LoRA，要把 `apply_lora` 用在 `vlm.lm` 上，而不是整个 `vlm`。

### 合并

训练完之后，ΔW = (α/r)·B·A 是一个普通的 out × in 矩阵，可以直接加进 W：

```
W' = W + (α / r) · B · A
```

`merge_lora` 把每个 `LoRALinear` 换回一个权重为 W' 的 `nn.Linear`。合并后的模型和原模型结构完全相同，推理没有任何额外开销。

### LoRA 省了什么、没省什么

| | 全参 | LoRA |
|---|---|---|
| 参数（权重本身） | 全部 | 全部（底座冻结但仍要在内存里，可以用 bf16 或更低精度） |
| 梯度 | 全部可训练参数 | 只有 A、B |
| 优化器状态 | 全部可训练参数 × 2 | 只有 A、B × 2 |
| 激活值 | 全部 | **大部分**（28.3 节：梯度要穿过语言模型；第 2 部分：111.72 vs 139.57 MB） |
| 计算量 | 前向 + 反向 | 前向 + 反向，但不算底座权重的梯度 |

LoRA 省的是**静态内存**里的梯度和优化器状态。当模型很大、批很小时，这是大头（28.2 节：7B 模型的全参微调要 105 GB，LoRA 只要 14 GB）；当序列很长、批很大时，激活值才是大头，LoRA 帮不上，要靠梯度检查点。

计算量：反向时，每个线性层要算两个矩阵乘法：对输入的梯度和对权重的梯度，各和前向一样大。LoRA 冻结了底座，后一个就不用算了，所以理论上一步的计算量从 3 份前向降到约 2 份。但第 2 部分我们的小模型上并没有变快：宽度 256 时矩阵乘法本身很快，LoRA 多出来的那些小运算的固定开销占了上风。

### QLoRA（了解）

既然底座冻结了，它的精度可以更低：QLoRA（2023）把底座量化成 4 位（每个参数 0.5 字节），LoRA 的 A、B 仍然用 16 位训练。7B 模型的底座从 14 GB（bf16）降到约 3.5 GB。前向时把 4 位权重临时解压成 bf16 参与计算。代价是一点精度和速度。本书不实现量化。

## 28.6 冻结哪一部分

VLM 有三个部件，训练时每个都可以选择训练、冻结或装 LoRA。常见的组合：

| 阶段 | 视觉塔 | 连接器 | 语言模型 | 为什么 |
|---|---|---|---|---|
| 对齐（第 22 章阶段 1） | 冻结 | 训练 | 冻结 | 连接器是随机初始化的，先让它学会"翻译"，避免它一开始的乱输出破坏预训练好的两端 |
| 指令微调（LLaVA-1.5） | 冻结 | 训练 | 训练 | 视觉塔已经很好，保护它；语言模型要学会按指令回答 |
| 大规模多模态预训练（Qwen2-VL 第二阶段） | 训练 | 训练 | 训练 | 数据量大时，视觉塔也跟着调整，能提高细粒度能力（如 OCR） |
| 小数据的任务适配 | 冻结 | 训练 | LoRA | 显存小、数据少；LoRA 限制了改动的幅度，也减少过拟合和遗忘（第 32 章） |

（Qwen2-VL 的技术报告分三个阶段：第一阶段只训练视觉塔，第二阶段全部训练，第三阶段的指令微调又冻结视觉塔、只训练语言模型。不同的模型、不同的阶段做法各不相同，以各自的报告为准。）

从内存的角度，第 2 部分已经告诉我们：

- 冻结**前面**的部件（视觉塔）省得最多：它的激活值、梯度、优化器状态都不要了；
- 冻结**后面**的部件（语言模型）只省梯度、优化器状态和一小部分激活值，因为梯度还要穿过它；
- 所以"只训连接器"不是最省内存的，"冻结视觉塔、训练其余部分"在激活值上反而省得更多（122.87 vs 139.57 MB），尽管可训练参数多得多。

从**效果**的角度，没有一个放之四海皆准的答案，这正是第 6 部分要你自己测的：同样 2000 步，全参、冻结视觉塔、冻结语言模型、不同 r 的 LoRA，在六个任务上各得多少分？

## 28.7 GPU 上还有什么

上面数的是"模型的张量"。在 GPU 上实际占用的显存还要多出这些：

- **CUDA 上下文**：PyTorch 一初始化 CUDA，就占几百 MB（存放 kernel 代码等），和模型无关；
- **缓存分配器**：PyTorch 释放的显存不还给系统，而是留着下次用（`torch.cuda.memory_reserved()` 比 `memory_allocated()` 大）。`nvidia-smi` 看到的是 reserved 加上下文；
- **碎片**：大小不一的张量反复分配、释放，中间留下用不上的空隙；
- **临时结果**：比如 logits（批 × 序列 × 词表大小，Qwen3.5 的词表有 24.8 万，fp32 的 logits 每个 token 就要约 1 MB，这一项可以比一层的激活值还大）、矩阵乘法的工作空间；
- **反向时的峰值**：反向开始时梯度开始出现、激活值还没释放完，峰值往往出现在这个时候。

所以实际的经验做法是：先按本章的方法估算，留 20–30% 的余量；然后在 GPU 上用 `torch.cuda.max_memory_allocated()` 测一步的峰值。第 7 部分（需要 `--gpu`）对比了 `SavedTensors` 的数字和 CUDA 前向前后 `memory_allocated()` 的增量。

## 28.10 常见错误

| 错误 | 症状 | 原因与修正 |
|---|---|---|
| 以为 bf16 混合精度让显存减半 | 估算偏小一半，一跑就 OOM | 有 fp32 主权重和 fp32 优化器状态，静态内存仍是 16 字节/参数（28.2 节） |
| 以为冻结语言模型就不存它的激活值 | 只训连接器也 OOM | 梯度要穿过语言模型（28.3 节第 2 部分） |
| LoRA 的 B 也随机初始化 | 刚装上 LoRA 损失就变了，从一个更差的起点出发 | B 必须为 0（28.5 节第 5 部分的第一个检查） |
| 冻结之后又装 LoRA，或者装两次 | LoRA 的参数 `requires_grad=False`，优化器里是空的，或者 backward 报错 | `apply_lora` 最后重新打开所有 A、B（练习 28.2） |
| 优化器在冻结之前建好 | 冻结的参数仍然在优化器里，有 weight decay 的话照样会被改动 | 先设置 `requires_grad`，再用 `[p for p in params if p.requires_grad]` 建优化器 |
| `target_modules` 匹配到视觉塔 | LoRA 参数比预期多，视觉塔也被改了 | 对 `vlm.lm` 调用，或者用完整路径匹配；装好之后打印 `replaced` 检查 |
| 检查点和 `use_reentrant=True` 一起用在冻结的前几层后面 | 警告"None of the inputs have requires_grad"，梯度是 None | 用 `use_reentrant=False` |
| 推理时忘了 `torch.no_grad()` | 推理也占很多内存 | 没有 `no_grad` 时 autograd 照样保存激活值（第 2 部分最后一行的反面） |
| 用 `nvidia-smi` 的数字判断模型用了多少显存 | 数字比估算大很多，而且释放之后不下降 | 那是缓存分配器 reserved 的加上 CUDA 上下文（28.7 节）；看 `max_memory_allocated()` |

## 28.12 深入一步

### 激活值、批大小与梯度累积

激活值 ∝ 批大小。如果批 32 放不下，可以用批 8 跑 4 次再更新一次（梯度累积，第 18 章），数学上和批 32 一样（注意第 26 章说的按 token 平均的陷阱），激活值只有 1/4，代价是时间：小批在 GPU 上的利用率更低。梯度检查点是另一种换法：保持批 32，多花 20–30% 的时间。两者可以一起用。

### 为什么检查点的位置选在块的边界

检查点保存的是"块的输入"，每个 token 1 个向量；块内部有 23 个。选在块的边界，存的最少、重算的范围最清楚。更细的选择（比如只重算 MLP）能少花一些时间，但要改模型的代码。数学上，用 √L 个检查点可以把 L 层的激活值降到 O(√L)，代价是一次额外的前向（Chen 等，2016）。

### LoRA 为什么能用很小的 r

一种解释（Aghajanyan 等，2020，"内在维度"）：预训练好的模型，只要在一个很低维的子空间里调整参数，就能适配新任务；预训练越充分，这个维度越低。这也解释了为什么对**从零开始的**模型 LoRA 效果不好：模型还没学会大部分东西，需要的变化是"高秩"的。我们第 16 章的语言模型只在很小的语料上预训练过，第 6 部分 LoRA 的表现会告诉你它离"预训练充分"有多远。

## 28.13 横向对照

| 手段 | 省什么 | 代价 | 什么时候用 |
|---|---|---|---|
| bf16 混合精度 | 激活值减半、计算更快 | 数值误差（第 11 章） | 几乎总是 |

## 28.14 本章小结

1. 训练内存 = 静态内存（参数、梯度、优化器状态）+ 激活值。全参 AdamW 训练每个参数 16 字节，**bf16 混合精度也是 16 字节**；
2. 激活值 ∝ 批大小 × 序列长度。我们的 GPT 每层每个 token 存 23.9 个 d 维向量，可以逐项数出来；MLP 占一半，Flash 注意力不存 T × T 的矩阵；
3. 冻结后面的部件（语言模型）不能省掉它的激活值：梯度要穿过它。只训连接器时激活值仍有全部训练的 62%；
4. 梯度检查点把激活值降到 1/5–1/10，多花 20–30% 的时间，梯度完全不变；
5. LoRA 用 r × (in + out) 个参数表示 ΔW，B = 0 初始化保证从原模型出发，训练后可以精确合并；它省的是梯度和优化器状态，不省激活值；
6. 对 VLM，视觉 token 数是激活值最大的旋钮。

## 参考答案

1. 权重和梯度虽然是 bf16（2 + 2 字节），但多了一份 fp32 主权重（4 字节），优化器的 m、v 也是 fp32（8 字节），合计还是 16 字节。混合精度省的是激活值（每个数 2 字节）和计算时间。
2. 不需要保存 x：x 只用来算 W 的梯度 `gᵀ x`。W 需要（用来算 x 的梯度 `g W`），但 W 是参数，本来就在内存里，不算额外开销。
3. 视觉塔在最前面，冻结之后没有任何梯度需要穿过它，它的激活值全部不用存；语言模型在最后，冻结之后梯度仍要穿过它传给连接器，大部分激活值（非线性运算的输入）仍然要存。
4. 重算用的是同样的输入、同样的权重，算出来的激活值完全相同，梯度当然相同。dropout 需要同样的随机数：`torch.utils.checkpoint` 默认保存并恢复随机数生成器的状态，所以仍然一致。
5. B = 0 保证 ΔW = 0（从原模型出发）；A 随机保证 B 的梯度 ∝ A·x 不为 0，第一步就能学。反过来（A = 0、B 随机）也能让 ΔW = 0，而且 A 的梯度 ∝ Bᵀ·g 也不为 0，所以理论上也行；惯例是 B = 0，peft 也是这样。都随机则 ΔW ≠ 0，一开始就破坏了原模型；都为 0 则两者的梯度都是 0，永远学不动。
6. 省梯度和优化器状态（以及底座可以用低精度存）。当激活值是大头时（批大、序列长，比如长文档 OCR），LoRA 几乎不省内存，因为激活值和全参训练差不多（第 2 部分：111.72 vs 139.57 MB）。
7. `no_grad` 下 autograd 不建计算图，不保存任何张量（第 2 部分"全部冻结"一行：0 B），每一层的输出用完就可以释放。
8. 全参 fp32：3 × 10⁹ × 16 = 48 × 10⁹ 字节 ≈ 44.7 GB；bf16 混合精度：同样 ≈ 44.7 GB；LoRA：3 × 10⁹ × 2 + 30 × 10⁶ × 16 = 6.48 × 10⁹ 字节 ≈ 6.0 GB。
9. 8 × (2048 + 8192) = 81,920 个；原层 2048 × 8192 = 16,777,216 个；占 0.49%。
10. 每个 d 维 fp32 向量 1 KB。16 × 300 = 4800 个 token，23.9 × 4 × 4800 KB = 458,880 KB ≈ 448 MB。检查点之后：(1 × 4 + 3.4) × 4800 KB = 35,520 KB ≈ 35 MB。（这里用了 23.9，它已经包含了均摊的输出层；检查点之后输出层的 3.4 要单独加回来。）
11. 优化器在装 LoRA 之前建好：它拿到的是原来的参数，没有 LoRA 的 A、B，LoRA 永远不会被更新；而原来的参数虽然被冻结了（没有梯度，AdamW 跳过它们），这个优化器也已经没有用了。应该先 `apply_lora`，再用 `[p for p in model.parameters() if p.requires_grad]` 建优化器。
12. 先算出 `B @ A`（out × in 的大矩阵）再乘 x：数学上正确，但计算量和内存都和一个完整的线性层一样大，而且要保存这个大矩阵给反向用，失去了 LoRA 的好处。应该 `(x @ A.T) @ B.T`。另外漏了 dropout。
13. `no_grad` 下 autograd 不保存任何东西，`s.bytes` 永远是 0。要数训练时的激活值，必须在需要梯度的前向里数（`model.train()`，不用 `no_grad`）。
