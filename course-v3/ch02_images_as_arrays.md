# 第 2 章　图像就是数组

## 本章在全景图中的位置

VLM 的第一步，是把一张图像交给视觉编码器。但计算机里并没有"图像"这种东西，只有一张张整数表。本章把"图像"彻底拆开：像素是什么、坐标怎么数、彩色怎么存、怎样缩放、怎样把 0–255 的整数变成模型要的小数。同时，我们写出全书第一个零件——**渲染器**：它把字符、文字行和公式画成图，并且精确记录每个符号的位置。后面所有 OCR 数据都由它产生。

第 24 章拆解真实模型（Qwen3.5、SmolVLM）的图像预处理时，你会发现它们做的事情，就是本章这几个操作的组合。

## 学习目标

1. 能把任意一张灰度图或彩色图说成"一个什么形状、什么类型的数组"，并正确写出取某个像素的下标；
2. 能用边界框 `(x0, y0, x1, y1)` 描述一个区域，并用切片把它裁出来，不犯"x、y 写反"和"差一"错误；
3. 能手算并亲手实现灰度转换、最近邻、双线性、区域平均三种缩放，说出各自什么时候用；
4. 能解释为什么"位置对齐"和"保持长宽比"对识别那么重要，并用实验数字支持你的解释；
5. 能写出把 `uint8` 图像变成模型输入的完整步骤（除以 255、反色、减均值除标准差、换通道顺序）。

## 前置检查

1. Python 中 `a = [10, 20, 30, 40]`，`a[1:3]` 是什么？（答案：`[20, 30]`，左含右不含。）
2. NumPy 中 `x = np.zeros((2, 3))`，`x.shape` 是什么？`x[1, 2]` 指哪个元素？（答案：`(2, 3)`；第 1 行第 2 列，从 0 开始数。）
3. 1 个字节能表示多少个不同的整数？（答案：2⁸ = 256 个，无符号时是 0–255。）

如果有一题不会，先回到第 1 章复习列表切片和 NumPy 下标。

## 2.1 像素：一张图就是一张整数表

### 直觉

把一张照片放大、再放大，最后会看到一个个小方格，每个方格只有一种颜色。这些小方格叫**像素**（pixel，picture element 的缩写）。一张图就是像素排成的网格。

对于**灰度图**（黑白照片），每个像素只需要一个数来表示它有多亮。约定俗成的规则是：

- 用 **0 到 255** 的整数；
- **0 是黑，255 是白**，中间是不同深浅的灰。

为什么是 0–255？因为一个**字节**（byte，8 个二进制位）恰好能表示 2⁸ = 256 个不同的数。用一个字节存一个像素，既省空间，人眼也分辨不出更细的灰度差别。这种"0–255 的无符号整数"在 NumPy 里的类型名叫 **`uint8`**（unsigned integer, 8 bits）。

### 手算

我们来"手画"一张 5×5 的图：全白，中间一条竖线，左上方加一个点，像数字 1。

```
列号:  0    1    2    3    4
行0: 255  255  255  255  255
行1: 255    0    0  255  255     ← (1,1) 和 (1,2) 涂黑
行2: 255  255    0  255  255
行3: 255  255    0  255  255
行4: 255  255  255  255  255
```

先在纸上画出来，然后看代码（`labs/ch02/pixels.py` 第 1 部分）：

```python
img = np.full((5, 5), 255, dtype=np.uint8)   # 一个 5×5、每个元素都是 255 的数组：全白
img[1:4, 2] = 0                              # 第 1、2、3 行的第 2 列，涂黑：一条竖线
img[1, 1] = 0                                # 第 1 行第 1 列，涂黑：数字 1 的"头"
```

逐行解释：

- `np.full(形状, 值, dtype=类型)`：造一个指定形状、所有元素都等于"值"的数组。`(5, 5)` 是形状，先写**行数**，再写**列数**；
- `img[1:4, 2]`：逗号前面是行，`1:4` 表示第 1、2、3 行（左含右不含）；逗号后面是列，`2` 表示第 2 列。整个表达式选中了 3 个像素，一起赋值为 0；
- `img[1, 1]`：第 1 行第 1 列的那一个像素。

运行 `python -m labs.ch02.pixels`，第 1 部分的输出是：

```
数组：
 [[255 255 255 255 255]
 [255   0   0 255 255]
 [255 255   0 255 255]
 [255 255   0 255 255]
 [255 255 255 255 255]]
形状 (5, 5) 类型 uint8
字符画：

 @@
  @
  @

img[1, 2] = 0 （第 1 行第 2 列，黑）；img[0, 0] = 255 （白）
```

"字符画"是 `miniocr/data/render.py` 里的 `to_ascii` 函数打印的：它把越黑的像素画成越"密"的字符（`@` 最黑，空格最白），让你不用打开图片就能在终端里看到图像。全书都会用它来"看"小图。它的核心只有一行：

```python
chars[(255 - int(v)) * levels // 255]     # v 越小（越黑），下标越大，取到越密的字符
```

> **一个容易踩的坑**：这里必须先 `int(v)`。`v` 是 `uint8` 类型，`255 - v` 本身没问题，但如果写成 `(255 - v) * levels`，乘法的结果仍然是 `uint8`，超过 255 就会**溢出**（例如 `np.uint8(200) * np.uint8(2)` 得到 144，而不是 400），NumPy 有时连警告都不给。凡是要对 `uint8` 做加减乘除，**先转成 `int` 或 `float`**，这是本章第一条纪律。

### 一张图占多大内存

一张 H 行、W 列的 `uint8` 灰度图，有 H×W 个像素，每个 1 字节，占 H×W 字节。32×32 的字符图是 1024 字节，1 KB；一张 1000×1000 的文档扫描图是 100 万字节，约 1 MB。记住这个数量级，第 22 和 28 章算显存时会用到。

## 2.2 坐标系与边界框

### 两套说法：(x, y) 与 [行, 列]

描述一个像素的位置，有两套说法，**这是图像处理中最常见的错误来源**：

| 说法 | 写法 | 先写什么 | 用在哪里 |
|---|---|---|---|
| 几何坐标 | `(x, y)` | 先横后竖：x 是第几列，y 是第几行 | 画图函数（Pillow）、边界框、模型输出的坐标 |
| 数组下标 | `img[行, 列]` | 先竖后横：先行后列 | NumPy、PyTorch |

本书统一约定（写在 `render.py` 开头）：

- 原点在**左上角**；**x 向右增大，y 向下增大**（和数学课上 y 向上不同！屏幕和图像都是从上往下数行的）；
- 像素 `(x, y)` 就是数组元素 `img[y, x]`。

记忆方法："**x 是列，y 是行；数组先行后列，所以 y 在前。**"

### 边界框

一个矩形区域用四个数表示，叫**边界框**（bounding box，简称 box）：

```
(x0, y0, x1, y1)    左上角 (x0, y0)，右下角 (x1, y1)，右边界和下边界**不含**
```

"右、下不含"和 Python 切片的"左含右不含"一致，好处是：

- 宽 = `x1 - x0`，高 = `y1 - y0`，不用加 1；
- 裁剪就是 `img[y0:y1, x0:x1]`，不用加 1；
- 两个框左右紧挨着时，左框的 `x1` 等于右框的 `x0`，不重叠也不留缝。

`miniocr/data/imgops.py` 里的 `crop` 就这一行：

```python
def crop(img, box):
    x0, y0, x1, y1 = box
    return img[y0:y1, x0:x1]       # 注意：先 y（行）后 x（列）
```

> **手算练习**：一张 32×32 的图里，字符墨迹占据第 10–25 列、第 7–24 行（都含两端）。它的框是什么？裁出来的形状是什么？
>
> 答案：框 `(10, 7, 26, 25)`（右、下边界 +1 变成"不含"），裁出来的形状是 `(25-7, 26-10) = (18, 16)`——**形状先写行数**。下一节的实验会得到一模一样的数字。

还有一种常见的框格式是 `(x, y, w, h)`（左上角加宽高），COCO 数据集就用它；另一种是 `(cx, cy, w, h)`（中心加宽高），YOLO 用它。拿到别人的数据，**第一件事是弄清框的格式**，画几个框在图上看看对不对。

## 2.3 渲染一个字符

### 渲染器做什么

**渲染**（render）就是"把文字画成图"。我们用 Pillow 库来画。Pillow 是 Python 里最常用的图像库，`from PIL import Image, ImageDraw, ImageFont` 就是在导入它。

`render.py` 里的 `render_glyph` 画一个字符（glyph，"字形"，指一个字符画出来的样子）：

```python
def render_glyph(ch, rng, size=32, noise=0.0):
    im = Image.new("L", (size, size), 255)                       # ①
    draw = ImageDraw.Draw(im)
    fs = int(rng.integers(int(size * 0.55), int(size * 0.8) + 1)) # ②
    f = font(fs)
    x0, y0, x1, y1 = draw.textbbox((0, 0), ch, font=f)           # ③
    w, h = x1 - x0, y1 - y0
    dx = int(rng.integers(0, max(1, size - w))) - x0              # ④
    dy = int(rng.integers(0, max(1, size - h))) - y0
    stroke = int(rng.random() < 0.3)                              # ⑤
    draw.text((dx, dy), ch, font=f, fill=0, stroke_width=stroke, stroke_fill=0)
    arr = add_noise(np.array(im, dtype=np.uint8), rng, noise)     # ⑥
    return arr, ink_box(np.array(im, dtype=np.uint8))             # ⑦
```

逐行看：

1. `Image.new("L", (宽, 高), 255)`：新建一张白色的灰度图。`"L"` 是 Pillow 对灰度模式的叫法（luminance，亮度）。**注意 Pillow 写尺寸是 (宽, 高)，NumPy 的形状是 (高, 宽)**，又是一处 x、y 顺序相反的地方；
2. 随机选一个字号，在格子大小的 55%–80% 之间。`rng` 是一个随机数生成器（第 1 章讲过 `np.random.default_rng(seed)`），所有随机性都从它来，所以同一个种子总得到同一张图；
3. `textbbox`：先"假装"在 (0, 0) 处画这个字符，量出它的墨迹会占据哪个框。注意 `x0, y0` 通常不是 0——字体在字符上方和左边都留有空白；
4. 随机平移，但保证整个字符不出界。减去 `x0` 是为了抵消第 3 步量出的空白；
5. 30% 的概率加一圈描边，让笔画变粗；
6. 转成 NumPy 数组。`np.array(Pillow图像)` 直接得到形状 `(高, 宽)` 的 `uint8` 数组。可选地加高斯噪声；
7. `ink_box` 在**没加噪声**的图上找出所有比 128 暗的像素，返回它们的外接框——这就是我们要的"标注"。

为什么字号、位置、粗细都要随机？因为真实世界里，同一个字符从来不会两次长得完全一样。如果训练数据里所有的 "A" 都在同一个位置、同样大小，模型可能只学会"某几个固定位置有黑点就是 A"，换个位置就不认识了。本章 2.8 节的实验会让你亲眼看到这个问题有多严重。

（上下的空行已省略。）几个值得注意的地方：

- **墨迹只占 14.6%**。一张字符图的绝大部分是背景。这意味着：如果一个模型"偷懒"，把所有像素都预测成白色，按像素算的准确率也有 85%。第 34 章的 Q-Mask 用 Dice 损失而不只用逐像素的交叉熵，原因之一就在这里；
- **边缘不是纯黑纯白**。`.`、`:`、`-` 这些"淡"字符是灰色的像素：字体渲染时，笔画边缘只盖住了像素的一部分，Pillow 就把它画成灰色，这叫**抗锯齿**（anti-aliasing）。所以"墨迹"需要一个阈值来定义，本书用 128；
- 框 `(10, 7, 26, 25)` 和上一节手算的完全一致。

### 字体、基线与文字行

画一整行文字时，字符不能各画各的，它们要"站"在同一条线上，这条线叫**基线**（baseline）：

```
         ┌─┐
   ┌──┐  │ │  ┌──┐        ← 上升部（ascender）：b、d、h、k、l 的竖笔伸到这里
   │  │  │ │  │  │
───┴──┴──┴─┴──┴──┴──┬──── ← 基线：大部分字母的底部
                    │       下降部（descender）：g、j、p、q、y 的尾巴伸到基线以下
                    └──
```

- 基线以上的高度叫 **ascent**（上升高度），以下的深度叫 **descent**（下降深度）；
- 小写字母 x 的高度叫 **x 高度**（x-height），它决定了一行字"看起来多大"。

`render_line` 就是这样排的：先定一条基线（大约在图高的 72% 处，再随机上下浮动 1 像素），然后从左到右，每个字符的"基线左端"放在当前位置，画完后往右移动这个字符的**前进宽度**（advance width，`f.getlength(ch)`，包括字符本身和它右侧的留白）：

```python
base = int(H * 0.72) + int(rng.integers(-1, 2))
for ch in text:
    if ch == " ":
        boxes.append(None)                                     # 空格没有墨迹，也就没有框
    else:
        b = draw.textbbox((x, base), ch, font=f, anchor="ls")  # anchor="ls"：(x, base) 是左端、基线
        draw.text((x, base), ch, font=f, fill=0, anchor="ls")
        boxes.append(...)
    x += f.getlength(ch)
```

`anchor="ls"` 告诉 Pillow：我给的坐标是字符的 **l**eft（左端）和 ba**s**eline（基线），而不是默认的左上角。没有这一步，"g" 和 "a" 会顶端对齐，看起来就像 "g" 往下掉了。

第 3 章会把同样的思想推广到公式：上标要升高、缩小，分数要把分子放在分数线上方——这叫**盒子模型排版**，本章"深入一步"会先介绍它。

## 2.4 彩色图：每个像素三个数

### RGB

彩色屏幕上的每个像素由红（R）、绿（G）、蓝（B）三个发光点组成，混合出各种颜色。所以彩色图的每个像素需要 **3 个数**，各自 0–255：

| 颜色 | (R, G, B) |
|---|---|
| 黑 | (0, 0, 0) |
| 白 | (255, 255, 255) |
| 纯红 | (255, 0, 0) |
| 黄（红+绿） | (255, 255, 0) |
| 中灰 | (128, 128, 128) |

一张 H×W 的彩色图存成形状 `(H, W, 3)` 的数组，最后一维叫**通道**（channel），依次是 R、G、B。`img[y, x]` 得到这个像素的 3 个数，`img[y, x, 0]` 是它的红色分量，`img[..., 0]`（`...` 表示"前面所有维度都要"）是整张图的红色通道，形状 `(H, W)`。

> **注意**：另一个常用的图像库 OpenCV 读进来的彩色图，通道顺序是 **BGR**（蓝绿红）。把 OpenCV 读的图直接交给按 RGB 训练的模型，红和蓝会互换，模型效果会莫名其妙地变差，却不会报错。本书只用 Pillow，都是 RGB。

### ShapesWorld 的场景图

```
形状 (64, 64, 3)  ← (高, 宽, 通道)
  yellow circle   中心像素 img[10,51] = (230, 200, 30)   定义的颜色 (230, 200, 30)
  green  square   中心像素 img[48,22] = (40, 170, 60)   定义的颜色 (40, 170, 60)

```

打开 `outputs/ch02/scene.png` 看看，再打开 `scene_channels.png`：三张小图分别是 R、G、B 通道单独显示成灰度。黄色圆在 R 和 G 通道里很亮（230、200），在 B 通道里很暗（30）——因为黄 = 红 + 绿。

注意几件事：

- 描述是按物体**从左到右**排序的（`describe` 按框的 `x0` 排序）：绿方块在 x=22 附近，黄圆在 x=51 附近，所以绿方块在前。规定唯一的排序，描述就只有一种写法，评测时可以直接比较字符串——第 3 章会看到"写法不唯一"带来的麻烦；
- 背景颜色每张图随机（215–255 之间的浅色），模拟不同的光照。这样模型不能靠"背景一定是纯白"来偷懒；
- 物体互不重叠，所以"有几个""最左边是什么""某物体在哪"都有唯一的标准答案。这是后面能**自动打分**的前提（第 31 章的可验证奖励）。

### 彩色转灰度（练习 2.3）

很多 OCR 模型只吃灰度图（文字的颜色通常无关紧要）。最直接的想法是三个通道取平均，但人眼对三种颜色的敏感度不同：**对绿色最敏感，对蓝色最不敏感**。同样亮度数值的绿光看起来比蓝光亮得多。所以标准做法（ITU-R BT.601，一个电视标准）是加权平均：

```
gray = 0.299·R + 0.587·G + 0.114·B
```

三个权重加起来等于 1，所以白 (255,255,255) 还是 255，黑还是 0。

**手算**：纯红 (255, 0, 0) 变成 `0.299 × 255 = 76.2`，四舍五入成 76——一个相当深的灰。纯绿 (0, 255, 0) 变成 `0.587 × 255 = 149.7` → 150，亮得多。

实测输出里 ShapesWorld 四种颜色的灰度：

```
  red    (220, 40, 40) → 灰度 0.299×220+0.587×40+0.114×40 = 93.8
  green  (40, 170, 60) → 灰度 0.299×40+0.587×170+0.114×60 = 118.6
  blue   (40, 80, 220) → 灰度 0.299×40+0.587×80+0.114×220 = 84.0
  yellow (230, 200, 30) → 灰度 0.299×230+0.587×200+0.114×30 = 189.6
```

看出问题了吗？**红 93.8 和蓝 84.0 在灰度图里几乎一样**。一个只看灰度图的模型，很难回答"红色的是哪个"。所以 ShapesWorld 的任务必须用彩色输入，而 MiniDoc 的文字图用灰度就够了。"预处理会丢掉什么信息"，是每次设计输入时都要问的问题。

实现（`imgops.py`，练习 2.3）：

```python
def to_gray(rgb):
    rgb = rgb.astype(np.float64)                                        # 先转小数，避免 uint8 溢出
    gray = 0.299 * rgb[..., 0] + 0.587 * rgb[..., 1] + 0.114 * rgb[..., 2]
    return np.clip(np.round(gray), 0, 255).astype(np.uint8)             # 四舍五入、截断到 0–255、转回 uint8
```

`np.clip(x, 0, 255)` 把小于 0 的变成 0、大于 255 的变成 255。这里理论上不会越界，但这是把小数转回 `uint8` 之前的固定动作：**`astype(np.uint8)` 不会截断，而是"绕回去"**，`np.array([256.0]).astype(np.uint8)` 得到 0，`-1` 得到 255。

测试 `labs/ch02/test_imgops.py::test_gray_matches_pillow` 检查你的结果和 Pillow 的 `Image.convert("L")` **逐像素完全相同**。

## 2.5 形状约定：HWC、CHW 与 BCHW

一次处理一张图太慢，模型通常一次处理一**批**（batch）图。把 B 张图叠起来，就多了一维。不同的库对维度顺序有不同的约定：

| 写法 | 含义 | 谁用 |
|---|---|---|
| `(H, W)` | 灰度图 | NumPy、Pillow |
| `(H, W, C)` | 彩色图，通道在最后（"HWC"，channels-last） | NumPy、Pillow、matplotlib |
| `(C, H, W)` | 通道在最前（"CHW"，channels-first） | PyTorch 的单张图 |
| `(B, C, H, W)` | 一批图，通道在前（"BCHW" 或 "NCHW"） | PyTorch 卷积层（第 12 章） |

第 4 部分的实测输出：

```
8 张彩色图叠起来： (8, 64, 64, 3)  ← (B, H, W, C)
换成通道在前：     (8, 3, 64, 64)  ← (B, C, H, W)，PyTorch 的卷积要这种
同一个数：imgs[3, 10, 20, 1] = 236   chw[3, 1, 10, 20] = 236
占用内存：98304 字节 = 8×64×64×3 个 uint8；转成 float32 后是 393216 字节（4 倍）
```

- `np.stack(列表)` 把形状相同的数组沿一个新的第 0 维叠起来；
- `imgs.transpose(0, 3, 1, 2)` 重新排列维度：新的第 0 维是原来的第 0 维（B），新的第 1 维是原来的第 3 维（C），依此类推。数字本身一个都没变，只是"读取的顺序"变了——"第 3 张图、第 10 行、第 20 列、绿色通道"在两种写法下是同一个数 236；
- 模型计算用 `float32`（每个数 4 字节），所以内存变成 4 倍。图像在磁盘上和数据加载时用 `uint8` 存，进模型前一刻才转成小数，这能省下 3/4 的内存和带宽。

> **为什么 PyTorch 要通道在前？** 卷积对每个通道分别做二维运算，通道在前时，同一个通道的 H×W 个像素在内存里是连续的，计算更方便。这只是历史约定，现代 GPU 上 channels-last 有时反而更快，PyTorch 也支持。你只需要记住：**拿到一个数组，先打印它的 `shape`，弄清每一维是什么。**

## 2.6 缩放

模型的输入大小通常是固定的或受限制的，而现实中的图大小各异，所以几乎每个模型的预处理都要**缩放**（resize）。缩放的核心问题是：**输出的每个像素，应该取输入里的哪些像素、怎样组合？** 三种最常用的方法回答不同。

### 像素中心约定

先解决一个看似细小、却让很多实现出错的问题：输出像素 `i` 对应输入的哪个位置？

把每个像素看成一个**单位长度的小格子**，像素 `i` 占据区间 `[i, i+1)`，它的**中心**在 `i + 0.5`。缩放就是把整个区间 `[0, out)` 均匀拉伸到 `[0, in)`，比例是 `in / out`。所以：

```
输出像素 i 的中心  i + 0.5   （在输出坐标里）
             ↓ 乘以 in/out
在输入坐标里的位置  (i + 0.5) × in / out
```

这个约定叫"像素中心对齐"（Pillow、OpenCV 默认都这样，PyTorch 里叫 `align_corners=False`）。另一种约定（`align_corners=True`）把两端的像素中心对齐，本章"深入一步"会比较。**同一个模型训练和推理时用了不同的约定，图像会整体错位半个像素**，对 OCR 这种对细节敏感的任务，可能就是几个百分点的差别。

### 最近邻（练习 2.4）

**做法**：算出输出像素中心在输入里的位置，它落在哪个输入像素的格子里，就**直接复制**那个像素。落在哪个格子 = 向下取整：

```
src = floor((i + 0.5) × in / out)
```

**手算**：一行 6 个像素 `[10, 20, 30, 40, 50, 60]`，缩成 4 个。比例 6/4 = 1.5。

| 输出 i | (i+0.5)×1.5 | 向下取整 | 取到的值 |
|---|---|---|---|
| 0 | 0.75 | 0 | 10 |
| 1 | 2.25 | 2 | 30 |
| 2 | 3.75 | 3 | 40 |
| 3 | 5.25 | 5 | 60 |

结果 `[10, 30, 40, 60]`——20 和 50 直接被丢掉了。实现：

```python
def resize_nearest(img, out_h, out_w):
    in_h, in_w = img.shape[:2]
    ys = np.floor((np.arange(out_h) + 0.5) * in_h / out_h).astype(int)   # 每个输出行对应的输入行
    xs = np.floor((np.arange(out_w) + 0.5) * in_w / out_w).astype(int)   # 每个输出列对应的输入列
    ys = np.clip(ys, 0, in_h - 1)                                        # 防止浮点误差越界
    xs = np.clip(xs, 0, in_w - 1)
    return img[ys[:, None], xs[None, :]]
```

最后一行用了 NumPy 的**花式下标**（fancy indexing）：`ys[:, None]` 形状是 `(out_h, 1)`，`xs[None, :]` 形状是 `(1, out_w)`，两者**广播**（第 1 章）成 `(out_h, out_w)` 的下标网格，一次取出所有像素。等价于两重循环 `out[i, j] = img[ys[i], xs[j]]`，但快几百倍。彩色图 `(H, W, 3)` 也能直接用：只对前两维下标，第三维整个保留。

- **优点**：快；不产生新的像素值（标注图、类别图缩放时必须用它，因为"类别 2 和类别 4 的平均"没有意义）；
- **缺点**：放大时出现"马赛克"锯齿；缩小时**直接丢弃**大部分像素，细笔画可能整条消失。

### 双线性（练习 2.5）

**做法**：输出像素中心对应输入里的一个**小数位置**，用它周围最近的像素按距离加权平均。

先看一维。注意这里位置要再减 0.5：输入像素 `j` 的**中心**在 `j + 0.5`，我们想知道小数位置落在哪两个"中心"之间，所以把坐标换成"以像素中心为整数"的写法：

```
x = (i + 0.5) × in / out − 0.5
```

如果 `x = 2.3`，它在像素 2 的中心和像素 3 的中心之间，离 2 近（距离 0.3），离 3 远（距离 0.7）。离得越近权重越大：

```
值 = 0.7 × 像素2 + 0.3 × 像素3        即  (1 − 0.3) × 左 + 0.3 × 右
```

**手算**：还是 `[10, 20, 30, 40, 50, 60]` 缩成 4 个。

| 输出 i | x = (i+0.5)×1.5−0.5 | 左 / 右像素 | 权重 | 值 |
|---|---|---|---|---|
| 0 | 0.25 | 10 / 20 | 0.75 / 0.25 | 12.5 → **12** |
| 1 | 1.75 | 20 / 30 | 0.25 / 0.75 | 27.5 → **28** |
| 2 | 3.25 | 40 / 50 | 0.75 / 0.25 | 42.5 → **42** |
| 3 | 4.75 | 50 / 60 | 0.25 / 0.75 | 57.5 → **58** |

为什么 12.5 变成 12、27.5 却变成 28？因为 NumPy 的 `np.round` 用的是"**四舍六入五成双**"（banker's rounding）：恰好在 .5 时，取最近的**偶数**。这样大量取整时，误差不会系统性地偏向一边。初学者常以为是代码错了，其实是规则不同。

二维就是做三次一维插值：先在上面一行沿 x 插值，再在下面一行沿 x 插值，最后把这两个结果沿 y 插值。四个邻居的权重分别是 `(1−wx)(1−wy)`、`wx(1−wy)`、`(1−wx)wy`、`wx·wy`，加起来等于 1。

```python
def resize_bilinear(img, out_h, out_w):
    in_h, in_w = img.shape[:2]
    src = img.astype(np.float64)
    y = (np.arange(out_h) + 0.5) * in_h / out_h - 0.5     # 输出像素中心在输入坐标中的位置
    x = (np.arange(out_w) + 0.5) * in_w / out_w - 0.5
    y = np.clip(y, 0, in_h - 1)                           # 两端超出的部分，贴到边上
    x = np.clip(x, 0, in_w - 1)
    y0 = np.floor(y).astype(int)                          # 上面那一行
    x0 = np.floor(x).astype(int)                          # 左边那一列
    y1 = np.minimum(y0 + 1, in_h - 1)                     # 下面那一行（不能超出图像）
    x1 = np.minimum(x0 + 1, in_w - 1)
    wy = (y - y0)[:, None]                                # 离上面那一行的距离，越大越靠近下面
    wx = (x - x0)[None, :]
    if img.ndim == 3:                                     # 彩色图：权重多加一维，广播到 3 个通道
        wy, wx = wy[..., None], wx[..., None]
    top = src[y0[:, None], x0[None, :]] * (1 - wx) + src[y0[:, None], x1[None, :]] * wx
    bot = src[y1[:, None], x0[None, :]] * (1 - wx) + src[y1[:, None], x1[None, :]] * wx
    out = top * (1 - wy) + bot * wy
    return np.clip(np.round(out), 0, 255).astype(np.uint8)
```

- **优点**：放大时平滑，没有马赛克；
- **缺点**：每个输出像素**只看 4 个输入像素**。大幅缩小时（比如缩到 1/4），每个输出像素本该代表 16 个输入像素，双线性却只看其中 4 个，剩下的被忽略——细笔画仍然可能消失。

测试 `test_bilinear_upscale_matches_pillow` 检查**放大时**你的结果与 Pillow 的 `BILINEAR` 相差不超过 1（取整方式不同）。为什么只测放大？因为 Pillow 缩小时会自动扩大采样范围（做了"抗锯齿"），和教科书上的双线性已经不是一回事了。这本身就是一个重要的真实世界细节：**不同库的"bilinear"并不相同。**

### 区域平均（练习 2.6）

**做法**：输出像素 i 在输入里覆盖了一个区间 `[i × in/out, (i+1) × in/out)`。把这个区间里的输入像素**按覆盖长度加权平均**。缩小时每个输入像素都被用到，一个也不丢。这种方法也叫 box filter，OpenCV 里叫 `INTER_AREA`。

**手算**：`[10, 20, 30, 40, 50, 60]` 缩成 4 个，每个输出像素覆盖 1.5 个输入像素。

| 输出 i | 覆盖区间 | 覆盖了 | 值 |
|---|---|---|---|
| 0 | [0, 1.5) | 像素 0 全部（长 1）+ 像素 1 的一半（长 0.5） | (1×10 + 0.5×20) / 1.5 = 13.3 → **13** |
| 1 | [1.5, 3) | 像素 1 的一半 + 像素 2 全部 | (0.5×20 + 1×30) / 1.5 = 26.7 → **27** |
| 2 | [3, 4.5) | 像素 3 全部 + 像素 4 的一半 | (40 + 25) / 1.5 = 43.3 → **43** |
| 3 | [4.5, 6) | 像素 4 的一半 + 像素 5 全部 | (25 + 60) / 1.5 = 56.7 → **57** |

**把它写成矩阵**。上表的权重可以排成一个 4×6 的矩阵 `A`（第 i 行是输出像素 i 对每个输入像素的权重）：

```
      像素0  像素1  像素2  像素3  像素4  像素5
i=0 [ 0.667  0.333  0      0      0      0     ]
i=1 [ 0      0.333  0.667  0      0      0     ]
i=2 [ 0      0      0      0.667  0.333  0     ]
i=3 [ 0      0      0      0      0.333  0.667 ]
```

每一行加起来是 1（这是"平均"的意思）。一行像素是一个长度为 6 的向量 `v`，缩放结果就是矩阵乘向量 `A @ v`。这个矩阵就是 `imgops.py` 里的 `_area_matrix(6, 4)` 算出来的，运行一下就能看到这些数。

二维呢？先把每一**列**竖着缩（左乘竖直方向的矩阵 `Ay`），再把每一**行**横着缩（右乘水平方向矩阵的转置 `Axᵀ`）：

```
out = Ay @ img @ Ax.T        形状： (out_h, in_h) @ (in_h, in_w) @ (in_w, out_w) = (out_h, out_w)
```

```python
def resize_area(img, out_h, out_w):
    Ay = _area_matrix(img.shape[0], out_h)
    Ax = _area_matrix(img.shape[1], out_w)
    src = img.astype(np.float64)
    if img.ndim == 3:
        out = np.einsum("ih,hwc,jw->ijc", Ay, src, Ax)    # 彩色图：对每个通道做同样的两次矩阵乘法
    else:
        out = Ay @ src @ Ax.T
    return np.clip(np.round(out), 0, 255).astype(np.uint8)
```

`np.einsum` 用字母标出每一维，按"相同字母相乘、在输出里消失的字母求和"的规则计算。`"ih,hwc,jw->ijc"` 读作：`out[i,j,c] = Σ_h Σ_w Ay[i,h] · src[h,w,c] · Ax[j,w]`，正是对每个通道 c 做 `Ay @ src[:,:,c] @ Ax.T`。第 4 章讲矩阵乘法时会再见到它。

"缩放是一个矩阵乘法"这个观点非常重要：它说明缩放是**线性**的（两张图先相加再缩放，等于先缩放再相加），也说明了为什么它可以写进神经网络里、可以对它求梯度。第 12 章的平均池化，就是区域平均的特例。

### 三种方法对细笔画的影响

用一个极端的例子把差别看清楚：一行 8 个像素，只有第 0 个是黑的（一条 1 像素宽的竖笔画），缩成 2 个像素。

```
输入 [0, 255, 255, 255, 255, 255, 255, 255]，缩成 2 个
最近邻：输出 0 的中心 (0.5)×4 = 2 → 取像素 2 = 255           笔画消失
双线性：x = 0.5×4 − 0.5 = 1.5 → 像素 1、2 各半 = 255          笔画消失
区域平均：输出 0 覆盖像素 0–3 → (0+255+255+255)/4 = 191      笔画变淡，但还在
```

这就是为什么 `letterbox`（2.8 节）在缩小时默认选择区域平均：**缩小用区域平均，放大用双线性，标注图用最近邻。**

### 实测：把一个 "8" 缩小

第 5 部分把一个 32×32 的 "8" 分别用最近邻和双线性缩到 16×16 和 8×8：

```
--- 缩小到 16×16：最近邻（左）与 双线性（右）
                   |
 :@+#%             |     *##+
 @   @.            |    =*  *=
 *+  @             |    =*  *=
  %@@.             |     ###*
 @   *-            |    ++  +-
 @   :%            |    %.  .%
 @:  %=            |    #=  =#
  +%#:             |    .*##*.
--- 缩小到 8×8：最近邻（左）与 双线性（右）
 #+        |    --
.          |
 :*        |    **
#          |   -  =
           |    --
```

（下方的空行已省略。）16×16 时，最近邻的笔画断断续续（第 2 行的 "8" 左上角和右边都断了），双线性连贯得多。到 8×8，两者都几乎认不出是 "8" 了。

```
先缩到 8×8 再放大回 32×32，与原图的平均像素差 23.0（信息丢了就回不来）
```

平均每个像素差了 23（满分 255）。缩小是**有损的**，丢掉的细节放大也找不回来。这引出了本章最重要的实验问题：**分辨率到底需要多高？**

## 2.7 实验：分辨率、对齐与识别

### 实验设计

我们用一个最简单的"识别器"——**最近模板分类器**——来做实验，它不需要任何训练算法：

1. 对 62 个字符（10 个数字 + 26 个小写 + 26 个大写）中的每一个，渲染 40 张图，**求平均**，得到这个字符的"模板"（一张模糊的平均图）；
2. 对每张测试图，计算它和 62 个模板的距离（逐像素差的平方和），**离哪个模板最近，就判为哪个字符**。

代码是 `pixels.py` 里的 `nearest_template_accuracy`，最关键的一行：

```python
d = ((X[:, None, :] - T[None, :, :]) ** 2).sum(-1)    # (n_test, 62)：每张测试图到每个模板的距离
```

`X` 是测试图（每张拉平成一个长向量），形状 `(20, size×size)`；`T` 是模板，形状 `(62, size×size)`。加了 `None` 之后分别变成 `(20, 1, size×size)` 和 `(1, 62, size×size)`，相减时广播成 `(20, 62, size×size)`，再对最后一维求和，就得到每对之间的距离。第 1 章的广播在这里一次算完了 1240 个距离。

随机猜的准确率是 1/62 ≈ 1.6%。

**在运行之前，先在纸上写下你的预测**：

1. 直接比较 32×32 的像素，准确率大约多少？
2. 分辨率降到 16、8、4，准确率怎样变化？
3. 如果先把字符"对齐"（裁出墨迹框、缩放到统一大小、居中），准确率会怎样？

### 实测结果

```
--- 直接比较像素（不对齐）
  32×32（1024 个像素）准确率   4.4%   最常见的混淆: i→I×7, M→W×7, e→F×6, z→F×6, 5→6×5, b→K×5
  16×16（ 256 个像素）准确率   4.6%   最常见的混淆: M→W×7, z→F×6, b→K×5, d→b×5, i→I×5, V→6×5
   8×8 （  64 个像素）准确率   3.8%   最常见的混淆: M→W×8, z→F×6, W→g×6, 5→6×5, e→F×5, i→I×5
   4×4 （  16 个像素）准确率   3.7%   最常见的混淆: l→i×8, j→i×7, M→W×7, r→i×6, 9→b×5, d→b×5
--- 先做字符归一化（对齐位置和大小）
  32×32（1024 个像素）准确率  89.5%   最常见的混淆: c→C×12, s→S×12, X→x×10, o→O×9, V→v×8, Z→z×8
  16×16（ 256 个像素）准确率  85.3%   最常见的混淆: i→j×18, z→Z×14, s→S×13, v→V×11, c→C×10, X→x×10
   8×8 （  64 个像素）准确率  81.5%   最常见的混淆: z→Z×14, c→C×13, o→O×10, O→Q×10, s→S×9, I→l×9
   4×4 （  16 个像素）准确率  70.6%   最常见的混淆: c→C×16, z→Z×14, h→t×13, s→S×13, o→O×12, x→X×12
```

### 怎么读这个结果

**第一，不对齐时几乎是瞎猜（4% 左右），分辨率高也没用。** 原因是字符的位置和大小是随机的。同一个 "A"，一张在左上角，一张在右下角，它们的像素几乎没有重叠，"逐像素比较"认为它们完全不像。求平均得到的模板也只是一团模糊的灰影。**位置的差异淹没了形状的差异。**

**第二，先对齐，准确率从 4% 跳到 89.5%。** 对齐的代码是 `imgops.py` 里的 `normalize_glyph`：

```python
def normalize_glyph(img, size, thresh=128):
    ys, xs = np.nonzero(img < thresh)                        # 所有墨迹像素的坐标
    if len(xs) == 0:
        return np.full((size, size), 255, dtype=np.uint8)    # 没有墨迹：返回空白
    c = img[ys.min():ys.max() + 1, xs.min():xs.max() + 1]    # 裁出墨迹的外接框
    out, _, _ = letterbox(c, size, size, resize=resize_area) # 保持比例缩放、居中
    return out
```

这是经典 OCR 的一个标准步骤，叫**字符归一化**。它把"位置"和"大小"这两个与字符身份无关的因素消掉，只留下"形状"。同一个分类器、同样的数据，换一个预处理，准确率差了 20 倍。

**第三，对齐之后，分辨率才开始起作用**：32→89.5%，16→85.3%，8→81.5%，4→70.6%。分辨率越低，越多细节被平均掉。而且，只有 16 个像素时还有 70.6%，说明字符的"大体轮廓"所携带的信息比我们想象的多。（注意：归一化之后，渲染器画出的同一个字符只剩十几种不同的图，测试图大多与训练图完全相同，所以对齐后的这些准确率偏乐观。第 10 章会量化这个问题，并用随机形变解决它。）

**第四，看混淆的是什么。** 对齐后最常见的错误是 `c→C`、`s→S`、`X→x`、`o→O`、`z→Z`——**大小写对**。这不是分类器"笨"：`normalize_glyph` 把每个字符都缩放到同样大小，**把"大小"这个信息也一起消掉了**，而小写 c 和大写 C 恰恰只有大小不同。低分辨率时还多了 `i→j`、`I→l`、`h→t` 这类笔画细节的混淆。

这个现象揭示了一个普遍原则：**预处理会消除一些变化，但被消除的信息有时正是你需要的。** 字符归一化消除了大小，也就无法区分大小写；要区分它们，需要知道字符相对于**整行文字**（基线、x 高度）的大小。这正是为什么现代 OCR 识别的是**整行**而不是单个字符（第 13 章），也是为什么 VLM 要看整张图（第 22 章）。

**第五，这个实验对 VLM 的意义。** 神经网络不需要人工对齐——第 12 章的卷积网络会自己学会"不管字符在哪里都能认出来"，第 19 章的 ViT 会看到它需要多少数据才学会。但"分辨率决定能看清多少细节"这一点，对任何模型都成立。Qwen3.5 这样的 VLM，每个视觉 token 对应 32×32 个像素（第 24 章）：如果一个字符在缩放后只剩 8×8 个像素，它在模型眼里就只占一个 token 的 1/16。**OCR 模型往往需要比通用 VLM 更高的输入分辨率**，原因就在这里。

## 2.8 长宽比与 letterbox

### 问题

文字行和公式通常是**又宽又矮**的：一张公式图是 48×192，宽是高的 4 倍。如果模型要求输入是 48×48 的正方形，有两种做法：

1. **硬压**（squash）：直接缩放成 48×48，横向压缩 4 倍、纵向不变——字被挤扁了；
2. **letterbox**：保持长宽比缩放，直到能放进 48×48，再把空白部分补成背景色。名字来自电影：宽银幕电影在 4:3 的电视上播放时，上下会留黑边，像信封（letterbox）的开口。

第 7 部分的实测输出：

```

letterbox: scale=0.250，左右补 0、上下补 18 像素
```

```
--- 硬压成 48×48（字被横向挤扁）
                             =:       +
                        :: :  :      .:
                        =-:%  :       :
                        :- :  :    -- :
                                -%:--
                       =@@@@@@@=    -
                          :      . --
                          :*       --
                          :.:
                          :..
                          :*
--- letterbox 成 48×48（比例不变，但字变得很小）
                        :- =  :       :
                          :.    .: :-

```

（空行已省略。为了在终端里显示，两张图都又缩到了 24×48。）打开 `outputs/ch02/formula.png` 看原图。

两种做法都很糟：硬压让字形严重变形，"a" 和 "1" 挤在一起；letterbox 保住了比例，但整张图缩小到 1/4，公式只剩 12 像素高，几乎所有细节都丢了，图的上下 3/4 是白边，白白浪费。

**结论：对又宽又长的文字图，用固定的正方形输入是错误的设计。** 真实的解决方案有三类（本章"横向对照"详细比较）：

- 文字行识别器（第 13 章）固定**高度**、让宽度随文字长度变化；
- Qwen 系列 VLM 支持**任意长宽比**，只要求宽和高都是 32 的倍数，按原比例缩放（第 24 章）；
- 另一些 VLM 把大图**切成多块**正方形分别编码。

### letterbox 的实现与坐标换算

```python
def letterbox(img, out_h, out_w, fill=255, resize=None):
    in_h, in_w = img.shape[:2]
    scale = min(out_h / in_h, out_w / in_w)                     # 两个方向都要放得下，取较小的比例
    nh, nw = max(1, round(in_h * scale)), max(1, round(in_w * scale))
    small = (resize or (resize_area if scale < 1 else resize_bilinear))(img, nh, nw)
    canvas = np.full((out_h, out_w) + img.shape[2:], fill, dtype=np.uint8)
    py, px = (out_h - nh) // 2, (out_w - nw) // 2               # 上边、左边各补多少（居中）
    canvas[py:py + nh, px:px + nw] = small
    return canvas, scale, (px, py)
```

**手算**：48×192 放进 48×48。`scale = min(48/48, 48/192) = min(1, 0.25) = 0.25`。缩放后 `nh = 12, nw = 48`。上下补 `(48 − 12) // 2 = 18`，左右补 `(48 − 48) // 2 = 0`。和实测输出一致。

几个细节：

- `img.shape[2:]`：灰度图是空元组 `()`，彩色图是 `(3,)`。`(out_h, out_w) + img.shape[2:]` 让同一行代码同时支持两种图；
- `resize or (...)`：调用者可以指定缩放方法；不指定时，缩小用区域平均，放大用双线性——正是上一节的结论；
- **函数同时返回 `scale` 和 `(px, py)`**。这不是可有可无的：图变了，**图上的标注也要跟着变**。原图里的点 `(x, y)` 在新图里是：

```
x' = x × scale + px
y' = y × scale + py
```

边界框的四个数也按这个公式换算。如果忘了换算，或者只乘了 `scale` 忘了加 `pad`，框就会整体偏移，"框对不上字"。模型输出坐标时（第 23 章的定位任务），还要做**反向**换算：`x = (x' − px) / scale`，才能画回原图上。测试 `test_letterbox_keeps_aspect_and_maps_boxes` 检查的正是这一点：换算后的框里，确实是那个字符的墨迹。

`outputs/ch02/formula_boxes.png` 画出了公式中每个符号的框（由 `render_formula` 生成，第 3 章详细介绍）。检查框和字是否对得上，是做任何 OCR 数据之后的**第一步检查**。

## 2.9 归一化：从整数到模型的输入

### 为什么要变成小数

神经网络内部做的是大量的乘法和加法（第 4 章），用的是浮点数。直接把 0–255 的整数送进去，也能算，但数值太大会让训练不稳定（第 11 章会解释原因：输入大，每层输出就大，梯度也大）。所以几乎所有模型都把像素先变成 **0 附近的小数**。

`to_float`（练习 2.7）做三件事，顺序很重要：

```python
def to_float(img, mean=None, std=None, invert=False):
    x = img.astype(np.float32) / 255.0                 # 1. 0–255 → 0–1
    if invert:
        x = 1.0 - x                                    # 2. 反色：墨迹=1，背景=0
    if mean is not None:
        x = (x - np.asarray(mean, dtype=np.float32)) / np.asarray(std, dtype=np.float32)   # 3. 标准化
    return x
```

第 8 部分的实测输出（输入是四个像素 `[0, 64, 128, 255]`）：

```
原始         [[0, 64, 128, 255]]
/255         [ 0.000,  0.251,  0.502,  1.000]
反色 1-x     [ 1.000,  0.749,  0.498,  0.000]  ← 墨迹=1，背景=0
(x-0.5)/0.5  [-1.000, -0.498,  0.004,  1.000]  ← Qwen3.5 的做法，范围 [-1, 1]
CLIP 的 mean/std 下，纯白像素 (255,255,255) 变成 [ 1.930,  2.075,  2.146]
```

**手算**：`64 / 255 = 0.251`；`(0.251 − 0.5) / 0.5 = −0.498`；`128 / 255 = 0.502`，`(0.502 − 0.5)/0.5 = 0.004`。

### 三种做法各有道理

- **只除以 255**：最简单，范围 [0, 1]；
- **反色**：文字图大部分是白色背景（上一节测到墨迹只占 14.6%）。不反色时，背景是 1、墨迹是 0，网络的输入大部分是"1"；反色后背景是 0，只有墨迹处非零。对第 10 章那种简单的网络，这让"有字的地方"直接对应"大的输入"，训练更容易。这不是必须的，更深的网络两种都能学会；
- **减均值除标准差**（standardization）：让输入大致以 0 为中心、尺度为 1。`mean` 和 `std` 可以每个通道一个。
  - Qwen3.5（以及 SigLIP 系列）用 `mean = std = 0.5`，把 [0, 1] 线性映射到 [−1, 1]；
  - CLIP 用的是它训练数据集上统计出来的每通道均值和标准差（mean ≈ (0.481, 0.458, 0.408)，std ≈ (0.269, 0.261, 0.276)），所以纯白像素变成了约 2 而不是 1。

**最重要的规则：用预训练模型时，必须用它训练时的那一组 mean 和 std。** 模型的参数是在某种输入分布下学出来的。把一个按 CLIP 归一化训练的编码器喂上 `[−1, 1]` 的输入，它不会报错，但看到的"颜色"全错了。第 24 章会从真实模型的配置文件里读出这些数；第 35 章的"自己动手"里，你会在 SmolVLM 上亲手测一测用错 mean/std 时识别会坏到什么程度。

### 最后一步：换通道顺序、加批维度

把所有步骤串起来，就是一个完整的（简化版）预处理流水线：

```
uint8 (H, W, 3)
   │ letterbox / 缩放
   ▼
uint8 (H', W', 3)
   │ to_float(mean, std)
   ▼
float32 (H', W', 3)
   │ hwc_to_chw
   ▼
float32 (3, H', W')
   │ 多张图 np.stack
   ▼
float32 (B, 3, H', W')   ← 送进模型
```

真实 VLM 的 processor 还会再做一步：把图切成小方块（patch），每块拉平成一个向量——这是第 19 章 ViT 的内容。

| 现象 | 原因 | 怎么查 |

## 2.12 真实世界对照

**真实模型的预处理就是本章操作的组合。** 以 Qwen3.5-0.8B 为例（第 24 章会逐行读它的代码）：

1. 把图转成 RGB；
2. 用一个叫 `smart_resize` 的函数决定目标尺寸：**保持长宽比**，使宽和高都是 32 的倍数，并且总像素数落在一个允许的范围内（太小就放大，太大就缩小）。为什么是 32？因为它的视觉编码器每个 patch 是 16×16 像素，相邻的 2×2 个 patch 再合成一个视觉 token，所以一个 token 对应 32×32 像素；
3. 用双三次插值（bicubic，一种比双线性更平滑的插值，用周围 4×4 个像素）缩放；
4. 除以 255，再用 `mean = std = 0.5` 标准化到 [−1, 1]；
5. 切成 patch，送进视觉编码器。

你会发现：它**不用 letterbox，也不硬压**，而是保持原比例，只在宽高上做一点点取整。这正是 2.8 节结论的工业界答案。

**OCR 对分辨率的需求。** 2.7 节的实验说明，字符太小就认不出。真实的文档 OCR 模型普遍允许很高的输入分辨率（上百万像素），代价是视觉 token 数随像素数线性增长——一张 1024×1024 的图，按每个 token 32×32 像素算，就是 32×32 = 1024 个视觉 token。第 22、24 章会算这笔账，第 34 章会看到 Xiaomi-OCR-0 怎样在一个 0.8B 的小模型上处理这个问题。

**渲染数据。** 用程序渲染文字来造训练数据，是 OCR 领域几十年来的标准做法：经典的 SynthText、TextRecognitionDataGenerator 都是这样做的。我们的渲染器只用一种字体，真实的合成器会用成百上千种字体，加上透视变形、模糊、光照、背景纹理等。第 33 章会讨论"合成数据和真实数据之间的差距"（domain gap），以及 Xiaomi-OCR-0 的"定向合成"怎样补齐真实数据的短板。

## 2.13 深入一步

### 两种像素对齐约定的数学

像素中心对齐（`align_corners=False`）：输出像素 i 对应的输入坐标

```
x_in = (i + 0.5) × in / out − 0.5
```

角点对齐（`align_corners=True`）：让输出的第一个和最后一个像素中心，恰好对准输入的第一个和最后一个像素中心：

```
x_in = i × (in − 1) / (out − 1)
```

两者的区别：缩放 6 → 4 时，像素中心对齐给出 `[0.25, 1.75, 3.25, 4.75]`（关于中心 2.5 对称，两端各有 0.25 的余量）；角点对齐给出 `[0, 1.667, 3.333, 5]`（两端顶格）。角点对齐的问题是：缩放比例实际上是 `(in−1)/(out−1)` 而不是 `in/out`，图像内容会有轻微的拉伸，而且把一张图放大 2 倍再缩小 2 倍回不到原位。所以 PyTorch 从 0.4 版本以后默认改成了 `align_corners=False`。

**验证一下**：在像素中心对齐下，`out = in` 时 `x_in = (i + 0.5) − 0.5 = i`，恒等映射，好；放大 2 倍时 `x_in = (i + 0.5)/2 − 0.5 = i/2 − 0.25`，输出像素 0 和 1 对应输入的 −0.25 和 0.25，关于输入像素 0 的中心对称，好。

### 为什么最近邻在"恰好一半"时和 Pillow 不一致

测试 `test_nearest_matches_pillow_except_ties` 的名字里有个 "except ties"。当 `(i + 0.5) × in / out` 恰好是整数时，这个位置正好落在两个输入像素的交界上。例如 32 缩到 16：`(i + 0.5) × 2 = 2i + 1`，**每一个**采样点都恰好落在交界上（像素 2i 和 2i+1 之间）。数学上取哪个都可以；我们的实现用 `floor`，取右边那个；Pillow 内部用浮点数累加计算位置，有时会得到 `2.9999999` 这样略小的值而取左边那个。这种"交界上的平局"是浮点数的固有问题（第 11 章），测试允许这些行列不一致。**一个实现与参考实现"几乎一致"时，要弄清不一致的地方是 bug 还是平局。**

### 缩放的频率视角（为什么缩小要先平均）

把一行像素看成一个信号。黑白相间的条纹 `[0, 255, 0, 255, ...]` 是变化最快的信号（"高频"）。如果每隔一个像素取一个（缩小 2 倍的最近邻），可能全取到 0，也可能全取到 255——**一个快速变化的图案，变成了一个完全不变的图案**。这种现象叫**混叠**（aliasing）。信号处理里有一个定理（奈奎斯特采样定理）说：采样频率必须至少是信号最高频率的两倍，否则就会混叠。缩小图像等于降低采样频率，所以在采样之前，必须先把那些"太快"的变化平滑掉——这就是区域平均（以及 Pillow 缩小时自动扩大的滤波范围）在做的事情，叫**抗锯齿滤波**。第 12 章的卷积就是一种可学习的滤波器，第 19 章 ViT 的"patch 嵌入"也可以看作一种带滤波的降采样。

### 盒子模型排版（预告第 3 章）

公式的排版不能像文字行那样"一个接一个排在基线上"：上标要升高、缩小；分数要把分子放在分数线上方、分母放在下方。`render.py` 用的是 TeX 的**盒子模型**（box model）思想，每个排版单元是一个盒子 `Box(w, asc, desc, cmds)`：

- `w`：宽度；`asc`：基线以上的高度；`desc`：基线以下的深度；
- `cmds`：盒子里要画的东西，坐标相对于盒子左端和基线。

排版就是**递归地把小盒子拼成大盒子**：

- 一行：盒子从左到右排，宽度相加，`asc` 和 `desc` 取最大值；
- 上标：基础盒子的右边放一个用 0.7 倍字号排出的盒子，往上移 0.42 倍字号；下标往下移 0.28 倍字号；
- 分数：分子、分母用 0.8 倍字号，水平居中，分子的底部在分数线上方，分母的顶部在分数线下方，分数线位于基线上方 0.3 倍字号处（数学排版中的"轴"，axis，也是加减号的高度）；
- 根号：内容盒子的左边画一个勾，上方画一条横线。

最后把整个盒子画到图上，同时记录每个符号的框。因为排版是**沿着语法树递归**进行的，所以符号的框天然按照"语法树叶子的从左到右顺序"排列——但前提是同一个底的下标先于上标处理。我们最初的实现先画上标，结果框的顺序和 `leaves()` 不一致，测试 `test_formula_boxes_follow_leaves_and_stay_inside` 抓到了这个 bug。这说明：**数据生成器也需要测试。** 第 34 章的 Q-Mask 需要"每段文字在图上的位置"，正是这种由渲染器自动产生的精确标注。

## 2.14 横向对照：怎样把任意大小的图交给模型

| 做法 | 怎么做 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|
| 固定尺寸 + 中心裁剪 | 短边缩放到 224，再从中间裁出 224×224 | 简单，批处理方便 | 两边的内容被裁掉——对文档是灾难 | CLIP 的标准预处理 |
| 固定尺寸硬压 | 直接缩放成正方形 | 不丢内容 | 长宽比失真 | SigLIP 的常见用法 |
| 补成正方形 | 用背景色（或均值色）把图补成正方形再缩放 | 不丢内容、不变形 | 浪费像素；长图会被缩得很小 | LLaVA-1.5 |
| 固定高度、宽度可变 | 高度缩放到固定值，宽度按比例 | 适合文字行 | 只适合一维的文字行 | CRNN 等文字行识别器（第 13 章） |
| 原生分辨率（动态尺寸） | 保持比例，宽高取整到 patch 的倍数，token 数随图变化 | 不丢、不变形、细节保留 | token 数不固定，大图很贵；批处理要拼接 | Qwen2-VL 及以后的 Qwen 系列（第 24 章） |
| 切块（tiling） | 大图切成若干固定大小的正方形块，各自编码，再加一张缩略全图 | 能用固定尺寸的编码器处理高分辨率 | 块与块的边界处可能切断文字；token 多 | LLaVA-NeXT、InternVL、SmolVLM |

选择的原则回到本章的两个实验：**不要丢掉内容**（裁剪会丢）、**不要让字太小**（分辨率决定能否认出）、**不要变形**（变形让同一个字长得不一样）。对 OCR，后两条尤其重要，所以现代 OCR 模型几乎都选原生分辨率或切块。

## 2.15 本章小结

- 灰度图是 `(H, W)` 的 `uint8` 数组，0 黑 255 白；彩色图是 `(H, W, 3)`，通道依次是 R、G、B；
- 几何坐标 `(x, y)` 先横后竖，数组下标 `img[y, x]` 先行后列；边界框 `(x0, y0, x1, y1)` 右下不含，裁剪就是 `img[y0:y1, x0:x1]`；
- `uint8` 运算会溢出，`astype(np.uint8)` 不会截断；先转小数、先 `clip`；
- 灰度转换要加权（0.299, 0.587, 0.114），而且会丢掉颜色信息（ShapesWorld 的红和蓝几乎同灰）；
- 缩放的三种方法：**最近邻**（快、不产生新值，用于标注图）、**双线性**（看 4 个邻居，适合放大）、**区域平均**（用到所有像素，适合缩小）；区域平均可以写成矩阵乘法 `Ay @ img @ Axᵀ`；
- 位置不对齐时逐像素比较几乎无效（4%），对齐后达到 89.5%；分辨率越低，细节越少；预处理消除的信息（如大小）可能正是需要的（大小写）；
- 宽长图用正方形输入既不能硬压也不宜 letterbox；真实 VLM 用原生分辨率或切块；缩放后**框要跟着换算**；
- 进模型前：除以 255 →（可选）反色 → 减均值除标准差（必须与预训练时一致）→ 换成通道在前 → 叠成批。

## 参考答案

1. 宽 640，高 480（形状先行后列）。`img[100, 200, 2]` 是第 100 行、第 200 列（即 `(x, y) = (200, 100)`）像素的蓝色分量。
2. 人眼对三种颜色的敏感度不同，绿最敏感、蓝最不敏感，加权平均更符合人眼感受的亮度。ShapesWorld 的红 (220,40,40) 和蓝 (40,80,220) 转成灰度后分别是 93.8 和 84.0，几乎一样，灰度图上无法区分红蓝，所以颜色相关的任务必须用彩色输入。
3. 区域平均让输出像素覆盖范围内的**每个**输入像素都按覆盖比例参与平均，细笔画至少会让结果变暗；双线性只看离采样点最近的 4 个像素，缩小倍数大时，大部分输入像素根本不参与计算，细笔画如果恰好不在这 4 个里就消失了。
4. `normalize_glyph` 把每个字符的墨迹框都缩放到同样大小，消除了"大小"这个信息；而 c/C、s/S、o/O、x/X、z/Z 这些字母的大小写形状几乎相同，只是大小不同，所以无法区分。
5. 模型的参数是在特定的输入分布下学出来的，换一组 mean/std，输入的数值整体偏移、缩放，模型"看到"的颜色和亮度全错了。不会报错——数组形状完全正确——只是效果变差，所以特别难发现。
6. 放大比例 4/8 = 0.5。`x = (i + 0.5) × 0.5 − 0.5`：i=0 时 `x = −0.25`，截断到 0，值 = 0；i=1 时 `x = 0.25`，`0.75 × 0 + 0.25 × 100 = 25`；i=2 时 `x = 0.75`，`0.25 × 0 + 0.75 × 100 = 75`。（继续算下去：i=3 → x=1.25 → 125，i=4 → 1.75 → 175，i=5 → 2.25 → 175，i=6 → 2.75 → 125，i=7 → 3.25 截断到 3 → 100。）
7. 每个输出覆盖 4/3 ≈ 1.333 个输入像素。输出 0：[0, 1.333)，覆盖像素 0 的 1、像素 1 的 0.333；输出 1：[1.333, 2.667)，覆盖像素 1 的 0.667、像素 2 的 0.667；输出 2：[2.667, 4)，覆盖像素 2 的 0.333、像素 3 的 1。除以 1.333 后：
   ```
   [[0.75, 0.25, 0,    0   ],
    [0,    0.5,  0.5,  0   ],
    [0,    0,    0.25, 0.75]]
   ```
   每行和为 1。
8. `scale = min(64/60, 64/240) = 0.2667`；`nh = round(60 × 0.2667) = 16`，`nw = 64`；`py = (64 − 16) // 2 = 24`，`px = 0`。框变成 `(40×0.2667 + 0, 10×0.2667 + 24, 80×0.2667, 50×0.2667 + 24) ≈ (10.7, 26.7, 21.3, 37.3)`，取整约为 `(11, 27, 21, 37)`。
9. `200/255 = 0.784`，`(0.784 − 0.5)/0.5 = 0.569`。反色：`1 − 0.784 = 0.216`。
10. `8 × 3 × 224 × 224 × 4 = 4,816,896` 字节，约 4.8 MB。
11. 第一种写法是对的：行取全部 `0:h`，列取左半 `0:w//2`。第二种写法把行列写反了：当 `shape = (32, 100)` 时，`img[0:50, 0:32]` 实际上选中的是全部 32 行（50 超出范围被截断）的前 32 列——涂黑了一个 32×32 的方块，而不是左半边。没有报错，结果却错了，这正是 x/y 写反最危险的地方。
12. `uint8` 加法会溢出：值为 230 的像素加 50 得到 280，超出 255 后绕回成 24，亮的地方反而变黑。改为：`brighter = np.clip(img.astype(np.int32) + 50, 0, 255).astype(np.uint8)`。
13. `x.transpose(0, 3, 1, 2)`（或 `np.transpose(x, (0, 3, 1, 2))`）。
