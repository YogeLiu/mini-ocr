# 第 27 章 图像作为张量

## 本章导读

先看一个真实的例子。验证集里有一张公式图，宽 298 像素、高 32 像素，内容是

```text
I_\Sigma(A)=\{\,x\in\Sigma_1\setminus A\mid A\cup\{x\}\in\Sigma_{q+1}\,\}
```

我们把同一张图用六种方式处理后交给 Qwen3.5-0.8B，下面列出其中四种：

| 处理 | 送进 processor 的尺寸（高×宽） | 视觉 token | 结果 |
|---|---|---|---|
| 不缩放（native） | 32×298 | 9 | 完全正确 |
| 等比例缩到 128，补白（letterbox128） | 128×128 | 16 | 读成 `\chi _ { A } ( \mathbf { x } ) = …`，字符编辑距离 74 |
| 最近邻拉伸到 128×128（nearest128） | 128×128 | 16 | 陷入 `\scriptsize` 重复，编辑距离 320 |
| 等比例缩到 384，补白（letterbox384） | 384×384 | 144 | 完全正确 |

（本项目观察：RTX 4090（租用），bf16，原图验证集逐条输出 `outputs/book/ch27/gpu/original/qwen35_val_original_*.jsonl` 中 id 为 `0b4206309013904d9c1ce9c6` 的记录。）

四种输入的张量形状都合法，模型都老老实实地输出了一串 LaTeX，没有任何报错，可结果从全对到彻底跑偏。参考答案只有 71 个字符，最近邻那一版错了 320 个字符。

这一章讲一张图从文件变成张量的路上发生了什么，哪一步会悄悄弄丢小字。

本章的结论先放在这里：

1. 图片在内存里是 `HWC`（高、宽、通道），PyTorch 的视觉模型要 `CHW`。换轴要用 `permute`，不能用 `reshape`。
2. 缩小一张图，就是让一个新像素代表好几个旧像素。最近邻和不抗锯齿的双线性是**抽样**，细线可能整条消失；面积缩放是**平均**，线还在，但变淡了。
3. 归一化把像素值挪到模型训练时习惯的范围。它不增加也不减少信息，但必须和预训练时**一模一样**。
4. 形状对了不等于信息还在。小字丢在缩小的那一刻，后面再放大也补不回来。
5. 分辨率、视觉 token 数、留白比例这三件事经常一起变。看到大图更好，先问到底是哪一个在起作用。

**学完本章，你能做到：**

1. 说清高、宽、通道的含义，写出 `HWC` 和 `CHW` 的互相转换，解释 stride 的变化。
2. 用一个小矩阵手算最近邻、双线性、面积三种缩放，说出它们对细线的不同影响；算出 letterbox 的缩放比例和留白。
3. 写出归一化公式和逆变换，说出归一化不一致会造成什么后果。
4. 解释"缩小后形状看起来没问题，但识别率下降"的几种原因，并知道该先查哪条日志。
5. 读懂本章的分辨率对照，指出其中分辨率和视觉 token 数的混杂。

> **回顾（第 1 章）：** 张量有形状、dtype、device 三个属性；数据在内存里是一条直线，**步长**（stride）告诉我们沿每一维走一步要跳几个数；`transpose`、`permute` 只改 stride，不搬数据，所以结果常常不连续。**回顾（第 26 章）：** Qwen 的 processor 先用 `smart_resize` 把图的高、宽调到 32 的倍数，再切成 16×16 的 patch，相邻 2×2 个 patch 合并成一个视觉 token，所以一个视觉 token 对应缩放后图上 32×32 像素的一块。

**本章每个数字都标出来源。**"数学结论"可以从公式推出来；"本项目观察"来自 lab 的实测，GPU 部分全部在 RTX 4090（租用）上以 bf16、batch 8、贪心解码、`max_new_tokens=128`、零样本（不训练）跑出，文件在 `outputs/book/ch27/gpu/`，样本数在每张表里注明；"待验证"是还没有实测的推断。

**本章用到两组验证图，各 200 张。** 一组是开源数据集自带的**原图**，主要的结论都看它。另一组是**受控图**：从同一个验证集顺序里取能被 mathtext 渲染的公式，统一用 DPI 200、白边 12 像素重新渲染，用来隔离字体和图片来源的影响。两组共有 108 个公式重合，但不是同一批图（本项目观察，`data/manifest.json`）。测试集 100 张在选型冻结后只评选中的那一个配置，评一次（27.6.5 节）。

**本章只报 OCR 主任务面板（第 0 章 0.9.3 节）的一部分**：规范化后的完全匹配（正文写作 EM，即 EM_norm）和字符 CER，另列达到生成上限的条数。CER_token 和 `well_formed` 记在结果 JSON 里，正文不列；可编译率和渲染一致率没有计算。27.3.6 节的像素指标比的是缩放前后的图，不是渲染一致率。

## 27.1 一张图在内存里长什么样：HWC 与 CHW

### 27.1.1 同一堆数，两种摆法

一张 RGB 图片有三个轴：**高**（H，多少行像素）、**宽**（W，多少列像素）、**通道**（C，每个像素有几个数，RGB 是 3 个）。

磁盘上的 PNG、JPEG 文件存的是压缩过的字节，不是像素表。PNG 是无损压缩，解码后每个像素的值和保存时一样；JPEG 是有损压缩，笔画边缘可能多出一圈杂色。`Image.open` 读进来、解码以后，才得到每个像素的值，常见的是每个通道一个 0 到 255 的整数，也就是 `uint8`。解压后的大小可以直接算：本章开头那张 32×298 的 RGB 图有 32 × 298 × 3 = 28608 个 `uint8`，也就是 28608 字节（数学结论）。PIL 用 **mode** 记录每个像素有几个数、各是什么意思：`L` 是单通道灰度，`RGB` 是三通道，`RGBA` 多一个透明度，`P` 是调色板模式，每个像素存的是调色板里的编号。同样是一张公式图，读进来的 mode 可能不同，所以 27.1.5 节的代码第一步先统一 mode。

用 PIL 打开图片、转成 NumPy 数组，得到的是形状 `(H, W, C)`，叫 **HWC**。PyTorch 的卷积层和视觉模型约定的却是 `(C, H, W)`，叫 **CHW**；再加上批量维就是 `(N, C, H, W)`。

所以图片进入模型前，第一步就是把轴换个顺序。这一步很容易写错，而且写错了**不报错**。

### 27.1.2 抽屉和胶片

HWC 像一排排小抽屉：每个像素是一个抽屉，里面并排放着 R、G、B 三个数。读完一个像素的三个数，才轮到下一个像素。

CHW 像三张透明胶片：第一张只印红色亮度，第二张只印绿色，第三张只印蓝色。三张叠起来才是彩色图。

从抽屉到胶片，要做的是**把每个抽屉里的第 1 个数挑出来组成第一张胶片**，以此类推。这一步是换轴：每个数还属于原来那个像素、原来那个通道，只是排列顺序变了。把那条数直接按新形状重新切段就不对了，27.1.3 节会看到它错在哪里。

### 27.1.3 手算：一张 2×2 的彩色小图

拿一张只有 2×2 个像素的图（这也是本章测试 `test_axis_order_alpha_and_roundtrip` 用的那张）：

| 位置 | 左列 | 右列 |
|---|---|---|
| 上行 | (1, 2, 3) | (40, 50, 60) |
| 下行 | (80, 90, 100) | (254, 255, 0) |

HWC 数组形状 `(2, 2, 3)`。内存里按最后一维变得最快的顺序排成一条直线：

```text
1, 2, 3, 40, 50, 60, 80, 90, 100, 254, 255, 0
```

**正确的换轴** `permute(2, 0, 1)`，形状变成 `(3, 2, 2)`：

```text
R: [[  1,  40],     G: [[  2,  50],     B: [[  3,  60],
    [ 80, 254]]         [ 90, 255]]         [100,   0]]
```

每张胶片都是同一种颜色的四个像素。右上角像素的三个通道是 `x[:, 0, 1] = (40, 50, 60)`，和原图一致。

**错误的写法** `reshape(3, 2, 2)`：reshape 不改变内存顺序，只是把那条直线每 4 个数切一段：

```text
"R": [[1, 2], [3, 40]]     "G": [[50, 60], [80, 90]]     "B": [[100, 254], [255, 0]]
```

第一张所谓的红色胶片里混进了左上像素的 G、B 和右上像素的 R。形状一模一样是 `(3, 2, 2)`，内容全乱了（数学结论）。

一张 48×96 的随机图也是这样：lab 第 1 部分直接比较两种写法，结果是 `reshape_is_permute = false`（本项目观察，`mechanisms/tensor.json`）。

### 27.1.4 stride：换轴到底换了什么

还是第 1 章的老规矩，看 stride。一张 48×96 的 HWC 图，连续存放时 stride 是 `(96×3, 3, 1) = (288, 3, 1)`：换一行跳 288 个数，换一列跳 3 个，换一个通道跳 1 个（数学结论）。

`permute(2, 0, 1)` 只把 stride 跟着轴一起换位，变成 `(1, 288, 3)`，数据没动，所以它**不连续**。再调用 `.contiguous()`，PyTorch 才真的按 CHW 顺序复制一份，stride 变成 `(48×96, 96, 1) = (4608, 96, 1)`（数学结论）。lab 第 1 部分记录的正是 `chw_shape = (3, 48, 96)`、`chw_stride = (4608, 96, 1)`（本项目观察，`mechanisms/tensor.json`）。

为什么要连续？`view` 要求新形状能用现有 stride 表示，换轴后的张量常常做不到（例如把 `(3, 48, 96)` 摊平成一维就会报错）；很多 CUDA 内核也假定连续内存。在入口处一次做好，后面就少一类奇怪报错。

### 27.1.5 对照代码：`image_to_chw`

代码在 `miniocr/data/image_tensors.py`，练习 27.1：

```python
def image_to_chw(image, device="cpu"):
    rgba = image.convert("RGBA")                      # ① 统一成带透明度的四通道
    paper = Image.new("RGBA", rgba.size, "white")     # ② 一张白纸
    paper.alpha_composite(rgba)                       # ③ 把图"贴"到白纸上
    hwc = torch.from_numpy(np.asarray(paper.convert("RGB")).copy()).to(device)  # ④ (H, W, 3) uint8
    return hwc.permute(2, 0, 1).contiguous().float() / 255   # ⑤ CHW、连续、float32、[0, 1]
```

逐行看：

- ① 到 ③ 处理透明背景。一张透明底的 PNG，透明处的 RGB 值可能是 (0, 0, 0)。直接 `convert("RGB")` 会丢掉透明度，背景变成纯黑，黑字黑底，模型什么也看不见。先贴到白纸上，透明处才是白色。测试里用一张全透明的图检查：转换后每个值都必须是 1。本章用到的 200 张原图验证图都是 RGB 模式，没有透明通道（本项目观察），但这道防线要留着。
- ④ `np.asarray` 给出 HWC 的 `uint8` 数组。`.copy()` 让张量有自己的可写内存。
- ⑤ 先换轴、再连续、再转浮点、再除以 255。其实 PyTorch 的 `/` 遇到 `uint8` 会自动提升成浮点，`torch.tensor([0, 128, 255], dtype=torch.uint8) / 255` 得到 float32 的 `[0, 0.502, 1]`（本地 CPU 复算），所以不写 `.float()` 直接除也不会出错；显式写 `.float()` 只是让 dtype 一目了然。要防的是整数除法 `//`：`uint8 // 255` 只剩 0 和 1。

反方向是 `chw_to_image`：`clamp(0, 1)`、乘 255、四舍五入、转 `uint8`、`permute(1, 2, 0)` 换回 HWC。注意它**显式**做了舍入，往返一次最多差半个灰度级。测试检查 2×2 小图往返后逐字节相等。

### 27.1.6 真实模型里的形状

到了真实的 processor 里，CHW 会再被包上几层（本项目观察，逐条输出里的 `batch_pixel_values_shape` 字段）：

- **SmolVLM-256M** 一批 8 张图的 `pixel_values` 形状是 `[8, 1, 3, 512, 512]`：批量、每条样本的图片数、通道、高、宽。中间那个 3 就是 CHW 的 C。
- **Qwen3.5-0.8B** 的 `pixel_values` 是二维的，例如一批 8 张 128×128 的图是 `[512, 1536]`。每一行是一个 patch，1536 = 3 × 2 × 16 × 16：通道 × 时间 × patch 高 × patch 宽（数学结论，第 26 章讲过时间轴是把静态图复制成两帧）。每张 128×128 的图切出 8×8 = 64 个 patch，8 张就是 512 行（数学结论）。

两种形状来自两种批量化办法。`torch.stack` 把几个张量沿一个新轴叠起来，要求它们形状完全相同。SmolVLM 在本实验配置下把每张图都变成 512×512（27.5.2 节），所以可以直接叠成五维。Qwen 保留每张图自己的尺寸，各图切出的 patch 数不同，没法叠，于是把所有图的 patch 首尾接成一张二维大表，另用 `image_grid_thw` 记下每张图的网格，从而知道每张图占了哪几行。

CHW 没有消失，只是被压进了每一行里。第 29 章讲 ViT 时会把这一步拆开。

### 27.1.7 常见错误

- **用 `reshape` 或 `view` 换轴。** 形状对，颜色乱。验法：造一个 R、G、B 三值都不同的像素，看它换轴后是否还在同一个位置。
- **忘了 `/255`，或者除了两次。** 前者让输入范围变成 [0, 255]，后者让它挤在 [0, 0.004]。验法：打印 `min`、`max`。
- **把 `/` 写成 `//`。** 整数除法 `uint8 // 255` 只剩 0 和 1，灰度层次全丢，图变成纯黑白。
- **RGB 和 BGR 搞反。** OpenCV 读图默认是 BGR。对黑白公式图影响不大，对彩色图会把红蓝互换。

## 27.2 归一化：把尺子的零点对齐

### 27.2.1 为什么还要再变换一次

像素值已经在 [0, 1] 里了，为什么还要再变换一次？

因为模型在预训练时，见到的输入都经过了某个固定的变换。它学会的每一个权重，都是在那种输入的刻度上调出来的。你喂给它的数，必须用**同一把尺子**量。

### 27.2.2 公式与手算

逐通道归一化：

```text
z[c, h, w] = (x[c, h, w] − mean[c]) / std[c]
```

逆变换：`x = z × std + mean`。

本章两个模型在本实验的配置里，processor 都用 `mean = std = (0.5, 0.5, 0.5)`（本项目观察，结果 JSON 里记录的 `processor` 字段）。代进去：

| 原始灰度 | 除以 255 | 归一化后 |
|---|---|---|
| 0（纯黑） | 0 | (0 − 0.5) / 0.5 = −1 |
| 128 | 0.50196 | 0.00392 |
| 255（纯白） | 1 | +1 |

所以 [0, 1] 被映射到 [−1, 1]，中点 0.5 对到 0（数学结论）。lab 第 1 部分在随机图上测得归一化后范围正好是 [−1, 1]，逆变换的最大绝对误差是 1.49×10⁻⁸，这是 float32 的舍入，不是 bug（本项目观察，`mechanisms/tensor.json`）。

**手算一个尺子不对的例子。** 假设模型训练时用 mean = std = 0.5，你却用了 ImageNet 常见的 mean = 0.485、std = 0.229（红色通道）。一个纯白像素：

```text
模型期望：(1 − 0.5) / 0.5 = 1
你给的：  (1 − 0.485) / 0.229 ≈ 2.25
```

整张图的白底都被放大了一倍多（数学结论）。模型从没见过这么亮的白，后果是什么，没有实测，不能下结论（待验证），但这已经不是它训练时的输入分布了。

### 27.2.3 为什么归一化有用

1. **训练时**，输入以 0 为中心、尺度相近，第一层的加权和不会全部偏向一边，梯度更好调。
2. **推理时**，它的作用只剩一个：**和训练时保持一致**。归一化是可逆的仿射变换，不增加也不减少任何信息。mean 不为 0 时它带一个平移，不是严格意义上的线性映射，本章默认值下就是 f(x) = 2x − 1。

所以归一化不能用来提升小字识别。想救小字，得在缩放那一步想办法（27.3、27.4 节）。

### 27.2.4 对照代码：`normalize`

练习 27.2：

```python
def normalize(chw, mean=(.5, .5, .5), std=(.5, .5, .5), inverse=False):
    if chw.ndim != 3 or len(mean) != chw.shape[0] or len(std) != chw.shape[0]:
        raise ValueError("expected CHW and one mean/std per channel")      # ① 每个通道一对 mean/std
    m, s = [torch.as_tensor(v, dtype=chw.dtype, device=chw.device)[:, None, None]
            for v in (mean, std)]                                          # ② 形状 (3,) → (3, 1, 1)
    if not torch.all(s > 0):
        raise ValueError("std must be positive")                           # ③ 不能除以 0
    return chw*s+m if inverse else (chw-m)/s                               # ④ 广播到 (3, H, W)
```

关键在 ②。`mean` 本来是形状 `(3,)`。如果直接和 `(3, H, W)` 相减，按第 1 章的广播规则，它会从**最后一维**对齐，也就是和 W 对齐：W 既不是 3 也不是 1 时报错；W 恰好等于 3 时**不报错但算错**（按列减均值）；W 等于 1 时也不报错，输出宽度被广播成 3。加上 `[:, None, None]` 变成 `(3, 1, 1)`，才对齐到通道轴（数学结论）。

测试 `test_normalization_channelwise_inverse` 用三个不同的 mean/std 检查：第 0 通道第一个元素 0 经过 (0 − 0.1) / 0.2 = −0.5；逆变换回到原值；std 含 0 或 mean 只有一个数都要报错。

### 27.2.5 常见错误

- **归一化两次。** 自己归一化一遍，再交给 `do_normalize=True` 的 processor 又做一遍：[0, 1] → [−1, 1] → [−3, 1]。
- **自己除了 255，processor 又 rescale 一次。** transformers 的 processor 默认 `do_rescale=True`，会再乘 1/255。transformers 的文档说明：如果传入的图已经在 0 到 1 之间，要设 `do_rescale=False`。
- **mean/std 抄错模型。** 不同模型用不同的统计量。以 processor 配置文件为准，不要凭印象。

## 27.3 缩放的三种算法：最近邻、双线性、面积

### 27.3.1 新像素替谁说话

把一张 8 行的图缩成 2 行，每个新像素要代表 4 个旧像素。问题是：**怎么代表？**

三种常见答案：

- **最近邻**：找离自己中心最近的那个旧像素，照抄它。像抽签，抽到谁就是谁。
- **双线性**：找最近的两个旧像素（二维是四个），按距离加权平均。像只问两个邻居的意见。
- **面积**：把自己覆盖的所有旧像素按覆盖面积平均。像开全体会议，每人按出席时长投票。

对普通照片，这三种差别不大。对公式图，差别要命：分式线、减号、上下标的笔画，常常只有 1 到 2 个像素粗。

### 27.3.2 坐标约定：像素是小方格

先约定坐标。把每个像素看成一个**小方格**，第 i 个像素占据区间 [i, i+1)，中心在 i + 0.5。

源图长 `in`，目标长 `out`，比例 `s = in / out`。目标第 j 个像素的中心在 j + 0.5，对应到源图坐标是 `(j + 0.5) × s`。

- **最近邻（nearest-exact）**：取 `floor((j + 0.5) × s)` 号源像素，也就是目标像素中心落在哪个源方格里，就抄谁。
- **双线性（align_corners=False）**：减去 0.5，把中心坐标换成以像素中心为整数的坐标 `u = (j + 0.5) × s − 0.5`，这样源像素 i 的中心正好在 u = i。然后在 `floor(u)` 和 `floor(u) + 1` 两个源像素之间按距离插值：离 u 越近，权重越大，权重是 `1 − |u − i|`。越界时取边界像素。
- **面积**：目标第 j 个像素覆盖源区间 `[j × s, (j + 1) × s)`，每个源像素的权重 = 它和这个区间的重叠长度 ÷ s。

这三条都是数学结论，也是 `resize_chw` 采用的约定。二维缩放可以先缩高、再缩宽，两个方向各算一次。

### 27.3.3 手算：一条分式线从 8 行缩到 2 行

拿一张 8×8 的图，白底（值 1），第 3 行是一条横贯全图的黑线（值 0），相当于一条 1 像素粗的分式线。张量形状 `(3, 8, 8)`，缩到 `(3, 2, 2)`。

因为线是横的，每一列都一样，只需要算一列。这一列是：

```text
行号: 0  1  2  3  4  5  6  7
值:   1  1  1  0  1  1  1  1
```

s = 8 / 2 = 4。

**最近邻。** 目标第 0 行中心对应源坐标 0.5 × 4 = 2，取第 2 行，值 1；目标第 1 行对应 1.5 × 4 = 6，取第 6 行，值 1。结果 `[1, 1]`。**线没了。**

**双线性。** 目标第 0 行：u = 0.5 × 4 − 0.5 = 1.5，在第 1、2 行之间各占一半：(1 + 1) / 2 = 1。目标第 1 行：u = 5.5，在第 5、6 行之间：1。结果 `[1, 1]`。**线也没了。** 不抗锯齿的双线性只看两个邻居，第 3 行恰好不是任何一个目标像素的邻居。

**面积。** 目标第 0 行覆盖源区间 [0, 4)，四行各占权重 1/4：(1 + 1 + 1 + 0) / 4 = 0.75。目标第 1 行覆盖 [4, 8)：1。结果 `[0.75, 1]`。**线还在，但从纯黑变成了浅灰。**

完整的输出（每个通道相同）：

```text
最近邻 / 双线性:  [[1,    1   ],     面积:  [[0.75, 0.75],
                  [1,    1   ]]             [1,    1   ]]
```

现在把线**往上挪一行**，放在第 2 行：

| 方法 | 线在第 3 行 | 线在第 2 行 |
|---|---|---|
| 最近邻 | [1, 1]，消失 | [0, 1]，完整保留，纯黑 |
| 双线性 | [1, 1]，消失 | [0.5, 1]，半灰 |
| 面积 | [0.75, 1] | [0.75, 1] |

（数学结论；本地 CPU 上用 `resize_chw` 复算一致，本项目观察。）

从这张小表可以读出两点：

1. **最近邻和不抗锯齿的双线性都是抽样。** 细线能不能留下，取决于它碰巧落在采样网格的哪个位置。差一个像素，结果从消失变成完整。这叫**相位**依赖。
2. **面积缩放保住了墨水总量，但把它摊薄了。** 1 像素粗的线缩小 4 倍，深度只剩 1/4。如果后面有人用 0.5 做阈值判断这里有没有墨，0.75 会被判为白。

**抗锯齿（antialias）怎样补救双线性。** 上面的双线性丢线，是因为缩小 4 倍时它仍然只问两个邻居，中间的源像素没人问。这种细节因采样太稀而丢失或变形的现象叫**混叠**（aliasing），锯齿状边缘就是它在斜线上的样子。抗锯齿的做法是把双线性的权重放宽：权重仍是一个三角形，原来是 `1 − |u − i|`，只覆盖距离 1 以内的两个像素；缩小 s 倍时改成 `1 − |u − i| / s`，覆盖距离 s 以内的所有像素，再把权重归一，让它们加起来是 1。

在 8 → 2 的例子里 s = 4，用像素中心的坐标算距离（第 i 行中心在 i + 0.5）。目标第 0 行中心在 2，第 0 到 5 行的距离是 1.5、0.5、0.5、1.5、2.5、3.5，权重是 1 − 距离 / 4，乘 8 以后是 5、7、7、5、3、1，第 6、7 行距离 ≥ 4，权重 0。三角形本来还伸到图的上方，那里没有像素，所以权重和只有 28/8 = 3.5，归一时就除以它。第 3 行那条线分到 5/28 的权重，结果是 1 − 5/28 = 23/28 ≈ 0.821。目标第 1 行中心在 6，第 2 到 7 行的权重乘 8 是 1、3、5、7、7、5，图的下方同样缺一截，权重和也是 3.5，第 3 行分到 3/28，结果 25/28 ≈ 0.893。线没有消失，变成了两行深浅不同的灰（数学结论；本地 CPU 上 `F.interpolate(..., antialias=True)` 得到 0.8214、0.8929，和 27.10 节表里的数一致）。

> **停下来想一想：** 面积缩放永远不会让线完全消失，那它是不是最好的方法？如果模型训练时看的都是清晰锐利的笔画，一条浅灰的线对它意味着什么？

### 27.3.4 手算面积权重：3 个像素缩成 2 个

非整数比例时，面积缩放的权重不是简单的每 k 个一组求平均。算一个 3 → 2 的例子，s = 1.5：

- 目标第 0 个覆盖 [0, 1.5)：源像素 0 重叠 1，源像素 1 重叠 0.5。除以 1.5，权重 (2/3, 1/3, 0)。
- 目标第 1 个覆盖 [1.5, 3)：源像素 1 重叠 0.5，源像素 2 重叠 1。权重 (0, 1/3, 2/3)。

写成矩阵，形状 `[out, in] = [2, 3]`：

```text
[[2/3, 1/3,  0 ],
 [ 0,  1/3, 2/3]]
```

每一行的和是 1（数学结论：重叠长度加起来正好是 s）。所以一张全白的图缩完还是全白，一行像素的平均值缩完也不变。测试 `test_fractional_area_is_coverage_not_adaptive_pool` 检查的正是这个矩阵，以及 `[0, 0, 1]` 缩成 `[0, 2/3]`。

为什么测试名里特别说不是 adaptive pool？PyTorch 的 `adaptive_avg_pool` 在非整数比例时，把窗口边界取整后做普通平均，不按重叠长度加权。它和真正的面积积分在整数比例时一样，非整数时不一样。本书用自己写的权重矩阵，把面积缩放这个词的含义固定下来。

### 27.3.5 对照代码：`area_weights` 与 `resize_chw`

练习 27.3：

```python
def area_weights(source, target, device="cpu"):
    starts = torch.arange(target, ...)[:, None] * source/target   # ① 每个目标像素覆盖区间的起点，形状 [target, 1]
    pixels = torch.arange(source, ...)[None, :]                   # ② 每个源像素的左边界，形状 [1, source]
    overlap = (torch.minimum(starts+source/target, pixels+1)
               - torch.maximum(starts, pixels)).clamp(min=0)      # ③ 区间重叠长度，广播成 [target, source]
    return overlap/(source/target)                                # ④ 除以 s，每行和为 1
```

③ 算的是两个区间的交集长度：右端点取小，减去左端点取大，负数记 0。它用第 1 章的广播一次算出整张 `[target, source]` 表。拿 3 → 2 代进去：`starts = [[0], [1.5]]`，`pixels = [[0, 1, 2]]`，第 0 行的重叠是 `min(1.5, [1, 2, 3]) − max(0, [0, 1, 2]) = [1, 0.5, −0.5]`，负数记 0 后是 `[1, 0.5, 0]`，除以 1.5 就是上面手算的 (2/3, 1/3, 0)。

```python
def resize_chw(chw, hw, method="bilinear"):
    h, w = hw
    if method == "area":
        wy, wx = area_weights(chw.shape[1], h), area_weights(chw.shape[2], w)   # [h, H] 和 [w, W]
        return torch.einsum("yh,chw,xw->cyx", wy, chw, wx)                     # 先缩高、再缩宽
    kwargs = dict(align_corners=False) if method == "bilinear" else {}
    return F.interpolate(chw[None], size=(h, w),
                         mode="nearest-exact" if method == "nearest" else method, **kwargs)[0]
```

- 面积分支：`einsum` 里 `y` 是目标行、`h` 是源行、`x` 是目标列、`w` 是源列。等价于 `wy @ chw[c] @ wx.T` 对每个通道做一次。
- 另外两种交给 PyTorch 的 `F.interpolate`。它要四维输入，所以 `chw[None]` 临时加一个批量维，算完 `[0]` 去掉。
- 最近邻用 `nearest-exact`，按像素中心取样，和 27.3.2 节的公式一致。老的 `nearest` 模式用的是 `floor(j × s)`，会整体偏半个像素。
- 双线性**没有**打开 `antialias`。这是故意的：本章要展示不抗锯齿的双线性这种最常见也最容易出事的写法。打开以后的效果见 27.3.3 节末尾的手算。

测试 `test_nearest_and_bilinear_center_convention` 用 `[0, 1]` 放大到长度 4：最近邻得到 `[0, 0, 1, 1]`，双线性得到 `[0, 0.25, 0.75, 1]`。你可以用 27.3.2 节的公式手算验证：双线性第 1 个目标像素 u = 1.5 × 0.5 − 0.5 = 0.25，在 0 和 1 之间取 0.25 处，值 0.25。

### 27.3.6 实测：三个分式的缩放

lab 第 2 部分用三个已知的单分式（例如 `\frac{a_i+b^{2}}{c_j+d^{2}}`），在 DPI 200 下渲染，加 12 像素白边后每张图约 70 到 80 像素高、90 到 111 像素宽，再用 3 种边长 × 4 种处理缩放。下面摘 32 和 64 两档，每格是 3 个公式的均值（本项目观察，在 RTX 4090（租用）上运行，但这部分与 GPU 无关；`mechanisms/pixels.json`）：

| 边长 | 方法 | 几何 | 墨迹召回 | 分式线二值保留 | 分式线连续墨迹 |
|---|---|---|---|---|---|
| 32 | 最近邻 | 拉伸 | 0.458 | 0.333 | 0.325 |
| 32 | 双线性 | 拉伸 | 0.410 | 0.333 | 0.448 |
| 32 | 面积 | 拉伸 | 0.234 | 0.000 | 0.346 |
| 32 | 双线性 | letterbox | 0.317 | 0.000 | 0.096 |
| 64 | 最近邻 | 拉伸 | 0.793 | 0.992 | 0.807 |
| 64 | 双线性 | 拉伸 | 0.777 | 0.667 | 0.721 |
| 64 | 面积 | 拉伸 | 0.756 | 0.667 | 0.674 |
| 64 | 双线性 | letterbox | 0.715 | 0.333 | 0.489 |

怎么读这几列：处理后的图先去掉留白、再放回原图坐标，然后和原图逐像素比较。"墨迹召回"是原图深色像素里仍是深色（< 0.5）的比例；"分式线二值保留"只看分式线那一行；"连续墨迹"是那一行平均还剩多少黑，不做阈值。

三点观察：

1. **面积缩放的二值指标最差，连续指标却不差。** 32 边长时面积缩放的分式线二值保留是 0，连续墨迹 0.346，比最近邻的 0.325 还高。这就是 27.3.3 节说的线还在、但变淡了：墨水在，只是没深到过阈值。
2. **相位决定成败。** 逐条看原始记录：64 边长、双线性拉伸时，第二个公式的分式线二值保留是 0，另外两个都是 1（本项目观察，`pixels.json` 逐条记录）。同一种方法，换一张图就翻转。
3. **加号会变成减号。** 在 `resizing.png` 里，32 边长的最近邻和双线性把 `1+x^{n+1}` 的加号竖笔吃掉了，看起来像减号（本项目观察，`mechanisms/resizing.png`）。对 OCR 来说，这已经换了一个符号。

两个提醒：只有 3 个公式，不能据此给方法排名；128 边长那一档对这三张图其实是**放大**（原图最长边不到 128），所以那一档几乎所有方法都接近满分，不说明缩小时的情况。

### 27.3.7 常见错误

- **以为双线性自带抗锯齿。** PyTorch 的 `F.interpolate(mode="bilinear")` 默认 `antialias=False`，大比例缩小时只看两个邻居。PIL 的 `BILINEAR` 在缩小时会把滤波范围按比例放宽，做的就是 27.3.3 节末尾那种抗锯齿。同样叫双线性，结果不同（27.10 节）。
- **用二值阈值判断线还在不在。** 面积缩放的线常常是浅灰。只看二值指标会冤枉它，只看连续指标又会忽略模型可能认不出浅灰线这一点。两个都看。
- **对一张图下结论。** 相位依赖意味着单张图的结果很偶然。至少换几个位置、几张图再说。

## 27.4 几何：拉伸，还是 letterbox

### 27.4.1 公式是长条

很多视觉模型或者预处理流程要求正方形输入。可公式图大多是**长条**：原图验证集 200 张图的宽高比中位数是 4.8，最宽的一张达到 22.8（本项目观察，按 `data/` 中的图片尺寸统计）。

把长条塞进正方形，有两种办法：

- **拉伸（square）**：高、宽各自缩放到目标边长。不浪费画布，但字被压扁或拉高。
- **letterbox**：保持长宽比，按最长边缩放，剩下的地方补白。字形不变，但内容只占画布的一小条。

名字来自电影：宽银幕电影在 4:3 电视上播放时，上下补黑边，像信封的样子。

### 27.4.2 手算：298×32 的公式放进 128×128

就用本章开头那张图，高 32、宽 298，目标边长 128。

**拉伸：** 高从 32 放大到 128（× 4），宽从 298 缩小到 128（× 0.43）。每个字符被横向压到原来不到一半，纵向拉高 4 倍。

**letterbox：**

```text
scale = 128 / max(32, 298) = 128 / 298 ≈ 0.4295
新高 rh = round(32 × 0.4295) = round(13.74) = 14
新宽 rw = round(298 × 0.4295) = 128
上留白 top = (128 − 14) // 2 = 57
下留白 = 128 − 57 − 14 = 57
```

（数学结论；和逐条输出里记录的 `resized_hw = [14, 128]`、`top = 57` 一致，本项目观察。）

整张 128×128 的画布里，只有 14 行是公式。原来 32 像素高的一行字，现在 14 像素高；而上标 `q+1` 本来就只有字高的一半左右，现在大约只剩 6 到 7 个像素（这一句是估算，待验证）。

最后一步为什么要取整：像素只能是整数行、整数列，13.74 行没法存，所以要四舍五入到 14。取整让实际比例和 scale 略有出入，这里纵向实际缩到原来的 14 / 32 = 0.4375 倍，比 0.4295 稍大（数学结论）。留白也一样，补边要放整数行，`(128 − 14) // 2` 正好整除；不能整除时多出的那一行放在哪边，27.4.3 节的代码有约定。

同一张图放进 384×384：scale = 384 / 298 ≈ 1.289，新高 round(41.2) = 41，新宽 384（数学结论）。这次是**放大**，字从 32 像素长到 41 像素。

### 27.4.3 对照代码：`transform_image`

练习 27.4：

```python
def transform_image(image, side, method="bilinear", geometry="letterbox", device="cpu"):
    x = image_to_chw(image, device)                                   # ① (3, H, W)
    h, w = x.shape[1:]
    scale = side/max(h, w)                                            # ② 按最长边算比例
    rh, rw = ((max(1, round(h*scale)), max(1, round(w*scale)))
              if geometry == "letterbox" else (side, side))           # ③ letterbox 保比例，square 直接拉
    small = resize_chw(x, (rh, rw), method)                           # ④ 真正的缩放只发生在这里
    top, left = (side-rh)//2, (side-rw)//2                            # ⑤ 奇数留白：多出的 1 行留在下/右
    canvas = x.new_ones((3, side, side))                              # ⑥ 白色画布（值 1）
    canvas[:, top:top+rh, left:left+rw] = small                       # ⑦ 贴到中间
    return chw_to_image(canvas), dict(original_hw=[h, w], resized_hw=[rh, rw], top=top, left=left, ...)
```

- ③ 里的 `max(1, …)` 防止极扁的图被算成 0 行。
- ⑤ 用整数除法，`(side − rh)` 是奇数时上面少一行、下面多一行。测试 `test_letterbox_padding_and_identity_metric` 专门造了一张 7×2 的图放进 10×10：rh = round(2 × 10/7) = round(2.86) = 3，top = (10 − 3) // 2 = 3，下面留 4 行。
- ⑥ 画布是**白色**。公式图是白底黑字，补黑边会凭空多出两大块墨迹。
- 返回的元数据 `meta` 记下了怎么变换的。度量时用 `restore_coordinates` 去掉留白、放回原坐标，才能和原图逐像素比较。这一步只统一坐标，**不能恢复丢掉的信息**。

### 27.4.4 宽公式的代价：内容只占画布的一小块

letterbox 保住了字形，代价是画布大部分是白纸。对长条公式，这个代价很大。

我们按逐条记录重新数了一遍（本项目观察，由 `original/qwen35_val_original_letterbox*.jsonl` 的 `transform` 字段重新计算，n=200）：

| 原图验证集 | letterbox128 | letterbox384 |
|---|---|---|
| 缩放比例中位数 | 0.40（缩小） | 1.20（放大） |
| 被放大的图占比 | 3.5% | 66% |
| 缩放后公式高度中位数 | 27 像素 | 80 像素 |
| 缩放后公式高度 ≤ 16 像素的图 | 37 张（18.5%） | 0 张 |
| 公式区域面积 ÷ 1024（约合多少个视觉 token 落在公式上） | 平均 3.8 | 平均 33.8 |

最后一行的意思：Qwen 一个视觉 token 管 32×32 = 1024 像素。letterbox128 的画布一共 16 个 token，平均只有不到 4 个 token 的面积盖在公式上，其余全是白纸。

> **停下来想一想：** 拉伸不浪费画布，letterbox 不变形。对一张宽高比 10:1 的公式，你更愿意要每个字被压扁到十分之一宽，还是整个公式只占画布十分之一高？有没有第三种办法？

### 27.4.5 常见错误

- **用黑色补边。** 白底公式补黑边，模型会以为图上有两条粗黑框。
- **以为 letterbox 没有损失。** 字形没变，字却变小了。长公式在正方形里尤其吃亏。
- **丢掉变换元数据。** 不记 `top`、`left`、`resized_hw`，之后就没法把模型的注意力、框或者像素差异对回原图。

## 27.5 形状没问题，识别率却下降

这一节回答本章开头的问题。先看整体数字，再拆原因。

### 27.5.1 现象

Qwen3.5-0.8B 在原图验证集上，五种预处理的结果（本项目观察，RTX 4090（租用），bf16，n=200，`original/qwen35_val_original_*.json`）：

| 配置 | 送进 processor 的尺寸 | 视觉 token | EM | CER | 达到 128 上限的条数 |
|---|---|---|---|---|---|
| native | 原尺寸 | 平均 23.1（2 到 96） | 0.035 | 0.306 | 57 |
| nearest128 | 128×128 | 16 | 0.000 | 1.045 | 127 |
| bilinear128 | 128×128 | 16 | 0.010 | 0.800 | 94 |
| area128 | 128×128 | 16 | 0.010 | 0.766 | 88 |
| letterbox128 | 128×128 | 16 | 0.015 | 0.844 | 102 |

EM 是抽取答案、规范化之后的完全匹配率；CER 是**语料级**字符错误率：所有样本的编辑距离之和 ÷ 所有参考答案的字符数之和。

四种 128 配置的张量形状完全一样，都是合法的 128×128 RGB 图，processor 也都顺利切出 8×8 个 patch。可 CER 是 native 的 2.5 到 3.4 倍，达到生成上限的条数从 57 条增加到 88 到 127 条（本项目观察，同上）。

逐条对比：native 答对、letterbox128 答错的有 4 条；反过来 native 答错、letterbox128 答对的，0 条（本项目观察，按两份 JSONL 的 `score.em_norm` 逐条重新计数）。

为什么？至少有四个原因叠在一起。

### 27.5.2 原因一：信息丢在缩小的那一刻

27.3 节的手算已经说明，缩小时细线可能整条消失，或者变成浅灰。这一步丢掉的东西，后面**任何**放大都找不回来。放大只能在已有像素之间插值，猜不出被抹掉的笔画。

SmolVLM-256M 是一个现成的例子。按本地 transformers 5.19.0 的源码，本实验配置下（关闭图片分块），它的 processor 先把图按最长边缩放到 512，再缩放成 512×512 的正方形，插值用 LANCZOS（结果 JSON 里记录的 `resample = 1`）。所以 SmolVLM 看到的永远是 `[3, 512, 512]`，永远是 64 个视觉 token（本项目观察，`batch_pixel_values_shape` 与 `visual_tokens` 字段）。

形状和 token 数完全不变，变的只是这 512×512 是从多少原始信息放大来的。结果（本项目观察，RTX 4090（租用），bf16，n=200，`original/smol_val_original_*.json`）：

| SmolVLM-256M，原图验证集 | 视觉 token | CER | 达到上限的条数 |
|---|---|---|---|
| native | 64 | 1.046 | 87 |
| letterbox384 | 64 | 1.113 | 122 |
| letterbox128 | 64 | 1.381 | 162 |

SmolVLM 在这个任务上基本不会转写公式，EM 全部不超过 0.005，CER 全部大于 1，它的绝对成绩不能说明什么。但在 **token 数固定**的前提下，先缩到 128 的那一版明显更糟，方向和 Qwen 一致。受控验证集上也是这个方向：letterbox128 的 CER 1.702，letterbox384 是 1.294（本项目观察，n=200，`rendered/smol_val_rendered_*.json`）。

### 27.5.3 原因二：processor 还会再动一次

你在外面做的缩放不是最后一次。processor 还有自己的缩放规则。

Qwen 的 `smart_resize`（第 26 章）把高、宽调到 32 的倍数，并把面积限制在 `[min_pixels, max_pixels]` 之间。第 26 章用的是 `min_pixels = 65536`；本章的 lab 把它改成了 1024（结果 JSON 里 `size.shortest_edge = 1024`）。为什么？

算一下：一张 128×128 的图面积 16384，小于 65536。如果用第 26 章的设置，`smart_resize` 会把它放大约 2 倍到 256×256，变成 8×8 = 64 个视觉 token（数学结论）。那样一来，128 配置就和 256 配置分不清了，还多了一次你没打算做的插值。改成 1024 以后，128×128 原样保留，16 个视觉 token；384×384 也原样保留，12×12 = 144 个（数学结论，和逐条记录的 `grid = [1, 8, 8]`、`[1, 24, 24]` 一致，本项目观察）。

所以要看 processor 之后的形状，不要看你送进去的形状。本章开头那张图在 native 配置下，送进去是 32×298，processor 之后是 32×288，网格 2×18，只有 9 个视觉 token（数学结论，与记录一致）。手算一遍 `smart_resize`：高 32 ÷ 32 = 1，取整还是 1，乘回 32 得 32；宽 298 ÷ 32 = 9.3125，四舍五入成 9，乘回 32 得 288。面积 32 × 288 = 9216，落在 [1024, 262144] 之间，不用再放大或缩小。最后按 16×16 切 patch，得到 2×18 的网格，2×2 合并后是 1×9 = 9 个视觉 token。所以即使你选了不缩放，processor 也把宽度从 298 缩到了 288。

### 27.5.4 原因三：看起来不像训练时的图

nearest128 在像素指标上并不差：受控验证集上它的墨迹召回 0.693，比 area128 的 0.590 还高；可它的 CER 是 0.948，area128 是 0.754（本项目观察，n=200，`rendered/qwen35_val_rendered_*.json` 的 `pixel_metrics_mean` 与 `metrics`）。

像素保留得多，识别反而更差。一个合理的解释是：最近邻产生锯齿状、断断续续的笔画，这种图很少出现在模型的预训练数据里；模型认的是这像不像它见过的字，光是像素保留得多还不够（这是推断，待验证）。

### 27.5.5 原因四：错误会被生成过程放大

一旦模型看不清，它不会说看不清，它会**编**。本章开头那张图在 nearest128 下陷入 `\scriptsize { \scriptsize { …` 的重复，一直写到 128 个 token 的上限，编辑距离 320，是参考长度 71 的 4.5 倍（本项目观察）。

CER 能大于 1，原因就在这里：编辑距离可以超过参考长度。128 配置达到上限的条数暴涨，也可以这样理解：缩放造成的视觉损失，经过自回归生成，放大成一长串错误。

### 27.5.6 一张诊断清单

遇到形状对、成绩差，按这个顺序查：

1. **processor 之后**的 `pixel_values` 形状和视觉 token 数（本章 lab 的逐条输出都记了）。
2. 把缩放后的图存下来，**用眼睛看**。分式线、加号、上下标还在吗？
3. 缩放后公式本身有多少像素高，而不只是画布多大。
4. 达到生成上限的条数、平均输出长度。暴涨说明模型在编。
5. 像素指标和识别指标对照看。它们方向可以不一致（27.5.4 节）。

## 27.6 分辨率与小字：一个混杂的对照

### 27.6.1 结果

把 Qwen 的 letterbox384 也放进来（本项目观察，RTX 4090（租用），bf16，n=200）：

| Qwen3.5-0.8B | 视觉 token | 原图 EM | 原图 CER | 受控 EM | 受控 CER |
|---|---|---|---|---|---|
| native | 原图 23.1 / 受控 36.3（平均） | 0.035 | 0.306 | 0.105 | 0.160 |
| letterbox128 | 16 | 0.015 | 0.844 | 0.015 | 0.930 |
| letterbox384 | 144 | 0.060 | 0.292 | 0.095 | 0.225 |

（文件：`original/` 和 `rendered/` 下的 `qwen35_val_*_{native,letterbox128,letterbox384}.json`。）

从 128 到 384，原图 CER 从 0.844 降到 0.292。很容易得出结论：分辨率越高越好，小字需要大图。这个结论下得太快了，下一节看为什么。

### 27.6.2 混杂：一次改了好几样东西

从 letterbox128 换到 letterbox384，至少同时变了三样东西：

1. **公式上的像素**：缩放后公式高度中位数从 27 像素变成 80 像素（27.4.4 节）。
2. **视觉 token 总数**：从 16 变成 144，是 9 倍（数学结论）。语言模型能看的视觉位置多出 128 个。
3. **缩小还是放大**：128 几乎全是缩小，384 有 66% 是放大（27.4.4 节）。缩小时几个旧像素并成一个，细线可能丢掉；放大不会把像素并掉，但插值和取整到 `uint8`（27.1.5 节）仍会改变细节。

这三样一起变，收益就**不能只归因于分辨率**。也许起作用的是 token 预算：模型有更多位置来存放视觉信息。也许是像素。也许两者都有。这叫**混杂**：两个可能的原因被捆在一起，一个对照实验分不开它们。

### 27.6.3 拆开看的线索

现有数据不能完全拆开，但有几条线索指向同一个方向。它们都只是**一致**，不是证明。

**线索一：token 数差不多，结果差很多。** native 平均 23.1 个 token，128 配置是 16 个，同一个量级；可 CER 是 0.306 对 0.77 到 1.05（原图，本项目观察）。差别主要不在 token 数。

**线索二：token 数固定，像素少的更差。** SmolVLM 固定 64 个 token，letterbox128 仍然最差（27.5.2 节）。

**线索三：盖在公式上的 token 面积。** 用 27.4.4 节的口径算，原图验证集上 letterbox384 平均约 33.8 个 token 的面积落在公式上，native 是 23.1；受控验证集的图更大，letterbox384 对其中 68% 的图是缩小，只有约 25.7，native 是 36.3（本项目观察，按逐条记录重新计算）。而成绩恰好是：原图上 letterbox384 好于 native，受控图上 native 好于 letterbox384。这两组里，都是盖在公式上的面积大的那个成绩好。

**线索四：小字的那 37 张图。** letterbox128 下公式高度 ≤ 16 像素的 37 张原图，EM 0、CER 1.050；同样这 37 张，letterbox384 下 CER 0.205，native 下 0.249（本项目观察，按逐条记录重新计数）。这些图本身并不特别难，是缩得太小才读不出来。

### 27.6.4 还缺什么实验

要真正分开像素和 token 的作用，需要固定一个、只变另一个。例如：

- 先把公式区域裁出来，去掉大部分留白，再在**相同的 token 预算**下比较不同的源分辨率。
- 或者想办法固定模型看到的像素、只改 token 数。注意，单纯改 `max_pixels` **做不到**这一点：`smart_resize` 会真的把图缩放到新网格。例如 384×384 的图在 `min_pixels = 1024` 下，`max_pixels = 262144` 时保持 384×384、144 个 token，改成 16384 就被缩成 128×128、16 个 token，像素也跟着变了（数学结论，按本地 transformers 5.19.0 的 `smart_resize` 复算）。要真正固定像素，得动 patch 合并或 token 选择这类模型内部环节（待验证）。

这些本章没有做，结论只能写成：本章观察与"公式上的有效像素是主因"一致，待验证。这是 R3 预处理对照里很值得做的一项（27.8 节）。

### 27.6.5 冻结与测试集

lab 只看原图验证集来选设置，规则是 EM 高优先、再看 CER 低、再看视觉 token 少。两个模型、六种配置里，选中的是 Qwen3.5-0.8B + letterbox384（本项目观察，`freeze/frozen.json`）。

冻结以后，在 100 张原图测试集上评一次（本项目观察，RTX 4090（租用），bf16，n=100，`final/qwen35_test_original_letterbox384.json`）：

| 指标 | 值 | 95% 区间（按公式 bootstrap，2000 次，seed 0） |
|---|---|---|
| EM（规范化） | 0.050 | [0.010, 0.100] |
| CER | 0.353 | [0.284, 0.412] |
| 达到 128 上限 | 30 / 100 | 不适用 |

两点要注意。第一，EM 区间从 1% 到 10%，100 张图太少，只能说很低。第二，按本书的测试集规则（第 0 章 0.10.1 节），这里只报数字，开发期间**不看错例**，也不能因为这个数字回头换配置；最终报告定稿以后，才可以解封做错例分析。验证集 EM 0.060、测试集 0.050，同一个量级，没有迹象表明选择过拟合了验证集，但样本太少，说不了更多。

还要说清楚：0.8B 的小模型零样本只有 5% 左右的完全匹配。这里的 EM 用的也是第 18 章的 `extract_formula`，它会删掉句末标点，误伤本来以标点结尾的答案（第 26 章 26.7.3 节）。本章没有换规则重算，所以这个绝对值可能偏低，偏多少不知道。第 33 章会做 LoRA 微调，但它有自己的零样本基线（生成上限 256 token、逐张评测），这里的数字不要和它直接比。

## 27.7 颜色空间与数据增强（概括）

这两件事本章不做实验，列一张表记住边界就够了。

| 项目 | 做了什么 | 对公式 OCR 要记住的 |
|---|---|---|
| RGB / BGR | 交换通道顺序 | 必须和 processor 一致；OpenCV 默认 BGR |
| 灰度 | 三通道合成一个 | 黑白公式可以用，但模型若要三通道，要复制回 3 份 |
| sRGB / 线性 RGB | 非线性编码换算 | 本章直接在 sRGB 编码值上插值，没有实验线性光域 |
| 透明通道 | RGBA → RGB | 先贴白底，再丢透明度（27.1.5 节） |
| 亮度、对比度 | 改像素强弱 | 会改变浅灰细线是否过阈值 |
| 噪声、模糊 | 模拟拍摄和扫描 | 更难不等于更像真实数据 |
| 裁剪、旋转、透视 | 几何变形 | 可能裁掉上下标，或者改变题意 |
| 颜色抖动 | 随机扰动各通道 | 对单色公式图不一定有意义 |

数据增强是训练时的手段。本章所有实验都是零样本推理，没有训练（训练步数 0，本项目观察）。后面训练模型的章节会用到其中几项。

## 27.9 常见错误

换轴、`/255`、BGR 见 27.1.7 节；`mean` 忘了 `[:, None, None]` 见 27.2.4 节，归一化或 rescale 做两次见 27.2.5 节；双线性抗锯齿、二值阈值见 27.3.7 节；补黑边、丢元数据见 27.4.5 节。下面几条前面没有单列：

| 错误 | 现象 | 怎样发现 |
|---|---|---|
| 只看自己送进去的尺寸 | 以为改了分辨率，其实 processor 又缩放了一次 | 记录 processor 后的网格和视觉 token 数 |

## 27.10 和真实框架的对应

以下按本地安装的源码核对：Pillow 12.3.0、transformers 5.19.0、PyTorch 2.14.1；远程 GPU 环境的 Pillow 是 10.2.0，transformers 同为 5.19.0。本地没有安装 torchvision。

**PIL 的 `Image.resize(size, resample=None, box=None, reducing_gap=None)`。** `resample` 可选 `NEAREST`、`BOX`、`BILINEAR`、`HAMMING`、`BICUBIC`、`LANCZOS`。不指定时，普通 RGB 图默认 `BICUBIC`（"1" 和 "P" 模式的图默认 `NEAREST`）。整数编码是 NEAREST = 0、LANCZOS = 1、BILINEAR = 2、BICUBIC = 3、BOX = 4、HAMMING = 5，所以结果 JSON 里 Qwen 的 `resample: 3` 是 BICUBIC，SmolVLM 的 `resample: 1` 是 LANCZOS。

PIL 缩小时会按比例放宽滤波器，所以它的 `BILINEAR` 和 PyTorch 不抗锯齿的 bilinear 不是一回事。拿 27.3.3 节的 8×8 线图（线在第 3 行）缩到 2×2，本地 CPU 上的结果（本项目观察，Pillow 12.3.0、PyTorch 2.14.1）：

| 实现 | 第 0 行 | 第 1 行 |
|---|---|---|
| 本章 `resize_chw` bilinear（= `F.interpolate`，不抗锯齿） | 1.00 | 1.00 |
| `F.interpolate(..., antialias=True)` | 0.82 | 0.89 |
| PIL `BILINEAR` | 0.82 | 0.89 |
| PIL `BOX` | 0.75 | 1.00 |
| 本章 `resize_chw` area | 0.75 | 1.00 |

PyTorch 文档说 `antialias=True` 配合 `align_corners=False` 时，缩小结果与 Pillow 一致。这个例子上确实接近：PyTorch 是 0.8214、0.8929，PIL 是 209/255 ≈ 0.8196、228/255 ≈ 0.8941，保留两位小数相同，剩下的差别来自 PIL 在 `uint8` 上取整（本项目观察，本地 CPU）。

PIL 的 `BOX` 在这个整数比例（8 → 2）上和本章的面积缩放结果相同，但两者**不是同一个算法**。非整数比例时就分开了：把一行 `[0, 0, 255]` 从 3 个像素缩成 2 个，PIL `BOX` 得到 `[0, 255]`，归一化后是 `[0, 1]`；本章按覆盖长度积分得到 `[0, 2/3]`（27.3.4 节，测试 `test_fractional_area_is_coverage_not_adaptive_pool`）（本项目观察，Pillow 12.3.0，本地 CPU）。换一个库，同名的缩放方法结果就可能不同，所以复现别人的预处理时，要连库和版本一起抄。

**PyTorch 的 `torch.nn.functional.interpolate`。** `mode` 可选 `nearest`、`nearest-exact`、`bilinear`、`bicubic`、`area` 等；`align_corners` 只对线性类插值有意义，本章用 `False`（像素中心约定）；`antialias` 默认 `False`，只支持 `bilinear`、`bicubic`、`lanczos`。文档还特别说明，老的 `nearest` 模式和 OpenCV 的 `INTER_NEAREST` 一样有已知问题，`nearest-exact` 才和 PIL、scikit-image 的最近邻一致。它的 `area` 模式内部是自适应平均池化，非整数比例时和本章按重叠长度加权的面积缩放不完全相同（27.3.4 节）。

**transformers 的 image processor。** 处理一张图的固定流水线是：`do_convert_rgb` → `do_resize`（配合 `size`、`resample`）→ `do_rescale`（乘 `rescale_factor`，即 1/255）→ `do_normalize`（`image_mean`、`image_std`）→ 各模型自己的切块。本章 Qwen 的 `Qwen2VLImageProcessor` 正是这个顺序：resize、rescale、normalize、patchify。三个开关都可以单独关掉。如果你已经自己做过某一步，就把对应开关设成 `False`，避免做两遍。

两个模型各自的特殊之处：

- **Qwen（`Qwen2VLImageProcessor`）**：`size = {"shortest_edge": …, "longest_edge": …}`，这两个数是 `smart_resize` 的最小、最大**面积**，不是边长。本章设为 1024 和 262144。
- **SmolVLM（`Idefics3ImageProcessor`）**：`do_image_splitting=False` 时，先按 `size["longest_edge"]` 等比例缩放，再缩放成 `max_image_size["longest_edge"]` 的正方形。本章两者都是 512，所以任何输入最后都是 512×512 的拉伸图。

**torchvision。** `torchvision.transforms.v2.Resize` 也有 `interpolation` 和 `antialias` 参数，`Normalize` 做逐通道归一化。本地没有安装，具体默认值待验证。

## 27.11 小结

图片文件解码、统一成 RGB 后是 `uint8` 的 `HWC` 数组，进模型的第一步是换成 `CHW`，要用 `permute`，`reshape` 形状对但内容错。缩小时，最近邻和不抗锯齿的双线性在抽样，细线会随相位整条消失；抗锯齿把双线性的三角形权重按缩放比例放宽，面积缩放按覆盖长度平均，两者都让细线留下来，但变成浅灰。归一化只是对齐预训练的刻度，不增减信息，但必须一致。形状对、成绩差，是几个原因叠在一起：信息在缩小时已经丢了，processor 可能再缩放一次，图可能不像训练时见过的样子（这一条是推断），生成时的胡编又把错误放大。本章 128 → 384 的提升同时改变了像素和视觉 token 数，现有线索指向公式上的有效像素，但要单独的对照实验才能确认。验证集上选中的 Qwen3.5-0.8B + letterbox384，在 100 张测试图上 EM 0.050、CER 0.353（本项目观察）。

复习时抓住下面几条：

- **布局**：`HWC → CHW` 用 `permute(2, 0, 1)`，再 `.contiguous()`；连续的 `(C, H, W)` 张量 stride 是 `(H·W, W, 1)`。批量化用 `torch.stack` 要求每张图同形状，否则就像 Qwen 那样把 patch 摊平拼接，另记每张图的网格。
- **归一化**：`z = (x − mean[c]) / std[c]`，逆变换 `x = z·std + mean`。mean、std 要先变成 `(3, 1, 1)` 才对齐通道轴。`x` 先按 `/255` 到 [0, 1]，这一步和 processor 的 rescale 只能做一次。
- **缩放的坐标**：比例 `s = in / out`，目标第 j 个像素中心对应源坐标 `(j + 0.5)·s`。最近邻取 `floor((j + 0.5)·s)`；双线性用 `u = (j + 0.5)·s − 0.5`，在相邻两个源像素间按 `1 − |u − i|` 加权；抗锯齿把权重换成 `max(0, 1 − |u − i| / s)` 再归一；面积按区间 `[j·s, (j + 1)·s)` 的重叠长度 ÷ s 加权，每行和为 1。这里的 `/ s` 只在缩小（s > 1）时才放宽；放大时双线性照常只看两个邻居。
- **letterbox**：`scale = side / max(H, W)`，新尺寸 `round(H·scale)`、`round(W·scale)`（至少 1），上、左留白 `(side − 新尺寸) // 2`，奇数时多的一行留在下、右，画布用白色。
- **Qwen 的 processor**：`smart_resize` 先把高、宽四舍五入到 32 的倍数，面积超出 `[min_pixels, max_pixels]` 再整体缩放，视觉 token 数 = 高 × 宽 / 1024。看 processor 之后的形状，不看自己送进去的。
- **最常见的错误**：用 `reshape` 换轴；归一化或 rescale 做两次；把 128 → 384 的收益全记在分辨率头上，忽略同时变了的视觉 token 数。
