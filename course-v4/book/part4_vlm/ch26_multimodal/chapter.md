前三部分里，模型只和文字打交道：输入是 token，输出也是 token。可公式识别的输入是一张**图片**。一张图在电脑里是一大块像素，不是 token。模型怎样读它？

## 本章导读

先看一个小实验。把一张写着 x² + y² = z² 的图片交给 Qwen3.5-0.8B（一个约 8.5 亿参数的 VLM；本项目观察：实测参数 852,985,920），提示它"把图里的公式转成 LaTeX，只输出公式，不要 markdown"。它的回答是：

```text
 $$x ^ { 2 } + y ^ { 2 } = z ^ { 2 }$$
```

（本项目观察：RTX 4090（租用），bf16，greedy 解码，n=1，lab 第 3 部分。）

内容对了。但仔细看，这一行里藏着好几个问题：

- 模型是怎样把 160×63 像素的图读进去的？读成了多少个 token？（**表示**）
- 它写 `^ { 2 }` 的时候，看的是图上的哪一块？（**对齐**）
- 它只是照抄，还是理解了这是勾股定理？如果图上写错了，它会不会自作主张改对？（**推理**）
- 我们明明说了"不要 markdown"，它为什么还加了 `$$`？（**生成**）
- 这张干净的渲染图认对了，换成论文里截下来的真实公式还行吗？（**迁移**）
- 参考答案是 `x^2+y^2=z^2`，逐字比较它是错的，抽出 `$$` 里的公式、按项目规则规范化后再比较又是对的。到底算对还是算错？（**量化评估**）

这六个词就是卡内基梅隆大学多模态机器学习课程（CMU 11-777）总结的**六个核心问题**。本章不教新算法，只画一张地图：每个问题是什么，在公式识别里长什么样，后面哪一章去解决它。

本章还要讲清楚一件结构上的事。一个 VLM 由三部分组成：视觉编码器把图变成一串向量，连接器把这些向量改成语言模型能接收的宽度，语言模型负责写出文字。视觉 token 和语言模型的连接主要有**两种方式**，我们会用两段很短的代码，把形状一个轴一个轴地对清楚。

> **回顾：注意力与三种结构（第 8 章、第 9 章 9.7 节）**

> - 注意力 = 软查找：查询 Q 和每个键 K 算相似度，softmax 成权重，再对值 V 加权平均。

> - 输出长度跟着查询走：查询有 T 个，输出就有 T 个。
> - Encoder 双向可见；Decoder 因果可见（下三角 mask）；Encoder-Decoder 的 Decoder 用交叉注意力回看 Encoder 的输出。

## 26.1 什么是多模态

### 26.1.1 模态：信息的载体

**模态**（modality）是信息被记录和表达的方式。文字是一种模态，图片是一种，声音是一种，视频又是一种。**多模态**就是同时处理两种以上的模态。

为什么要把多模态单独拿出来研究？因为不同模态长得太不一样了。CMU 的综述把这叫**异质性**（heterogeneity）。拿公式来说：

| | 图片 | LaTeX 文字 |
|---|---|---|
| 基本单位 | 像素，0 到 255 的整数 | token，词表里的编号 |
| 结构 | 二维网格，有上下左右 | 一维序列，只有前后 |
| 一个 `²` 占多少 | 几十个像素 | `^ { 2 }` 四个 token，或 `^2` 两个 |
| 噪声长什么样 | 模糊、断线、压缩块 | 拼错命令、漏括号 |

公式识别（OCR）就是在两个差别这么大的世界之间搭桥：输入是二维的像素，输出是一维的 LaTeX。

从外面看，OCR 只是一个图片进、文字出的函数，为什么要拆成六个问题？打个比方。你请一位朋友帮你抄黑板上的公式。他要先**看清**黑板（表示），知道自己正在抄哪一块（对齐），明白分数线下面的东西都属于分母（推理），用你要的格式写下来（生成），换一块字迹潦草的黑板也能抄（迁移），最后你还得有办法判断他抄得对不对（量化评估）。每一步都可能出错，而且错法完全不同。

## 26.2 表示：图片怎样变成 token

### 26.2.1 语言模型只吃向量序列

你在第二部分写的 GPT，输入是一串 token 编号，经过嵌入层变成 `[T, d]` 的向量序列。语言模型的所有层都只认这种形状。

图片是 `[H, W, 3]` 的像素块。要让语言模型看图，第一步就是把它变成一串向量，每个向量的宽度和文字 token 的宽度一样。这一步叫**表示**（representation）：用什么样的向量来代表一种模态的信息。

### 26.2.2 把图剪成邮票

想象把一张图剪成很多张小邮票，每张 16×16 像素。每张邮票压成一个向量，就是一个视觉 token。剪得越细，邮票越多，细节保留得越好，但 token 也越多，计算越贵。

Qwen3.5 还多做一步：把相邻的 2×2 四张邮票再**合并**成一个 token。所以最后一个视觉 token 对应图上（缩放后）32×32 像素的一块。

把这几步串起来，就是一个 VLM 处理图片的整条路线，也是第 27 到 32 章要逐段拆开的东西：

1. **预处理**（processor）：把图缩放到合适的大小，切成 16×16 的 patch（第 27 章讲缩放，本节下面算一遍）。
2. **视觉编码器**（vision encoder）：一个 ViT，在 Qwen 的代码里是视觉塔 `model.visual` 中 merger 之前的部分。它先把每个 patch 压成一个向量，再让 patch 之间互相做注意力，每个向量里就带上了别处的信息。输入几个 patch，输出就是几个向量（第 29 章）。
3. **连接器**（connector）：Qwen 叫它 merger，代码里也放在视觉塔里面，把相邻 4 个 patch 的向量拼成一个，再用一个小 MLP 投影到语言模型的宽度。2×2 合并就发生在这里（第 32 章）。
4. **语言模型**：把这些向量当成 token 嵌入，和文字 token 排在同一个序列里往下算（26.8 节）。

这里有一个反直觉的地方：**token 数由图的面积决定，不由公式的复杂度决定。** 一张写着 `Q^2=H` 的图和一张写着长长矩阵的图，只要缩放后面积相近，视觉 token 数就差不多。模型不会因为公式难就多看几眼。

### 26.2.3 例子：图 1 变成 78 个 token

一步一步算图 1（宽 160、高 63）。Qwen 的 processor 先用 `smart_resize` 把图缩放到合适大小，再切块。规则（数学结论，代码在 `miniocr/models/vlm_anatomy.py` 的 `smart_resize`）：

1. 高、宽各自四舍五入到 32 的倍数（32 = patch 16 × 合并 2）。
2. 如果面积小于 `min_pixels`（本章设为 65536），整体放大，再向上取整到 32 的倍数；如果大于 `max_pixels`（262144），整体缩小，向下取整。

代入图 1：

| 步骤 | 计算 | 结果 |
|---|---|---|
| 四舍五入 | 高 63 → 64，宽 160 → 160 | 64×160 = 10240，小于 65536 |
| 放大倍数 | √(65536 / (63×160)) | ≈ 2.55 |
| 新高 | ⌈63 × 2.55 / 32⌉ × 32 = 6 × 32 | 192 |
| 新宽 | ⌈160 × 2.55 / 32⌉ × 32 = 13 × 32 | 416 |
| patch 网格 | 192/16 × 416/16 | 12 × 26 = 312 个 patch |
| 2×2 合并 | 312 / 4 | **78 个视觉 token** |

和实测完全一致：processor 给出的网格 `image_grid_thw` 是 `[1, 12, 26]`，视觉 token 数 78（本项目观察：RTX 4090（租用），`main/controlled.jsonl`）。三张图的结果：

| | 原图（宽×高） | 缩放后（宽×高） | 网格 | 视觉 token | 输入总 token | 生成 token |
|---|---|---|---|---|---|---|
| 图 1 | 160×63 | 416×192 | 12×26 | 78 | 114 | 25 |
| 图 2 | 97×73 | 320×224 | 14×20 | 70 | 106 | 27 |
| 图 3 | 163×95 | 352×224 | 14×22 | 77 | 113 | 37 |

缩放后尺寸由网格乘 16 得到（数学结论）；其余各列是本项目观察（RTX 4090（租用），bf16，n=3）。

注意两件事：

- **三张小图都被放大了两倍多。** 原图面积都不到 65536，触发了下限。放大不会凭空增加信息，只是让每个字符占更多的 patch。
- **输入总 token = 视觉 token + 36。** 那 36 个是聊天模板的特殊 token 和指令文字，每张图都一样（本项目观察：100 张验证图的 `non_image_input_tokens` 全是 36）。

再看 100 张真实验证图：视觉 token 在 65 到 90 之间，平均 75.65（本项目观察：RTX 4090（租用），n=100，`tokens.csv`）。用面积预算可以推出上下界：一个合并后的 token 占 32×32 = 1024 像素，所以 token 数至少 65536/1024 = 64，至多 262144/1024 = 256（数学结论）。这个范围对本章这组 65536/262144 的预算成立；`smart_resize` 放大时向上取整、缩小时向下取整，并不是严格的面积夹子，换一组预算就可能越出范围，即使两个预算同样相差 4 倍（第 32 章 32.2.3 节）。真实图片都很小，全都落在下限附近。

### 26.2.4 对照代码：数 token 的断言

`tour.py` 的 `predict` 里有这样两行（lab 第 3 部分）：

```python
visual_tokens = int(inputs["image_grid_thw"].prod().item()) // processor.image_processor.merge_size**2
expanded = int((inputs["input_ids"] == image_id).sum().item())
if visual_tokens != expanded:
    raise AssertionError("grid 合并计数应等于输入中的视觉占位 token 数")
```

第一行是我们刚才手算的公式：网格 1×12×26 = 312，除以 merge_size² = 4，得 78。第二行去 `input_ids` 里数图片占位符 `<|image_pad|>` 实际出现了几次。两个数必须相等，否则就是 processor 和你的理解不一致。三张图加 100 张验证图，这个断言一次都没有触发。

这个断言也透露了 Qwen3.5 怎样把图片放进序列。看实际的提示词（本项目观察：`main/controlled.jsonl` 的 `prompt` 字段）：

```text
<|im_start|>user
<|vision_start|><|image_pad|><|vision_end|>Transcribe the mathematical formula ... <|im_end|>
<|im_start|>assistant
<think>

</think>
```

模板里只写了**一个** `<|image_pad|>`。processor 把它展开成 78 个，之后模型再把这 78 个位置的嵌入替换成视觉编码器算出的向量。也就是说，Qwen3.5 走的是 26.8 节要讲的第一类结构：视觉 token 直接排进文字序列。

### 26.2.5 常见误解

- **"公式越复杂，视觉 token 越多。"** 不对。token 数只看缩放后的面积。tokens.png 把 100 张图的视觉 token 数和生成 token 数画在一起：视觉 token 挤在 65 到 90，生成 token 从 13 到 256 都有，两者看不出明显关系（本项目观察）。
- **"放大图片就能看清小字。"** 放大只是插值，原图上糊成一团的下标，放大后还是一团。能否看清，取决于原图分辨率和 patch 的大小关系。第 27 章专门讨论缩放，第 29 章讨论 patch 大小。
- **"一个 token 对应一个字符。"** 不对。一个视觉 token 管 32×32 的一块，可能盖住半个字符，也可能盖住一个上标加旁边的空白。长条形公式更明显：一张 578×36 的验证图被缩放成 1056×64，只有 2 行合并 token（4 行 patch，网格 4×66）。一个上标和它的底数，很可能挤在同一行 token 里。

## 26.3 对齐：图上哪一块对应哪个 token

### 26.3.1 什么是对齐

模型输出 `x ^ { 2 }` 里的 `2` 时，看的应该是图上 x 右上角那个小 2。一种模态的某一部分和另一种模态的某一部分互相对应，这种关系叫**对齐**（alignment）。

对齐对 OCR 是命根子。抄公式的人一旦抄串了，比如把分母的内容写进分子，或者把下标挂到错误的符号上，输出就全乱了。

### 26.3.2 一个真实的对齐错误

验证集第 41 张图（本项目观察：RTX 4090（租用），`main/val.jsonl` 第 41 行，从 0 数起）：

```text
参考：\nabla_{(i}\xi_{j)a} = 0 ,
输出：\nabla _ { ( i \xi _ { j } ) _ { a } } = 0
```

图上是 ∇ 带一个下标 `(i`，ξ 带一个下标 `j)a`。这是物理里常见的"对称化下标"写法，括号跨了两个符号。模型把 `\xi` 整个塞进了 ∇ 的下标里，又把 `a` 挂成了第二层下标。

每个字符它都认出来了：∇、(、i、ξ、j、)、a 一个不少。错的是**位置关系**：哪个字符属于哪个符号的下标。这属于对齐错误。

### 26.3.3 怎样才能看见对齐

最直接的想法是把注意力权重画出来，看模型在看哪里。

先泼一盆冷水。lab 第 2 部分的 `shapes.png` 右图画了一张交叉注意力权重的热图，标题特意写着 "Random cross-attention, NOT alignment"。那张图的输入是随机张量，权重也是随机初始化的，它五颜六色、有深有浅，看上去很像模型在关注某些区域，但它**什么也没学过**。

所以，一张注意力热图本身证明不了对齐。要证明"输出 `2` 时看的是右上角"，需要做干预实验，比如把右上角那块遮住，看 `2` 会不会消失。第 31 章做了遮挡实验，不过遮的是画布中央一整片，看的是整体分数。那一章还会介绍 saliency map（显著图）：对某个输出 token，求它的 log 概率对输入像素的梯度。saliency 本身不是干预，只描述局部的敏感程度，亮区要靠遮挡去核实。

另一条路是**直接训练对齐**。第 30 章的 CLIP 让整张图和整句话在同一个向量空间里靠近，这是粗粒度的对齐；第 31 章的 OCR 把视觉 token 拼在文本前面当前缀，在训练中让注意力自己学会细粒度的对齐。

### 26.3.4 常见误解

- **"注意力权重大的地方就是模型依据的地方。"** 不一定。注意力只是信息流的一部分，残差连接和后面的层都可能改写它。热图是线索，不是证据。
- **"输出的字符都对，对齐就没问题。"** 第 41 张图就是反例：字符全对，结构全错。CER（字符错误率）对这种错误不敏感，26.7 节会再遇到它。

## 26.4 推理：转写不是解题

### 26.4.1 OCR 需要哪种推理

一提推理（reasoning），很多人想到的是做数学题。可 OCR 恰恰**不能**做数学题：图上写的是 `1+1=3`，输出就必须是 `1+1=3`，不能改成 2。

那 OCR 需要什么推理？**结构推理。** 看到一条横线，要判断它是分数线还是减号；看到右上角的小字，要判断上标到哪里结束；看到 `\sum` 下面的 `i=1`，要知道它是求和下限，不是一个独立的等式。这些判断都要把好几处视觉证据组合起来，一步看不出来。

CMU 的综述把推理定义为"组合多步、多模态的证据得出结论"。对 OCR 来说，结论就是公式的**结构树**。

### 26.4.2 语言先验：模型的脑补

VLM 的语言模型部分读过海量文本。它知道 `\in` 后面常跟 `\mathbb{Z}`（整数集），知道 `\left(` 后面要有 `\right)`。这种根据上下文猜下一个 token 的知识叫**语言先验**。

先验是把双刃剑。看验证集第 0 张图（本项目观察：RTX 4090（租用），`main/val.jsonl` 第 0 行）：

```text
参考：z_k = (z_{1,k}, z_{2,k})\in Z, \ \ \ \ k=1,..., K,
输出：z _ { k } = \left( z _ { 1 , k } , z _ { 2 , k } \right) \in \mathbb { Z } , \quad k = 1 , \ldots , K
```

打开 `val_images/0000.png` 看，图上的 Z 是普通的斜体 Z，不是黑板粗体。模型却写成了 `\mathbb { Z }`。很可能是"`\in` 后面的 Z 多半是整数集"这个先验盖过了图上的证据。

但"很可能"不是"确定"。另一种解释是：这张图只有 270×38 像素，模型根本没看清字体。**到底是视觉没看清，还是语言脑补了？** 只凭一个输出分不出来。第 31 章的遮挡、错配、白图和第 33 章的"视觉依赖对照"（给一张错误的图，看输出变不变）能看出模型整体上有多依赖图像，但不能替单条错例判病因；要判这一张，还得针对这一张做对照。

> **停下来想一想：** 如果图上写的是 `1+1=3`，你希望模型输出什么？怎样构造一组测试，检查模型会不会自作主张把它"改对"？

### 26.4.3 推理出错的另一面：丢结构

第 83 张图更极端：

```text
参考：\bigg{(}\bigoplus_{\prod_j\epsilon_j=1}\bigotimes_jU_j^{\epsilon_j}\bigg{)}\oplus …
输出：\left( \bigoplus _ { j = 1 } ^ { j } U _ { j } ^ { \epsilon _ { j } } \right) \oplus …
```

图上 ⊕ 下面是一行很小的 `∏_j ε_j = 1`，旁边还有一个 ⊗_j。模型把下限简化成了 `j = 1`，凭空加了一个上限 `^ { j }`，还整个丢掉了 `\bigotimes`。这一条的字符编辑距离是 63（本项目观察，`main/val.jsonl` 第 83 行的 `ed_char`，参考规范化后共 150 个字符）。小字看不清（表示问题）和结构猜错（推理问题）缠在一起，公式 OCR 的错例常常是这个样子。

### 26.4.4 常见误解

- **"推理能力越强的模型，OCR 越好。"** 未必。会推理的模型更容易把图上的错误顺手纠正掉，或者把不常见的写法换成常见的写法。OCR 要的是忠实转写。
- **"开启 thinking 模式能提高 OCR。"** 本章关闭了 thinking（模板里那对空的 `<think></think>` 就是关闭后的样子），没有做开和关的对照，所以没有结论（待验证）。

## 26.5 生成：输出 LaTeX 的格式与长度

### 26.5.1 生成要回答什么

**生成**（generation）是产出另一种模态的内容。CMU 综述把生成分成摘要、翻译、创作三类。OCR 属于"翻译"：从图片翻译成 LaTeX，内容要一一对应，不能多也不能少。

生成要回答三个问题：用什么格式写？写多长？什么时候停？

### 26.5.2 格式：模型有自己的口音

回到本章开头那三行输出。提示词明明写了 "without explanation or markdown"，三条输出却都包着 `$$ … $$`；开源验证集的 100 条原始输出，也是 100 条都以 `$$` 开头（本项目观察：RTX 4090（租用），n=100）。

还有一个更隐蔽的习惯：**每个符号之间都加空格**，花括号一个不省。参考写 `x^2`，模型写 `x ^ { 2 }`。这是 im2latex 一类 OCR 数据集常见的"规范化 LaTeX"风格，模型很可能在训练中见过大量这种格式（待验证：我们没有看过 Qwen3.5 的训练数据）。

在 LaTeX 里，`x^2` 和 `x ^ { 2 }` 排出来完全一样，因为数学模式忽略空格，单字符上标加不加花括号也一样。所以这只是写法上的口音，排版结果没有错。可口音会骗过评测脚本，26.7 节细说。

图 3 多出来的那层花括号 `= { \frac … }` 也是同类：在 LaTeX 里，`{ \frac{a}{b} }` 只是多了一个分组，排版结果和不加一样。

### 26.5.3 长度：生成多少、何时停

三张教学图分别生成了 25、27、37 个 token（本项目观察：RTX 4090（租用），n=3）。这些数包含结束标记，所以比你肉眼数的符号多一点。

验证集里有一张图生成到了上限：第 97 张，一个含两个 2×2 矩阵的长公式，写满 256 个 token 也没写完，结尾停在 `\frac { 2 7 b ^ { 2 } } { 4`（本项目观察：100 张中截断 1 张）。截断的输出缺了右边的 `$$`，后面的抽取规则就找不到完整的公式块，结果开头的 `$$` 原样留在了"抽取后"的答案里。一个生成问题，顺手又制造了一个评测问题。

### 26.5.4 对照代码：同时保留两份输出

`tour.py` 的 `infer_rows` 对每张图存两份结果：

```python
result["raw_score"] = score_pair(row["formula"], result["raw"])
result["score"] = score_pair(row["formula"], result["extracted"])
```

`raw` 是模型的原话，`extracted` 是第 18 章写的 `extract_formula` 从原话里抠出来的公式。抽取是启发式规则，可能抠错，所以**原话永远要留着**。测试 `test_raw_and_extracted_are_both_preserved` 专门检查这一点。

### 26.5.5 常见误解

- **"提示词写清楚了，模型就会照做。"** 本章的提示词写了不要 markdown，模型 100% 加了 `$$`。小模型不一定严格遵守格式指令。要改格式，最可靠的办法是第 33 章的微调，或者在评测端写好抽取规则。
- **"截断的样本删掉就好。"** 不行。删掉难样本，分数就会虚高。lab 第 4 部分规定 100 张全部计入汇总。

## 26.6 迁移：从教学图到真实图

### 26.6.1 零样本迁移

**迁移**（transference）是把在一处学到的本领用到另一处。对 VLM 来说，最直接的迁移是**零样本**：模型从没在你的数据上训练过，直接拿来用。本章的全部结果都是零样本，训练步数为 0。

### 26.6.2 一个落差

| | 样本数 | 抽取后规范化 EM | 字符 CER |
|---|---|---|---|
| 三张教学图 | 3 | 3/3 | 0 |
| 开源验证集 | 100 | 13/100 | 0.122 |

（本项目观察：RTX 4090（租用），bf16，`main/controlled.json`、`main/val.json`。）

从全对掉到 13%。13/100 的 Wilson 95% 区间是 0.078 到 0.210（本项目观察：`summary.csv`；这个区间假设样本独立同分布，而这 100 张是按文件顺序取的前 100 个，不是随机抽样，所以它只是参考）。

### 26.6.3 为什么会掉：先列差别，别急着下结论

很想说"模型在真实图上不行"。先别急。两组之间至少有三处不同：

1. **公式难度不同。** 教学图是三个短公式；验证集 65% 是长公式，还有矩阵、修饰符号。
2. **图像风格不同。** 教学图是 mathtext 渲染的大字；验证集来自论文，字体是 Computer Modern，字号更小，原图高度只有 19 到 107 像素（本项目观察，n=100）。
3. **参考答案的写法不同。** 验证集的参考保留了作者的原始写法，比如 `\ \ \ \`、末尾的逗号、`\bigg{(}`；教学图的参考是我们自己写的干净版本。

三处差别同时存在，所以这个落差**不是因果结论**。lab 第 4 部分也这样提醒：这不是一个配对的消融实验。要知道哪个因素影响最大，得一次只改一处。第 27 章（预处理）、第 33 章（微调）各做一部分这样的对照。

第 3 点说明，分数掉下来可能有一部分不是模型的问题，下一节就看这一点。

## 26.7 量化评估：分数到底在说什么

### 26.7.1 怎样判断一个输出对不对

**量化**（quantification）这个问题问的是：我们怎样测量、理解一个多模态模型？对 OCR 来说，最基本的一层是：**怎样判断一个输出对不对。**

听起来简单，先看三张图的结果。

### 26.7.2 同一组输出，三个答案

对三张教学图，同样的三条输出，换三种判法（本项目观察：RTX 4090（租用），bf16，n=3，`main/controlled.json`、`main/controlled.jsonl`）：

| 判法 | 结果 | 为什么 |
|---|---|---|
| 原输出 + 规范化 EM | 0/3 | 多了 `$$`，规范化也去不掉 |
| 抽取后 + 规范化 EM | 3/3 | 去掉 `$$`，空格规范化后完全一样 |
| 抽取后 + mathtext 像素比较 | 0/3 一致 | 像素差 0.951、0.591、0.957 |

同样的输出，可以是 0 分，也可以是满分。

第一行的原输出 CER 是 0.16。可以手算验证：规范化后三条参考共 17 + 26 + 32 = 75 个字符；每条输出多出 `$$` 和 `$$` 共 4 个字符，三条共 12 处编辑，12/75 = 0.16（数学结论，各项字符数来自 `controlled.jsonl` 的 `len_char` 和 `ed_char`）。

第三行最出人意料：内容规范化后完全一致，像素差却高达 0.59 到 0.96。这里的像素差是把参考和输出各渲染成图，裁掉空白、左上角对齐后，用只在一张图里有墨迹的像素数，除以至少在一张图里有墨迹的像素数；0 表示逐像素一致，1 表示墨迹完全不重合。

原因在渲染器：matplotlib 的 mathtext 不是真正的 TeX，它对 `x ^ { 2 }` 这种带空格的写法排版和 `x^2` 不同。在本地 CPU 上渲染，`x^2+y^2=z^2` 得到宽 71、高 21 像素的图，`x ^ { 2 } + y ^ { 2 } = z ^ { 2 }` 得到宽 85、高 18 像素的图（本项目观察：本地 CPU，`miniocr.eval.render.render`，默认 DPI）。尺寸都不一样，逐像素比较当然对不上。这是 mathtext 的怪癖，不代表真正的 LaTeX 也会这样（待验证：本章没有用 TeX 引擎渲染）。

### 26.7.3 验证集：评测规则本身会犯错

验证集的 100 条输出也是这样：原输出的规范化 EM 是 0/100，抽取后是 13/100；字符 CER 从 0.158 降到 0.122（本项目观察：RTX 4090（租用），n=100，`main/val.json`）。

但 13/100 就是真相吗？把 `val.jsonl` 里每条的 `ed_char` 数一数：恰好差 1 个字符的样本有 32 条（本项目观察，按文件字段计数）。翻开看，大多数是同一种情况。看两个例子：

```text
第 90 张 参考：\{e\}(n,F) = g(n).
        原输出：$$\{ e \} ( n , F ) = g ( n ) .$$
        抽取后：\{ e \} ( n , F ) = g ( n )

第 16 张 参考：H^{abc} \equiv e^\phi \epsilon^{abcd} \nabla_d\sigma \, ,
        原输出：$$H ^ { a b c } \equiv … \nabla _ { d } \sigma \ ,$$
        抽取后：H ^ { a b c } \equiv … \nabla _ { d } \sigma \
```

第 90 张：模型连图上末尾的句点都认出来了，原输出去掉 `$$` 以后，规范化比较和参考一致。可抽取规则会"去掉一个句末的 `.`、`,`、`;`"。这条规则是第 18 章为 LLM 的聊天输出写的，18.6.2 节已经看到它会误伤本来以标点结尾的目标。到了 OCR 这里，图上本来就有的句点被它删了，差 1 个字符，判错。

第 16 张更糟：模型写的是 `\ ,`（一个空格命令加一个逗号），抽取规则删掉逗号后，剩下一个孤零零的反斜杠 `\`。抽取规则把一个本来正确的输出改坏了。

所以量化评估要单独算一个问题：评测流程（抽取规则 + 规范化 + 比较方法）也相当于一个模型，它也会犯错。你在练习 26.4 里会亲手算一算，换一种抽取规则，13/100 会变成多少。

### 26.7.4 常见误解

- **"EM 低就是模型差。"** 先看是谁错了。上面的例子里，一部分错误出在评测规则上。
- **"渲染比较最客观。"** 渲染比较绕开了写法差异，但引入了渲染器的差异。mathtext 只支持 LaTeX 的一部分，比如 `\begin{array}` 它就画不出来；验证集里有多少公式受影响，本章没有统计（待验证）。
- **"在测试集上看看错例，好改进规则。"** 不行。本章所有观察都只用教学图和验证集，测试集没有评测（`run.json` 里 `test_evaluated` 为 false）。开发期的错例分析、改规则，都只能在验证集上做，测试集的错例要等最终报告定稿后才能解封（第 22 章；评测协议见第 0 章 0.10.1 节、第 5 章 5.1.3 节）。

## 26.8 两类结构：拼接，还是交叉注意力

六个问题讲完，回到结构。26.2.2 节列过 VLM 的三个部件：视觉编码器、连接器、语言模型。视觉编码器把图变成了 V 个视觉向量，每个宽 Dv；语言模型手里是 T 个文字向量，每个宽 Dt。两边的宽度一般不相等，个数也不相等。怎样把两边接起来，让语言模型在写每个 token 时都能用上图里的信息？这一步把两种模态的信息合到一起，多模态文献里常叫它**融合**（fusion），CMU 的综述把它算作表示问题下面的一个子问题（精读第 1 篇）。主流的做法有两类。

为了把形状看清楚，lab 第 2 部分用随机张量搭了两个最小的连接器，代码在 `miniocr/models/multimodal.py`。下面先用 lab 的默认小尺寸讲：批量 B=2，视觉 token V=6，文字 token T=5，视觉宽度 Dv=8，文字宽度 Dt=12。

### 26.8.1 方式一：视觉 token 拼到文字前面

把图片翻译成几十个外语单词，直接插进句子里。语言模型不用改任何结构，它只觉得这句话变长了，开头多了一些它要学着理解的词。

做法分两步：

1. **连接器**（connector，也叫投影层）：一个线性层，把每个视觉向量的宽度从 Dv 变成 Dt。只改宽度，不改个数。
2. **拼接**：沿着序列轴（第 1 轴）接到文字前面。

```python
class VisualPrefix(nn.Module):
    def __init__(self, vision_dim=8, text_dim=12):
        super().__init__()
        self.projection = nn.Linear(vision_dim, text_dim)

    def forward(self, vision, text):
        _check_inputs(vision, text)
        return torch.cat((self.projection(vision), text), dim=1)
```

**形状逐项对照**（数学结论，和 lab 第 2 部分 `shapes.json` 一致）：

| 张量 | 形状 | 说明 |
|---|---|---|
| vision | [2, 6, 8] | B, V, Dv |
| projection(vision) | [2, 6, 12] | 宽度对齐到 Dt，个数仍是 6 |
| text | [2, 5, 12] | B, T, Dt |
| cat(…, dim=1) | [2, 11, 12] | 长度 V+T = 11 |

参数量：线性层 8×12 个权重加 12 个偏置，共 108 个（数学结论，和 CPU 运行的 `prefix_parameters` 一致）。

关键在 `dim=1`。如果写成 `dim=2`（沿宽度拼），两个张量第 1 轴长度不同（6 和 5），会直接报错；就算碰巧 V=T，也会得到宽度 Dt+Dt（视觉已投影到 Dt；本节默认是 24）的缝合怪，语义完全错了。**拼接改变的是长度，连接器改变的是宽度**，这两个轴不能混。

再看**遮罩**。拼起来以后，语言模型要对 11 个位置做自注意力。谁能看谁？本章的教学实现 `prefix_mask` 做了一个明确的选择：

- 视觉位置互相全看（图片已经完整给定，没有"未来"）；
- 视觉位置不看文字；
- 文字位置能看所有视觉位置，文字之间因果（只看过去）。

V=2、T=3 时的遮罩（1 是可见；数学结论，测试 `test_prefix_cannot_leak_future_text` 检查的就是这个矩阵）：

```text
       v1 v2 t1 t2 t3
v1  [   1  1  0  0  0 ]
v2  [   1  1  0  0  0 ]
t1  [   1  1  1  0  0 ]
t2  [   1  1  1  1  0 ]
t3  [   1  1  1  1  1 ]
```

左上角是一块全 1（第 9 章 9.7.1 的 Encoder 遮罩），右下角是下三角（9.7.2 的 Decoder 遮罩）。

这只是一种选择。很多真实模型（比如 LLaVA）直接沿用语言模型原来的因果遮罩，视觉 token 之间也是因果的，因为视觉编码器已经双向地把整张图看过一遍了。两种选择都不会泄漏答案，关键是**文字不能看未来的文字**。测试里有一个扰动实验：把最后一个文字 token 加上 100，前 4 个位置的输出必须一字不变，第 5 个位置的输出必须改变。

Qwen3.5 就属于这一类。图 1 的输入序列长 114，其中 78 个是视觉 token、36 个是模板和指令（26.2.3 节）。不同的是，Qwen 的图片 token 插在用户消息里图片出现的地方，而不一定在整个序列的最前面。

### 26.8.2 方式二：交叉注意力

另一种做法让文字在需要的时候回头查图片，图片不进句子。就像第 9 章的译员：写译文时随时回看原文。具体来说，查询 Q 来自文字，键 K 和值 V 来自视觉。

```python
class CrossAttention(nn.Module):
    def __init__(self, vision_dim=8, text_dim=12):
        super().__init__()
        self.q = nn.Linear(text_dim, text_dim, bias=False)
        self.k = nn.Linear(vision_dim, text_dim, bias=False)
        self.v = nn.Linear(vision_dim, text_dim, bias=False)

    def forward(self, vision, text):
        _check_inputs(vision, text)
        query, key, value = self.q(text), self.k(vision), self.v(vision)
        logits = query @ key.transpose(-2, -1) / math.sqrt(query.shape[-1])
        weights = torch.softmax(logits.float(), dim=-1).to(value.dtype)
        return weights @ value, weights
```

注意 `k` 和 `v` 的输入宽度是 `vision_dim`。这两个线性层**顺便充当了连接器**：把 Dv 投影到 Dt。所以交叉注意力不需要单独的投影层。

**形状逐项对照**（数学结论，和 `shapes.json` 一致）：

| 步骤 | 计算 | 形状 |
|---|---|---|
| 查询 | q(text) | [2, 5, 12] |
| 键、值 | k(vision)、v(vision) | 各 [2, 6, 12] |
| 分数 | query @ keyᵀ / √12 | [2, 5, 6] |
| 权重 | softmax(dim=-1) | [2, 5, 6]，每行和为 1 |
| 输出 | weights @ value | [2, 5, 12] |

权重的形状是 `[B, T, V]`：每个文字位置对每个视觉位置一个权重。softmax 沿最后一轴（视觉轴）做，所以每个文字位置的 6 个权重加起来是 1。输出长度是 T=5，**跟着查询走**，图片再大，输出也不会变长。

参数量：Q 是 12×12，K、V 各 8×12，都不带偏置，共 144 + 96 + 96 = 336 个（数学结论）。

测试 `test_cross_attention_matches_independent_sdpa_and_uses_vision` 把这个手写版本和 PyTorch 的 `scaled_dot_product_attention` 逐数对拍；还检查了一件事：把视觉输入换成全零，输出必须改变。如果不变，说明文字根本没在看图。

还有一个可以手算的小例子（`test_zero_query_means_uniform_visual_average`）：如果文字查询全是 0，所有分数都是 0，softmax 后权重均匀，输出就是所有视觉值的平均。两个视觉值 [2, 4] 和 [6, 8]，平均是 [4, 6]（数学结论）。

DeepMind 的 Flamingo 走的是这条路：在冻结的语言模型层之间插入新的交叉注意力层，并且用一个初始化为 0 的门控（tanh 门）把它包起来。训练开始时门是关着的，模型和原来的语言模型完全一样，然后慢慢学会开门看图。

### 26.8.3 放大以后：lab 的正式运行

lab 第 2 部分的正式运行把尺寸放大到 B=8、V=64、T=32、Dv=32、Dt=48（本项目观察：RTX 4090（租用），bf16，`main/shapes.json`）：

| | 方式一：拼接 | 方式二：交叉注意力 |
|---|---|---|
| 关键张量 | 拼接结果 [8, 96, 48] | 权重 [8, 32, 64]，输出 [8, 32, 48] |
| 遮罩 | [96, 96] | 不需要因果遮罩 |
| 连接部分参数 | 1584 | 5376 |

参数量都可以手算：32×48 + 48 = 1584；48×48 + 32×48 + 32×48 = 5376（数学结论）。交叉注意力的参数多，是因为它自带了 Q、K、V 三个矩阵；而拼接方式的"注意力参数"藏在语言模型原有的层里，没算进来。所以这一行不能理解成"拼接更省参数"。

两种连接器都做了一次反向传播，所有输入和参数的梯度都有限且非零；没有做任何参数更新（训练步数 0）。

精度也有影响：在 bf16 下，交叉注意力权重每行的和与 1 最多差 0.000610（本项目观察，正式运行）；CPU fp32 的默认运行只差约 1.2×10⁻⁷（本项目观察：`local_tour.log`）。代码里先在 fp32 中做 softmax，再转回 bf16，转换时的舍入就留下了这点误差。所以测试里检查"行和为 1"时，低精度要给容差。

### 26.8.4 两类结构对照

| | 拼接（视觉前缀） | 交叉注意力 |
|---|---|---|
| 视觉信息从哪里进 | 输入序列，和文字一起过每一层 | 专门插入的交叉注意力层 |
| 语言模型要不要改结构 | 不用，只是序列变长 | 要插入新层 |
| 序列长度 | V+T，视觉 token 多则自注意力变贵 | 仍是 T；每层交叉注意力多一个 T×V 的矩阵 |
| 代表模型 | LLaVA、Qwen-VL 系列、Qwen3.5 | Flamingo；第 9 章的 Encoder-Decoder |
| 本书哪里用 | 第 31 章的小公式 OCR；第 32、33 章的真实 VLM | 本章的最小实现；第 31 章只作对比，可作为扩展自己做 |

计算量差在哪里，可以粗算一下（数学结论）：拼接方式每层自注意力的分数矩阵是 (V+T)²；交叉注意力每层自注意力是 T²，再加交叉注意力的 T×V。V=78、T=36 时，(78+36)² = 12996，而 36² + 36×78 = 4104。视觉 token 越多，拼接方式越贵。所以第 32 章要讲"视觉 token 合并"：Qwen 那个 2×2 合并，一下子把 token 数砍到四分之一。

> **停下来想一想：** 视觉 token 从 78 翻倍到 156，拼接方式的序列长度和交叉注意力的权重矩阵，各是哪个轴变长？输出的文字长度会变吗？

### 26.8.5 常见误解

- **"拼接方式里，视觉 token 也要预测下一个 token。"** 不用。视觉位置没有下一个视觉 token 可预测，训练时它们的标签被遮掉（第 33 章的 label mask）。
- **"两种方式差别很大，一种一定更好。"** 不一定。它们是在简单、不改语言模型，和省序列长度、精细控制之间做取舍。近几年开源 VLM 多用拼接，主要是因为它简单，能直接复用现成的语言模型。

## 26.9 其他模态：音频和视频（概括）

六个问题和两类结构，不只适用于图片。简单看两个例子：

- **音频。** 声音先变成频谱图（时间 × 频率的二维图），再像图片一样切块或用卷积压成 token 序列。语音识别和 OCR 很像，都是把感知信号转写成文字。OpenAI 的 Whisper 就是一个 Encoder-Decoder：编码器读音频，解码器用交叉注意力回看，逐个写出文字。
- **视频。** 视频是一串图片，token 数随帧数成倍增长，表示问题变得特别尖锐：一段视频动辄几千、几万个视觉 token。所以视频模型通常要控制视觉 token 数量：许多模型在时间上合并相邻帧，也有的靠抽帧、空间池化等办法控制长度。Qwen 的 processor 其实已经为视频留了位置：每个 patch 的长度是 3×2×16×16 = 1536（数学结论），其中的 2 是时间轴。处理静态图片时，它把同一张图复制成两帧（代码见 `vlm_anatomy.py` 的 `replica_processor`）。三张教学图的 `pixel_values` 形状 [312, 1536]、[280, 1536]、[308, 1536] 印证了这一点（本项目观察）。

本书只做图片到文字。对齐语音和文字、跟踪视频里的对象，有各自的难点，感兴趣可以从精读里的综述入手。

## 26.11 常见错误

| 错误 | 现象 | 原因 | 怎样发现 |
|---|---|---|---|
| 沿错误的轴拼接 | `torch.cat` 报尺寸不匹配；或 V=T 时得到宽度 Dt+Dt 的张量 | 用了 `dim=2`，把长度和宽度混了 | 检查拼接结果是不是 `[B, V+T, Dt]` |
| 忘了连接器 | 拼接时宽度对不上 | 视觉宽度 Dv 和文字宽度 Dt 不同 | 先打印两边最后一轴 |
| 遮罩全可见 | 训练损失降得飞快，生成时一塌糊涂 | 文字看到了未来的文字，等于抄答案 | 扰动最后一个 token，看前面位置的输出变不变 |
| softmax 沿错了轴 | 权重每行的和不是 1 | 用了 `dim=-2`，在文字轴上归一化 | 检查 `weights.sum(-1)` 是否接近 1 |
| 把随机热图当对齐 | 热图看起来合理 | 没训练的注意力也有深有浅 | 和打乱输入后的热图比较；做遮挡实验 |
| 渲染图黑白反了 | 白边框里是黑底白字 | `render` 返回 255 表示墨迹，存图前没反转 | 打开图片看；检查边框以内白色像素是否占多数。只查白边和有无深色像素抓不住这个错误，`test_render_polarity_and_cli_parts` 多查了边框以内这一条（习题调试题 4） |
| 只评原输出，或只评抽取后 | 分数 0 或分数虚高 | 没有区分模型错误和格式差异 | 两份都报，并抽查差 1 个字符的样本 |
| 换了机器，token 数变了 | 同一个公式，视觉 token 不同 | 字体环境不同，渲染出的图尺寸不同 | 核对图片 SHA 和尺寸，见下 |

最后一条是本章真实遇到的。同样的 `tour 1`，本地 CPU 渲染出的图 2 是 95×76，租用 GPU 机器上是 97×73（本项目观察：`local_tour.log` 与 `main/rendered.json`）。按 26.2.3 的规则，95×76 会被缩放到 288×256，得到 72 个视觉 token，而不是 70（数学结论）。所以比较两次运行时，先确认输入图片是不是同一张。

## 26.13 小结

多模态的难处来自异质性：图片是二维像素，LaTeX 是一维 token。CMU 11-777 把多模态的难点归成六个问题：表示、对齐、推理、生成、迁移、量化评估，它们是看同一个错例的六个角度。一个 VLM 由视觉编码器、连接器、语言模型三部分组成。Qwen3.5 把一张小公式图缩放到面积预算内，切成 16×16 的 patch，经过视觉编码器后再 2×2 合并，得到几十个视觉 token，数量由面积决定，与公式难度无关。连接视觉和语言主要有两类结构：投影后拼进文字序列（改长度），或者让文字用交叉注意力查询视觉（输出长度跟着文字走）。本章的零样本观察提醒我们，分数同时取决于模型和评测流程：同一组输出可以是 0/3，也可以是 3/3。

复习时抓住下面几条：

- **六个问题**：表示（图变成什么向量）、对齐（输出的哪一段对应图上哪一块）、推理（把几处视觉证据拼成结构树，OCR 要忠实转写，不解题）、生成（格式、长度、何时停）、迁移（教学图到真实图、零样本到微调）、量化评估（评测流程本身也会犯错）。给错例分类时，每个分类都是一个假设，要配一个能区分它的实验。
- **视觉 token 数**：`smart_resize` 先把高、宽变成 32 的倍数（面积低于 `min_pixels` 就放大、向上取整，高于 `max_pixels` 就缩小、向下取整），再切 16×16 的 patch、2×2 合并，所以 token 数 = (H′/16)×(W′/16)/4 = H′W′/1024。图 1：160×63 → 416×192 → 12×26 个 patch → 78 个 token。
- **拼接**：`[B, V, Dv]` 经连接器变成 `[B, V, Dt]`，沿第 1 轴和 `[B, T, Dt]` 拼成 `[B, V+T, Dt]`。连接器改宽度，拼接改长度。遮罩要让文字之间保持因果，视觉位置也不看文字，这样文字才不会直接或绕道看到未来的文字。
- **交叉注意力**：Q 来自文字，K、V 来自视觉，权重 `[B, T, V]` 沿最后一轴（视觉轴）做 softmax，输出 `[B, T, Dt]`，长度跟着查询走。K、V 的线性层顺带充当连接器。
- **代价**：拼接方式每层自注意力的分数矩阵是 (V+T)²，交叉注意力是 T² 加 T×V，视觉 token 越多拼接越贵，所以真实 VLM 要合并视觉 token。
- **最常见的错误**：把随机或未经干预验证的注意力热图当成对齐的证据；只报原输出或只报抽取后的分数，分不清模型错误和格式差异。
