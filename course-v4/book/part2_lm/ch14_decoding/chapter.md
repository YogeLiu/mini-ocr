# 第 14 章　解码策略

## 本章导读

完成第 13 章的实验后，你手里会有一个训练好的 LaTeX GPT。它每一步吐出的只是一行 logits：词表里每个 token 一个分数。怎样从这行分数里挑出下一个 token，就是**解码策略**。模型一点没变，只换解码方式，输出就可能从"整整齐齐的 `\frac{a}{b}`"变成"`\ \ \ \ \ \ \ \ \ `"，或者变成一个空公式。

本章回答三个问题：

1. 采样时怎样把一行 logits 变成"要从中抽的分布"？温度、top-k、top-p（核采样）、min-p、重复惩罚各管什么，按什么顺序执行？
2. 束搜索怎样找"整体概率高"的序列？它为什么偏爱短句，长度惩罚怎样纠正？
3. 什么任务用贪心或束搜索，什么任务用采样？

**重点：** top-p（14.5）、束搜索（14.7）及其偏短与长度惩罚（14.8）。**概括：** 投机解码（14.10，只讲思路）。贪心和温度比较简单，讲得短一些。

**怎样读本章：** 14.3–14.6 用同一个"五 token 例子"贯穿，你可以拿纸笔跟着算，每个数字都能在实验手册第 1 部分的输出里找到。14.7–14.8 用一个五个 token 的玩具语言模型，所有序列都能手算。

**和项目的关系：** TexPixel 的公式识别是"答案唯一"的任务，推理时一般用贪心或束搜索；到第 25 章 GRPO，需要对同一个输入采样一组回答、比较它们的奖励，那时要用温度采样让回答有差异。

本章所有代码在 `miniocr/decoding.py`，实验在 `tour.py`（命令见 [lab.md](lab.md)）。本章的生成循环**每一步都把整段序列重新送进模型**，不用 KV cache；怎样省掉这部分重复计算是第 15 章的内容。

第 13 章的完整训练由你完成，正文不提供结果。所以本章在 LaTeX GPT 上的数字都来自 150 步的冒烟模型，只证明流程跑通；哪种解码更好，要用你自己的检查点回答（14.9.3 节）。

> **回顾：这一章用到的旧知识**
>
> - **softmax**：p_i = exp(z_i) / Σ_j exp(z_j)。给所有 logit 加同一个常数，概率不变。被设成 −∞ 的 logit，概率是 0。（第 3 章）
> - **自回归生成**：语言模型给出 P(y_t | y_<t)，整条序列的概率是各步条件概率的乘积，取 log 就是和：log P(y) = Σ_t log P(y_t | y_<t)。（第 7 章）
> - **BOS / EOS**：每条公式前加 BOS、后加 EOS。生成时从 BOS 开始，模型吐出 EOS 就算写完。（第 12 章）
> - **mathtext 可解析率与 Wilson 区间**：用 matplotlib 的 mathtext 能否解析近似"能否编译"；比例的 95% 置信区间用 Wilson 区间。（第 0、13 章）

## 14.1 解码是什么：从一行 logits 到一串 token

### 14.1.1 一个现象

拿同一个检查点，从同一个公式开头 `T(S` 出发，让它往下写。实验手册第 5 部分在一个只训练了 150 步的冒烟模型上（**本项目观察**，CPU，tour 第 5 部分，冒烟模型，只证明流程）：

- 贪心解码写出了 `T(S \ \ \ \ \ \ \ \ …`，一个 `\ ` 重复到长度用完；
- 温度 0.7 的采样写出了 `T(S \tauV0-0k`，然后遇到 EOS 停下。

这两个输出都很糟糕——冒烟模型本来就不会写公式——但糟糕的**方式**完全不同：一个陷入复读，一个乱跳。模型给的是分布，解码决定你从分布里拿走什么。

### 14.1.2 两类做法

生成第 t 个 token 时，模型给出 logits z ∈ ℝ^V。解码有两大类：

| 类别 | 目标 | 代表 | 结果是否随机 |
|---|---|---|---|
| 搜索 | 找概率尽量高的那一条序列 | 贪心、束搜索 | 确定 |
| 采样 | 从分布里抽一条"像样"的序列 | 温度、top-k、top-p、min-p | 随机 |

搜索把模型当成一个打分器："哪条序列分最高？"采样把模型当成一个写作者："按你的习惯写一条。"两者都可以叠加重复惩罚。

采样类方法的共同结构是一条**流水线**：logits 依次经过几个"处理器"，每个处理器要么改分数（重复惩罚、温度），要么把一部分 token 设成 −∞（top-k、top-p、min-p），最后 softmax、抽样。本章的实现固定这条顺序（`miniocr/decoding.py` 的 `PROCESS_ORDER`）：

```text
原始 logits → 重复惩罚 → 温度 → top-k → top-p → min-p → softmax → 抽样
```

14.6.3 节会讲为什么是这个顺序。

## 14.2 贪心解码

**结论：** 每一步取 argmax。确定、简单、可复现；但它只看眼前一步，容易复读，也不保证整条序列的概率最高。

```text
y_t = argmax_i z_i
```

贪心不需要 softmax：softmax 是单调的，不改变最大值的位置。温度、top-k、top-p 也都不改变最大值的位置（只要最大值不并列），所以**贪心时这些参数全部无效**。本章的 `process_logits` 在 `greedy=True` 时只做重复惩罚，跳过其余步骤——重复惩罚会改变谁最大，所以 OCR 里常见"贪心 + 重复惩罚"的组合。

贪心有两个毛病：

1. **短视。** 第一步选了概率 0.7 的 token，可能把自己带进一条后面全是小概率的路。14.7 节会看到一个例子：贪心选出的序列概率是 0.2268，而另一条序列的概率是 0.30（**数学结论**，14.7.4 节手算）。
2. **复读。** 如果模型在某种上下文里"最可能的下一个 token"恰好让上下文保持同样的模式（例如再写一个 `\ `，下一步最可能的还是 `\ `），贪心就会一直写下去，因为它没有任何随机性帮它跳出来。14.1.1 节的 `\ \ \ \ …` 是这样的例子：这次观察到它连续复读直到生成上限（24 个 token），至于再写下去会不会停，没有验证。tour 第 5 部分里，冒烟模型贪心解码的 50 条续写，distinct-2（不同二元组占比，14.9.2 节定义）只有 0.0017（**本项目观察**，CPU，tour 第 5 部分，冒烟模型，只证明流程）——几乎全是同一个二元组在重复。

## 14.3 温度采样

### 14.3.1 定义

**结论：** 先把 logits 除以温度 T，再 softmax、按概率抽。T < 1 让分布更尖（更保守），T > 1 让分布更平（更大胆）。

```text
p_i(T) = exp(z_i / T) / Σ_j exp(z_j / T)
```

两个 token 的概率比是 p_i / p_j = exp((z_i − z_j)/T)。T 越小，分数差被放得越大；T 越大，分数差被压得越小。极限情况（**数学结论**）：

- T → 0：最大的那个概率趋于 1（最大值唯一时），采样退化为贪心；
- T → ∞：所有概率趋于 1/V，变成均匀乱抽。

熵随温度单调不减：记 β = 1/T，可以推出 dH/dT = Var_p(z) / T³ ≥ 0（**数学结论**，Var_p(z) 是 z 在分布 p 下的方差；推导留作习题）。

### 14.3.2 五 token 例子

本章贯穿用的例子（tour 第 1 部分）：五个 token 及其 logits

| token | x | y | ^ | + | } |
|---|---|---|---|---|---|
| logit | 2.0 | 1.0 | 0.5 | 0.0 | −1.0 |

不同温度下的概率和熵（**本项目观察**，tour 第 1 部分；也可以手算验证）：

| T | x | y | ^ | + | } | 熵（nat） |
|---|---|---|---|---|---|---|
| 0.5 | 0.8292 | 0.1122 | 0.0413 | 0.0152 | 0.0021 | 0.6086 |
| 1.0 | 0.5630 | 0.2071 | 0.1256 | 0.0762 | 0.0280 | 1.2065 |
| 2.0 | 0.3745 | 0.2272 | 0.1769 | 0.1378 | 0.0836 | 1.4915 |

T = 0.5 时 x 几乎包办；T = 2 时连 `}` 也有 8% 的机会。tour 第 3 部分在 T = 0.5、1.0、1.5 下各抽 5000 次，经验频率和理论概率的最大绝对差约 0.01（最大的一处是 T = 1.5 时 y：理论 0.2252、经验 0.2148；T = 1 时 x 的理论值 0.5630、经验值 0.5722，**本项目观察**）。有限次抽样有误差，这是正常的。

> **温度不能设成 0。** 除以 0 会得到 ±∞ 或 NaN。想要贪心就直接用 argmax。`apply_temperature` 遇到 T ≤ 0 会报错，并提示"要贪心请用 greedy"。很多框架接受 `temperature=0` 并把它解释成贪心，那是框架替你做了特判（**待验证**，以你所用框架的文档为准）。

温度只改"形状"，不砍掉任何 token：再小的概率也不是 0。一个 V = 50000 的词表，每个 token 只要有 10⁻⁵ 的概率，合起来就是一大块"长尾"。每一步都有一点机会抽到长尾里的怪 token，写长了总会抽到——一旦抽到，模型就得在一个它从没见过的上下文里继续写，往往越写越乱。top-k 和 top-p 就用来解决这个问题。

## 14.4 top-k 采样

**结论：** 只在分数最高的 k 个 token 里抽，其余设为 −∞，剩下的重新归一化。

```text
保留集合 = { i : z_i ≥ 第 k 大的 z }
```

top-k 由 Fan et al.（2018）在故事生成中使用而流行。它简单有效，但 k 是个**固定**数，不管模型此刻有多大把握：

- 模型很确定时（例如刚写完 `\frac` 后面几乎只能是 `{`），k = 20 也会把 19 个不该出现的 token 放进候选；
- 模型很犹豫时（例如公式开头可以是几百种符号），k = 20 又可能砍掉大量合理选择。

两个实现细节：

- **并列。** 本书的 `top_k_filter` 保留"不小于第 k 大值"的全部 token，与第 k 大并列的都留下，所以可能多于 k 个。5 个 logit 全相等时，top-k = 2 保留了全部 5 个（**本项目观察**，tour 第 1 部分"平坦"分布）。
- **k ≥ V 或 k ≤ 0** 时不过滤。

## 14.5 top-p（核采样）

### 14.5.1 动机：候选数应该跟着把握走

top-k 的毛病在于"固定个数"。我们想要的是：模型有把握时候选少，没把握时候选多。什么量能反映"把握"？概率本身。于是换一个规则：从概率最高的 token 开始往下数，累计概率够了 p 就停。

这就是 Holtzman et al.（2020）提出的 **nucleus sampling（核采样）**，常叫 top-p。被保留下来的那一小撮 token 叫做"核"（nucleus）。

### 14.5.2 直觉：装箱子

把 token 按概率从大到小排成一队，手里拿一个容量为 p 的箱子。从队头开始一个个往箱子里放，**放进去后箱子满了（累计 ≥ p）就停**。最后放进去的那个，可能让箱子"溢出"一点——它也算在核里。

- 分布很尖：第一个 token 就有 0.9，p = 0.8 时箱子一下就满了，核里只有 1 个；
- 分布很平：每个 token 只有 0.001，要放 800 个才满。

tour 第 1 部分的对照（**本项目观察**）：p = 0.8 时，5 个等概率 token 的平坦分布保留 4 个；五 token 例子（T = 1）保留 3 个；同一个例子在 T = 0.5 时只保留 1 个（x 一个就有 0.8292）。而 top-k = 2 对平坦分布保留 5 个（并列），对尖锐分布保留 2 个——它不看把握，只看名次。

### 14.5.3 推导

设排序后的概率是 p_(1) ≥ p_(2) ≥ … ≥ p_(V)。核是满足下式的**最小**集合：

```text
V^(p) = 最小的集合 S，使 Σ_{i∈S} p_i ≥ p
```

**为什么"从大到小取前缀"就是最小的集合？** 假设某个大小为 m 的集合 S 已经满足 Σ ≥ p。把 S 里的元素逐个换成还没被选中的、更大的概率，和只会变大，仍然 ≥ p。换到最后，S 就变成了前 m 大的那些。所以前缀里第一个满足条件的长度 m*，就是所有满足条件的集合里最小的大小（**数学结论**；并列时最小集合可能不唯一，排序决定选哪个）。

接着是**判断条件**。设 c_j = p_(1) + … + p_(j) 是累计概率。第 j 个 token 要不要留？看它**之前**的累计概率：

```text
保留第 j 个  ⇔  c_{j−1} < p      （c_0 = 0）
```

- 如果 c_{j−1} < p，说明前 j − 1 个还没装满，第 j 个必须放进去；
- 如果 c_{j−1} ≥ p，说明箱子早满了，第 j 个不要。

第 1 个 token 的 c_0 = 0 < p 恒成立，所以**至少保留 1 个**——即使 p 很小。最后，在核内重新归一化：

```text
p'_i = p_i / Σ_{j∈V^(p)} p_j   （i ∈ V^(p)），否则 0
```

实现上不用显式除：把核外的 logit 设成 −∞，再 softmax，效果完全一样。

### 14.5.4 带数字的例子：五 token 一步步过流水线

现在把五 token 例子完整地过一遍流水线。设置（tour 第 1 部分）：`x` 和 `}` 之前已经出现过；重复惩罚 1.2，温度 0.8，top-k = 4，top-p = 0.8。下面每个概率都是"当前这一行 logits 的 softmax"（**本项目观察**，tour 第 1 部分；每一步都可以手算核对）。

**第 0 步：原始。**

| | x | y | ^ | + | } |
|---|---|---|---|---|---|
| logit | 2.0 | 1.0 | 0.5 | 0.0 | −1.0 |
| 概率 | 0.5630 | 0.2071 | 0.1256 | 0.0762 | 0.0280 |

**第 1 步：重复惩罚（1.2）。** x 和 } 出现过。x 的 logit 为正，除以 1.2：2.0 / 1.2 = 1.6667；} 的 logit 为负，乘以 1.2：−1.0 × 1.2 = −1.2。两个都变小了（14.6 节解释为什么正负要分开处理）。

| | x | y | ^ | + | } |
|---|---|---|---|---|---|
| logit | 1.6667 | 1.0 | 0.5 | 0.0 | −1.2 |
| 概率 | 0.4830 | 0.2480 | 0.1504 | 0.0912 | 0.0275 |

**第 2 步：温度（0.8）。** 每个 logit 除以 0.8：

| | x | y | ^ | + | } |
|---|---|---|---|---|---|
| logit | 2.0833 | 1.25 | 0.625 | 0.0 | −1.5 |
| 概率 | 0.5496 | 0.2389 | 0.1278 | 0.0684 | 0.0153 |

T < 1，分布变尖了：x 从 0.4830 升到 0.5496。

**第 3 步：top-k（k = 4）。** 第 4 大的 logit 是 0.0，只有 } 的 −1.5 比它小，} 被设成 −∞。剩下 4 个重新归一化：

| | x | y | ^ | + | } |
|---|---|---|---|---|---|
| logit | 2.0833 | 1.25 | 0.625 | 0.0 | −∞ |
| 概率 | 0.5581 | 0.2426 | 0.1298 | 0.0695 | 0 |

**第 4 步：top-p（p = 0.8）。** 按概率排序（这里恰好已经是 x, y, ^, +），逐个算"之前的累计概率" c_{j−1}：

| 排名 j | token | 概率 | c_{j−1} | c_{j−1} < 0.8？ |
|---|---|---|---|---|
| 1 | x | 0.5581 | 0 | 是，保留 |
| 2 | y | 0.2426 | 0.5581 | 是，保留 |
| 3 | ^ | 0.1298 | 0.8007 | 否，去掉 |
| 4 | + | 0.0695 | 0.9305 | 否，去掉 |

（累计值的四位小数是 Python 手算，**数学结论**。）x 和 y 加起来 0.8007，刚好越过 0.8，核就是 {x, y}。在核内重新归一化：

| | x | y | ^ | + | } |
|---|---|---|---|---|---|
| 最终概率 | 0.6971 | 0.3029 | 0 | 0 | 0 |

0.6971 = 0.5581 / 0.8007，0.3029 = 0.2426 / 0.8007。tour 第 1 部分最后一行 `最终采样分布=[0.6971, 0.3029, 0.0000, 0.0000, 0.0000]` 就是这个结果。

注意 0.8007 和 0.8 只差 0.0007。如果 y 的概率再小一点点，^ 就会被留下。top-p 的集合在边界附近对微小的变化很敏感，所以处理顺序（温度在 top-p 之前还是之后）会改变结果，14.6.3 节详谈。

> **停下来想一想：** 如果把 p 从 0.8 改成 0.55，核里有几个 token？改成 0.56 呢？（提示：x 自己是 0.5581。）

### 14.5.5 对照代码

`top_p_filter`（`miniocr/decoding.py`）：

```python
def top_p_filter(logits, p, min_keep=1):
    """保留累计概率首次达到 p 的最小前缀，至少 min_keep 个。"""
    if not 0 < p <= 1 or not isinstance(min_keep, int) or min_keep < 1:
        raise ValueError("p 须在 (0,1]，min_keep 须为正整数")
    if p == 1:
        return logits.clone()
    ordered, indices = logits.sort(dim=-1, descending=True)
    prob = ordered.softmax(-1)
    cum_before = prob.cumsum(-1) - prob
    # 浮点舍入可能在恰好相等的边界多/少留一个；不人为添加 epsilon。
    keep = cum_before < p
    keep[:, :min_keep] = True
    keep = torch.zeros_like(keep).scatter(1, indices, keep)  # 回到原 token 编号！
    return logits.masked_fill(~keep, -torch.inf)
```

用 14.5.4 第 4 步的数字逐行走一遍（输入是 top-k 之后的那行 logits，形状 (1, 5)）：

1. `logits.sort(descending=True)`：`ordered` = [2.0833, 1.25, 0.625, 0.0, −∞]，`indices` = [0, 1, 2, 3, 4]（这个例子恰好已经有序；一般情况下 `indices` 是乱的）。
2. `ordered.softmax(-1)`：`prob` = [0.5581, 0.2426, 0.1298, 0.0695, 0]。−∞ 的 softmax 是 0，所以被 top-k 去掉的 } 不会"复活"。
3. `prob.cumsum(-1) - prob`：累计和减去自己，就是"之前的累计"。`cum_before` = [0, 0.5581, 0.8007, 0.9305, 1.0]。这一行就是 14.5.3 节的 c_{j−1}。
4. `keep = cum_before < p`：[True, True, False, False, False]。
5. `keep[:, :min_keep] = True`：保证至少留 1 个。这里第 1 个本来就是 True，没有变化；但 p 极小或者浮点误差时它是保险。
6. `scatter(1, indices, keep)`：**把排序后的掩码放回原来的词表位置**。`keep` 的第 j 个元素说的是"排第 j 名的 token"，而不是"编号为 j 的 token"。`scatter` 把它写到编号 `indices[j]` 上。这个例子里 `indices` 恰好是 0..4，看不出区别；一旦最大值不在第 0 位，忘了这一步就会屏蔽错 token（14.11 节有例子）。
7. `masked_fill(~keep, -inf)`：核外设成 −∞。不需要手动归一化，后面的 softmax 会自动做。

为什么用 `cum_before < p` 而不是 `cumsum <= p`？后者会漏掉"让箱子溢出"的那个 token。用 14.5.4 的数字：cumsum = [0.5581, 0.8007, …]，`cumsum <= 0.8` 只保留 x，核从 {x, y} 变成 {x}，这就不是"累计 ≥ p 的最小集合"了。

### 14.5.6 min-p（选做）

top-p 的一个弱点：分布极平时，p = 0.9 可能要保留几千个 token，其中很多和最大值比起来小得可怜。**min-p**（Nguyen et al., 2024）换了一个相对阈值：

```text
保留 { i : p_i ≥ min_p × max_j p_j }
```

最大概率高时门槛高、候选少；最大概率低时门槛低、候选多——思路和 top-p 一样是"跟着把握走"，只是用最大值而不是累计和来衡量把握。五 token 例子在重复惩罚和温度之后（最大概率 0.5496），min-p = 0.1 的门槛是 0.0550，保留 x, y, ^, +，去掉 }（0.0153）（**本项目观察**，tour 第 1 部分）。

```python
def min_p_filter(logits, min_p):
    ...                                   # 省略：参数检查；min_p == 0 时原样返回
    prob = logits.softmax(-1)
    return logits.masked_fill(prob < min_p * prob.amax(-1, keepdim=True), -torch.inf)
```

本章的流水线把 min-p 放在 top-p 之后；min_p = 0 时它什么都不做。真实框架里 min-p 和 top-p 的先后**待验证**。

## 14.6 重复惩罚与完整流水线

### 14.6.1 动机

14.2 节看到贪心会复读。一个直接的办法：已经出现过的 token，下一次少给点分。这就是**重复惩罚**，出自 Keskar et al.（2019）的 CTRL 模型。

### 14.6.2 正负号：为什么要分开处理

CTRL 论文里的写法是把出现过的 token 的 logit 除以 θ（论文用 θ = 1.2）。对正的 logit，除以 1.2 确实变小；但**对负的 logit，除以 1.2 反而变大**：−1.0 / 1.2 = −0.8333 > −1.0。本想惩罚，结果奖励了。

Hugging Face transformers 的实现修正了这一点：logit > 0 时除以 penalty，logit < 0 时乘以 penalty（**待验证**：以你安装版本的 `RepetitionPenaltyLogitsProcessor` 源码为准）。这样不论正负，penalty > 1 时 logit 总是变小（等于 0 的不变）。本书采用这个约定：

```python
def apply_repetition_penalty(logits, prev, penalty):
    ...
    out = logits.clone()
    if penalty == 1 or prev is None or prev.numel() == 0:
        return out
    seen = logits.gather(1, prev)  # 总是读取原值；重复索引写回的是同一个变换值。
    changed = torch.where(seen > 0, seen / penalty, seen * penalty)
    return out.scatter(1, prev, changed)
```

用五 token 例子（prev = x, }，penalty = 1.2）：

- `gather` 取出 x 和 } 的原 logit：[2.0, −1.0]；
- `torch.where`：2.0 > 0 → 2.0 / 1.2 = 1.6667；−1.0 不大于 0 → −1.0 × 1.2 = −1.2；
- `scatter` 写回原位置。

tour 第 2 部分对比了 } 的三种结果（**本项目观察**）：

| 做法 | } 的 logit | } 的概率 |
|---|---|---|
| 原始 | −1.0 | 0.0280 |
| 正确：正除负乘 | −1.2 | 0.0275 |
| 错误：负数也除 | −0.8333 | 0.0392 |

错误写法让 } 的概率从 0.0280 升到 0.0392——惩罚变成了奖励。

两个细节：

- **重复出现只罚一次。** prev 里 x 出现了 3 次，也只除一次 1.2，因为 `gather` 读的总是原值，重复索引写回的是同一个数。如果想"出现越多罚越重"，那是 frequency penalty（OpenAI API 和 vLLM 有这个参数，按出现次数减去一个量，**待验证**），不是本节的乘性惩罚。
- **prev 包括提示。** `sample_sequences` 把"到目前为止的整个序列（含提示）"当作 prev。对 LaTeX 来说这是个问题：`{`、`}`、`^` 本来就该反复出现，惩罚它们会伤害语法。所以重复惩罚的系数通常只取 1.05–1.3 这样的小值（经验范围，**待验证**），用不用、用多大要实测。

### 14.6.3 处理顺序

现在把所有处理器串起来。本书的顺序是：

```text
重复惩罚 → 温度 → top-k → top-p → min-p → softmax → 抽样
```

```python
PROCESS_ORDER = ("重复惩罚", "温度", "top-k", "top-p", "min-p")

def process_logits(logits, cfg, prev=None, trace=None):
    out = logits.clone()
    if isinstance(trace, list):
        trace.append(("原始", out.clone()))
    stages = [lambda x: apply_repetition_penalty(x, prev, cfg.repetition_penalty)]
    if not cfg.greedy:
        stages += [lambda x: apply_temperature(x, cfg.temperature),
                   lambda x: top_k_filter(x, cfg.top_k),
                   lambda x: top_p_filter(x, cfg.top_p),
                   lambda x: min_p_filter(x, cfg.min_p)]
    for name, transform in zip(PROCESS_ORDER, stages):
        out = transform(out)
        if isinstance(trace, list):
            trace.append((name, out.clone()))
    return out
```

`trace` 记录每一步之后的 logits，14.5.4 节的五张表就是 tour 第 1 部分把 `trace` 逐行打印出来的结果。贪心时只有第一个阶段。

为什么是这个顺序？

1. **重复惩罚最先。** 它修改的是"模型对每个 token 的原始打分"，属于对模型的修正；温度和截断则属于"怎样从修正后的打分里抽"。对本书这种乘除式的惩罚，先后其实可以交换：T > 0 不改变正负号，(z/T)/θ = (z/θ)/T，(z/T)·θ = (z·θ)/T（**数学结论**）。但减法式的惩罚（例如 frequency penalty，从 logit 里减去一个固定量）就不能交换了：(z − c)/T ≠ z/T − c。统一"惩罚在前"可以避免这类歧义。
2. **温度在截断之前。** 截断（top-k、top-p）应该作用在"你真正要从中抽样的分布"上。温度改变了分布形状，top-p 的核就该由温度之后的分布决定。

**顺序真的会改变结果。** 还是五 token 例子（重复惩罚和 top-k 之后）：

- **温度在前**（本书）：温度 0.8 之后再 top-p，核是 {x, y}，最终 [0.6971, 0.3029]（14.5.4 节）；
- **温度在后**：先在 T = 1 的分布 [0.4966, 0.2550, 0.1546, 0.0938] 上做 top-p，累计到 y 只有 0.7516 < 0.8，核是 {x, y, ^}；再除以温度，最终 [0.5998, 0.2607, 0.1395]（**数学结论**，Python 手算）。

保留的 token 个数从 2 变成了 3。原因很清楚：T < 1 让分布变尖，x 和 y 加起来更快地越过 0.8。

top-k 和温度的先后无所谓：温度不改变排名，所以 top-k 保留的集合不变（**数学结论**）。敏感的是 top-p 和 min-p，因为它们看的是概率的大小。

> **停下来想一想：** 有人说"top-p 和 top-k 同时用，顺序无所谓"。对吗？构造一个例子：先 top-k 再 top-p，和先 top-p 再 top-k，保留集合一样吗？（提示：top-k 之后会重新归一化。）

各框架的顺序不完全一样。换框架时，**先查清它的处理顺序**，再比较参数（14.12 节）。

## 14.7 束搜索

从这一节起，转到搜索类方法。

### 14.7.1 动机：贪心的短视

贪心每一步拿当前最好的，但"每一步最好"加起来不等于"整条最好"。我们想要的（对 OCR 这类答案唯一的任务）是：

```text
y* = argmax_y log P(y | 提示) = argmax_y Σ_t log P(y_t | y_<t, 提示)
```

精确求解要枚举所有序列：长度 L、词表 V 时有 V^L 条，V = 8000、L = 30 根本数不过来。**束搜索**是一个折中：每一步只保留分数最高的 B 条部分序列（B 叫束宽，beam width）。

### 14.7.2 直觉：同时走几条路

想象你在一个陌生城市找最近的路回酒店。贪心是"每个路口都走看起来最近的方向"，可能被一条死胡同骗进去。束搜索是派 B 个朋友同时走：每到一个路口，所有人的所有可能走法放在一起比，只留总路程最短的 B 条，其余放弃。B = 1 就退化成贪心；B 足够大就等于把所有路都走一遍。

### 14.7.3 算法

状态：一组**存活**候选（还没写完），一组**完成**候选（以 EOS 结尾）。每条候选记录 token 序列和累计 log 概率。

1. 开始：存活候选只有一条空序列，累计 log 概率 0。
2. 每一步：
   - 把每条存活候选扩展成 V 条（接上每个可能的下一个 token），新分数 = 旧分数 + log P(新 token | 前缀)；
   - 把所有扩展合在一起，按累计 log 概率从大到小排序，取前 B 条；
   - 这 B 条里，以 EOS 结尾的移入"完成"列表，**以后绝不再扩展**；其余成为新的存活候选。
3. 没有存活候选，或者达到最大生成长度时停止。达到上限时还没写完的候选，也作为"被截断"的候选参与最后的比较。
4. 在所有候选中，按最终得分选最好的一条（14.8 节会给最终得分加上长度惩罚）。

本书的约定：**EOS 候选占用当步的 B 个名额**。也就是说，如果某一步排名前 B 的候选里有一条以 EOS 结尾，这一步就只剩 B − 1 条存活候选继续扩展。这让 beam = 1 严格等于贪心。真实框架的约定不同（例如 Hugging Face 每步多取一些候选，凑满 B 条未完成的，**待验证**），14.12 节再说。

### 14.7.4 带数字的例子：一个会"写空公式"的玩具模型

为了能手算，用一个只有 5 个 token 的 bigram 玩具语言模型（`short_bias_toy()`，tour 第 4 部分）。它的下一个 token 只取决于上一个 token：

| 上一个 token | 下一个 token 的概率 |
|---|---|
| `<bos>` | `<eos>` 0.30，`x` 0.70 |
| `x` | `^` 0.60，`<eos>` 0.40 |
| `^` | `2` 0.60，`x` 0.40 |
| `2` | `<eos>` 0.90，`^` 0.10 |

最大生成长度 4。所有能完整结束的序列及其概率（**数学结论**，就是把转移概率连乘；tour 第 4 部分的枚举表打印了同样的数）：

| 序列 | 概率 | log 概率 | 长度（含 EOS） |
|---|---|---|---|
| `<eos>`（空公式） | 0.30 | −1.2040 | 1 |
| `x <eos>` | 0.7 × 0.4 = 0.28 | −1.2730 | 2 |
| `x ^ 2 <eos>` | 0.7 × 0.6 × 0.6 × 0.9 = 0.2268 | −1.4837 | 4 |
| `x ^ x <eos>` | 0.7 × 0.6 × 0.4 × 0.4 = 0.0672 | −2.7001 | 4 |

（另有两条长度 4、没写完就被截断的序列 `x ^ x ^` 和 `x ^ 2 ^`，概率更小，这里略去。）

假设参考答案是 `x^2`。看三种解码：

**贪心：** 第一步 x（0.7 > 0.3），第二步 ^（0.6 > 0.4），第三步 2（0.6 > 0.4），第四步 EOS（0.9）。得到 `x ^ 2 <eos>`，概率 0.2268。对了！

**束搜索，B = 2：**

- 第 1 步：扩展空序列，得 `x`（−0.3567）、`<eos>`（−1.2040）。取前 2：两条都留下。`<eos>` 结束了，移入完成列表；存活只剩 `x`。
- 第 2 步：扩展 `x`，得 `x ^`（log 0.42 = −0.8675）、`x <eos>`（−1.2730）。`x <eos>` 移入完成；存活 `x ^`。
- 第 3 步：扩展 `x ^`，得 `x ^ 2`（log 0.252 = −1.3783）、`x ^ x`（log 0.168 = −1.7838）。都存活。
- 第 4 步：四个扩展里最高的两个是 `x ^ 2 <eos>`（−1.4837）和 `x ^ x ^`（−2.2946）。前者完成，后者到上限被截断。
- 最终比较累计 log 概率：`<eos>` 的 −1.2040 最高。

**束搜索返回了空公式。** tour 第 4 部分的输出：`beam=2；alpha=0.0000；结果=<eos>`，beam = 3 同样是 `<eos>`；暴力枚举所有序列的最优解也是 `<eos>`（**本项目观察**，与上面的手算一致）。

束搜索没有出错，它确实找到了概率更高的序列；错的是"概率最高 = 最好"这个假设。束越宽，越接近精确搜索，就越容易把这种"概率高但没用"的序列找出来。Stahlberg & Byrne（2019）在神经机器翻译上发现，精确搜索的最优解经常就是空译文——同一个现象。

### 14.7.5 对照代码

`beam_search`（`miniocr/decoding.py`）写成"与模型无关"的形式：它不直接调用 GPT，而是接受一个 `step_fn(前缀列表) → (n, V) 的 log 概率`。玩具模型和 GPT（经 `gpt_step_fn` 包装）都能传进去，这样才能在玩具分布上和暴力枚举对拍。

```python
def beam_search(step_fn, prompt, max_new, beam, eos, alpha=0.0, return_all=False):
    ...
    alive, finished = [([], 0.0)], []
    for _ in range(max_new):
        candidates = sorted(_extensions(step_fn, prompt, alive), key=lambda c: -c[1])[:beam]
        alive = []
        for tokens, total in candidates:
            if eos is not None and tokens[-1] == eos:
                finished.append(_hypothesis(tokens, total, eos, alpha))
            else:
                alive.append((tokens, total))
        if not alive:
            break
    pool = finished + [_hypothesis(tokens, lp, eos, alpha) for tokens, lp in alive]
    ...
    pool.sort(key=lambda h: -h.score)
    return pool if return_all else pool[0]
```

对照 14.7.4 节 B = 2 的手算：

- `alive = [([], 0.0)]`：一条空序列，累计 log 概率 0。
- `_extensions`：把所有存活候选组成一个批次，**每步只调用一次** `step_fn`，再对每一行把每个**正概率**的下一个 token 接上，分数相加。第 1 步得到 [`x`: −0.3567, `<eos>`: −1.2040]（零概率的边不进候选）。
- `sorted(...)[:beam]`：按累计 log 概率取前 2。**EOS 候选也占名额**——这里取到的两条里有一条是 `<eos>`。
- `if tokens[-1] == eos`：移入 `finished`，之后不会再出现在 `alive` 里，也就不会被扩展。
- `if not alive: break`：所有候选都结束了，提前停。
- 循环结束后，`alive` 里剩下的是被截断的候选，和 `finished` 一起进 `pool`。
- `_hypothesis` 计算最终得分 `score = logprob / gnmt_length_penalty(长度, alpha)`；alpha = 0 时分母是 1，就是累计 log 概率。

两个可以由测试验证的性质（`test_ch14_decoding.py`）：

- **beam = 1 等于贪心**：每步只留 1 条，就是 argmax。测试在玩具分布和随机初始化的小 GPT 上都检查了这一点。
- **束足够宽时等于暴力枚举**：束宽 ≥ V^max_new 时什么都没剪掉。测试在随机生成的小 bigram 分布上与 `brute_force_search` 逐个对比。

## 14.8 束搜索为什么偏短：长度惩罚

### 14.8.1 根本原因：log 概率只减不增

每多写一个 token，累计 log 概率就加上一个 log P(y_t | y_<t)。概率不超过 1，所以这一项 ≤ 0：

```text
log P(y_1, …, y_{t+1}) = log P(y_1, …, y_t) + log P(y_{t+1} | y_≤t) ≤ log P(y_1, …, y_t)
```

**沿同一条生成路径，每多写一个 token，累计 log 概率只减不增**（**数学结论**；只有那一步概率恰好为 1 时才相等）。注意这不等于"任何长序列都比任何短序列概率低"：如果 P(EOS | BOS) = 0.1、P(x | BOS) = 0.9、P(EOS | x) = 0.9，那么较长的 `x <eos>` 概率 0.81，远高于空序列的 0.1。但它意味着：长序列每多一步都要交一次"税"，就算每一步都写得很好，税也会累积；短序列交税少，EOS 只要在早期有一点像样的概率，就容易胜出。14.7.4 节里，空公式只交了一次税（0.30），`x^2` 交了四次（0.7、0.6、0.6、0.9），连乘下来 0.2268 输给了 0.30。

注意贪心反而没掉进这个坑：它第一步就比较了 0.7 和 0.3，选了 x，根本没有"回头比较整条序列"的机会。偏短是**比较整条序列**带来的问题，束越宽，比较得越彻底，问题越明显。

### 14.8.2 修正：按长度归一化

最直接的想法：比较"平均每个 token 的 log 概率"，即除以长度 |y|。更一般地，除以 |y|^α，α 控制修正力度。

本书采用 Wu et al.（2016）在 GNMT 中使用的长度惩罚：

```text
lp(y) = ((5 + |y|) / 6)^α
score(y) = log P(y) / lp(y)
```

- |y| 是**生成的 token 数，含 EOS，不含提示**（本书的口径）；
- α = 0：lp = 1，不修正；
- α 越大，对长序列越宽容。log P(y) 是负数，除以一个更大的 lp，得分就更接近 0，也就更高。

为什么是 (5 + |y|)/6 而不是 |y|？加 5 让短序列之间的差别变缓：|y| 从 1 到 2，|y|^1 翻倍，而 (5 + |y|)/6 只从 1 变到 1.1667。除以 6 是为了让 |y| = 1 时 lp = 1。GNMT 论文报告在他们的翻译任务上 α 取 0.6–0.7 左右效果较好（**待验证**，见精读）；对 LaTeX OCR 的最佳 α 需要你自己在验证集上调。另一种常见写法是直接用 |y|^α，Hugging Face transformers 的 `length_penalty` 参数就是这种（**待验证**）。

GNMT 长度惩罚的取值（**数学结论**，tour 第 4 部分打印了同一张表）：

| |y| | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| α = 0.6 | 1.0000 | 1.0969 | 1.1884 | 1.2754 | 1.3587 | 1.4386 |
| α = 1.0 | 1.0000 | 1.1667 | 1.3333 | 1.5000 | 1.6667 | 1.8333 |

### 14.8.3 带数字的例子：α 怎样改变答案

回到玩具模型的三条候选（tour 第 4 部分；也可以手算）：

| 序列 | log P | α = 0 | α = 0.6 | α = 1.0 |
|---|---|---|---|---|
| `<eos>` | −1.2040 | **−1.2040** | −1.2040 / 1 = −1.2040 | −1.2040 |
| `x <eos>` | −1.2730 | −1.2730 | −1.2730 / 1.0969 = **−1.1605** | −1.2730 / 1.1667 = −1.0911 |
| `x ^ 2 <eos>` | −1.4837 | −1.4837 | −1.4837 / 1.2754 = −1.1633 | −1.4837 / 1.5 = **−0.9891** |

粗体是每列的最高分。随着 α 增大，答案从空公式变成 `x`，再变成 `x^2`（**本项目观察**，tour 第 4 部分的"暴力最优"三行）。α = 0.6 时 `x` 只以 −1.1605 对 −1.1633 险胜，差 0.003。长度惩罚只是一个可调的旋钮，α 选得不同，答案就不同。

tour 第 4 部分还显示，α = 1.0 时 beam = 1、2、3 都得到 `x ^ 2 <eos>`。

本书的实现有一个简化：**长度惩罚只用于最终排序，束内剪枝仍按累计 log 概率**。这意味着如果一条长序列在中途就被剪掉了，最终的长度惩罚救不回它。这个玩具例子里 `x ^ 2 <eos>` 一路都在束里，所以没受影响；真实模型上剪枝和长度惩罚的交互更复杂，框架的做法也各不相同（**待验证**）。

> **停下来想一想：** 能不能把 α 设得非常大，比如 α = 5？会发生什么？（提示：看截断的候选 `x ^ x ^`，它的 log 概率是 −2.2946，长度也是 4。如果最大长度改成 20，长度为 20 的截断候选会怎样？）

### 14.8.4 另一种偏差：束搜索的复读

偏短之外，束搜索在开放式生成里还有一个出名的毛病：容易产生重复、乏味的文本。Holtzman et al.（2020）观察到，人写的文本，每个 token 的概率起伏很大，经常出现模型认为"不太可能"的词；而束搜索专挑高概率的路，写出来的东西概率高得"不像人"。这是他们提出 top-p 的动机之一。对于 OCR 这种答案唯一的任务，我们要的恰恰是"最可能的那个答案"，这个毛病不那么致命；但复读仍可能出现，这也是 OCR 常配重复惩罚的原因。

## 14.9 在 LaTeX GPT 上比较：可编译率与多样性

### 14.9.1 怎样选解码策略

先给结论：

| 任务 | 答案 | 推荐 | 理由 |
|---|---|---|---|
| 公式识别（OCR）、翻译、结构化抽取 | 唯一（或少数几个） | 通常优先贪心或束搜索；可加轻微重复惩罚 | 想要"最可能的答案"，输出稳定、可复现；准确率仍要在验证集上比较 |
| 开放式写作、对话、从 BOS 自由生成公式 | 很多都对 | 温度 + top-p（或 top-k、min-p） | 想要多样、自然；贪心和束搜索会复读、乏味 |
| GRPO 等强化学习的采样阶段 | 需要同一输入的一组回答来比较 | 温度采样（T 通常取 1 附近，**待验证**） | 学习信号主要来自组内奖励的差异；回答全都一样，（确定性）奖励也一样，就没有组内相对奖励信号（若启用 KL 正则，该项仍可能产生更新）。温度让组内更有机会出现奖励差异（第 25 章） |
| 自洽性投票（多次采样后投票） | 唯一 | 温度采样 + 投票 | 用多样性换稳健性 |

TexPixel 的识别模型（第四部分）推理时一般用贪心或束搜索。评测时还要注意：**解码方式是评测设置的一部分**，比较两个模型时必须用同样的解码参数。

### 14.9.2 两个指标

**可编译率**：沿用第 13 章的 mathtext 可解析率（`can_parse`），并给出 Wilson 95% 区间。它只回答"语法过不过关"，不回答"写得对不对"。

**多样性**：distinct-n（Li et al., 2016）：

```text
distinct-n = 全部样本中不同的 n 元组个数 / n 元组总数
```

n 元组在每条样本内部取，不跨样本拼接。distinct-2 接近 1 表示几乎没有重复的二元组；接近 0 表示大量复读。另一个简单指标是 `unique_ratio`：不同的完整字符串占样本数的比例。

tour 第 5 部分的口径：每条提示是 BOS 加一条验证公式的前 3 个内容 token；可解析率和 unique_ratio 看完整文本（提示 + 续写），distinct-n 和平均生成长度只看续写部分（不含提示和 EOS）。没写到 EOS 就被截断的样本也计入分母。

## 14.10 概括：投机解码

> **概括：投机解码只讲思路**
>
> **问题。** 大模型每生成一个 token 都要完整跑一次前向。生成是串行的：第 t + 1 个 token 必须等第 t 个算完。
>
> **思路。** 找一个小得多的"草稿模型"q，让它先快速猜 k 个 token；再让大模型 p 一次前向**并行**检查这 k 个位置。猜对的直接收下，猜错的地方纠正，后面的作废。一次大模型前向可能产出不止一个 token（Leviathan et al., 2023；Chen et al., 2023）。
>
> **关键：输出分布完全不变。** 对每个草稿 token x（从 q 抽出），以概率 min(1, p(x)/q(x)) 接受；拒绝时从"残差分布" norm(max(0, p − q)) 重新抽一个。可以证明，这样得到的 token 恰好服从 p（**数学结论**）：
>
> ```text
> P(抽中 x 并接受) = q(x)·min(1, p(x)/q(x)) = min(p(x), q(x))
> P(拒绝)         = 1 − β，  β = Σ_x min(p(x), q(x))
> P(输出 x)       = min(p(x), q(x)) + (1 − β)·max(0, p(x) − q(x)) / (1 − β)
>                 = min(p(x), q(x)) + max(0, p(x) − q(x)) = p(x)
> ```
>
> β 是接受率；1 − β 恰好等于残差的总质量 Σ max(0, p − q)，所以分母能约掉。两个边界：q(x) = 0 的 token 不会被草稿抽中，第一项直接写成 min(p, q) = 0 就不必除以 0，它只能通过残差输出；β = 1 时必有 p = q，草稿永远被接受，不需要重抽，残差项也就不出现。
>
> **小验证。** tour 第 6 部分取 p = [0.40, 0.25, 0.15, 0.15, 0.05]，q = [0.15, 0.35, 0.25, 0.05, 0.20]：解析算出的输出分布与 p 的最大差为 0，接受率 β = 0.65；抽 20000 次的经验分布与 p 最大差 0.0025，经验接受率 0.6522（**本项目观察**）。β 可以手算：min(p, q) = [0.15, 0.25, 0.15, 0.05, 0.05]，和为 0.65。
>
> **能快多少？** 取决于草稿模型有多准（接受率）、有多便宜，以及硬件。本书只验证了单个 token 的分布正确性，**没有实现多 token 投机解码，也没有测加速比**。

## 14.11 常见错误

tour 第 7 部分把下面前四个错误都故意写了一遍，并和正确实现对照（**本项目观察**，tour 第 7 部分）。

**1. 温度放在 top-p 之后。**
- 现象：采样分布与预期不符，核的大小随温度变化的方式不对。tour 里五 token 例子用 T = 2：正确顺序（先温度）核是 {x, y, ^, +}；错误顺序（先 top-p）核是 {x, y, ^}。T = 2 让分布变平，本该需要更多 token 才凑够 0.8。
- 怎样发现：用一个 T ≠ 1 的小例子，打印每一步的保留集合（`process_logits` 的 `trace`），和手算对比。

**2. top-p 排序后忘了映射回原索引。**
- 现象：被屏蔽的是"排在第 j 名的位置"上的词表编号，而不是"第 j 名的 token"。tour 把五个 logit 打乱成 [}, ^, x, +, y] 的顺序，正确实现保留 {^, x, y}；错误实现保留了 {}, ^, x}——把 y 扔了，把概率最低的 } 留下了。
- 怎样发现：**测试时用最大值不在第 0 位的 logits。** 如果测试的 logits 本来就降序排列，`indices` 恰好是 0..V−1，有没有 `scatter` 结果都一样，bug 就藏住了。

**3. 束搜索在 EOS 之后继续扩展。**
- 现象：完成的候选后面被接上更多 token，继续参与计分。tour 的玩具模型里 `<eos>` 之后只能接 `<eos>`（概率 1），于是错误实现得到 `<eos> <eos> <eos> <eos>`。α = 0 时 log 概率不变（−1.2040），看起来"没事"，只是多了几个 EOS；但 α = 1.0 时长度被虚增到 4，得分变成 −1.2040 / 1.5 = −0.8026，**胜过了正确答案 `x ^ 2 <eos>` 的 −0.9891**。真实模型在 EOS 之后的分布更是没训练过的垃圾。
- 怎样发现：断言"送进 step_fn 的前缀，没有一条以 EOS 结尾"。测试 `test_finished_never_expanded_and_eos_takes_slot` 就是用一个记录调用的 step_fn 检查这一点。

**4. 重复惩罚对负 logit 也用除法。**
- 现象：负 logit 被"惩罚"后反而变大。tour 里 } 的概率从 0.0280 升到 0.0392。
- 怎样发现：断言"penalty > 1 时，每个出现过的 token 的 logit 都不增"。

**5. 用 temperature = 0 表示贪心。**
- 现象：除以 0 得到 inf 或 NaN，`softmax` 输出 NaN，`multinomial` 报错或抽出奇怪的 token。
- 怎样发现：本书的 `apply_temperature` 直接拒绝 T ≤ 0。自己写时要么特判，要么用独立的 `greedy` 开关。

**6. 比较策略时口径不一致。**
- 现象：束搜索只跑了 10 条，采样跑了 50 条，就拿可解析率直接比；或者一个算了提示、一个没算。
- 怎样发现：每次都打印条数和口径（tour 第 5 部分的 `内容口径` 和 `比较口径` 两行），看 Wilson 区间的宽度。

**7. 束搜索的长度口径混乱。**
- 现象：长度惩罚里的 |y| 有时含提示，有时不含 EOS，同一模型换个提示长度，答案就变了。
- 怎样发现：在代码里写死一个口径（本书：生成 token 数，含 EOS，不含提示），并在玩具例子上手算一个得分对拍。

以下对应关系基于本书写作时对 Hugging Face transformers 和 vLLM 的了解，**全部待验证**，版本更新可能改变细节；以你所用版本的文档和源码为准。

| 本书 | Hugging Face transformers | vLLM |
|---|---|---|
| `DecodeConfig` | `GenerationConfig`（`do_sample`、`temperature`、`top_k`、`top_p`、`min_p`、`repetition_penalty`、`num_beams`、`length_penalty`…） | `SamplingParams` |

两点提醒：

- **处理顺序。** transformers 的 top-p 实现是"按升序排序，去掉累计概率 ≤ 1 − p 的那些"，在数学上与本书的"保留之前累计 < p 的"基本一致，但在恰好相等的边界上可能差一个 token（**待验证**）。如果你要和框架的输出逐位对拍，先确认顺序和边界条件。
- **束搜索的细节差别很大**：EOS 是否占名额、什么时候停、剪枝时是否已经用了长度归一化。本书为了能和暴力枚举对拍，选了最简单的约定。

## 14.13 小结

- 解码分两类：**搜索**（贪心、束搜索）找概率高的序列，结果确定；**采样**按流水线 **重复惩罚 → 温度 → top-k → top-p → min-p → 抽样** 处理 logits，顺序会改变结果，尤其是温度和 top-p 的先后。
- **top-p** 保留"累计概率 ≥ p 的最小前缀"，判断条件是"之前的累计 < p"，至少留一个，排序后的掩码必须 scatter 回原编号；它让候选数跟着模型的把握变化，这是它比 top-k 好的地方。
- **束搜索**每步按累计 log 概率保留 B 条，完成的候选不再扩展；累计 log 概率只减不增，所以它**偏爱短序列**，束越宽越明显，甚至会返回空公式。**长度惩罚** score = log P / ((5 + |y|)/6)^α 可以纠正，但 α 是需要调的旋钮。
- **重复惩罚**要正除负乘，否则负 logit 会被奖励。
- 答案唯一的任务（OCR）用贪心或束搜索；开放式生成和 GRPO 采样用温度采样。比较解码策略时同时看可编译率、多样性和长度，并用 Wilson 区间判断差别是否可信。冒烟模型的数字只证明流程跑通，哪种解码在 LaTeX GPT 上更好，要用你第 13 章完整训练得到的检查点测出来。

**术语表：** 解码策略、贪心解码、温度、熵、长尾、top-k、top-p、核采样（nucleus sampling）、核、min-p、重复惩罚、处理器、处理流水线、束搜索、束宽、存活候选、完成候选、截断候选、累计 log 概率、长度惩罚、长度归一化、GNMT 长度惩罚、暴力枚举、distinct-n、unique_ratio、可编译率、投机解码、草稿模型、接受-拒绝采样、接受率、残差分布。
