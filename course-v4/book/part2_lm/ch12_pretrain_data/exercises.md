## 答案与提示

### 概念题要点

**12.1** (1) 规范键是比较用的尺子，不一定能还原成可编译的 LaTeX 原文（解析失败时又退回原串，两种格式混在一起）；模型最终要输出人写的 LaTeX，训练分布应该像真实输出。(2) 规范键比原文长约 9%（本项目观察，CPU，第 2 部分），加了大量花括号，浪费上下文和计算。另一个可接受的理由：规范化会丢掉信息（如 `\left`、间距命令），模型就学不会生成它们。

**12.2** (a) 每组只留一条，训练集里没有重复，但删掉了副本（副本本身可能反映真实分布中的常见公式）；(b) 训练集内部仍有重复，但整组只在一边，没有跨集泄漏。想同时减少训练集内的重复（省算力、少背诵）时选 (a)，或者在 (b) 之后再对 train 内部去重。两者都必须在**划分之前**按规范键处理，不能先随机划分再去重。

**12.3** 重复比例近似和抽样比例 f 成正比（数学结论，12.3.4 节），1% 的样本会把重复率低估约 100 倍（如果重复多是成对的）。应该在几个不同规模的前缀上测，观察趋势；或者直接在全量上用哈希做精确去重（一遍扫描，代价和条数成正比）。

**12.4** Python 对字符串的 `hash` 每个进程加不同的随机盐（除非设定 `PYTHONHASHSEED`）。单进程内哈希是一致的，所以一次去重的结果"自洽"，签名之间仍可比较；但跨进程同一个 shingle 的整数不同，签名不同：结果不可复现，保存下来的签名也不能和新算的比较，分布式计算时不同机器的签名不可比。

**12.5** 假阳性会被当成近重复删掉。12.6.3 节 84 个候选里只有 31 个 J ≥ 0.8，省掉核验就会多删 53 对里的公式（本项目观察，CPU，第 6 部分；实际多删的条数取决于这些对怎样连成簇）。

**12.6** 不能。Jaccard 只看片段重合多少，不看含义。降低代价的办法：提高阈值；对长公式使用更严格的阈值或改用 containment 之外的指标；对删除的簇做抽查；在项目里，训练集去重宁可保守（少删），而训练集与测试集之间的泄漏检查宁可严格（把高 J 的测试样本标记出来人工看）。

**12.7** 对从不生成矩阵、`\le` 等 mathtext 不支持写法的模型有利：它们的"可编译率"更高，但不代表更好。原因相同：检查器只覆盖 LaTeX 的子集，把"检查器不支持"误当成"错误"。

**12.8** 计算量和学习量都按 token 计。按条数定比例时，平均长度不同的源实际占比会偏：12.8.2 节"B 占 10% 条数"对应 23.6% 的 token（数学结论）。场景：长文档源（书）和短文档源（问答）按条数 1 : 1 混合，书的 token 远多于问答，模型实际主要在读书。

**12.9** 少分词器内容：重新训练过的同名分词器会把旧编号解释成别的文字，静默产生乱码（12.9.3 节）。少数据版本：数据换了一批，旧 token 文件仍被加载，训练的不是你以为的数据。少格式版本：文件格式从 uint16 改成 uint32 后，旧文件按新格式读，每两个编号被拼成一个。缓存键不能发现"改了数据不改版本号"，因为数据版本只是人维护的字符串（练习 12.6 补上这一点）。

**12.10** 去污染（检查训练数据是否混进评测题）对应测试泄漏；质量过滤（启发式规则或分类器）对应误删风险：过滤器的偏好会变成数据的偏好。

### 手算题答案

**12.11**
1. n = 2：{(a,+), (+,b), (b,=), (=,c)} 与 {(a,+), (+,b), (b,=), (=,d)}。交集 3 个，并集 5 个，J = 3/5 = 0.6。
2. n = 3：{(a,+,b), (+,b,=), (b,=,c)} 与 {(a,+,b), (+,b,=), (b,=,d)}。交集 2 个，并集 4 个，J = 2/4 = 0.5。
3. 本题变小。这里改的是最后一个 token，n = 2 和 n = 3 都只破坏最后一个 shingle；但 n 越大，shingle 总数越少（5 − n + 1 个），剩下的共同 shingle 从 3 个降为 2 个，比例就降了。一般地，改一个 token 至多影响 n 个窗口；但 shingle 是集合，重复片段会合并，所以"n 越大 Jaccard 越小"不是必然结论，要具体计算。

（数学结论）

**12.12**
1. A ∩ B = {1, 3}，A ∪ B = {1, 2, 3, 5}，J = 2/4 = 0.5。
2. h₁ = x + 1：A → 2, 4, 6，min 2；B → 2, 3, 4，min 2。
   h₂ = 3x + 2：A → 5, 11 mod 7 = 4, 17 mod 7 = 3，min 3；B → 5, 8 mod 7 = 1, 4，min 1。
   h₃ = 2x + 5：A → 7 mod 7 = 0, 11 mod 7 = 4, 15 mod 7 = 1，min 0；B → 0, 9 mod 7 = 2, 4，min 0。
   签名 A = (2, 3, 0)，B = (2, 1, 0)。
3. 3 位里 2 位相等，估计 2/3 ≈ 0.6667，比真值大 0.1667。理论标准差 √(0.5 × 0.5 / 3) ≈ 0.2887，差距不到一个标准差，正常。

（数学结论）

**12.13**
1. √(0.25 / 128) ≈ 0.0442。
2. 0.25 / k ≤ 0.0001，k ≥ 2500。
3. 签名计算要算 k × m 个哈希值，时间和存储都和 k 成正比。12.6.3 节里签名用时约 2.4–2.5 秒，占近重复去重总用时约 2.8–2.9 秒的大部分（本项目观察，CPU，第 6 部分），k 从 128 加到 2500，哈希矩阵变成约 20 倍大，签名里与 k 成正比的那部分时间也随之变成约 20 倍；而去重只需要粗略区分"像 / 不像"，再由精确核验把关，不需要这么准。

**12.14**
1. t = (1/4)^{1/2} = 0.5。s = 0.6：0.6² = 0.36，1 − 0.36 = 0.64，0.64⁴ ≈ 0.1678，P ≈ 0.8322。
2. t = (1/2)^{1/4} ≈ 0.8409。s = 0.6：0.6⁴ = 0.1296，1 − 0.1296 = 0.8704，0.8704² ≈ 0.7576，P ≈ 0.2424。
3. 阈值 0.8 时，(4, 2) 的转折点 0.5 在阈值左边较远，J ≥ 0.8 的对几乎都能抓到（s = 0.8 时 P = 1 − 0.36⁴ ≈ 0.9832），但 J 在 0.5–0.8 的对也大量成为候选，核验成本高。(2, 4) 的转折点 0.8409 在阈值右边，s = 0.8 时 P = 1 − (1 − 0.4096)² ≈ 0.6514，会漏掉约三分之一的近重复。一般选 (4, 2)：漏掉的近重复无法补救，多出的候选可以靠精确核验挡住。k = 8 太短，两种切法都不理想，实际应加大 k。

（数学结论）

**12.15** s = t 时 s^r = ((1/b)^{1/r})^r = 1/b，代入得 1 − (1 − 1/b)^b。b = 2：1 − 0.5² = 0.75；b = 16：1 − (15/16)¹⁶ ≈ 0.6439。因为 (1 − 1/b)^b → e^{−1}，所以 b → ∞ 时趋向 1 − 1/e ≈ 0.6321。（数学结论）

**12.16**
1. 40,000 / 1,000,000 = 0.04。
2. 按"每条独立以概率 0.1 入选"的模型，每对两条都被抽中的概率 0.1² = 0.01，期望 400 对（若是固定抽 100,000 条，概率是 100000 × 99999 / (10⁶ × 999999)，期望约 399.9964 对，几乎相同）；子集约 100,000 条，比例 400 / 100,000 = 0.004，是全量的 1/10。
3. 组大小 g = 20、抽样比例 f = 0.1 时，在独立入选模型下 m 服从二项分布 B(20, 0.1)（固定条数抽样时是超几何分布，总体很大时两者几乎相同）。E[m] = 2，P(m ≥ 1) = 1 − 0.9²⁰ ≈ 1 − 0.1216 = 0.8784，期望可删条数 ≈ 2 − 0.8784 = 1.1216。20 对两两重复各贡献 0.01，共 0.2。一组 20 条的贡献约是 20 对两两重复的 5.6 倍。这解释了 12.3.4 节实测比例比"成对模型"预测得大：真实语料里有大组。

（数学结论）

**12.17**
1. 设重复组个数为 G，有同伴的条数是 D + G，1 ≤ G ≤ D，所以比例在 (D/N, 2D/N] = (0.06, 0.12] 之间。训练集几乎包含所有其他条目，有同伴的验证条目几乎一定泄漏。

### 编程题提示

**练习 12.1** 参考答案就在标记之间。注意 `x` 必须是 uint64，且已对 P 取模，否则 a·x 可能溢出。`min(axis=1)` 是按行（每个哈希函数）取最小，不是按列。

**练习 12.2** 桶表 `defaultdict(list)` 必须在段循环**里面**新建（见调试题 12.21 的反例）。切片是 `sig[band*rows:(band+1)*rows]`。用集合收集候选，因为同一对可能在多个段同桶。

**练习 12.3** 构造方法：取 0…99 当 A，取 (100 − c)…(199 − c) 当 B，交集大小 c，J = c / (200 − c)。每个 J 区间里对数不同，区间内实测比例的标准差约 √(P(1−P)/对数)。签名之间并不完全独立（共用同一组哈希系数），差距明显大于抽样误差时先查代码。

**练习 12.4** 把 train 和 eval 拼在一起算签名，记住分界下标；候选对 (i, j) 只在 i < 分界 ≤ j 时计入。规范键泄漏要按 eval 的条数计：`sum(exact_key(t) in train_keys for t in eval_texts)`；集合交集只能告诉你泄漏了哪些键，一个键可能对应多条 eval 公式。`standard_split` 按规范键分组，所以规范键泄漏应为 0（本项目观察，CPU，第 3 部分已核验）；近重复泄漏不保证为 0，结果以你的运行为准。

**练习 12.5** 替换 token 要在规范 token 序列上做，再用空格拼回，这样 `shingles` 读到的就是你改过的序列（`normalization_key` 对已规范的串通常不再改动，但要抽查）。一个 token 的改动会破坏至多 3 个 3-shingle，长公式的 J 高，短公式的 J 可能低于 0.8，所以要先按精确 J 分组再算召回。

**练习 12.6** 总摘要可以对每条的摘要逐个 `update` 进同一个 `hashlib.sha256()` 对象，顺序要固定。测试用 `tmp_path` 和一个小分词器，参照 `test_stale_tokenizer_and_version`。

**练习 12.7** containment 不对称：C(A, B) ≠ C(B, A)。找候选时可以先用 LSH 找 J 较高的对，但 J < 0.5 的对大多不会成为候选，所以要在一个小子集上暴力找，或者按 shingle 建倒排索引。

1. 用了 Python 内置 `hash`。字符串哈希每个进程加随机盐，每次运行签名不同，LSH 分桶和估计都随之变化。

**12.21**
1. 所有段共用一张桶表，第 1 段的值和另一条公式第 2 段的值碰巧相同也会同桶。候选对只会变多（正确实现的同桶对仍然同桶）。
2. 会改变结果，而且不只是浪费时间。多出来的候选对里，J 低于阈值的会被核验挡住；但其中也可能有 J ≥ 阈值、正确实现本来没抓到的对，它们通过核验，增加合并边，改变最终的簇。此外，同一条签名在两个段里的值相同时，它的下标会两次进入同一个桶，产生 (i, i) 这样的自配对（Jaccard 为 1，核验挡不住），还可能出现 (j, i)（j > i）这样的反向重复对。核验只保证每条被接受的边满足阈值，不保证和正确实现结果相同。
