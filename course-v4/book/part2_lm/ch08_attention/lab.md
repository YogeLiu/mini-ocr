## 3. 实验二：缩放对训练的影响

**问题：** 正文 8.6 节用随机数说明了不缩放时梯度会消失。在真实训练中，这会让模型学不会吗？

**预测：** 如果去掉 `/ math.sqrt(d)`，d = 64、4 个头（每头 16 维）的查表模型还能学会吗？如果每头 256 维呢？

**运行：** `LookupNet` 里的 `MultiHeadAttention` 调用的是 `miniocr.nn.attention` 模块里的 `attention` 函数。只把函数复制到你自己的文件里改掉，模型并不会用到它；要把模块里的这个名字替换掉才行：

```python
import math
import torch
import miniocr.nn.attention as A

orig = A.attention

def no_scale(q, k, v, mask=None):                  # 和原函数一样，只是不除以 √d
    scores = q @ k.transpose(-2, -1)
    if mask is not None:
        scores = scores.masked_fill(~mask, float("-inf"))
    w = scores.softmax(-1)
    return w @ v, w

# 先验证替换真的生效：同一个输入，两种实现的权重应该不同
m = A.MultiHeadAttention(64, 1)
x = torch.randn(1, 5, 64)
m(x); w1 = m.last_weights
A.attention = no_scale
m(x); w2 = m.last_weights
A.attention = orig
assert not torch.allclose(w1, w2), "替换没有生效"
```

确认替换生效以后：

1. 训练无缩放的模型之前写 `A.attention = no_scale`，训练完写 `A.attention = orig` 恢复。
2. 用 `LookupNet(Vp, T_PAIR, len(VALS), n_layers=1, d=64, n_heads=4)`（每头 16 维）和 `LookupNet(..., d=256, n_heads=1)`（每头 256 维）分别训练，对比有缩放和无缩放。可以直接调用 `tour.py` 里的 `fit_lookup` 和 `pair_batch`。
3. 每 100 步记录一次 loss，以及查询位置权重的熵（需要在 `fit_lookup` 里加几行记录代码）。

**观察：** loss 曲线下降的速度；权重的熵是否很快接近 0。

**记录：** 四种组合（每头 16 维 / 256 维 × 有 / 无缩放）的最终正确率和 loss 曲线。

提示：每头维度为 16 时，√16 = 4，不缩放的影响可能不大；维度越大影响越明显。实际结果以你的运行为准。

## 4. 实验三（进阶，选做）：一个训练不动的例子

这个实验没有标准答案，是留给你探索的。

### 4.1 现象

第 10 部分最后换了一种格式：键和值各是一个 token，`a 3 c 7 … | c → 7`，序列长 14。作者的结果（本项目观察）：

| 模型或基线 | 正确率 |
|---|---|
| MLP，看全部 14 个 token | 91.9% |
| 注意力 2 层 | 33.6% |
| 基线：随机选一个值的位置 | 25.2%（理论约 25%） |
| 基线：选出现次数最多的值（众数） | 33.5% |

注意力 2 层的预测和"众数"一致的比例是 77.0%。

这次注意力反而输给了 MLP。

### 4.2 为什么一层很难做到

查询 `c` 要匹配的是键 `c`，但答案在**键后面那个位置**。在这里描述的按键匹配并取回内容的机制下，一层注意力只能直接取回匹配位置**本身**的内容，难以直接完成"找到 c，再取它右边的值"这两步操作。

两层配合提供了一种直接的解法：

1. 第 1 层：每个值的位置先看一眼它前面的键，把"我是 c 的值"这个信息复制过来。
2. 第 2 层：查询再去匹配这些"已经带上键信息"的值的位置。

这种两层配合的结构在文献里叫**归纳头**（induction head）。这解释的是上述机制的限制，并不是说任何宽度、头数的单层模型都绝对不可能解决这个任务。

### 4.3 模型停在了哪里

正确率 33.6% 不等于"随机选一个出现过的值"（约 25%），而几乎等于"选出现次数最多的值"（33.5%），并且 77% 的预测和众数一致（本项目观察）。这**提示**模型可能主要依赖"哪个值出现得多"，而很少用到查询。但这只是行为上接近众数基线，还不能证明模型完全没用查询，剩下 23% 的预测就和众数不同。

要确认，需要做一次**干预实验**：固定 6 个键值对不变，只换问题（依次问 6 个不同的键），看模型的预测和 logits 变不变。如果完全不变，才能说模型没有用到查询。这一步留给你在 4.4 节里一起做。

为什么停在这里？一种解释是两层必须**同时**成形才有用：只有第 1 层学会了复制、第 2 层还没学会匹配时，loss 几乎不降，反过来也一样（**待验证的假设**）。

### 4.4 你可以试的方向

- 加深到 3 层。
- 课程式训练：先训练只有 2 对的短序列，再逐渐加长。
- 手工初始化：把第 1 层的权重设成"每个位置主要看前一个位置"的解，再训练。
- 待验证的配置：训练到 2 万步、更大或更小的学习率、更长的预热，以及加因果 mask 或改成单头；这些配置能否跳出平台，需要实际运行后记录。
- 先做 4.3 节说的干预实验，弄清模型现在到底用没用查询，再决定往哪个方向改。

每试一种方法，记下配置、loss 曲线和最终正确率。即使都没成功，也写下你观察到了什么。

### 4.5 要记住的教训

不是"注意力不行"，而是：**loss 长时间不动，不一定是代码错了，也可能是模型停在了一个"平台解"上。** 排查时先构造几个简单的基线（随机、众数……），看模型的预测和哪个基线一致。

## 5. 故障演练：mask 约定相反

**场景：** 你把自己的模型迁移到 `nn.MultiheadAttention` 上。训练能跑，loss 也在下降，但验证集的效果明显比原来差。

**请按下面的步骤排查**，每一步写下你看到了什么：

1. 固定一个批次，打印两个实现在同一输入上的注意力权重。（第 9 部分的输出：同一个 `keep = [True, True, False]`，传给 `key_padding_mask` 后，第 1 个查询的权重是 [0.0, 0.0, 1.0]。）
2. 查 `nn.MultiheadAttention` 的文档，看 `key_padding_mask` 里 True 的含义。
3. 改成传 `~keep`，再打印一次权重。

**要总结的教训：** mask 写反不会报错，模型也会想办法从错误的输入里学点东西，所以 loss 照样下降。换实现时，先在固定输入上对拍权重。
