# 第 6 章　实验手册：分词与 BPE

每个实验都按“预测 → 运行 → 观察 → 记录”来做。先写预测，再看输出。猜错没关系，能解释差别就有收获。

## 0. 准备

在仓库根目录进入课程目录，使用已经装好依赖的环境：

```bash
cd course-v4
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour
CUDA_VISIBLE_DEVICES="" python -m pytest -q book/part2_lm/ch06_tokenization
```

运行前先激活已装好依赖的环境。在模块名后写部分号，就只运行这些部分。输出里的用时包含该部分首次触发的公共数据准备或分词器训练。

脚本默认 CPU。它只读取本地缓存，不联网、不下载、不加载语言模型权重。LaTeX 缓存缺失时自动使用 `SAMPLE_FORMULAS`，也可以加 `--small` 主动检查降级流程。小样例只能检查流程，不适合下结论。Qwen、GPT-2、中英语料不可用时，对应比较会打印跳过提示。

GPT-2 分词器会在第 17 章下载 GPT-2 时一起拿到。到时可以回来重跑第 1、11 部分，比较三类文本的切分、相同验证集上的平均 token 数和命令切开比例。本章没有缓存就跳过。

输出放在 `outputs/book/ch06/`：

- `compression.png`：验证集字节/token 随合并次数变化的曲线。
- `bpe_2000_20000_default.json`、`bpe_4000_20000_default.json`：默认实验的分词器。文件名记录请求合并数、训练条数和预分词方案。脚本每次重新训练，不会误读旧实验缓存。

每次运行会覆盖同名产物。实验记录里保留各次终端输出，另存需要比较的图片。

划分协议见 `miniocr.data.latex_corpus`。先用规范化结果分组，再按稳定哈希排序，整组划入验证、测试和训练集合。解析失败时用清洗后的原串分组。固定数据快照、划分种子和留出条数；改变训练条数不会改变留出集。本章只评验证集，不查看测试集表现。边界组不拆开，所以验证条数可能略多于目标。

## 3. 实验一：合并次数与压缩率

**预测：** 看训练语料之前，画一条你猜的曲线。合并次数越多，每 token 平均字节数会怎样变？收益会一直一样大吗？默认规则能不能最终把 `\frac` 合成一个 token？

**运行：**

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 8 10
```

脚本只训练最长的合并表，较短分词器取它的前缀。各行使用相同训练集和验证集。小语料可能提前停下，比较时看“实际合并次数”。

**观察：** 对照压缩率、平均公式长度、nat/token 和 bits/byte。再看目标命令的预分词结果。区分“没学到”与“被词块边界禁止”这两种情况。

**记录：** 抄下每行结果，贴上曲线。用一句话说明曲线后段为什么可能变平。没有必要追求最高压缩率；词表也会影响后续模型的参数量。

## 4. 实验二：训练语料多少，验证表现有什么不同

**预测：** 固定合并预算，只用较少的公式训练，验证压缩率会怎样变？早期高频合并和晚期合并，哪一类更容易变化？

**运行：**

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 8 10 --n-train 1000
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 8 10 --n-train 20000
```

不要修改 `standard_split` 的 seed、留出条数或数据快照。只改变训练条数。脚本会打印两次运行的验证条数。

**观察：** 在相同的请求合并次数下比较验证压缩率和 bits/byte。若实际合并次数不同，记下来；较少语料可能没有足够的重复相邻对。零合并的原始字节分词器无需训练，同一验证集的 token 总数、平均长度和字节/token 应相同。但 unigram 概率仍从训练集估计，改变训练量后，nat/token、困惑度和 bits/byte 都可能变化。

**记录：** 为两次运行各填一行，列出请求与实际合并次数、训练条数、压缩率和 bits/byte。不要把训练集上的压缩率当作泛化效果。

## 5. 实验三：让反斜杠命令成为完整词块

**预测：** 如果预分词先把 `\frac` 当作一个完整词块，它会更早成为单 token 吗？中文、数字与标点会受到什么影响？压缩率一定更好吗？

**运行：**

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 4 8
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 4 8 --command-blocks
```

`miniocr/tokenizer.py` 提供的 `COMMAND_PAT` 不是挖空练习，tour 直接导入它。它先匹配反斜杠命令，并从普通标点分支中排除反斜杠，避免花括号抢走嵌套命令的开头。训练函数和分词器构造函数显式接收同一个 `pattern`；实例保存、加载时也保留规则，不修改全局 PAT。词块只是允许 BPE 在其中合并，并不直接分配整个词块一个编号。

**观察：** 先确认所有词块拼回原文，数字仍按位切。再看 `\frac`、`\mathrm`、`\alpha` 是否能变成单 token，以及早期合并结果的变化。`\left(` 含命令和括号，仍可能跨词块。

**记录：** 写下修改前后的 PAT、验证压缩率、目标命令首次合并的位置。把原来的切分与新的切分并排放好，解释差异，别只留一句“更好了”。

## 6. 故障演练：训练和编码用了不同的 PAT

**预测：** 训练时 `abc` 可以合并，编码时却逐字符切开。程序会报错吗？解码能还原原文，是否就证明编码正确？

**运行：**

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch06_tokenization.tour 12
```

读 `part12_pitfalls` 中标为“错误编码”的小例子：它保留合并表，给新实例传入逐字符的 `pattern`，故意让编码规则与训练规则不同。

**观察：** 正确结果与错误结果都能还原原文，但 token 序列不同。随后查看有缓存和无缓存的计时：两者必须输出完全相同的编号，才能把耗时差归因于缓存。不要混淆“分词算法改变”和“缓存省去了重复计算”。

**记录：** 抄下错误前后的 token 序列。写出修复：训练和构造分词器时传入相同的 `pattern`，变更规则后重新训练并创建新实例；保存、加载后也检查编号序列完全一致。再运行本章测试。另记下逐 token 解码与整体解码的差别，解释为什么不能把半个汉字分别解码后再拼接。
