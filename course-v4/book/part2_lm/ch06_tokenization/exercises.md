## 答案

### 概念题

**C1.**
- 字符级：词表小；序列长，遇到训练时没见过的字符会产生 OOV。
- 词级：序列短；词表巨大、OOV 严重。
- 子词级：常见组合合并、罕见的拆开，在词表大小和序列长度之间折中；需要训练，切出来的单位不一定有语言学意义。

**C2.** 因为它的词表有 8 万多个词条，其中 84% 只出现过一次；验证集里 48% 的 token 是 OOV，99.45% 的公式至少含一个 OOV。OOV 只能换成 `<unk>`，信息直接丢失，模型根本没法正确读入这些公式。

**C3.** 字符级的 OOV 为 0，只是因为这批公式几乎都是 ASCII 字符。验证集里一旦出现训练时没见过的汉字、emoji 或特殊符号，就会产生 OOV。字节级的初始词表是全部 256 个字节值，任何文本编码后都是字节序列，每个字节都在词表里，所以不可能出现 OOV。

**C4.** 单独解码一个只含半个汉字的 token，UTF-8 解码会失败（报错或变成 `�`）。正确做法是：先把所有 token 的字节拼接起来，再对完整的字节串整体解码。

**C5.** 预分词先把文本切成词块，BPE 只在词块内部合并、不跨越边界。这样可以避免学出跨越词和标点、或者跨越两个词的 token，比如把 `dog.`、`dog!` 学成不同的 token，或者把一个词的尾巴和下一个词的开头合在一起。

**C6.** 默认 PAT 里，`\` 属于"符号串"分支，`frac` 属于"字母串"分支，它们被切进不同的词块。BPE 不能跨越词块边界，所以它们永远不会合并。`frac` 自己在一个词块里，可以合并成单个 token（6.8.2 节的实验里，它排在第 13 位）。

**C7.** 固定的平局规则保证同样的语料训练两次得到完全相同的合并表，结果才可复现。如果随机选，每次训练的分词器都可能不同，用旧分词器训练的模型配上新分词器，token 编号就对不上了。

**C8.** 能缩短，但只能让训练语料少一个 token。代价是占用一个词表位置，而这个组合在训练集里只出现过一次，在新数据上几乎遇不到，对泛化没有帮助。收益太小、成本固定，所以我们的实现选择停止。这是工程取舍，不是"不能再压缩"。

**C9.** BPE 的合并是按顺序贪心进行的，第 k 条规则只依赖前 k−1 条规则执行后的语料状态，和后面的规则无关。所以前 k 条规则恰好就是"只训练 k 次"的结果。Unigram 是从大词表逐步删减，每一步删掉哪个取决于当前的整个词表，不存在这种"前缀"关系。

**C10.** 训练时，排名靠前的合并已经在语料里全部执行过，后面的规则是在这个状态下学到的。例如 `(b, c)` 排在 `(a, b)` 前面，说明训练时所有 `bc` 都已经合并，模型从没见过"`b` 后面跟 `c` 却没合并"的切法。用错误的顺序编码，切出来的是训练时从未出现过的 token 组合，模型对它们的统计是不可靠的。

**C11.** 词表越大，每个 token 平均装的字节越多，模型要在更多的候选里猜，所以每个 token 的 loss 升高。但同一段文本需要的 token 更少，总 loss 摊到每个字节上反而下降。bits/byte 摊的是固定不变的字节数，才是可比的。

**C12.** 用 `allow_special=False` 编码用户输入，让 `<|eos|>` 被当作普通字符切开。否则用户可以伪造结束符或消息边界，相当于"注入"了控制指令。只有程序自己拼装的模板文本才允许特殊 token。

**C13.** LaTeX 语料里几乎没有中文，2000 条合并规则里没有一条涉及汉字的字节，所以中文只能逐字节编码。这说明分词器擅长的就是它的训练语料，换了领域可能完全退化。

**C14.** 我们的 4000 条规则全部花在 LaTeX 的常见模式上，比如 `mathbb`、`pmatrix`、`ldots`；Qwen 的词表要覆盖全世界的语言和代码，分给 LaTeX 的只是一小部分，它会把 `mathbb` 切成 `math` + `bb`。

**C15.** 很多常用汉字的 UTF-8 编码前两个字节相同，比如 `上`、`下`、`不`、`与` 都以 `e4 b8` 开头。所以 `e4 b8` 这个字节对的总次数，是所有这些字的出现次数之和，超过了任何一个完整汉字。BPE 只看次数，于是先合并它。

**C16.** 字节级分词不论怎样切，所有 token 的字节拼起来都是原文的字节，所以总能还原。错在切出来的 token 序列和训练时的切法不同：模型训练时看到的是另一种 token 分布，现在给它的是罕见甚至从未见过的组合，预测质量就会下降。

**C17.** 开头的 `\frac` 是完整词块，被切开是因为 Qwen 的合并表里没有"`\` + `frac`"这条规则，属于训练语料覆盖不足，换更多 LaTeX 语料重新训练（或扩充词表）就可能合并。`+\beta` 是预分词的符号分支把 `+\` 吞在一起，`beta` 落进另一个词块，属于词块边界问题，BPE 永远跨不过去，只能改预分词规则。

### 手算题

**H1.** 4 个字符。字节数：`α` 2 + `+` 1 + `模` 3 + `🙂` 4 = 10 个字节。未训练的字节级分词器切成 10 个 token。

**H2.**
(a) 第 1 轮：
- `h u`：hug 10 + hugs 5 = 15
- `u g`：hug 10 + pug 5 + hugs 5 = 20
- `p u`：pug 5 + pun 12 = 17
- `u n`：pun 12 + bun 4 = 16
- `b u`：4
- `g s`：5

最多的是 `u g`（20），合并成 `ug`。

(b) 第 2 轮，语料变成 `h ug`×10、`p ug`×5、`p u n`×12、`b u n`×4、`h ug s`×5。计数：`h ug` 15，`p ug` 5，`ug s` 5，`p u` 12，`u n` 16，`b u` 4。最多的是 `u n`（16），合并成 `un`。

第 3 轮，语料变成 `h ug`×10、`p ug`×5、`p un`×12、`b un`×4、`h ug s`×5。计数：`h ug` 15，`p ug` 5，`ug s` 5，`p un` 12，`b un` 4。最多的是 `h ug`（15），合并成 `hug`。

三条规则依次是：`u + g → ug`，`u + n → un`，`h + ug → hug`。

(c) `bugs` 拆成 `b u g s`。相邻对 `(b, u)`、`(u, g)`、`(g, s)` 中只有 `(u, g)` 在规则表里（排名 0），合并得到 `b ug s`。剩下 `(b, ug)`、`(ug, s)` 都不在规则表里，停止。结果：`b` `ug` `s`，3 个 token。

**H3.**
(a) 相邻对 `(b, c)` 排名 1，`(c, d)` 排名 0。选 `(c, d)`，得到 `b cd`。`(b, cd)` 不在表里，停止。结果 `b` `cd`。
(b) 从左往右先遇到 `(b, c)`，合并得到 `bc d`。`(bc, d)` 不在表里，停止。结果 `bc` `d`。
(c) 按排名：先合并 `cd` 得到 `a b cd`，再合并 `ab` 得到 `ab cd`。从左往右贪心：先合并 `ab` 得到 `ab c d`，再合并 `cd` 得到 `ab cd`。这次两者结果一样。反例只说明两种做法"可能"不同，不是每个输入都不同。

**H4.** 词表大小 = 256 + 4000 + 3 = 4259。特殊 token 的编号从 256 + 4000 = 4256 开始，依次是 `<|bos|>` 4256、`<|eos|>` 4257、`<|pad|>` 4258。所以 `<|eos|>` 是 4257。

**H5.**
- 甲：$2.8 \times 1000 / (0.6931 \times 3000) = 2800 / 2079.4 \approx 1.3465$
- 乙：$2.0 \times 1500 / (0.6931 \times 3000) = 3000 / 2079.4 \approx 1.4427$

甲的 bits/byte 更低，甲更好，尽管它的 nat/token 更高。

**H6.** 由 bits/byte = nat/token ÷ (ln2 × 每 token 字节数)，得 nat/token = 1.0 × 0.6931 × 2.0 ≈ 1.3863。困惑度 = $e^{1.3863} \approx 4.0$。

**H7.** 词块是 `1`、`2`、`3`、`+`、`4`、`5`。数字每位单独成块，`+` 是一个符号块。BPE 不能跨词块合并，所以至少 6 个 token。

**H8.** 长度之比 119.78 / 58.32 ≈ 2.054，平方约 4.22。注意力部分的计算量大约变成原来的 1/4.2。

### 编程题提示

- **6.1：** 一行：`return _PAT.findall(text)`。测试会检查 `"".join(pretokenize(t)) == t`。
- **6.2：** 每轮重建 `pairs`；记住加的是词块次数 `n`，不是 1（对照调试题 D2）。
- **6.3：** 先实现朴素版，再拿它当"标准答案"对拍。最常见的错误是忘记从 `where` 里删除旧对，或者忘记删掉次数降到 0 的对。
- **6.4：** 循环里每次重新收集候选对，取 `min` 排名。不要遍历整张规则表（对照 D3）。
- **6.5：** 只在 PAT 最前面加一个 `\\[A-Za-z]+` 分支还不够。正则是从文本左边逐个位置开始匹配的：在 `{\frac` 里，匹配从 `{` 开始，标点分支 ` ?[^\s\p{L}\p{N}]+` 会把 `{\` 一起吞掉，轮不到命令分支。所以还要把标点分支改成不吃反斜杠（`[^\s\p{L}\p{N}\\]`），再在最后补一个单独匹配 `\\` 的兜底分支，保证孤立的反斜杠也能被切出来。参考答案是 `miniocr/tokenizer.py` 里的 `COMMAND_PAT`。
- **6.6：** `codecs.getincrementaldecoder("utf-8")()` 的 `decode(b, final=False)` 遇到不完整的字节会先存着，等后续字节到了再输出。
- **6.8：** 最长匹配不保证和 BPE 一致，这正是 6.6 节要说明的问题。

### 调试题

**D1.** 逐个 token 解码再拼接。只要有 token 装的是半个汉字，就会变成 `�`。修复：`b"".join(self.vocab[i] for i in ids).decode("utf-8", errors="replace")`，先拼字节再整体解码。

**D2.** `pairs[(a, b)] += 1` 应该是 `+= n`。不加权的话，一个在语料里出现 10 万次的词块，和只出现 1 次的词块贡献一样，合并的选择完全错了。现象：在 6.5 节的玩具语料上，第 1 轮的计数变成每对最多 2，选出的合并和手算不一致，`test_toy_five_rounds_match_both_trainers` 和 `test_naive_first_merges_by_hand` 会失败。

**D3.** 结果是对的：按排名顺序把每条规则都应用一遍，和"每次选当前排名最小的候选对"得到同样的切分。问题是太慢：每个词块都要遍历整张规则表（几千到几万条），而大多数规则和这个词块毫无关系。正确的写法只看当前词块里实际存在的相邻对。

**D4.** 训练和编码用了不同的预分词规则。字节级分词怎样切都能还原原文，所以解码看不出问题；但切出来的 token 序列和训练时不同，模型看到的是没见过的分布，loss 变差。修复：训练和编码必须共用同一个 PAT；要改规则，就重新训练分词器和模型。

**D5.** `<|endoftext|>` 里的 `|` 在正则里是"或"的意思，没有转义的话，正则会匹配 `<`、`endoftext`、`>` 这些片段，把普通文本也切坏。修复：用 `regex.escape(s)` 转义每个特殊 token。另外应该按长度从长到短排列，避免一个特殊 token 是另一个的前缀时被短的抢先匹配。

**D6.** 两个模型的词表不同，困惑度（每 token 的 loss）不可比。词表大的模型每个 token 装的字节更多，每个 token 的困惑度自然更高。应该在同一份验证文本上计算 bits/byte 再比较。

### 闭卷手写

对照 6.5.5 节、6.6.1 节和 6.10.2 节的代码与公式检查。第 4 题的要点：按排名编码 `bcd` 得到 `b cd`，因为训练时 `cd` 最先合并，模型从没见过未合并的 `c d`；贪心得到 `bc d`，是训练语料里不存在的切法。
