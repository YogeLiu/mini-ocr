# 第 16 章　训练工程

## 本章导读

到第 15 章为止，我们关心的都是"模型算得对不对"。这一章换一个问题：**算得下吗？算多久？**

模型一变大，三样东西会先卡住你：

- **精度**：fp32 每个数 4 字节，又慢又占地方。换成 2 字节的 fp16 或 bf16，速度和显存都好看了，但数字会溢出、会变成 0、会悄悄丢掉小的更新。
- **显存**：参数、梯度、优化器状态、激活值，一样一样加起来，常常比你以为的大好几倍。
- **计算量**：要训练多少 token、设备一秒能做多少次浮点运算、你实际用上了几成。

这一章把这三笔账算清楚，做法是**先估算，再实测，再对照**。估算对上了，这笔账才算有了依据；对不上，就去查差值从哪里来，往往是漏了什么。

**学完这一章，你能做到：**

1. 说出 fp32、fp16、bf16 的位数分配，从位数算出范围和精度（16.1）。
2. 区分前向溢出和梯度下溢，知道前者要把运算放回 fp32、后者要靠 loss scaling（16.2、16.3）。
3. 说清 GradScaler 每一步在做什么，以及梯度裁剪为什么必须放在 unscale 之后（16.4）。
4. 解释混合精度为什么要一份 fp32 主权重（16.5）。
5. 算出训练的静态显存（约 16 字节/参数）的组成，用公式估算并实测激活值（16.6、16.7）。
6. 用梯度检查点拿计算换显存，说出代价是多少（16.8）。
7. 正确实现变长样本的梯度累积（16.9）。
8. 用 6ND 估算计算量，用实测吞吐算出 MFU（16.10），做一份资源核算报告（16.11）。

**这一章不做的事：** 不跑长训练，不用 GPU。所有数字来自三处：可以推导的**数学结论**；在本项目 CPU（AMD Ryzen 9 9950X，PyTorch 2.14.1，两线程）上跑 `tour.py` 得到的**本项目观察**，注明部分号；还没实测的标**待验证**。GPU 上的数字一律留给你自己在 Mac 或 5080 上测，填进 `lab.md` 末尾的空表。

> **回顾**
> - 第 3 章讲过 fp16 下 softmax 的上溢和稳定写法（减最大值），本章 16.2 只简单带过。
> - 第 13 章推导了 C ≈ 6ND（前向 2、反向 4），讲了 N 该数哪些参数（`matmul_params`）。本章 16.10 直接使用，重点放在实测和 MFU 上。
> - 第 15 章算过 KV cache 的显存。那是推理时的账；本章算的是训练时的账。

## 16.1 浮点数的三种格式

### 16.1.1 同样 2 字节，性格完全不同

fp16 和 bf16 都占 2 字节，看起来可以互换。试试把几个数存进去再取出来（本项目观察，第 1 部分）：

| 原值 | 存成 fp16 | 存成 bf16 |
|---|---|---|
| 70000 | **inf** | 70144 |
| 1e-8 | **0** | 1.0012e-8 |
| 1.001 | 1.0009765625 | **1.0** |
| 0.1 | 0.0999755859375 | 0.10009765625 |

fp16 装不下 70000，也装不下 1e-8；bf16 两个都装得下，可它把 1.001 变成了 1.0。

一个怕大怕小，一个看不清细节。要明白为什么，得看这 16 位是怎么分的。

### 16.1.2 科学计数法的二进制版

浮点数就是二进制的科学计数法：

$$x = (-1)^{\text{符号}} \times 1.\text{尾数} \times 2^{\text{指数}}.$$

16 位或 32 位分成三段：

- **符号位**：1 位，正还是负。
- **指数位**：决定"小数点挪几位"，也就是**范围**——能多大、能多小。
- **尾数位**：决定"1 后面有几位有效数字"，也就是**精度**——相邻两个数挨得多近。

打个比方：指数位是尺子的长度，尾数位是尺子的刻度密度。总位数固定时，尺子越长，刻度就越稀。

| 格式 | 符号 | 指数 | 尾数 | 总位数 |
|---|---|---|---|---|
| fp32 | 1 | 8 | 23 | 32 |
| fp16 | 1 | 5 | 10 | 16 |
| bf16 | 1 | 8 | 7 | 16 |

（数学结论，IEEE 754 与 bfloat16 的定义；第 1 部分打印并与 `torch.finfo` 对拍。）

bf16 的设计很直接：**把 fp32 的低 16 位尾数砍掉**。指数位和 fp32 一样多，所以范围一样大；尾数只剩 7 位，所以精度很粗。fp16 则是在范围和精度之间折中，结果两头都不够大方。

### 16.1.3 从位数算出范围和精度

设指数有 e 位，尾数有 m 位（不含那个隐含的首位 1）。

**第一步：偏置。** 指数位存的是无符号整数，要减掉一个偏置才得到实际的指数：

$$\text{bias} = 2^{e-1} - 1.$$

全 0 和全 1 两个指数编码另有用途（全 0 表示零和非正规数，全 1 表示 inf 和 NaN），所以正常的指数范围是 1 − bias 到 bias。

**第二步：最大值。** 指数取最大 bias，尾数全是 1，即 1.111…1₂ = 2 − 2⁻ᵐ：

$$\text{max} = (2 - 2^{-m}) \times 2^{\text{bias}}.$$

**第三步：最小正规数。** 指数取最小 1 − bias，尾数全 0：

$$\text{tiny} = 2^{1-\text{bias}}.$$

**第四步：最小非正规数。** 比 tiny 还小的数，放弃隐含的首位 1，用 0.000…1₂ 表示，这叫**非正规数**（subnormal）。最小的一个是

$$\text{subnormal} = 2^{1-\text{bias}} \times 2^{-m}.$$

非正规数是"渐进下溢"：越靠近 0，有效位越少，精度越差。比它再小一半，就只能舍入成 0。

**第五步：eps。** 1 和下一个可表示数之间的距离：

$$\text{eps} = 2^{-m}.$$

**第六步：任意位置的间隔。** 对正规数 x，它所在的区间 [2ᵏ, 2ᵏ⁺¹) 里，间隔都是 2ᵏ × eps，其中 k = ⌊log₂|x|⌋：

$$\text{spacing}(x) = 2^{\lfloor \log_2 |x| \rfloor} \times \text{eps}.$$

这是一个**相对**精度：数越大，间隔越大，但间隔与数之比大致不变（在 eps/2 到 eps 之间）。

### 16.1.4 数值例子：fp16 和 bf16

**fp16**（e = 5，m = 10）：

- bias = 2⁴ − 1 = 15
- max = (2 − 2⁻¹⁰) × 2¹⁵ = 65536 − 32 = **65504**
- tiny = 2⁻¹⁴ ≈ **6.10 × 10⁻⁵**
- subnormal = 2⁻¹⁴ × 2⁻¹⁰ = 2⁻²⁴ ≈ **5.96 × 10⁻⁸**
- eps = 2⁻¹⁰ ≈ **0.000977**

**bf16**（e = 8，m = 7）：

- bias = 127
- max = (2 − 2⁻⁷) × 2¹²⁷ ≈ **3.39 × 10³⁸**
- tiny = 2⁻¹²⁶ ≈ **1.18 × 10⁻³⁸**（和 fp32 相同）
- subnormal = 2⁻¹³³ ≈ **9.18 × 10⁻⁴¹**
- eps = 2⁻⁷ = **0.0078125**

fp32 的 max ≈ 3.40 × 10³⁸，eps = 2⁻²³ ≈ 1.19 × 10⁻⁷。（以上全部是数学结论；第 1 部分逐项与 `torch.finfo` 对拍，全部一致，最小非正规数还用 `torch.nextafter(0, 1)` 实测了一遍。）

现在回头解释 16.1.1 的表：

- **70000 → fp16 是 inf**：最大有限值是 65504，就近舍入下大于等于 65520 的数都舍入成 inf。
- **70000 → bf16 是 70144**：70000 落在 [2¹⁶, 2¹⁷) 里，bf16 的间隔是 2¹⁶ × 2⁻⁷ = 512。70000 / 512 ≈ 136.7，舍入到 137 × 512 = 70144。范围够，刻度粗。
- **1e-8 → fp16 是 0**：比最小非正规数 5.96 × 10⁻⁸ 的一半还小。
- **1.001 → bf16 是 1.0**：1 附近 bf16 的间隔是 eps = 0.0078，0.001 不到半格，舍掉了。

第 1 部分还打印了几个位置的间隔（数学结论）：

| x | fp16 间隔 | bf16 间隔 |
|---|---|---|
| 1 | 0.000977 | 0.0078 |
| 256 | 0.25 | 2 |
| 1000 | 0.5 | 4 |
| 65504 | 32 | 256 |

bf16 在 256 附近间隔是 2，所以 **256 + 1 = 256**（本项目观察，第 1 部分）。

### 16.1.5 代码：`float_format`

`miniocr/train/precision.py` 把上面的推导直接写成代码：

```python
_FORMATS = {"fp32": (8, 23, torch.float32), "fp16": (5, 10, torch.float16),
            "bf16": (8, 7, torch.bfloat16)}

def float_format(name):
    e, m, dtype = _FORMATS[name]
    bias = 2**(e-1)-1
    return dict(..., max=(2-2.0**-m)*2.0**bias, tiny=2.0**(1-bias),
                subnormal=2.0**(1-bias-m), eps=2.0**-m)
```

- 第 1 行：每种格式的 (指数位 e, 尾数位 m)。fp16 是 (5, 10)。
- `bias = 2**(e-1)-1`：fp16 得 15。
- `max`：(2 − 2⁻¹⁰) × 2¹⁵ = 65504。
- `tiny`：2^(1−15) = 2⁻¹⁴。
- `subnormal`：2^(1−15−10) = 2⁻²⁴。
- `eps`：2⁻¹⁰。

`spacing(x, dtype)` 用 `math.frexp` 取出 ⌊log₂|x|⌋，再乘 eps：

```python
return 2.0**(math.frexp(abs(x))[1]-1)*f["eps"]
```

`math.frexp(1000)` 返回 (0.977, 10)，即 1000 = 0.977 × 2¹⁰，所以 ⌊log₂ 1000⌋ = 10 − 1 = 9。fp16 下间隔 2⁹ × 2⁻¹⁰ = 0.5，和上表一致。

## 16.2 前向溢出：把危险的运算放回 fp32

### 16.2.1 归一化的结果是 1，中间却是 inf

RMSNorm 的输出大约是"单位大小"。但它要先算 x² 的均值。设一个 64 维向量每个元素都是 300（激活值偶尔这么大并不稀奇）：

$$\frac{1}{64}\sum x_i^2 = 300^2 = 90000 > 65504.$$

在 fp16 里，这一步就是 inf。接着 rsqrt(inf) = 0，输出 x × 0 = 0。本该是 1 的输出全变成了 0（本项目观察，第 2 部分：`fp16均方=inf`，朴素 RMSNorm 输出 `[0.0, 0.0, 0.0]`）。

这就是**前向溢出**：某个**中间结果**超出了范围。输入和输出都不大，坏在中间。

### 16.2.2 对策：输入可以是 fp16，中间要在 fp32 里算

办法是把容易溢出的运算先转成 fp32，算完再转回去。哪些运算危险？

- **求平方和、求和**：RMSNorm、LayerNorm 里的均值和方差，以及长序列的累加。
- **指数**：softmax、交叉熵。exp(12) ≈ 162755，已经超过 65504。
- **很长的累加**：下面马上看到，就算不溢出，也会"加不进去"。

项目里的 `RMSNorm` 就是这么写的（第 9 章）：内部先 `.float()`，算完再转回输入的 dtype。第 2 部分里同一个全 300 的向量，项目 RMSNorm 输出 `[1.0, 1.0, 1.0]`（本项目观察）。`GPT.forward` 的交叉熵也先 `.float()`（第 11 章）。

softmax 的故事第 3 章讲过，这里只看一眼结果（本项目观察，第 2 部分，logits = [12, 11, 0]，fp16）：

| 写法 | 结果 |
|---|---|
| 朴素 exp / sum（fp16） | [nan, 0, 0] |
| 先减最大值（fp16） | [0.73096, 0.26880, 4.47e-6] |
| fp32 | [0.73106, 0.26894, 4.49e-6] |

减最大值解决了溢出；和 fp32 的差别来自 fp16 只有约 3 位有效数字。

### 16.2.3 另一种坏法：加不进去

溢出至少会报 inf，容易发现。下面这个更阴险：什么都不报，只是数不对。

在 fp16 里把 0.01 连续加一万次，每次加完都存回 fp16。正确答案是 100。结果是（本项目观察，第 2 部分）：

- fp16：**32**
- fp32：100.003

为什么停在 32？算一下 32 附近的间隔：32 = 2⁵，fp16 间隔 = 2⁵ × 2⁻¹⁰ = 1/32 = 0.03125。0.01 不到半格（0.0156），32 + 0.01 舍入回 32。从此以后，每一次加法都白做（数学结论）。

规律是：**当累加和与每次的增量相差约 2ᵐ⁺¹ 倍以上，增量就被吞掉**。fp16 的 m = 10，相差两三千倍就开始出问题；bf16 的 m = 7，相差几百倍就开始。所以 loss 的求和、梯度范数的平方和、优化器里的累加，都要在 fp32 里做。（矩阵乘法内部的累加，GPU 通常用 fp32 累加器，具体取决于硬件和库，待验证。）

### 16.2.4 常见错误

- **现象**：fp16 训练时 loss 一开始就是 nan，或某几层输出全 0。
  **怎样发现**：给每层输出挂 forward hook，打印 `isfinite().all()` 和最大绝对值，找第一个出问题的层；看是不是归一化或 softmax。
- **现象**：bf16 训练的 loss 曲线比 fp32 "平"得可疑，后期降不动。
  **怎样发现**：检查 loss 累加、指标统计是不是在 bf16 里做的（16.2.3 的"加不进去"）。
- **误解**：以为 loss scaling 能解决前向溢出。不能。loss scaling 放大的是**反向**的梯度（下一节）；前向已经是 inf，乘什么都还是 inf。

## 16.3 梯度下溢与 loss scaling

### 16.3.1 梯度太小，存进 fp16 就没了

前向的问题是"太大"，反向的问题常常是"太小"。训练到后期，很多梯度分量在 10⁻⁶ 甚至 10⁻⁸ 量级。fp16 的最小正规数是 6.1 × 10⁻⁵，最小非正规数是 6.0 × 10⁻⁸。比 3 × 10⁻⁸ 小的梯度，存进 fp16 直接变成 0。

做个实验（本项目观察，第 3 部分）：一万个梯度，服从均值 0、标准差 10⁻⁷ 的正态分布，直接存成 fp16，再取出来：

- **23.78%** 变成了 0；
- 和原值的相对误差（L2）是 **0.170**。

将近四分之一的梯度消失，剩下的也大多落在非正规数区，有效位很少。

### 16.3.2 先放大，再缩回去

办法很像用放大镜：**东西太小看不清，先放大，看完再按比例换算回来**。

反向传播是线性的：loss 乘 S，每个梯度也乘 S。于是：

1. 反向之前，把 loss 乘一个大数 S（比如 2¹⁶ = 65536）；
2. 反向得到的梯度都是真实梯度的 S 倍，躲开了下溢区；
3. 更新参数之前，在 **fp32** 里把梯度除以 S，还原成真实大小。

这就是 **loss scaling**。

### 16.3.3 S 放大了什么，没放大什么

设真实梯度 g，fp16 的舍入记作 fl(·)。

- **不缩放**：存的是 fl(g)。|g| < subnormal / 2 时 fl(g) = 0。
- **缩放 S**：存的是 fl(Sg)，还原成 fl(Sg) / S。只要 S|g| 落进正规数范围 [6.1 × 10⁻⁵, 65504]，fl(Sg) 的相对误差就不超过 eps / 2 ≈ 4.9 × 10⁻⁴，除以 S（在 fp32 里，2 的幂，精确）不再增加误差。

所以 S 做的事是**把数挪到正规数区**，它**不增加尾数位数**。挪进去以后，精度就由 fp16 的 10 位尾数决定，再放大也不会更准。

S 也不能无限大：S·|g| 一旦舍入成 inf（fp16 就近舍入下，大于等于 65520 就变成 inf；65504 是最大有限值），除回去也没用。所以 S 要"足够大，又别太大"。

### 16.3.4 数值例子

同一批梯度，乘不同的 S（本项目观察，第 3 部分）：

| S | 变成 0 的比例 | 变成 inf 的比例 | 相对误差 |
|---|---|---|---|
| 1 | 23.78% | 0 | 0.170 |
| 2¹⁰ | 0.02% | 0 | 2.30 × 10⁻⁴ |
| 2¹⁶ | 0 | 0 | 2.04 × 10⁻⁴ |
| 2²⁴ | 0 | 0 | 2.04 × 10⁻⁴ |

从 2¹⁶ 到 2²⁴，误差几乎不再下降：S = 2¹⁶ 时绝大多数分量已经进入正规数区（按同样的种子复算，还有约 0.8% 的分量小于 tiny，到 2²⁴ 才全部进入），剩下的那点小分量对总体 L2 误差影响很小，误差主要来自 fp16 尾数本身的舍入。

验算一下 23.78%：|g| < 2⁻²⁵ ≈ 2.98 × 10⁻⁸ 才会舍成 0，即 |z| < 0.298（z 是标准正态）。查正态表，P(|z| < 0.298) ≈ 0.234（数学结论）。和实测的 0.2378 吻合。

第 3 部分还在一个小 MLP 上做了一次实际的反向：loss ≈ 2.0 × 10⁻¹¹（故意弄小），把梯度按 fp16 舍入。不缩放时 **100%** 的梯度是 0；S = 2¹⁶ 时零比例降到 2.5%，相对误差 0.0038（本项目观察）。

### 16.3.5 代码：`quantize_gradients`

```python
q = (grad.float()*scale).half()
restored = q.float()/scale
error = (restored-grad).norm()/grad.norm()...
return dict(zero_fraction=(q == 0).float().mean().item(),
            inf_fraction=torch.isinf(q).float().mean().item(), ...)
```

- `(grad*scale).half()`：放大后存成 fp16。S = 1 时 23.78% 变成 0。
- `q.float()/scale`：转回 fp32 再除以 S。注意顺序：先转 fp32 再除，否则在 fp16 里除，又掉回下溢区。
- `zero_fraction`、`inf_fraction`：两个方向的失败都要看。

这里模拟的只是"梯度存进 fp16"这一处的舍入。真实的 fp16 混合精度训练里，autocast 按设备和算子决定每个算子用什么精度，反向算子沿用对应前向的精度，所以低精度舍入不止这一处（具体误差待验证，需要在 GPU 上用 autocast 实测）。

## 16.4 GradScaler 怎样工作

### 16.4.1 S 该取多少？

16.3 留了个问题：S 太小，梯度下溢；S 太大，梯度溢出成 inf。而且训练过程中梯度的大小一直在变。手动调一个固定的 S 很难。

**GradScaler** 的做法是**动态调整**，规则只有两条：

1. **出现 inf 或 NaN**：可能是 S 太大了（也可能是别的数值问题，GradScaler 不分辨原因）。**这一步不更新参数**，S 减半。
2. **连续 N 步都正常**：也许 S 可以更大。S 翻倍。

### 16.4.2 一步训练里的顺序

用了 GradScaler，一步训练变成六个动作，顺序不能乱：

```
loss = model(x)                          # 前向
scaler.scale(loss).backward()            # ① loss × S，再反向：梯度是 S 倍
scaler.unscale_(optimizer)               # ② 梯度 ÷ S，同时检查有没有 inf/NaN
clip_grad_norm_(params, max_norm)        # ③ 在真实大小的梯度上裁剪
scaler.step(optimizer)                   # ④ 有 inf/NaN 就跳过，否则 optimizer.step()
scaler.update()                          # ⑤ 调整 S
```

第 13 章的 `train_pretrain` 就是这个顺序（scale → backward → unscale_ → clip → step → update）。

### 16.4.3 数值例子：八步走一遍

设 S 初值 2¹⁶ = 65536，增长间隔 2（连续 2 步正常就翻倍；真实默认是 2000，这里为了演示改小），第 2、3 步人为注入 inf。参数 p 初值 1，梯度恒为 1，学习率 0.1（本项目观察，第 4 部分）：

| 步 | 本步 S | 有 inf？ | 更新了吗 | 连续正常计数 | 下一步 S | p |
|---|---|---|---|---|---|---|
| 1 | 65536 | 否 | 是 | 1 | 65536 | 0.9 |
| 2 | 65536 | **是** | 跳过 | 0 | 32768 | 0.9 |
| 3 | 32768 | **是** | 跳过 | 0 | 16384 | 0.9 |
| 4 | 16384 | 否 | 是 | 1 | 16384 | 0.8 |
| 5 | 16384 | 否 | 是 | 2 → 翻倍，清零 | 32768 | 0.7 |
| 6 | 32768 | 否 | 是 | 1 | 32768 | 0.6 |
| 7 | 32768 | 否 | 是 | 2 → 翻倍，清零 | 65536 | 0.5 |
| 8 | 65536 | 否 | 是 | 1 | 65536 | 0.4 |

两个观察：

- 跳过的那两步，p 一点都没动。坏梯度没有污染参数和优化器状态。
- 每次正常更新，p 都只减 0.1，和 S 是多少无关。S 只是"中间换算"，最终的更新量由真实梯度决定。

第 4 部分把同一个序列交给 PyTorch 的 `torch.amp.GradScaler("cpu", init_scale=2**16, growth_interval=2)`，八步的 S、是否跳步、p 全部一致（本项目观察）。

### 16.4.4 代码：`SimpleGradScaler`

教学版在 `miniocr/train/precision.py`，挑最核心的三个方法看：

```python
def scale(self, loss):
    return loss*self._scale
```

前向得到的 loss 乘 S。反向时链式法则会把 S 带到每个梯度上。

```python
def unscale_(self, optimizer):
    ...
    bad = False
    with torch.no_grad():
        for g in grads:
            bad |= not bool(torch.isfinite(g).all())
            g.mul_(1.0/self._scale)
    self._states[key] = dict(stage="unscaled", found_inf=bad)
```

- 遍历每个梯度，检查有没有 inf/NaN，记在 `bad` 里。
- 原地除以 S。第 2 步里梯度被设成 inf，`bad = True`。
- 同一步再调用一次会报错：除两次 S，梯度就小了 S 倍。

```python
def step(self, optimizer):
    ...
    executed = not state["found_inf"]
    if executed:
        optimizer.step()

def update(self):
    if self.found_inf:
        self._scale = ... self._scale*self._backoff_factor ...   # 第 2 步：65536 → 32768
        self._growth_tracker = 0
    else:
        self._growth_tracker += 1
        if self._growth_tracker == self._growth_interval:        # 第 5 步：计数到 2
            ... self._scale*self._growth_factor ...              # 16384 → 32768
            self._growth_tracker = 0
```

`step` 在有 inf 时直接不调用 `optimizer.step()`；`update` 按上面两条规则改 S。对照 16.4.3 的表逐行走一遍，每个数都能对上。

### 16.4.5 为什么裁剪必须在 unscale 之后

梯度裁剪（第 4 章）的规则是"梯度范数超过 max_norm 就等比缩到 max_norm"。它比的是**真实梯度**的范数。

如果在 unscale 之前裁剪，看到的是 S 倍的梯度。第 4 部分的例子（本项目观察）：真实梯度 [3, 4]，范数 5；S = 1024；max_norm = 1；学习率 0.1。

| 顺序 | 裁剪时看到的范数 | 实际用于更新的梯度范数 | 更新量 |
|---|---|---|---|
| 正确：unscale → clip | 5 | 1.0 | 0.1 |
| 错误：clip → unscale | 5120 | 0.000977 | 9.77 × 10⁻⁵ |

错误顺序先把 5120 缩到 1，再除以 1024，得到 1/1024。更新量小了 1024 倍，而且**不报任何错**。训练会很慢，但你很难想到是这里出了问题。

> **停下来想一想：** 用 bf16 训练时，通常不用 GradScaler。为什么？（提示：16.1.4 里 bf16 的 tiny 是多少？）

## 16.5 主权重为什么要 fp32

### 16.5.1 一百次更新，一次都没生效

前两节解决了"梯度存不下"。还有一个问题在**参数更新**上。

设参数 p = 1.0，每步更新量 lr × g = 10⁻⁴，做 100 步，正确结果是 0.99。分别在三种精度里存参数（本项目观察，第 5 部分）：

| 参数精度 | 100 步后 |
|---|---|
| bf16 | **1.0** |
| fp16 | **1.0** |
| fp32 | 0.9899983 |

bf16 和 fp16 里，参数一动不动。

### 16.5.2 为什么一动不动

p 略小于 1 时落在 [0.5, 1) 里。bf16 在这里的间隔是 2⁻¹ × 2⁻⁷ = 2⁻⁸ ≈ 0.0039，半格是 0.00195。1 − 10⁻⁴ 离 1 只有 10⁻⁴，不到半格，舍入回 1。下一步还是一样（数学结论）。

fp16 在 [0.5, 1) 的间隔是 2⁻¹¹ ≈ 0.00049，半格 0.00024，10⁻⁴ 同样不到半格。

一般地，**更新量与参数之比小于约 eps / 4，这次更新就被吞掉**。而训练后期 lr × g / p 常常就是 10⁻⁴ 甚至更小的量级。这和 16.2.3 的"加不进去"是同一件事：参数就是一个长期的累加和。

### 16.5.3 对策：低精度算，高精度存

**混合精度训练**的标准做法：

- 保留一份 **fp32 主权重**（master weights）。优化器在它上面更新，小的更新可以累积起来。
- 每一步从主权重拷一份 bf16/fp16 的**计算副本**，前向和反向用它，快、省显存。
- 反向得到的低精度梯度转成 fp32，交给优化器更新主权重。

所以"混合"指的是计算用低精度、存储用高精度。

### 16.5.4 bf16 还是 fp16？

把前面几节放在一起：

| | fp16 | bf16 |
|---|---|---|
| 范围 | 小（max 65504） | 和 fp32 一样 |
| 精度 | 10 位尾数 | 7 位尾数 |
| 梯度下溢 | 常见，要 loss scaling | 很少，一般不用 |
| 前向溢出 | 要小心 | 很少 |
| 可训练参数的主权重 | 默认留 fp32 | 默认留 fp32 |

设备支持 bf16 时，大多数人选 bf16：省掉 GradScaler，少一类故障。它的代价是精度更粗，所以敏感运算仍要放 fp32，可训练参数默认也要留 fp32 主权重。冻结的参数不更新，不需要主权重。直接在 bf16 上更新也跑得起来，只是要承担小更新被吞掉的风险：第 33 章 33.3.6 节的 merger 就是这种情况，那里说明了要留意什么。你的设备是否支持 bf16、bf16 是否真的更快，取决于硬件和 PyTorch 版本（待验证，在 Mac/5080 上按 `lab.md`"在 Mac / 5080 上自己测"一节实测）。

## 16.6 静态显存：每参数约 16 字节

### 16.6.1 模型 1.2 GB，为什么训练要十几 GB？

第 15 章说过，Qwen3-0.6B 的 bf16 权重约 1.2 GB（待验证）。很多人第一次全参微调，以为准备 2 GB 显存就够了，结果一上来就 OOM（out of memory，显存不足）。

训练时显存分两类：

- **静态显存**：和批大小、序列长度无关，只看参数量。包括参数、梯度、优化器状态、主权重。
- **激活显存**：前向时保存下来、反向时要用的中间结果，随批大小和序列长度增长（16.7）。

这一节算静态的。

### 16.6.2 两种口径都是 16

用 AdamW 训练，每个可训练参数要存：

**口径一：纯 fp32**

| 项 | 字节 |
|---|---|
| 参数（fp32） | 4 |
| 梯度（fp32） | 4 |
| AdamW 一阶矩 m（fp32） | 4 |
| AdamW 二阶矩 v（fp32） | 4 |
| **合计** | **16** |

**口径二：混合精度（bf16 计算副本 + fp32 主权重）**

| 项 | 字节 |
|---|---|
| 计算用参数（bf16） | 2 |
| 梯度（bf16） | 2 |
| 主权重（fp32） | 4 |
| m（fp32） | 4 |
| v（fp32） | 4 |
| **合计** | **16** |

（数学结论；第 6 部分用 `static_memory(1, 1, ...)` 打印。）

两种口径**总量相同，组成不同**。混合精度省的不是静态显存，而是**激活显存**（激活用 2 字节存）和**计算时间**。很多人以为"换成 bf16，显存减半"，对静态部分来说并不成立。

有些参数冻结、不训练时，冻结的参数只需要存权重本身。设总参数 N、可训练参数 Nₜ，混合精度下：

$$\text{静态} = 2N + 14N_t \text{ 字节}.$$

（数学结论：2N 是所有参数的 bf16 权重；每个可训练参数再加梯度 2、主权重 4、m 和 v 共 8。）第 20 章的 LoRA 就是让 Nₜ 远小于 N。

### 16.6.3 数值例子

第 6 部分的估算（数学结论；参数量来源见各行）：

| 模型 | 参数量 | 全参 fp32 | 全参混合 | 只训 1%（混合） |
|---|---|---|---|---|
| 本项目 medium（V = 512） | 918,656 | 14.0 MiB | 14.0 MiB | 1.87 MiB |
| 本项目 large（V = 512） | 2,755,008 | 42.0 MiB | 42.0 MiB | 5.62 MiB |
| Qwen3-0.6B 骨架 | 596,049,920 | 8.88 GiB | 8.88 GiB | 1.19 GiB |

Qwen3-0.6B 的参数量由 `qwen_like_params` 从本地 Qwen3-0.6B config 按标准结构算出。config 里 `tie_word_embeddings=true`，嵌入共享。这个数和第 20 章的基座参数量 596,049,920 相同。

手算一遍 Qwen 那行：

- 全参：596,049,920 × 16 = 9,536,798,720 字节。除以 2³⁰ 得 **8.88 GiB**。
- 只训 1%：Nₜ = 5,960,499。2N = 1,192,099,840，14Nₜ = 83,446,986，合计 1,275,546,826 字节 ≈ **1.19 GiB**。几乎全是 bf16 权重本身。

全参微调 0.6B 的模型，**还没算激活**，静态部分就要将近 9 GiB。第三部分上 GPU 做实验之前，先算这笔账。

### 16.6.4 实测：真的数一遍张量字节

估算对不对，要实测。`measure_static_bytes` 遍历模型参数、`.grad` 和优化器的 `state`，把每块存储的字节加起来（共享权重只算一次）。在 tiny 模型（V = 512，139,584 个参数）上做一次反向和一次 AdamW 更新（本项目观察，第 6 部分）：

| 口径 | 估算（字节） | 实测（字节） | 差 |
|---|---|---|---|
| fp32 | 2,233,344 | 2,233,424 | 80 |
| 混合精度 | 2,233,344 | 2,233,424 | 80 |

估算 = 139,584 × 16 = 2,233,344（数学结论）。差的 80 字节是什么？PyTorch 的 AdamW 给每个参数张量存一个 `step` 计数（4 字节的张量）。tiny 有 20 个参数张量（2 层 × 9 个 + 嵌入 + 最后的 norm；输出层和嵌入共享），20 × 4 = 80，差值全部解释清楚。

### 16.6.5 代码：`measure_static_bytes`

```python
def size(t):
    st = t.untyped_storage()
    key = (str(t.device), st.data_ptr())
    if key in seen:
        return 0
    seen.add(key)
    return st.nbytes()
```

按存储（storage）去重：共享权重的嵌入和输出层是同一块内存，只算一次。

```python
for module, pk, gk in ((model, "params", "grads"), (master_model, "master", "master_grads")):
    if module is not None:
        for p in module.parameters():
            out[pk] += size(p)
            if p.grad is not None:
                out[gk] += size(p.grad)
```

计算模型的参数和梯度记到 params、grads；混合精度时，fp32 主模型的参数记到 master。

```python
def visit(value, name):
    if isinstance(value, torch.Tensor):
        n = size(value)
        if name == "step":
            out["step"] += n
        else:
            out["optim"] += n
```

递归遍历 `optimizer.state`：`exp_avg`（m）和 `exp_avg_sq`（v）记到 optim，`step` 单列。tiny fp32 时 m、v 各 558,336 字节，step 合计 80 字节。

注意：AdamW 的 m、v 是**第一次 `step()` 时才创建**的。只做前向反向就测，优化器状态是 0。这也是很多人实测时"显存在第一步之后突然涨一截"的原因。

## 16.7 激活显存

### 16.7.1 静态算对了，还是 OOM

静态显存和批大小无关。可实际训练时，批大小一加倍，显存就涨一大截。涨的是**激活**。

激活是"前向时算出来、反向时还要用"的中间结果。比如 y = xW，反向求 ∂L/∂W = xᵀ(∂L/∂y) 时要用到 x，所以前向时必须把 x 存下来。每一层都存一些，所有层加起来就是激活显存。

### 16.7.2 存的东西正比于 B × T，注意力还有 T²

每个 token 在每层都要存若干个长 d 或长 f 的向量，所以激活大致是

$$\text{激活} \approx L \times (a' \cdot B T + b' \cdot B h T^2).$$

第一项是"每个 token 存几个向量"；第二项来自注意力权重矩阵，形状 (B, h, T, T)。**B 翻倍，激活翻倍；T 翻倍，激活多于翻倍。**

### 16.7.3 逐项数出 manual 注意力的保存量

以本项目的 GPT（Pre-Norm、RMSNorm、manual 注意力、SwiGLU）为例。记 L = 层数，d = 宽度，f = SwiGLU 中间维，h = 头数，V = 词表，s = 每个数的字节（fp32 时 4）。用 `saved_tensors_hooks`（`miniocr/train/memory.py` 的 `SavedTensors`）逐个看 autograd 保存了什么，再按存储去重，得到每层：

| 项 | 形状 | 字节 |
|---|---|---|
| 两个 RMSNorm 的输入和归一化结果（内部 fp32） | 4 × (B, T, d) | 16BTd |
| 两个 RMSNorm 的 rsqrt | 2 × (B, T, 1) | 8BT |
| q/k/v 投影共用的输入、gate/up 共用的输入 | 2 × (B, T, d) | 2sBTd |
| 注意力里的 q、k、v | 3 × (B, T, d) | 3sBTd |
| 输出投影 o 的输入 | (B, T, d) | sBTd |
| SwiGLU 的 gate、up、silu(gate)、乘积 | 4 × (B, T, f) | 4sBTf |
| softmax 权重 | (B, h, T, T) | sBhT² |
| 因果 mask（布尔） | (T, T) | T² |

模型末端再加：最终 norm 的输入、归一化结果（fp32）和输出层的输入，共 (8 + s)BTd；最终 rsqrt 4BT；交叉熵保存的 log-softmax 4BTV；输入 idx 和 targets 各 8BT；一个 4 字节的标量。

于是，固定 B 时每层的保存量是 aT + bT²，其中

$$a = B\,[16d + 8 + s(6d + 4f)],\qquad b = sBh + 1.$$

（数学结论，在 `activation_bytes_estimate` 声明的范围内：fp32、manual 注意力、MHA、无 dropout、无检查点。这些项是通过阅读 `gpt.py` 并用 hook 观察得出的；换一个 PyTorch 版本，算子的保存策略可能变，所以要靠实测把关。）

还有两点：

- softmax 之前的**分数矩阵没有保存**，保存的是 softmax 之后的权重——softmax 的反向只需要它的输出。
- 返回给调用者的 logits（B × T × V × s）不在 autograd 的保存账里，但它也活在内存里，词表大时很可观。

### 16.7.4 数值例子：medium，B = 4，T = 64

medium：L = 4，d = 128，h = 4，f = 384，V = 512，fp32（s = 4）。

**每层系数：**

- a = 4 × [16 × 128 + 8 + 4 × (6 × 128 + 4 × 384)] = 4 × [2056 + 4 × 2304] = 4 × 11272 = **45,088**
- b = 4 × 4 × 4 + 1 = **65**

**块的部分：** L × (aT + bT²) = 4 × (45,088 × 64 + 65 × 4096) = 4 × (2,885,632 + 266,240) = 12,607,488。

**末端：**

- 最终 norm 与输出层输入：4 × 64 × 128 × 12 = 393,216
- rsqrt：4 × 64 × 4 = 1,024
- log-softmax：4 × 64 × 512 × 4 = 524,288
- idx、targets：2 × 4 × 64 × 8 = 4,096
- 标量：4

合计 922,628。

**总计：12,607,488 + 922,628 = 13,530,116 字节。**（数学结论。）

`SavedTensors` 实测：**13,530,116 字节**，一个字节都不差（本项目观察，第 7 部分）。

占比最大的是 SwiGLU 的四个中间量（46.5%），因为 f = 3d 比 d 宽；其次是 RMSNorm 的 fp32 中间量（15.5%）。注意力权重在 T = 64 时只占 7.7%。

### 16.7.5 扫描 B 和 T

（本项目观察，第 7 部分；四组的估算与实测全部完全相等。）

| B | T | 实测字节 | 相对 (4, 64) |
|---|---|---|---|
| 4 | 64 | 13,530,116 | 1 |
| 8 | 64 | 27,043,844 | 2.00 |
| 4 | 128 | 29,190,148 | 2.16 |
| 4 | 256 | 66,899,972 | 4.94 |

- **B 翻倍 → 1.9988 倍**，几乎正好翻倍。差的那一点是 mask（只和 T 有关）和标量，不随 B 增长。
- **T 翻倍 → 2.16 倍**，T 翻两番 → 4.94 倍。多出来的是 T² 项。到 T = 256，softmax 权重和 mask 合起来是 4 × 65 × 256² = 17,039,360 字节，占总量的 25%（数学结论）。

第 7 部分还用 B = 4 的三组 T 做最小二乘，拟合出每层 a = 45,088、b = 65，和公式一致。

**SDPA 怎样？** 同一个模型换成 `attn_impl="sdpa"`，B = 4、T = 128 时实测 25,225,220 字节，比 manual 的 29,190,148 少（本项目观察，第 7 部分）。SDPA 内部保存什么取决于后端，本章不给精确公式（待验证）。GPU 上的 FlashAttention 类实现不保存 T × T 的权重矩阵，反向时重算（本书不展开）。

## 16.8 梯度检查点：用计算换显存

### 16.8.1 能不能不存

激活随 B × T 增长，模型一深就装不下。能不能**不存**？

能。不存就得在反向时**重新算**。这就是**梯度检查点**（gradient checkpointing，也叫 activation checkpointing）。

### 16.8.2 只记路标

想象你走一条长路，回程要原路返回、每一步都要看来时的风景。全记下来太占脑子。折中办法是：**只在每个路口拍一张照片**（检查点），回程走到某一段时，从这段起点的照片出发，再走一遍这一段，把风景重新看一遍。

对 Transformer 来说，最自然的"路口"是每个块的输入：

- **前向**：每个块只保存它的输入 (B, T, d)，块内部的中间量用完就扔。
- **反向**：反向传到某个块时，用保存的输入把这个块的前向**再算一遍**，得到内部中间量，然后正常求梯度。

### 16.8.3 省多少、多算多少

**省多少。** 设每个块原本保存 A 字节，块输入是 BTd·s 字节。用检查点后每块只剩 BTd·s。medium、fp32 时每个 token 每层原本存约 11272 字节（16.7.4 的 a / B，不含 T² 项），检查点后只存 4d = 512 字节，大约是原来的 1/22（数学结论）。

**多算多少。** 训练原本是 1 次前向 + 1 次反向，反向约是前向的 2 倍（第 13 章），合计 3 份前向。检查点多做一次块的前向，变成 4 份：

$$\frac{4}{3} \approx 1.33 \text{ 倍}.$$

这是"所有计算都在块内、全部重算"时的上限（数学结论）。实际比这少一点，原因见下面的例子。

### 16.8.4 数值例子：medium，B = 4，T = 128

（本项目观察，第 8 部分。）

| | 无检查点 | 逐块检查点 | 比值 |
|---|---|---|---|
| 保存的激活 | 29,190,148 字节 | 2,893,828 字节 | 0.099 |
| 前向 + 反向 FLOPs | 3,221,225,472 | 4,026,531,840 | 1.25 |
| 前向 + 反向时间（中位数） | 约 17.7 ms | 约 22.2 ms | 约 1.25 |
| 梯度最大绝对差 | | | 0 |

**梯度完全相同。** 检查点不改变数学，只改变"什么时候算"。

**剩下的 2,893,828 字节是什么？** 手算（数学结论）：

- 4 个块的输入：4 × (4 × 128 × 128 × 4) = 1,048,576
- 末端（最终 norm/输出层输入、rsqrt、log-softmax、idx/targets、标量）：786,432 + 2,048 + 1,048,576 + 8,192 + 4 = 1,845,252
- 合计 2,893,828。和实测一字不差。

末端那部分不在任何块里，检查点管不到。词表大时，log-softmax 这一项（B × T × V × 4）会成为大头。

**为什么 FLOPs 比是 1.25 而不是 1.33？** 用 FlopCounterMode 实测的额外计算是 805,306,368 FLOPs。手算（数学结论）：

- 一个块的前向：线性层 2 × B × T × (4d² + 3df) = 2 × 512 × 212,992 = 218,103,808；注意力两次矩阵乘法 4 × B × T² × d = 33,554,432；合计 251,658,240。四个块 1,006,632,960。
- 输出层的前向 2 × B × T × d × V = 67,108,864 不重算。
- PyTorch 的非重入检查点（`use_reentrant=False`）在重算时，凑齐反向需要的张量就提前停下。块的最后一个算子 down 投影的输出反向用不上，所以不重算：4 × 2 × 512 × 128 × 384 = 201,326,592。
- 1,006,632,960 − 201,326,592 = **805,306,368**。正好等于实测。

**时间比约 1.25**，三次运行在 1.247 到 1.274 之间（本项目观察，第 8 部分，CPU 两线程，每次 3 次计时取中位数）。CPU 短计时会抖动；GPU 上时间比不一定等于 FLOPs 比（待验证）。

### 16.8.5 代码

`miniocr/train/memory.py` 里的 `CheckpointBlock`：

```python
def forward(self, *args, **kw):
    if torch.is_grad_enabled() and self.training:
        return checkpoint(self.block, *args, use_reentrant=False, **kw)
    return self.block(*args, **kw)
```

- 训练时，用 `torch.utils.checkpoint.checkpoint` 包住整个块。前向只存块的输入。
- 推理（不需要梯度）时，直接调用，零开销。

`checkpoint_blocks(model.blocks)` 把每个块都换成 `CheckpointBlock`。第 8 部分就是先 `deepcopy` 一份模型，再对副本调用它，保证两条路径的权重完全相同。

### 16.8.6 什么时候用

- 显存不够、而又不想减小批大小时用。额外计算 = 重算的 FLOPs / 原训练 FLOPs：全部计算都在块内且全部重算时上限约 33%，本章全块检查点的例子是 25%；只给部分块加检查点会更少（数学结论，取决于重算范围）。
- 也可以只给一部分块加检查点，在显存和时间之间连续调节。
- 有 dropout 时，重算要用和第一次相同的随机数，否则两次前向不一致。`torch.utils.checkpoint` 默认会保存和恢复随机数状态（`preserve_rng_state=True`）。

## 16.9 变长样本的梯度累积

### 16.9.1 显存只够 2 条，想要 4 条的效果

显存只够一次算 2 条样本，可你想用批大小 4。办法是**梯度累积**：把 4 条拆成 2 个小批，各做一次前向反向，梯度加在一起，再更新一次。

目标是：**累积后的梯度，和一次算 4 条完全一样**。

样本等长时，"每个小批的 loss 除以小批个数"就对了。可 SFT 里的回答、公式的长度差别很大。这时候，最常见的写法是错的。

### 16.9.2 大批的 loss 是什么

设 4 条样本的有效 token 数是 n₁, …, n₄，第 i 条第 t 个 token 的损失是 ℓᵢₜ。"一次算整批、按 token 平均"的 loss 是

$$\mathcal{L} = \frac{\sum_i \sum_t \ell_{it}}{\sum_i n_i}.$$

分母是**整批**的有效 token 总数 Nₜₒₜ。把它拆到两个小批 G₁、G₂：

$$\mathcal{L} = \frac{\sum_{i\in G_1}\sum_t \ell_{it}}{N_\text{tot}} + \frac{\sum_{i\in G_2}\sum_t \ell_{it}}{N_\text{tot}}.$$

所以每个小批应该**用 sum 损失除以整批的 token 总数**，而不是除以本小批的 token 数。（数学结论。）

常见的错误写法 `micro_mean` 是：每个小批先按自己的 token 数平均，再除以小批个数：

$$\mathcal{L}_\text{micro} = \frac{1}{2}\left(\frac{\sum_{G_1}\ell}{N_{G_1}} + \frac{\sum_{G_2}\ell}{N_{G_2}}\right).$$

只有 N_{G₁} = N_{G₂} 时它才等于 𝓛。

还有第三种：`sample`，先在每条样本内部平均，再对样本平均：

$$\mathcal{L}_\text{sample} = \frac{1}{4}\sum_i \frac{\sum_t \ell_{it}}{n_i}.$$

它没有算错 𝓛，它优化的是另一个目标：每条样本权重相同，不论长短。

### 16.9.3 数值例子：每个 token 的权重

4 条样本，有效长度 [2, 16, 16, 10]，共 44 个 token。分组 A：[0, 1] 一组（18 个 token），[2, 3] 一组（26 个）。每个 token 在最终梯度里的权重（数学结论）：

| 方式 | 样本 0 的 token | 样本 1 | 样本 2 | 样本 3 |
|---|---|---|---|---|
| token（正确） | 1/44 ≈ 0.0227 | 1/44 | 1/44 | 1/44 |
| micro_mean | 1/18 × 1/2 ≈ 0.0278 | 0.0278 | 1/26 × 1/2 ≈ 0.0192 | 0.0192 |
| sample | 1/2 × 1/4 = 0.125 | 1/16 × 1/4 ≈ 0.0156 | 0.0156 | 1/10 × 1/4 = 0.025 |

micro_mean 让"碰巧分到 token 少的那组"的 token 权重更大，也就是说，权重取决于怎么分组。

sample 让样本 0 的每个 token 权重是 token 方式的 5.5 倍。短样本被大大加权。

### 16.9.4 实测：和整批对拍

用一个两层的小 GPT，和"一次算整批"的梯度比相对 L2 差（本项目观察，第 9 部分）：

| 方式 | 分组 A | 分组 B | 换分组后梯度变化 |
|---|---|---|---|
| token | 9.2 × 10⁻⁸ | 9.9 × 10⁻⁸ | 9.0 × 10⁻⁸ |
| micro_mean | 0.194 | 0.203 | **0.350** |
| sample | 1.001 | 1.001 | 1.1 × 10⁻⁷ |
| pretrain.py 写法 | 1.4 × 10⁻⁷ | 1.4 × 10⁻⁷ | 1.5 × 10⁻⁷ |

分组 B 是 [0, 2] 和 [1, 3]：交换了两条同样长 16 但内容不同的样本，两组 token 数仍是 18 和 26。

- **token** 方式和整批的差在 10⁻⁷ 量级，是 fp32 舍入误差。
- **micro_mean** 差 19%–20%，而且换个分组梯度就变 35%。同样的数据、同样的模型，只因为分组不同，梯度就不同。
- **sample** 和整批差了约 100%：它优化的根本是另一个目标。但它不随分组变，说明它自洽。选不选它，是设计决定，要在报告里写清楚。
- **pretrain.py 写法**（第 13 章）：每个小批算 mean loss，再乘 count / valid（本小批有效数 / 总有效数）。mean × count = sum，所以等于 sum / valid，就是 token 方式。

### 16.9.5 代码

`miniocr/train/lm.py` 的 `accumulate_grads`：

```python
if mode == "token":
    total = sum(int((y != -100).sum()) for _, y in micro_batches)   # 44
...
for x, y in micro_batches:
    ...
    if mode == "token":
        loss = nll.sum() / total                                       # 本小批 sum ÷ 44
    elif mode == "micro_mean":
        loss = nll.sum() / valid.sum().clamp(min=1) / total            # ÷ 18（或 26）÷ 2
    loss.backward()
```

- token 方式先**遍历所有小批**数出有效 token 总数（44），再做前向，因为分母必须在任何反向之前就知道。
- micro_mean 时 `total` 是小批个数 2，分母是本小批的 18 或 26。

`train_pretrain` 里的写法（第 13 章）：

```python
counts = [int((y != bos).sum()) for _, y in batches]
valid = sum(counts)
...
loss = model(x, y, loss_mask=y != bos)[1] * (count/valid)
```

`model(...)[1]` 是本小批的 mean loss（除以 count），乘 count/valid 后就是 sum/valid。

> **停下来想一想：** 如果数据加载器保证每个小批的有效 token 数都相同（比如"按 token 数打包"），micro_mean 还会错吗？

## 16.10 6ND 与 MFU

### 16.10.1 两个问题

第 13 章推出训练计算量 C ≈ 6ND，并给出

$$\text{时间} \approx \frac{6ND}{\text{峰值 FLOP/s} \times \text{MFU}}.$$

这一节回答两个问题：6ND 准不准？你的设备 MFU 是多少？

### 16.10.2 实测 FLOPs：6ND 少算了什么

PyTorch 的 `torch.utils.flop_counter.FlopCounterMode` 能数出一次前向反向里矩阵乘法的 FLOPs（乘加记 2）。在 medium（V = 512）上，B = 4、T = 64，共 256 个 token（第 10 部分）：

| 量 | 值 | 来源 |
|---|---|---|
| N（matmul 口径） | 918,656 | 数学结论 |
| 6ND | 1,411,055,616 | 数学结论 |
| 注意力两次矩阵乘法，训练 12LBT²d | 100,663,296 | 数学结论 |
| 6ND + 注意力 | 1,511,718,912 | 数学结论 |
| **实测前向 + 反向** | **1,509,949,440** | 本项目观察 |
| 实测 / 6ND | 1.070 | |
| 实测 / (6ND + 注意力) | 0.99883 | |

注意力项怎么来：QKᵀ 和"权重 × V"每层前向各是 2BT²d，合计 4BT²d；训练按 3 倍算，12LBT²d = 12 × 4 × 4 × 64² × 128 = 100,663,296。manual 注意力算的是完整的 T × T 矩阵，被因果 mask 遮住的那一半也算了，所以这里不像 Kaplan 那样取一半（第 13 章 13.6.5）。

**剩下的 0.12% 差在哪？** 1,511,718,912 − 1,509,949,440 = 1,769,472 = 6 × 1152 × 256。1152 是 `matmul_params` 里顺带计入的归一化层 γ（4 层 × 2 × 128 + 128），它们只做逐元素乘法，不是矩阵乘法（数学结论）。差值也解释清楚了。

结论：T = 64 时，6ND 少算了约 7%，来自注意力。T 越长，这个比例越大（第 13 章算过比例 ≈ n_layer·n_ctx·d / N 的量级）。

### 16.10.3 MFU：你用上了几成

**MFU**（model FLOPs utilization）的定义：

$$\text{MFU} = \frac{\text{模型需要的 FLOPs/秒}}{\text{设备峰值 FLOPs/秒}} = \frac{6N \times \text{tokens/秒}}{\text{峰值}}.$$

分子用 6N 这个"模型本身需要的计算"，不算检查点之类的重算——多做的计算不算"有用功"。所以加了检查点以后，如果实测 tokens/秒下降（本章 CPU 上的例子每步慢了约 25%，16.8.4），MFU 就随之下降；在别的设备和配置上是否如此，要实测（待验证）。

**第一步：实测吞吐。** 第 10 部分在 medium 上（fp32，B = 4，T = 64），预热 2 步后，计时 5 个完整训练步（zero_grad + 前向 + 反向 + AdamW），取中位数（本项目观察，CPU 两线程）：

- 每步约 9.8 ms，**tokens/秒约 2.5 万到 2.6 万**（多次运行在 24,495 到 26,188 之间）。

**第二步：实现的 FLOP/s。** 6N × tokens/秒 = 6 × 918,656 × 26,187 ≈ **1.44 × 10¹¹ FLOP/s**，即约 144 GFLOP/s（本项目观察，第 10 部分那一次运行）。

**第三步：除以峰值。** 峰值要查你的设备规格，并且**精度要对应**：fp32 和 bf16 的峰值可能差好几倍；有些厂商标的是稀疏峰值，比稠密的高一倍。本机两个 CPU 核的 fp32 峰值本书没有核实（待验证），所以 tour 默认不算 MFU。你可以用 `--peak-tflops` 填进去：

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch16_training_engineering.tour 10 --peak-tflops <你的峰值>
```

举一个**假设**的例子说明算法：如果峰值是 1 TFLOP/s，那么 MFU = 1.44 × 10¹¹ / 10¹² = 14.4%。这个峰值是为了演示随便取的，不代表任何设备。

小模型的 MFU 通常很低：矩阵太小，喂不饱计算单元；优化器、归一化、Python 调度这些"非矩阵乘法"的开销占比大。

### 16.10.4 用 MFU 估算耗时

有了 MFU，就能估算更大的训练要多久。其实，如果 tokens/秒已经实测出来了，直接用

$$\text{时间} = \frac{D}{\text{tokens/秒}}$$

更简单，两种算法等价（数学结论）。MFU 的价值在于**换设备、换模型时外推**：假设 MFU 不变，就可以从规格表的峰值推出新设备上的耗时。这个假设很粗，外推之后一定要实测。

例：第 11 部分设一个 25,600 token 的教学预算，按实测约 2.6 万 tokens/秒，预计约 1 秒（本项目观察，第 11 部分）。

### 16.10.5 代码

```python
def training_flops(cfg, batch, context, accum=1):
    D = batch*context*accum
    n = parameter_counts(cfg)["matmul"]
    base = train_flops(n, D)                          # 6ND = 1,411,055,616
    extra = 12*cfg.n_layer*context*cfg.d_model*D      # 12·L·T·d·D = 12LBT²d
    return dict(..., six_nd=base, attention=extra, with_attention=base+extra, ...)
```

`extra` 写成 12·L·T·d·D：因为 D = BT，12LBT²d = 12·L·T·d·(BT)。代入 L = 4、T = 64、d = 128、D = 256 得 100,663,296。

```python
def count_flops(model, x, targets, backward=True):
    from torch.utils.flop_counter import FlopCounterMode
    model.zero_grad(set_to_none=True)
    with FlopCounterMode(display=False) as counter:
        loss = model(x, targets=targets)[1]
        if backward:
            loss.backward()
    return counter.get_total_flops()
```

在 `FlopCounterMode` 里跑一次前向反向，它拦截每个算子并累加 FLOPs。它主要统计矩阵乘法类算子，不是硬件指令计数。

## 16.11 资源核算：先估算，再实测，再对照

### 16.11.1 为什么要做核算

大训练动辄几小时、几天。开跑之后才发现 OOM，或者要跑一个月，代价太大。**资源核算**是开跑前的一页纸：

1. **先估算**：静态显存、激活、每步 FLOPs、总耗时。
2. **再实测**：小规模跑一两步，测真实的字节和吞吐。
3. **再对照**：差多少？差值能解释吗？解释不了就别开跑。

### 16.11.2 `resource_report`

`miniocr/train/resources.py` 的 `resource_report` 把前面几节串起来：

```python
counts = parameter_counts(model_cfg)
nt = round(counts["total"]*trainable_fraction)
static = static_memory(counts["total"], nt, "bf16" if precision == "mixed" else "fp32",
                       master_fp32=precision == "mixed")                       # 16.6
activation = activation_bytes_estimate(model_cfg, batch, context, ...)          # 16.7
flops = training_flops(model_cfg, batch, context, accum)                        # 16.10
achieved = 6*counts["matmul"]*tokens_per_sec ...
mfu = achieved/(peak_tflops*1e12) ...
```

注意 `batch` 是**微批**大小：梯度累积时，激活只按一个微批算（每个微批反向完就释放计算图），但每步 tokens 和 FLOPs 要乘 accum。

### 16.11.3 本章小模型的核算

medium（V = 512），fp32，B = 4，T = 64（本项目观察，第 11 部分）：

| 项 | 估算（字节） | 实测（字节） | 相对差 |
|---|---|---|---|
| 静态 | 14,698,496 | 14,698,648 | 1.0 × 10⁻⁵ |
| 激活保存量 | 13,530,116 | 13,530,116 | 0 |
| 静态 + 激活 | 28,228,612 | 28,228,764 | 5.4 × 10⁻⁶ |

静态差 152 字节 = 38 个参数张量 × 4 字节的 AdamW `step`（4 层 × 9 + 嵌入 + 最终 norm = 38）。全部对上。

**但这不是峰值显存。** 还有几样没算：

- 返回的 logits（B × T × V × s），16.7.3 说过；
- 反向过程中的临时梯度张量、AdamW 更新时的临时缓冲区；
- 分配器的缓存和碎片；
- CUDA 上下文本身占的显存。

反过来，训练循环用 `zero_grad(set_to_none=True)` 时，完整的梯度和全部前向激活不一定同时存活，所以"静态 + 激活"**既不是峰值，也不保证是峰值的下界**。真实峰值只能在你的设备上测（待验证）。另外注意，`torch.cuda.max_memory_allocated()` 只统计张量分配，不含 CUDA 上下文和分配器里未使用的缓存。

## 16.12 分布式训练（概括）

> **概括框：分布式训练**
>
> 一张卡放不下或算太慢时，就用多张卡。几种方法的区别在于**切分了什么**：
>
> - **DDP（数据并行）**：每张卡存一份完整的模型、梯度和优化器状态，各算一部分数据，反向后把梯度求平均。显存不省，只加速。
> - **ZeRO**：把 16.6 的静态账切开分给各张卡。阶段 1 切优化器状态（m、v、主权重），阶段 2 再切梯度，阶段 3 再切参数本身。设 N_d 张卡，阶段 3 下每张卡的静态显存约是 16 字节/参数的 1/N_d（数学结论，忽略通信缓冲区）。FSDP 是 PyTorch 里类似 ZeRO-3 的实现。
> - **张量并行**：把一个矩阵乘法切到多张卡上。
> - **流水线并行**：把不同的层放到不同的卡上。
>
> 本课程的实验都在单卡上完成，这些方法只需要知道它们省的是哪一块显存。

## 16.13 常见错误

| 错误 | 现象 | 怎样发现 |
|---|---|---|
| 归一化、softmax、loss 在 fp16 里算 | loss 一开始就是 nan，或某层输出全 0 | 见 16.2.4 |
| 以为 loss scaling 能救前向溢出 | 加了 GradScaler 还是 nan，S 一路减半到很小 | 打印 `scaler.get_scale()`；S 持续下降说明每步都检测到 inf 或 NaN，先查数据和前向（16.2、16.4） |
| fp16 不用 GradScaler | loss 下降得很慢或不降，没有报错 | 统计梯度里 0 的比例（16.3） |
| 裁剪放在 unscale 之前 | 训练异常慢，无报错 | 打印裁剪前的梯度范数：比正常大约 S 倍（16.4.5） |
| 参数直接存成 bf16、不留 fp32 主权重 | 后期 loss 不再下降 | 对比一步更新前后参数，很多元素完全没变（16.5） |
| 以为换 bf16 静态显存减半 | 估算偏小，OOM | 按 16.6 两种口径都是 16 字节/参数 |
| 实测静态显存时没先做一次 `optimizer.step()` | 实测比估算少约一半 | AdamW 的 m、v 在第一次 step 时才创建（16.6.5） |
| 估算激活漏了 logits 或 T² 项 | 长序列或大词表时 OOM | T² 项：用 `SavedTensors` 实测并与估算逐项对照（16.7）；logits 不在 `SavedTensors` 的账里，要按 B·T·V·s 单列，峰值在设备上另测（16.11） |
| 变长样本用 micro_mean 累积 | 梯度随分组变化；和不累积的结果对不上 | 和整批对拍；换一种分组看梯度变不变（16.9） |
| MFU 用错峰值精度 | MFU 高得离谱（甚至超过 1）或低得离谱 | 核对峰值是 fp32 还是 bf16、稠密还是稀疏（16.10） |

## 16.14 和真实框架的对应

| 本章 | 真实框架 |
|---|---|
| `SimpleGradScaler` | `torch.amp.GradScaler`：方法同为 `scale`、`unscale_`、`step`、`update`；默认 `init_scale=2**16`、`growth_factor=2.0`、`backoff_factor=0.5`、`growth_interval=2000`。本章第 4 部分逐步对拍一致。教学版只支持稠密 fp32 梯度和普通优化器 |
| 显式 bf16 计算副本 + fp32 主权重 | `torch.autocast(device_type, dtype=torch.bfloat16)`：参数保持 fp32，在进入矩阵乘法等算子时临时转成 bf16；其他算子用什么精度由设备和算子决定（PyTorch AMP 文档按设备列出算子表），反向沿用前向的精度。不要假设 softmax、归一化一定留在 fp32——项目的 RMSNorm 和交叉熵在 fp32 里算，是代码里显式 `.float()` 的结果。所以用 autocast 时，参数和梯度是 fp32（4 + 4），加 AdamW 的 8，静态仍是 16 字节/参数，另有转换缓存（待验证，需实测） |
| `CheckpointBlock` | `torch.utils.checkpoint.checkpoint(fn, *args, use_reentrant=False)`；Hugging Face 模型用 `model.gradient_checkpointing_enable()` |
| `accumulate_grads(mode="token")` | Hugging Face `Trainer` / TRL 的梯度累积在变长样本下怎样归一化，不同版本做法可能不同（待验证）；本书所用版本的做法在第 21 章 21.6.2 节核对 |
| `SavedTensors` | `torch.autograd.graph.saved_tensors_hooks`；GPU 上用 `torch.cuda.max_memory_allocated()` 看峰值 |
| `count_flops` | `torch.utils.flop_counter.FlopCounterMode`；更细的性能分析用 PyTorch profiler（本书不展开） |
| 16.12 的 ZeRO / FSDP | DeepSpeed ZeRO、`torch.distributed.fsdp`（本书不展开） |

## 16.15 小结

- fp16 有 5 位指数、10 位尾数，范围小（max 65504），前向会溢出、梯度会下溢；bf16 有 8 位指数、7 位尾数，范围和 fp32 一样，但精度粗，256 + 1 = 256。
- 前向溢出靠把求和、指数、归一化放回 fp32 解决；梯度下溢靠 loss scaling 解决。GradScaler 遇 inf 就跳过这一步并把 S 减半，连续正常就加倍；裁剪必须在 unscale 之后。低精度参数会吞掉小更新，所以要留 fp32 主权重。
- AdamW 训练的静态显存约 16 字节/参数，纯 fp32 和混合精度总量相同、组成不同；激活随 B × T 线性增长，注意力还带 T² 项。本章对小 GPT 的估算和实测逐字节相等。
- 梯度检查点只存块输入，激活降到约 1/10，代价是多算约 1/4 的 FLOPs；变长样本的梯度累积要用整批的 token 总数归一化，micro_mean 会让梯度随分组变化。
- 6ND 加上注意力项后与实测 FLOPs 相差 0.12%；MFU = 6N × tokens/秒 / 峰值。

## 16.16 精读

**1. Micikevicius et al., 2018, *Mixed Precision Training*（ICLR 2018）。** 读第 3 节（fp32 主权重、loss scaling、fp32 累加三个技术）。

- 论文说 fp32 主权重并非对所有网络都必要。它给出哪两个原因说明一些网络需要它？和 16.5 的"小更新被吞掉"对照。
- 论文用的是固定的 loss scale 还是动态的？和 GradScaler 的动态规则比，各有什么优缺点？
- 论文说哪些运算要用 fp32 累加？和 16.2.3 的例子对照。

**2. Chen et al., 2016, *Training Deep Nets with Sublinear Memory Cost*。** 读第 4.1 节（重算的思路）和第 4.3 节（√n 分段的推导）。

- 一个 n 层的网络，每 √n 层放一个检查点，激活显存为什么是 O(√n)？额外计算是多少？
- 本章是"每块一个检查点"。按论文的分析，这样省下的显存是什么量级？

**3. Rajbhandari et al., 2020, *ZeRO: Memory Optimizations Toward Training Trillion Parameter Models*（SC 2020）。** 读第 3 节中讲模型状态显存的部分。

- 论文把混合精度 Adam 的模型状态写成 2Ψ + 2Ψ + KΨ。K 等于多少？它和 16.6 的 2 + 2 + 4 + 4 + 4 怎样一一对应？
- 论文还列了哪些"剩余显存"（residual states）？和 16.11.3 列的"没算进去的东西"对照。
