## 答案与提示

**15.1** 第 t 步的注意力输出是 out_t = Σ_{j≤t} softmax_j(q_t · k_j / √dh) v_j。式子里只出现新位置的 q_t，但出现全部 k_1…k_t 和 v_1…v_t。也就是说，分数矩阵每步只需要新的一行（由 q 决定），而列（由 k 决定）一直在累积。q_j 只在第 j 步用一次，k_j、v_j 在第 j 步以后每一步都要用。

**15.2** 位置 j 的 k 转多少度只由 j 决定，转一次就永远不变，存转后的版本最省事。如果存转之前的，每一步都要把整段历史按各自的位置 0…past−1 重新转一遍（切出对应的 cos、sin），多做功，而且容易用错位置。

**15.3** 存 x：每 token 每层 1024 个数；存 k、v：2 · 8 · 128 = 2048 个数。存 x **少一半**。代价是每步都要对全部历史重新算 W_k x、W_v x（还有 k 的 norm 和 RoPE），每层多 2 · T · d_model · (2 · n_kv_head · head_dim) 次 FLOPs，T 越长越贵，等于把 KV cache 省下的投影计算又做了回来。没有 GQA 时，2 · n_kv_head · head_dim = 2 · d_model，存 x 同样少一半，计算代价同样存在。这个"存一个更小的向量、用时再投影"的想法，正是 MLA 的出发点（它存的是专门学出来的低维潜在向量）。

**15.4** 不能整体复用。双向模型里，新 token 会被所有旧位置看到，所以从第 1 层的注意力输出开始，旧位置的表示就变了；第 2 层及以上的旧 k、v 都要重算。只有第 1 层的 k、v 可以复用：它们只依赖嵌入（以及位置编码），不受新 token 影响。KV cache 依赖的是因果性。

**15.5** 贪心 token 只看 argmax，随机初始化的模型 logits 都很小、很接近，错一些也可能不改变 argmax。第 5 部分：pos0 写成 0 时，逐步 logits 最大差约 0.15，但贪心序列直到第 7 步才分叉；mask 偏移错误在逐 token 解码中完全不触发，贪心序列"无"分叉；先 repeat_kv 再缓存，结果完全正确但缓存大一倍。正确的检查是逐步对拍 logits，再加分段预填充和缓存大小的检查。

**15.6** 权重是所有请求共用的：读一次权重，B 条请求都用它算一个 token，权重的访存被 B 摊薄。KV cache 是每条请求自己的历史，B 条请求就要读 B 份，FLOPs 和这部分访存同比例增长，摊不薄。历史越长，KV cache 在总访存里占比越大，B 增大后剩下的几乎全是 KV cache 的访存，算术强度就趋于注意力部分的强度（加上一点线性层），见 15.13 第 3 问。

**15.7** 缓存的是复制后的 n_head 份而不是 n_kv_head 份，显存大了 n_head / n_kv_head 倍，GQA 的省显存效果全没了。复制出的几份内容相同，所以计算结果和正确实现一样，所有对拍测试都通过。检查办法：断言 `cache["k"].shape[1] == cfg.kv_heads()`，或用 `cache_nbytes(caches) == kv_cache_bytes_for(cfg, T, B, bytes_per)` 对拍。

**15.8** TTFT 主要由预填充决定，每 token 延迟主要由解码决定。只改善 TTFT 的例子：只替换预填充路径的矩阵乘内核、让它更快，解码路径保持不变（按 15.7 的粗算模型，预填充倾向于计算受限）。注意"缩短提示"不算：它同时减少了后续每步要读的 KV cache，也会改善每 token 延迟。只改善每 token 延迟的例子：用更高带宽的内存、GQA/MQA 减小要读的 KV cache、量化 KV cache（按粗算模型，解码倾向于访存受限）。具体效果要实测，这里只是方向。

**15.8a** 门槛要考虑数值量级和所用精度的舍入误差，不能直接沿用 fp32 的 10⁻⁵。0.0078 是 bf16 在 1 附近相邻可表示数的间距，本章没有给出 bf16 的实测门槛。贪心序列不能保证逐个相同：前两名 logits 的差小于舍入误差时，两个正确实现也可能选出不同 token，之后序列就会分开（15.3.4）。

**15.8b** 会。`self.pos(torch.arange(pos0, pos0 + T))` 按位置编号取可学习的位置嵌入；pos0 写错，新 token 在输入处就加上了错误位置的向量，后续表示和 logits 也会受影响。旧缓存按原位置算出，新块的位置必须接着已处理的长度编号（15.4.4）。

**15.9**
1. 形状 (3, 5)，第 i 行允许 j ≤ 2 + i：
   ```
   1 1 1 0 0
   ```

4. 2 · 2 · 1 · 4 · 9 · 1 · 4 = 576 字节。

**15.11**
1. 2 · 28 · 8 · 128 · 2 = 114688 字节 = 112 KiB。
2. 114688 · 8192 · 8 = 7516192768 字节 = 7 GiB；不用 GQA 翻倍，14 GiB。
3. 每个请求 114688 · 8192 = 939524096 字节 = 896 MiB；12 GiB = 12288 MiB；12288 / 896 ≈ 13.7，最多 13 个。（这里只算 KV cache，没算激活值和框架开销。）

**15.12**
1. T = 1000 + 500 + 500 = 2000；每 token 2 · 6 · 2 · 256 · 2 = 12288 字节；12288 · 2000 = 24576000 字节 ≈ 23.4 MiB。（严格说，最后一个生成的 token 没送进模型，是 1999 个位置，差别可以忽略。）
2. 24 层：每 token 49152 字节，· 2000 = 98304000 字节 ≈ 93.75 MiB，多算了 4 倍。
3. 18 层线性注意力的固定大小状态（不随 T 增长，但不是零），以及权重、激活值、视觉编码器等。

**15.13**
1. 线性层：解码 FLOPs = 2N，访存 = 2N 字节，强度 = **1**；预填充 T = 512：FLOPs = 2N · 512，访存 = 2N，强度 = **512**。
2. 每条序列：FLOPs = 4 · 28 · 16 · 128 · T_k，KV 读 = 2 · 28 · 8 · 128 · T_k · 2 字节 = 4 · 28 · 8 · 128 · T_k。比值 = 16 / 8 = **2**，即 n_head / n_kv_head，和 B 无关（B 在分子分母里同时出现，约掉了）。若把新 k、v 的写入也算上，访存多出 1/T_k，强度是 2T_k / (T_k + 1)，历史长时仍约等于 2。
3. T_k = 4097。每条请求 FLOPs = 2N + 4 · 28 · 2048 · 4097 = 1,191,968,768 + 939,753,472 = 2,131,722,240；访存 = KV 读 114688 · 4097 = 469,876,736 加 KV 写 114,688，共 469,991,424 字节。比值 ≈ **4.54**。第 7 部分 B = 128 时是 4.45，已经很接近极限：再加大批量也几乎没用。

**练习 15.7** 提示：每行的位置编号是 `arange(T) − 该行补齐数`（补齐位置可以夹到 0）；RoPE 表要按每行的位置分别取，形状 (B, T, dh)，传给 `apply_rope` 前要扩成 (B, 1, T, dh)，否则 B 会被广播到头那一维；mask 变成 (B, 1, T_new, T_past + T_new)，在因果 mask 上再"与"一个"key 不是补齐位置"的条件。小心：补齐位置自己那一行（作为查询）会全是 False，manual 实现对全 −∞ 的一行做 softmax 会得到 NaN，NaN 再经过下一层会污染别的位置。简单的办法是让补齐位置至少能看见自己（把对角线设为 True）；真实 token 的 key mask 已经把补齐位置挡住，它们的输出不会被用到。解码时每行的 pos0 也各不相同。

**15.15** 错在 `pos0=idx.shape[1] + step`，多了 1。第一个解码步（step = 1）送进去的是第 P + 1 个 token（从 1 数），位置应是 P（从 0 数），而这里给的是 P + 1，跳过了一个位置。正确的一行：`pos0=idx.shape[1] + step - 1`（等价地，`pos0=caches[0]["k"].shape[2]`，即已缓存长度）。确认方法：把当前完整序列整段前向一次，和缓存版本最后一个位置的 logits 对拍，最大差应在 10⁻⁷ 量级（第 3 部分）；再跑 `test_cache_generation_and_step_logits`。

**15.16** `tril()` 没有偏移，新块的第 i 行只能看 j ≤ i 的列，大部分旧缓存被挡住。逐 token 生成时 T = 1，走的是 `mask = None` 分支（整行可见，恰好正确），所以发现不了。正确写法：`mask = torch.ones(T, past + T, dtype=torch.bool).tril(past)`，对 T = 1 也成立，不需要特判。要加的是**分段预填充**测试：用多种切法（如 [6, 4]、[3, 3, 4]、[4, 1, 5]）和整段前向对拍全部 logits，即 `test_prefill_chunks`。

**15.17** 先 repeat_kv 再缓存，缓存的是 16 个头而不是 4 个，大了 16 / 4 = 4 倍。复制出的头内容相同，计算结果和正确实现一致，所以对拍全过。断言：`assert cache["k"].shape[1] == self.hk`；或在测试里断言 `cache_nbytes(caches) == kv_cache_bytes_for(cfg, T, B, 4)`。修法：先写缓存，再 repeat_kv。

**15.18** 预填充时 cos、sin 是 (T, dh)，k 也是 T 个位置，一一对应，所以预填充正确。这段代码先写缓存、后转 RoPE，缓存里存的是**转之前**的 k。解码时 cos、sin 只有新位置的 1 行，形状 (1, dh)；拼接后的 k 是 (B, h_kv, past + 1, dh)。(1, dh) 可以广播到 past + 1 行，所以**不报错**，但结果是把全部历史 k 都按新位置的角度转了一遍：旧 token 全被当成"和新 token 在同一个位置"，相对位置信息全丢了。

要在这种写法下得到正确结果，q 和 k 必须分开用不同的表：q 仍用新块位置的表（pos0 … pos0+T−1），拼接后的原始 k 用整段位置 0 … past+T−1 的表。如果把同一张整段表同时给 q 和 k，q 会被广播成 past + T 行，后面按 T 行合并头时就报错。分开处理后结果是对的，代价是每一步都要把全部历史重新转一遍，白做功，而且位置表一旦切错就全错。正确做法：先转，再存（15.2.3）。这道题也说明了广播的危险：形状"能广播"不等于形状"对"。

**15.19** 原因：(1) 补的 0 在右边，排在真实 token 后面，短提示那一行的"最后位置"是补齐位置，取 `[:, -1]` 的 logits 根本不是它真实末尾的预测；(2) 没有屏蔽补齐位置，之后生成的 token 能看到这些补齐 token 的 k、v；(3) 右补齐后，短提示的新 token 与真实提示之间多了 3 个位置的间隔，RoPE 的相对距离也变了。若改用左补齐并屏蔽补齐位置，纯 RoPE 模型整行位置统一平移不改变相对位置；可学习绝对位置嵌入则需要每行单独编号。本项目的 `GPT.forward` 和 `generate` 不支持不等长批量：批量里只放等长提示，否则逐条生成（15.9 的第 7 条）。真实框架一般左补齐，配合每行的位置编号和补齐 mask（练习 15.7）。
