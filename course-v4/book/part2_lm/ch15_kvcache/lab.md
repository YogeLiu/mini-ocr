# 第 15 章实验手册：KV cache 与推理效率

## 0. 准备

在 `course-v4/` 下运行：

```bash
CUDA_VISIBLE_DEVICES="" python -m pytest -q book/part2_lm/ch15_kvcache
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch15_kvcache.tour
```

部分号范围是 **1–9**，可单独运行，也可按指定顺序组合：

```bash
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch15_kvcache.tour 2 4
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch15_kvcache.tour 5 --seed 1
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch15_kvcache.tour 6 8 9 --ckpt outputs/book/ch13/runs/<你的run>/checkpoint.pt
```

先将 `<你的run>` 替换为实际目录名。`--seed` 默认 `0`；`--device cpu|mps|cuda` 默认 `cpu`。本实验验收只用 CPU，命令中的 `CUDA_VISIBLE_DEVICES=""` 隐藏 GPU。程序设置 `torch.set_num_threads(2)`，并将 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 设为 `2`；`HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`。全程离线、不下载、不训练、不读取语料。

**没有 `--ckpt` 时全部使用随机初始化模型，只验证数值一致性和观察计时趋势，不代表生成质量。** 有检查点时，第 6、8、9 部分使用 `identity["model"]` 恢复配置并加载 `model` 权重，第 9 部分从 `identity["bos"]` 开始、遇 `identity["eos"]` 停止；不需要分词器，也不解码文字。缺失检查点会报错。其余部分仍使用随机初始化模型，以便改变 MHA/GQA、归一化和注意力实现。

第 9 部分的随机模型采用第 13 章 tiny 的层数、宽度和头数，演示词表大小为 256、上下文上限为 256；编号 0 充当 BOS，不设置 EOS。第 6 部分的 tiny 对拍使用上下文 32。第 8 部分默认用较宽的随机模型，具体配置打印在输出中。检查点的上下文较短时，第 8 部分只测可容纳的长度，必要时使用其上限。

数学估算与实测分别标记为“数学结论”和“本项目观察”。计时只代表本机 CPU、当前线程数、模型与 PyTorch 实现，**不能推广到 GPU**；显式选择其他设备时输出会标记实际设备。不要从某一轮短计时推出硬件峰值或普遍加速倍数。命令默认只打印结果，不写产物；需要保存时可自行重定向到 `outputs/book/ch15/`，例如：

```bash
mkdir -p outputs/book/ch15
CUDA_VISIBLE_DEVICES="" python -m book.part2_lm.ch15_kvcache.tour > outputs/book/ch15/tour-seed0.txt
```

对照代码：[tour.py](tour.py)、[test_ch15_kvcache.py](test_ch15_kvcache.py)、[miniocr/kvcache.py](../../../miniocr/kvcache.py)。先写预测，再运行，将实际结果填入末尾空表。

## 1. 重复计算在哪里（15.1）

**做什么：** 在极小的两层模型上，先算长度 4 的序列，再追加一个 token 重算长度 5。hook 捕获每层注意力输入，重新计算经过归一化与 RoPE 的 K，以及未旋转的 V；对比前四个位置的 K/V、每层注意力输出和最终 logits。

**预测题：** 新 token 能否改变旧位置的表示？如果只想预测第六个 token，长度 5 前向中前四个位置的 Q 还需要吗？为什么存 K/V 而不是 Q/K/V？

**记录：** 旧/新 K/V 与 logits 的形状、各层前四位置最大差。零或浮点误差都符合数值一致性；旧 Q 用于旧位置的注意力输出，第五个位置只需要自己的 Q。保存的 K/V 仍需在后续注意力中被读取。

## 2. 缓存里有什么（15.2）

**做什么：** GQA + Q/K norm 模型预填充长度 10，逐层检查缓存形状，再送入一个 token。把缓存 K 与“线性投影 → 分头 → K norm → 各自位置的 RoPE”所得 K 对拍。

**预测题：** 缓存的头数应该等于 `n_head` 还是 `kv_heads()`？先复制头再缓存会影响结果还是容量？为什么不能把新位置的旋转角用到整份旧缓存上？

**记录：** 每层 `K形状`、`V形状`、`与投影归一化RoPE后K最大差`；解码一步前后长度轴的变化。形状约定为 `(B, h_kv, T, dh)`；缓存 K 已旋转，V 不旋转，二者都还没执行 `repeat_kv`。

## 3. 对拍：带 cache 与不带 cache（15.3）

**做什么：** 对 MHA、GQA、GQA + Q/K norm，分别用 manual 和 SDPA 注意力；使用两条等长提示，带/不带 cache 各贪心生成 30 个 token。另在无 cache 参考轨迹上逐步比较增量 logits 与整段重算的最后位置 logits。

**预测题：** 贪心序列相同，是否足以证明 cache 正确？为什么两个数值正确的实现也可能有很小的浮点差？若两条序列长度不等，能否直接将填充 token 当作历史？

**记录：** 每种配置的 `贪心完全相同` 与 `逐步logits最大差`。本实验只覆盖等长提示，不实现变长批量的 padding mask。先确认相同权重、输入、位置和 eval 模式，再判断误差；本章测试对正确路径要求最大差小于 `1e-5`。

## 4. 分段预填充：mask 与 pos0（15.4）

**做什么：** 打印 `T_past=3, T_new=2` 的 0/1 mask。对长度 10 的提示采用 `[10]`、`[6,4]`、`[3,3,4]`、`[4,1,5]`、`[1]*10`，分别用 manual 与 SDPA 计算，拼接各段全部 logits 与整段前向比较。

**预测题：** 手画两行 mask：每行应该看见哪些列？第二段的 `pos0` 是零、段号还是已处理 token 数？为什么只测单 token 解码抓不住所有 mask 错误？

**记录：** mask 矩阵、各切法的最大差。`cached_mask` 使用列号与绝对行号比较，等价于 `ones(T_new, T_past+T_new).tril(T_past)`；位置偏移决定 RoPE，mask 偏移决定可见范围，二者不能互相替代。

## 5. 故障演练（15.9）

**做什么：** 同一随机模型和提示对照正确实现、`pos0=0`、`mask_offset`、`pre_rope_k`、`no_cache_update`、`repeat_before_cache`。每种都记录 `[6,4]` 分段预填充误差、完整预填充后 20 次单 token 前向的最大误差、独立贪心轨迹相对无 cache 版本的首次分叉步，以及分段后的缓存字节比。

`pre_rope_k` 的具体错误是过早把 norm 后、RoPE 前的 K 存入缓存：当前块仍用旋转后的 K，下一块取出旧 K 时忘了补旋转。`no_cache_update` 只保存第一块，第二次前向临时拼接了新 K/V 却不写回，所以第三次前向才会丢失历史。`mask_offset` 的单 token 路径全可见，仅多 token 且有历史的路径误用 `tril()`。`repeat_before_cache` 则保留正确数值，但失去 GQA 节省缓存的效果。

**预测题：** 哪种故障可能让 `[6,4]` 的 logits 看起来正确，却留下错误的缓存长度？哪种故障在单 token 解码中完全不触发？为什么输出序列不分叉，也不能判定实现正确？

**记录：** 三种误差/分叉指标与缓存字节比。首次分叉从生成的第一个 token 起记为第 1 步，未分叉打印“无”。logits 对拍沿同一参考前缀前进，独立贪心则允许分叉，两种指标回答不同问题。随机 logits 很小，argmax 可能碰巧相同，要结合 logits 差判断。每次故障作用域结束都会恢复原前向；丢弃作用域内产生的错误缓存。

**亲手练习：** 在自己的临时副本中练习，每次只改一处，然后恢复：

1. 在 `prefill_chunks` 的模型调用中把 `pos0=pos` 改成 `pos0=0`，运行 `test_prefill_chunks`，观察哪些多段切法失败。
2. 在 `cached_mask` 中去掉 `T_past +`，运行 `test_cached_mask`。再读 `_bug_forward` 中 `mask_offset` 的条件，解释为什么它专门模拟“单 token 分支正确、多 token 分支错误”。
3. 在 GPT 注意力的个人副本里，把缓存写入移到 `apply_rope` 之前，运行 `test_cache_shapes_rope_and_bytes`；对照注入版 `pre_rope_k`，检查错误是否还影响当前块。
4. 在个人副本里只允许空 cache 写入，运行 `test_cache_generation_and_step_logits`；预测第二次与第三次前向分别会发生什么。
5. 将 `repeat_kv` 移到缓存写入之前，并保证后面不重复复制，运行形状/容量测试。即使生成对拍通过，缓存头数与字节数断言也应失败。

现成的 `test_bug_detection_and_restore` 和 `test_repeat_before_cache_correct_but_larger` 则是“确认故障被抓住”的测试：它们在正确的故障演练实现上应当通过。不要把故障版接入正式生成接口，也不需要修改教材其他章节。

## 6. 显存估算（15.5、15.6）

**做什么：** 对项目 GQA 小模型和第 13 章 tiny（或指定检查点），比较 fp32 预填充的实际张量字节与 `2·L·h_kv·dh·T·B·bytes_per`。随后只读取本地 HF `config.json`，估算两种 Qwen 骨架在 bf16 下的每 token 字节以及不同长度/批量的 KV 容量。

比较场景为 `T=4096/B=1`、`T=4096/B=32`、`T=32768/B=1`；分别列出原 GQA、假设不用 GQA、假设 MQA。Qwen3.5 还对照实际 full_attention 层数与假设全部层都是 full attention。没有本地文件时显示“来源=内置数值（待验证）”；找到文件时打印所选 snapshot 的完整路径，多份时按路径字典序选择最后一份。

**预测题：** 长度和批量各翻倍，容量如何变化？GQA 与 MQA 改变哪一项？为什么 Qwen3.5 的总层数不能直接代入普通 KV 公式？

**记录：** 项目模型公式/实际字节及相等性；真实模型的配置来源、层数、头数、头维、每 token 字节和各场景容量。Qwen3-0.6B 直接读取本地同名模型的 config.json；缺文件时使用内置回退配置并标注“待验证”。Qwen3.5 只计 full_attention 的随长度增长的 KV，不含 linear_attention 的固定状态。因此这不是完整推理显存，也不包含权重、激活、分配器开销；程序不报告模型权重大小。MiB/GiB 为二进制单位，同时保留原始字节数。

## 7. 预填充与解码的算术强度（15.7）

**做什么：** 用项目小模型和Qwen3-0.6B 配置（缺文件时使用待验证的内置回退），扫描预填充长度及解码批量，输出 FLOPs、访存字节、FLOPs/byte。全部是 bf16 数学粗算，不运行真实 Qwen 模型。

**预测题：** 预填充一次处理更多 token，权重读取成本能否被摊薄？固定历史长度下增加解码批量，算术强度为何上升，却不会无限线性增加？历史长度增长时 KV 读取项怎样影响结论？

**记录：** 预填充 `T=1,16,128,512,2048`，以及历史长度 `512/4096`、批量 `1/8/32/128` 的各项预算。对照 `step_cost` docstring 的口径：只计矩阵乘，乘加为两次 FLOP；线性参数含输出层，排除嵌入查表和 norm；权重每步读一次、历史和新 KV 各读一次、新 KV 写一次，忽略激活、softmax、RoPE 和动态 `torch.cat` 的复制。这里假设新 KV 写入后再被注意力读取，不假设它始终驻留片上缓存。预填充的注意力按整个矩形计，包含会被因果 mask 遮住的位置。

项目 GPT 满足 `n_head × head_dim = d_model`；本地 Qwen3 骨架不满足这个等式，必须用显式头维计算 Q/K/V/O 投影与注意力 FLOPs，不能伪造一个 GPTConfig 来套公式。Qwen3.5 混合线性注意力的 FLOPs 不适用这里的普通 Transformer 公式，本部分不估算它。算术强度只是解释计算与读写比例的模型，不能直接推导延迟，也不涉及任何具体 GPU 的峰值数字。

## 8. CPU 计时：每 token 时间随长度变化（15.7）

**做什么：** 默认随机模型为四层、宽度 256、上下文 1024、SDPA；有检查点时改用检查点模型。测当前总长度约 `64/128/256/512/1024` 的单步生成，以及提示长度 `64/256/1024` 的预填充。每组先预热一次，重复七次取中位数，计时前后同步设备。

单步实验先在计时区外缓存 `总长度−1` 个 token，再处理最后一个 token 并 argmax；无 cache 路径重算相同完整前缀。两条路径每轮都从相同提示开始，包含 Python 调度和动态缓存拼接。预填充实验包含缓存写入与首 token argmax，作为 TTFT 的 CPU 近似；不含分词、排队、网络与模型加载。输入使用重复 token 0，精度为 fp32、批量为 1。

**预测题：** 有 cache 时是否完全不再随长度增长？小模型的单步解码为何可能由固定开销主导？预填充的“每 token 毫秒”能否与用户看到的首 token 等待时间混为一谈？

**记录：** 设备、CPU 型号、线程数、torch 版本、模型配置、每个长度的有/无 cache 中位毫秒，以及预填充总毫秒和摊到每 token 的毫秒。关闭其他重负载后可重复本部分，保留各轮而不要只选最快的一轮。检查点上下文不足时记录实际测量长度；线程数指 PyTorch intra-op 和三个 BLAS/OpenMP 环境设置，不表示系统只存在两个线程。

## 9. 长公式生成速度（15.8）

**做什么：** 从 BOS 开始，贪心生成到总序列长度达到 `block_size` 或遇 EOS；有/无 cache 各完整计时一次，之前各用短前缀预热。检查点直接提供 BOS/EOS；没有检查点时使用随机 tiny 骨架，禁用 EOS，保证能观察到长度上限。

**预测题：** 端到端平均每 token 毫秒与第 8 部分某个固定长度处的单步延迟为何不同？如果检查点立即生成 EOS，两条路径的差异是否能充分体现长序列的效果？

**记录：** 模型来源、上下文上限、EOS 设置、输出是否完全相同、生成 token 数、两条路径总耗时与每 token 毫秒。生成数不含 BOS，包含生成出的 EOS；端到端时间包含预填充。只打印编号序列的比较和数量，不加载分词器，不声称随机 token 是有效 LaTeX。较大的自选检查点可能比默认随机模型运行更久。
