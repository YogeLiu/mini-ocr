## 2. 实验一：给每个指标找一个新的盲区

**问题：** 演示集是作者设计的。你能不能自己构造新的例子，让某个指标判错？

**预测：** 对下面每个目标，先在纸上写一对"参考 / 预测"，并预测各指标的结果：

1. 规范化后完全匹配判"不同"，但含义相同（不能用撇号，那是 P7）。
2. 规范化后完全匹配判"相同"，但含义不同（提示：想想 `SYNONYMS` 或 `SIZING` 里有没有不该合并的；或者 `\left` 后面跟的不是括号会怎样）。
3. 按 token 的编辑距离是 1，但你认为错误非常严重。
4. 渲染一致，但含义不同（提示：试试 `\mathrm{0}` 和 `\mathrm{O}`，或者 `|` 和 `\mid`，或者某些在当前字体下长得一样的符号）。
5. mathtext 能解析，但真正的 LaTeX 会报错（这个方向本章没有系统地测过）。

**运行：** 在 Python 里逐个检查：

```python
from miniocr.eval.metrics import score_pair
from miniocr.eval.render import compare_render
from miniocr.eval.latex_norm import normalize_latex
ref, pred = r"...", r"..."
print(normalize_latex(ref)); print(normalize_latex(pred))
print(score_pair(ref, pred)); print(compare_render(ref, pred))
```

**观察：** 哪些目标容易做到，哪些很难？目标 2 如果做到了，说明规范化器有一条规则太松，这比其他几个都严重。

**记录：** 每一对写一行：参考、预测、各指标结果、你认为的真实判断、这暴露了哪个指标的什么盲区。目标 5 没法在本机验证，写成"待验证"，等渲染器选型以后再测。

## 3. 实验二：规范化规则的松紧

**问题：** 每加一条规范化规则，EM 会升高。怎样判断一条规则是该加的，还是"太松"了？

**预测：** 下面三条候选规则，你认为哪些该加、哪些不该加？各自会让演示集的 EM 变成多少？

- A：把 `'` 换成 `^{\prime}`（连续的撇号合并到一个上标里，即选做练习 0.8）。
- B：把 `\mathrm{d}` 换成 `d`。
- C：去掉所有 `{` 和 `}`。

**运行：** 在 `latex_norm.py` 之外写一个包装函数，比如：

```python
from miniocr.eval import latex_norm as L

def normalize_with_rule_c(s):
    return " ".join(t for t in L.normalized_tokens(s) if t not in "{}")
```

再用 `exact_match` 的同样逻辑在演示集上算 EM（`DEMO` 在 `book/ch00_intro/tour.py` 里）。然后用测试 `test_normalize_different` 里的那几对检查：加了规则以后，含义不同的公式有没有被判成相同。

**观察：** EM 升高了多少；有没有"含义不同却被判相同"的例子。

**记录：** 三条规则各自的 EM 和反例。写一句话总结你判断"该不该加一条规则"的标准。

## 4. 实验三：渲染比较的容忍度

**问题：** 正文说 diff 不是"错误的严重程度"。如果允许 diff ≤ tol 也算一致，tol 取多少合适？

**预测：** 看第 7 部分的 diff 列：含义相同却不一致的 P5（0.919）、P6（0.442），真错了的 P12（0.018）、P13（0.083）。存在一个 tol，能让 P5、P6 判一致，同时 P12、P13 判不一致吗？

**运行：**

```python
from miniocr.eval.render import compare_render
from book.ch00_intro.tour import DEMO
for tol in [0.0, 0.01, 0.05, 0.1, 0.5]:
    rows = [compare_render(r, p, tol) for _, _, r, p, _ in DEMO]
    print(tol, [(d[0], x["image_match"]) for d, x in zip(DEMO, rows) if x["image_match"] is not None])
```

再试一试 dpi：`render(latex, dpi=200)` 和 `dpi=50` 下，P12、P13 的 diff 怎样变化（要自己调 `compare_images(render(r, dpi), render(p, dpi))`）。

**观察：** 有没有一个 tol 同时满足两边；dpi 改变后 diff 是否稳定。

**记录：** 一张 tol × 编号的表；你的结论。提示：如果找不到合适的 tol，这正说明"逐像素比较"这个方法本身的局限，精读选读的 CDM 就是为了解决这个问题。

## 5. 故障演练：EM 低得离谱

**场景：** 你写好了评测脚本，跑出来基线的 EM 只有 2%，CER 却只有 8%。同事说："CER 才 8%，EM 怎么可能这么低？"

**请按下面的步骤排查**，每一步写下你看到了什么：

1. 随机抽 10 个"EM 判错"的样本，把规范化后的参考和预测打印在一起，逐个看是哪里不同。
2. 检查参考答案是否也经过了 `normalize_latex`。（第 9 部分：只规范化预测时，演示集的 EM 是 0.0000。）
3. 检查两边是不是用了同一个版本的规范化函数（比如参考答案是很久以前用另一套脚本规范化好存下来的）。
4. 如果两边都没问题，统计这些样本的差异主要是哪类：真的错了，还是规范化器没覆盖的写法差异？后者说明要扩充规则（并升级规则的版本号）。

**要总结的教训：** EM 和 CER 的差距特别大时，先怀疑尺子，再怀疑模型。

## 6. 里程碑 M0：评测集、评测脚本、基线、错例表

> **前提：** 只有在 TexPixel 数据的使用权确认以后才开始。确认之前，不要把任何真实图片或标签放进仓库。下面的数量都标为"视可用数据而定"，由你根据实际情况决定并写进报告。

### 6.1 第一步：建目录和清单

按下面的结构建项目目录（放在仓库之外或者确认不会提交真实数据的位置）：

```text
project/
├── data/        raw/ processed/ validation/ test/
├── scripts/     数据检查、评测
├── outputs/     预测、指标、日志
└── reports/     M0、R1–R4
```

为每一张候选图片在 `data/manifest.csv` 里记一行：

| 字段 | 说明 |
|---|---|
| `id` | 唯一编号，一旦分配不再改 |
| `file` | 图片在 `data/raw/` 下的文件名 |
| `sha256` | 图片文件的 SHA-256（`hashlib.sha256(open(f, "rb").read()).hexdigest()`） |
| `source` | 来源（批次、渠道） |
| `license` | 使用权依据。说不清楚的，不放进清单 |
| `ref` | 参考 LaTeX |
| `annotator` / `checker` | 谁标注、谁校对 |
| `group` | 分组编号，第三步填：应该在同一边的样本（同一个公式的不同写法、同一张或近乎同一张图）编号相同 |
| `split` | 先空着，第三步填 |
| `added` | 加入日期 |

**检查：** `sha256` 有重复吗？重复的图片只保留一张。

### 6.2 第二步：检查参考答案

参考答案本身也会出错。在划分之前先做一遍检查：

```python
from miniocr.eval.latex_norm import is_well_formed, normalize_latex
from miniocr.eval.render import can_parse
```

1. `is_well_formed(ref)` 为 False 的，参考答案的花括号或参数有问题，回去对照图片修正。
2. `can_parse(ref)` 为 False 的，记下来。它们可能是真的有错，也可能只是 mathtext 不支持（矩阵、`\le` 等）。逐个看，分成两类，后一类在报告里写明"本章的渲染指标无法评测这些样本"。
3. 抽查至少一部分样本（数量视可用数据而定），人工对照图片核对参考答案。

**预测：** 你认为参考答案里有百分之几是有问题的？**记录** 实际检查出的数量和类型。

### 6.3 第三步：按公式分组划分

先分组，再按分组编号划分。注意：直接按规范化后的参考答案取哈希，只能保证**规范化结果相同的样本**落在同一边；规范化器没覆盖的等价写法会跨集合。演示集的 P7 就是反例：`f'(x)` 的哈希模 100 是 20，进 test；`f^{\prime}(x)` 是 57，进 validation（第 10 部分）。

1. 先用规范化后的参考答案给每个样本一个初始分组：规范化结果相同的，分组编号相同。
2. 合并该在一起的组：`sha256` 相同（同一张图）或近乎相同的图片；你已经知道的、规范化器没覆盖的等价写法（例如撇号和 `^{\prime}`）。合并以后把分组编号填进 `manifest.csv` 的 `group` 列。
3. 用分组编号取哈希，决定整组进验证集还是测试集：

```python
import hashlib

def split_of(group_id, test_percent=50):
    h = int(hashlib.sha1(str(group_id).encode("utf-8")).hexdigest(), 16)
    return "test" if h % 100 < test_percent else "validation"
```

几点要求：

- 验证集和测试集各要多少，视可用数据而定。测试集太小，数字的波动会很大（第 22 章会用 bootstrap 量化）；验证集太小，错例表看不出规律。
- 划分后检查两边的结构分布是否大致相同：用 `formula_tags` 数一数两边各有多少分式、上下标、矩阵、中文。差别很大时，考虑在每个标签内部分别划分。
- **划分完立刻冻结。** 把 `manifest.csv` 的 `group` 和 `split` 列填好，记下规范化规则的版本、分组的合并规则和划分日期。以后新增数据，只往新的批次里加，不要重新划分已有的样本。
- 以后如果有训练数据（第 19 章以后），用同样的分组方法检查训练集里有没有和验证集、测试集相同的公式。

### 6.4 第四步：跑基线

用现有系统（TexPixel 当前模型或 GLM-OCR 服务）分别在验证集和测试集上跑一遍，把结果存成 `outputs/baseline_validation.jsonl` 和 `outputs/baseline_test.jsonl`，每行：

```json
{"id": "...", "ref": "参考 LaTeX", "pred": "模型输出", "raw_output": "模型的原始返回（去掉包装之前）"}
```

同时在 `outputs/baseline_config.md` 里记下：系统名称和版本、调用方式（本地或服务、地址）、图片预处理、提示词（如果有）、生成参数、运行日期。

注意：

- 模型的原始输出常常带着 `$...$`、`\[...\]`、```` ```latex ```` 这类包装，要先剥掉。剥包装的代码也是评测协议的一部分，写进脚本，不要手工改。
- 模型没有返回结果（超时、报错）的样本，`pred` 记为空字符串，不要跳过。跳过会让分数偏高。（`miniocr.eval` 的错误率函数在参考和预测条数不同时会直接报错，就是为了防止这种遗漏。）
- **测试集的预测文件先存着，不要打分。** 第五、六步只用验证集；评测规则全部冻结以后，第七步才给测试集打分。

### 6.5 第五步：给验证集打分

```bash
python -m miniocr.eval.metrics outputs/baseline_validation.jsonl --out outputs/baseline_validation.csv --render
```

（`--render` 会调用 mathtext，比较慢；只要字符串指标时去掉它。）

把验证集的评测面板（正文 0.9.3 节）记下来。

### 6.6 第六步：在验证集上建错例表

打开 `outputs/baseline_validation.csv`，筛出 `em_norm` 为 False 的行，逐条对照图片，在"错误类型"一栏填上类型（正文 0.10.5 节的初始分类，可以按需要增减），在"备注"一栏写一句话说明。

- 错例太多时，先随机抽一部分（数量视可用数据而定），抽样的随机种子写进报告。
- 遇到"写法差异（其实是对的）"：记下来，汇总后决定要不要给规范化器加规则。加规则要升级版本号，并且重新计算验证集上基线的全部数字。这时测试集还没有打过分，改规则不会碰到它。
- 遇到"标注错误"：在 `manifest.csv` 里修正验证集的参考答案，并在修订记录里写明。不要去测试集里找标注错误。

最后统计每种错误类型的数量和比例，再按 `tags` 列分桶看：分式、上下标、矩阵、中文各自的 EM 和 CER_token 是多少。

**预测：** 在打开错例表之前，先写下你认为最多的三类错误。**记录** 实际的前三类，以及你据此提出的一个"下一步实验"的假设（例如："上下标错误占一半以上，猜测是图片缩放后上标太小，下一步对比不同的图片分辨率"）。

### 6.7 第七步：冻结评测协议，给测试集打一次分

验证集上的错例分析和规则修订都做完以后：

1. **冻结选型和评测协议。** 预先登记本次要评测的基线及其配置，记下规范化规则的版本、剥包装的规则、渲染器和字体、`miniocr.eval` 的版本。从这一刻起，M0 报告里不再改动其中任何一项。
2. **给测试集打一次分：**

```bash
python -m miniocr.eval.metrics outputs/baseline_test.jsonl --out outputs/baseline_test.csv --render
```

3. 把测试集的评测面板填进 M0 报告。**测试集只看汇总数字，开发期间不打开 `baseline_test.csv` 看错例，也不根据这些数字改任何设置。最终报告定稿后才可解封做错例分析。**（正文 0.10.1 节：选型冻结后，预先登记的候选可各评一次；本次 M0 只评登记的一个基线。）

如果看到测试集的数字以后又改了协议，就违反了上面的约定：在报告里写明，并按正文 0.10.1 节的做法补一份新的留出测试集。
