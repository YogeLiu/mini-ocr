# 第 0 章 导论：公式识别与评测

## 本章导读

这本书从头到尾围绕一个问题展开：

> 给一张公式图片，写出它的 LaTeX。

后面三十多章会讲张量、反向传播、Transformer、GPT、LoRA、强化学习、ViT、VLM……每学一样新东西，我们都会问：它能不能让公式识别变得更好？

"更好"要靠数字说话。可是数字从哪里来？模型输出了 `x^2 + y^2`，标准答案是 `x^{2}+y^{2}`，它算对还是算错？输出了 `x_{2}+y^{2}`，只差一个字符，该扣多少分？这一章不训练任何模型，只做一件事：**造一把可靠的尺子**。尺子不准，后面所有的"提升了 3 个点"都没有意义。

**学完本章，你能做到：**

1. 说出公式识别的输入和输出：一张公式图片 → 一段 LaTeX 字符串；说出它比普通文字识别难在哪里。
2. 解释为什么"LaTeX 字符串不同"不等于"数学含义不同"（例如 `x^2` 与 `x^{2}`），并写出一个 LaTeX 规范化函数：分词（把字符串切成一个个符号单位，叫 token）、逐 token 规则、解析成语法树、按规范写法写回。
3. 计算并解释五个指标：完全匹配、编辑距离（以及由它得到的 CER，即字符错误率，和按 token 的错误率）、可编译率、渲染后图片一致率；对每个指标，举出一个它会判错的例子；说出本书两版评测面板各用在哪里。
4. 说清"按字符"和"按 token"计算错误率的区别，以及语料级错误率和逐样本平均的区别。
5. 说清验证集和测试集的分工：验证集用来做决定，测试集是留出集；知道怎样记录每张图片的来源和使用权，怎样按公式分组划分以免泄漏。
6. 按实验手册完成里程碑 M0，也就是贯穿全书的 TexPixel 公式识别项目的第一步：建立验证集和测试集、写好评测脚本、跑出现有系统的基线、在验证集上建一张错例表。

## 0.1 问题：公式识别是什么

### 0.1.1 输入和输出

公式识别（formula recognition，也叫数学公式 OCR）的任务是：

```
输入：一张图片，上面是一个排好版的公式（印刷体或手写体）
输出：一段 LaTeX 字符串，用 LaTeX 把这个公式重新排版，应该得到同样的公式
```

比如图片上是一个二次方程的求根公式，模型应该输出：

```latex
x=\frac{-b\pm\sqrt{b^{2}-4ac}}{2a}
```

为什么输出是 LaTeX，而不是一张识别后的图片或者一棵语法树？因为 LaTeX 是数学界通用的写法，论文、教材、题库、网页上的公式几乎都能用它表示。拿到 LaTeX，就能编辑、检索、重新排版，也能交给计算机代数系统去算。

这本书的项目叫 TexPixel：拿一个公式识别系统，先把它评测清楚，再用书里学到的方法一步步改进它。

### 0.1.2 一个类比：听写

公式识别很像语文课上的听写，只不过"听"换成了"看"。

- 老师念一段话（图片），学生写下来（LaTeX）。
- 改听写的时候，老师要判断学生写的和原文"是不是一回事"。

这个类比带出了本章要解决的难题。听写"的地得"写错算错；但如果学生把一个句号写成了句点"."，算不算错？如果学生把"一千"写成"1000"呢？要不要扣分，取决于你想考什么。公式也一样：`x^2` 和 `x^{2}` 排出来一模一样，只是写法不同；`x^2` 和 `x_2` 只差一个字符，意思却完全不同。

不同的是，听写的原文只有一种写法，公式却有很多种合法写法，标准答案只是其中之一，所以不能直接比较字符串。

### 0.1.3 公式识别难在哪里

和识别一行普通文字相比，公式识别有四个额外的难点。

**难点一：二维结构。** 普通文字从左到右排成一行。公式不是：上标在右上方，下标在右下方，分子在分数线上面，分母在下面，矩阵是一个网格。模型看到的是二维的图，却要输出一维的字符串，必须把位置关系翻译成 `^`、`_`、`\frac{}{}` 这些符号。一个"2"写在 x 的右上方还是右下方，就是 `x^{2}` 和 `x_{2}` 的区别。

**难点二：形近符号。** 数字 1 和字母 l，数字 0 和字母 O，字母 x 和乘号 ×，希腊字母 α 和拉丁字母 a，ν（nu）和 v，求和号 ∑ 和希腊字母 Σ。印刷体里它们有时只差几个像素。题库里的公式还常常混着中文，例如"面积"和"面枳"这样的形近字。

**难点三：长序列。** 一个稍复杂的公式，LaTeX 有上百个字符。输出越长，中途出错的机会越多；一旦错了一个花括号，后面整段的结构可能都会乱。

**难点四：答案不唯一。** 同一个公式有很多种正确的 LaTeX 写法。这对训练和评测都是麻烦：训练时，模型被要求模仿标准答案的写法，而这种写法有一部分是随意的；评测时，我们得想办法不把"写法不同"判成"识别错了"。本章大部分篇幅都在处理这第四点。

### 0.1.4 中文、矩阵、分式、上下标

TexPixel 的数据里会出现几类典型结构，本章的演示例子把它们都覆盖到了：

## 0.2 OCR 简史（概括）

这一节只概括地讲，目的是让你知道这本书在技术发展的哪个位置。**下面提到的年份是作者凭记忆写的，没有逐一核对，一律标为待验证。**

**第一阶段：模板和规则。** 早期的 OCR 系统把每个字符和预先存好的模板逐像素比较，或者手工设计笔画、轮廓这类特征，再用规则判断。印刷体英文能做得不错，遇到新字体、噪声、公式这种二维结构就很吃力。早期的数学公式识别系统大多是两步走：先把每个符号切出来分别识别，再用文法规则分析符号之间的位置关系，拼成结构。

**第二阶段：学出来的特征。** 卷积神经网络（第 28 章）让"看图"这一步不再需要手工设计特征。识别手写数字的 LeNet（1990 年代，待验证）是这一阶段的代表。但"把一行字切成单个字符"仍然是难点。

**第三阶段：整行识别。** CTC 损失（2006 年前后，待验证）和 CNN + RNN 结构（例如 CRNN，2015 年前后，待验证）让模型可以直接从一整行图片输出字符序列，不再需要先切字符。这对普通文字很有效，但常规的按图像宽度展开的 CTC 识别器采用单调对齐：输出只能从左到右跟着图片走（多个时间步可以通过重复和空白合并成一个字符），难以直接表达复杂二维公式的读取顺序。

**第四阶段：编码器-解码器。** 编码器把图片变成一组特征，解码器像语言模型一样一个 token 一个 token 地生成 LaTeX，每一步用注意力（第 8 章）去图上找该看的地方。im2latex 数据集和对应的论文（Deng 等，2016 到 2017 年，待验证）是公式识别进入这一阶段的标志，它也是本章精读的论文。后来解码器换成了 Transformer。第 31 章你会亲手搭一个小 OCR，解码器也是 Transformer，但图像信息的接法更简单：把视觉 token 拼接到文字前面，不用交叉注意力（那一章会比较这两种接口）。

**第五阶段：视觉语言模型（VLM）。** 把一个强大的预训练语言模型接上视觉编码器，用海量图文数据训练，一个模型就能做文字识别、表格识别、公式识别、版面分析。近两年出现了一批专门面向文档的 VLM，例如 GLM-OCR、PaddleOCR-VL、Xiaomi-OCR、olmOCR 等（发布时间待验证）。它们是本书第四部分和第 36 章读技术报告的对象。

这本书的路线大致沿着第四、五阶段走：先学会语言模型（第二、三部分），再学视觉编码器，自己拼一个小 OCR（第 31 章），最后去理解和微调真实的 VLM。

不管哪个阶段都要评测，而且模型越强，评测越要细：完全匹配率已经很高时，剩下的错误往往最难也最隐蔽，粗糙的指标看不出差别。

## 0.3 为什么先讲评测

### 0.3.1 没有尺子，就不知道有没有进步

设想你在减肥，但家里的秤每次称的结果都差两三公斤。你吃了一周沙拉，秤上显示重了一公斤。是沙拉没用，还是秤不准？你没法知道。

做模型也是一样。后面的每一章都会提出一种改进：换个提示词、加一点数据、做一次 LoRA 微调、做一轮强化学习。判断它有没有用，靠的是在固定的数据上、用固定的评测脚本算出来的数字。尺子如果有系统性的偏差，比如把一大类正确的写法判成错，那它可能把一个有效的改进判成退步，也可能让你在一个错误的方向上越走越远。

所以这本书把评测放在第 0 章，放在所有模型之前。这个顺序参考了 CMU 11-667 的做法：先评测，再微调。

### 0.3.2 演示集：16 对手写的例子

为了把每个指标的长处和盲区看清楚，作者手写了 16 对"参考答案 / 模型预测"（实验脚本第 1 部分）。参考答案（reference）就是标准答案，模型预测（prediction）是假想的某个模型的输出。它们不是真实模型的输出，而是专门设计的：每个指标的盲区，都至少有一对能把它暴露出来。拿到有权使用的 TexPixel 数据以后，按实验手册把同样的流程再跑一遍。

| 编号 | 说明 | 参考答案 | 模型预测 | 含义相同吗 |
|---|---|---|---|---|
| P1 | 写法不同 | `x^{2}+y^{2}` | `x^2 + y^2` | 是 |
| P2 | 上下标顺序 | `\sum_{i=1}^{n}i^{2}` | `\sum^{n}_{i=1}i^2` | 是 |
| P3 | 省略花括号 | `\dfrac{1}{2}` | `\frac12` | 是 |
| P4 | 同义命令 | `a\leq b` | `a\le b` | 是 |

| P6 | 间距命令 | `\int_{0}^{1}f(x)\,dx` | `\int_0^1 f(x)dx` | 是 |
| P7 | 撇号 | `f'(x)` | `f^{\prime}(x)` | 是 |

| P13 | 中文形近字 | `S_{\text{面积}}=\pi r^{2}` | `S_{\text{面枳}}=\pi r^{2}` | 否 |
| P14 | 矩阵元素对调 | `\begin{pmatrix}a&b\\c&d\end{pmatrix}` | `\begin{pmatrix}a&b\\d&c\end{pmatrix}` | 否 |
| P15 | 缺右花括号 | `x^{2}` | `x^{2` | 否 |

脚本把每一对都渲染成了图片，保存在 `outputs/book/ch00/demo_pairs.png`，打开看一看，直观感受一下"含义相同"是什么意思。

**先猜一下：** 16 对里，原始字符串完全相同的有几对？答案是 0 对（第 1 部分）。如果直接比较字符串，这个"模型"的正确率是 0%，可它明明答对了 7 对。

### 0.3.3 理想的指标应该怎样

用这 16 对，可以说清楚我们想要一个什么样的指标：

1. **不冤枉**：P1 到 P7 应该判对。
2. **不放过**：P8 到 P16 应该判错。
3. **分轻重**：P12（错一个符号）应该比 P16（复读四遍）好得多；P8 虽然只差一个字符，意思却变了，不能当作"几乎全对"。
4. **能定位**：最好能告诉我们错在哪里，方便后面做错例分析。
5. **能复现**：同样的输入，在谁的机器上算都一样。

0.5 到 0.8 节会逐个讲这些指标，其中没有一个能同时做到这五点。所以实际评测时总是报告一组指标，每个指标负责它擅长的那一面。在讲指标之前，先解决"写法不同"这个最大的麻烦。

## 0.4 规范化：写法不同不等于含义不同

### 0.4.1 问题

P1 里，参考答案是 `x^{2}+y^{2}`，预测是 `x^2 + y^2`。差别有两处：

- 上标 `2` 外面有没有花括号。LaTeX 规定，`^` 后面如果只跟一个符号，花括号可以省略。
- 加号两边有没有空格。LaTeX 在数学模式里忽略普通空格，加号两边的间距由排版规则决定。

两种写法排版出来一模一样，含义也一样。这种差别在真实数据里非常多，原因也很好理解：参考答案是不同的人在不同年代用不同习惯写的；模型的输出又会模仿训练数据里最常见的那几种写法。两边对不上的地方，大部分都是这种"写法差异"。

**规范化（normalization）** 就是把各种等价的写法统一成一种"规范写法"，然后再比较。这有点像批改作文前先把全角标点和半角标点统一，把繁体字转成简体字：你关心的是内容，不是这些无关紧要的形式。

规范化必须**同时作用于参考答案和预测**，两边用完全相同的规则。这一点看起来理所当然，可 0.11 节的常见错误里就有反例：只规范化一边，完全匹配率会从 0.3750 掉到 0（第 9 部分）。

本章的规范化分四步：

```
LaTeX 字符串 ──分词──→ token 列表 ──逐 token 规则──→ token 列表 ──解析──→ 语法树 ──写回──→ 规范 token 列表
```

### 0.4.2 第一步：分词

**为什么要分词。** 字符是最小的单位，但对 LaTeX 来说太碎了。`\alpha` 是一个符号 α，却有 6 个字符。如果按字符处理，"把 `\alpha` 换成 `\beta`" 会被看成改了好几个字符，而它实际上只是换了一个符号。所以我们先把字符串切成一个个有意义的单位，叫 **token**（词元）。这里的 token 和第 6 章语言模型里的 token 是同一个概念，只不过这里是按 LaTeX 的语法手工切的，不是用 BPE 学出来的。因此本章的 token 数（以及后面的 CER_token）不能直接当成模型分词器的 token 数或序列长度预算：同一个公式交给 BPE 分词器，切出来的个数一般不同，需要用那个分词器重新数。

**切分规则**：从左到右扫描，每到一个还没读过的位置，就按下面的顺序判断这一处该怎么切（不是先对整个字符串做完第 1 条、再做第 2 条）：

1. 空白字符（空格、换行、制表符）丢掉。
2. `\begin{名字}` 和 `\end{名字}` 整体算一个 token，例如 `\begin{pmatrix}`。
3. 反斜杠后面跟一串英文字母：反斜杠连同这串字母算一个 token，例如 `\frac`、`\alpha`。
4. 反斜杠后面跟一个非字母的字符：两个字符合起来算一个 token，例如 `\,`（小间距）、`\{`（花括号符号本身）、`\\`（矩阵里的换行）。
5. 其他任何字符各算一个 token：字母、数字、运算符、括号、汉字。

几点说明：

- **规则 1 为什么能丢空白？** 数学模式里普通空格没有作用，`x + y` 和 `x+y` 一样。但命令名后面的空格是有用的：`\alpha b` 如果去掉空格变成 `\alphab`，就成了一个不存在的命令。扫描到 `\` 时，规则 3 读到空格就停，`\alpha` 被完整切出来；轮到空格这个位置，它才被规则 1 丢掉。所以普通数学模式的空格不产生 token，却参与决定命令在哪里结束，分词这一步保住了 `\alpha` 和 `b` 的边界。但有两处要注意：一是 `\text{…}` 里的空格是文字，本分词器同样丢掉了（0.4.7 节）；二是后面按字符算 CER 时，token 又被无分隔地拼回字符串，这条边界会重新丢失（0.6.6 节）。
- **规则 2 为什么要把 `\begin{pmatrix}` 当成一个 token？** 因为环境名是一个整体。如果拆成 `\begin`、`{`、`p`、`m`、`a`……，把 `pmatrix` 认成 `bmatrix`（圆括号矩阵变成方括号矩阵）就只算错一个字母，低估了这个错误。当成一个 token，错了就是错了整个环境。
- **规则 5 里数字一位一位地切。** `12` 是两个 token。这和第 6 章 Qwen 的分词器对数字的处理一样，好处是不会出现"12"和"1"、"2"两种切法。
- **汉字一个字一个 token。** 对中文来说，字是最自然的单位。

**数值例子**（实验脚本第 2 部分）：

```
\frac{a}{b} + x^2
→ ['\frac', '{', 'a', '}', '{', 'b', '}', '+', 'x', '^', '2']           11 个 token

S_{\text{面积}}=\pi r^{2}
→ ['S', '_', '{', '\text', '{', '面', '积', '}', '}', '=', '\pi', 'r', '^', '{', '2', '}']   16 个 token

\begin{pmatrix}a&b\\c&d\end{pmatrix}
→ ['\begin{pmatrix}', 'a', '&', 'b', '\\', 'c', '&', 'd', '\end{pmatrix}']   9 个 token
```

同一个公式，按字符数和按 token 数可以差很多（第 2 部分，都先去掉空白）：

| 公式 | 字符数 | token 数 |
|---|---|---|
| `\alpha+\beta` | 12 | 3 |
| `a+b` | 3 | 3 |
| `S_{\text{面积}}=\pi r^{2}` | 22 | 16 |
| `\begin{pmatrix}a&b\\c&d\end{pmatrix}` | 36 | 9 |

`\alpha+\beta` 和 `a+b` 都是"一个符号、加号、一个符号"，按 token 都是 3，按字符却差了 4 倍。这个差别直接影响错误率，见 0.6.5 节。

**代码**（`miniocr/eval/latex_norm.py`，练习 0.1）：

```python
def tokenize_latex(s):
    toks, i, n = [], 0, len(s)
    while i < n:
        c = s[i]
        if c.isspace():                                   # (1) 空白丢掉
            i += 1
        elif c == "\\":
            j = i + 1
            while j < n and s[j].isascii() and s[j].isalpha():
                j += 1                                    # (2) 向后吃掉一串英文字母
            if j == i + 1:                                # (3) 反斜杠后面不是字母
                toks.append(s[i:i + 2])
                i += 2
                continue
            name = s[i:j]
            if name in ("\\begin", "\\end"):              # (4) 环境名整体算一个 token
                ...                                       #     找到 { 和 }，拼成 "\begin{名字}"
            toks.append(name)
            i = j
        else:
            toks.append(c)                                # (5) 其他字符各算一个
            i += 1
    return toks
```

逐行解释：

**(1)** `str.isspace()` 对空格、换行、制表符都返回 True。

**(2)** 为什么要加 `isascii()`？Python 的 `isalpha()` 对汉字也返回 True。如果不加，`\text面积` 这种写法会把"面积"吞进命令名里，变成一个叫 `\text面积` 的 token。LaTeX 的命令名只能由英文字母组成。

**(3)** `j == i + 1` 说明反斜杠后面一个字母都没有，那就是 `\,`、`\{`、`\\` 这类"反斜杠 + 一个符号"的命令。字符串末尾单独一个反斜杠时，`s[i:i+2]` 只取到 `\` 本身，正好也是对的。

**(4)** 完整代码里，要跳过 `\begin` 和 `{` 之间可能有的空格，再用 `s.find("}", k)` 找到右花括号，把中间的名字去掉首尾空格后拼起来。

**(5)** 汉字、字母、数字、运算符都走这一支。

### 0.4.3 第二步：逐 token 的规则

有些写法差异只看单个 token 就能处理，不需要理解结构。本章用三条规则：

**规则一：同义命令换成同一个名字。** 例如：

| 写法 | 换成 | 为什么等价 |
|---|---|---|
| `\dfrac`、`\tfrac` | `\frac` | 都是分式，只是字号不同（display / text 样式） |
| `\le`、`\ge`、`\ne` | `\leq`、`\geq`、`\neq` | 同一个符号的两个名字 |
| `\to` | `\rightarrow` | 同一个箭头 |
| `\lbrace`、`\rbrace` | `\{`、`\}` | 同一个符号 |
| `\vert` | `\|` | 同一条竖线 |

完整的表在 `SYNONYMS` 里。

**规则二：删掉间距命令。** `\,`、`\;`、`\:`、`\!`、`\quad`、`\qquad`、`~` 这些命令只调整符号之间的空白，不改变公式的含义。P6 里参考答案在 `dx` 前面加了一个小间距 `\,`，这是排版上的讲究，识别时漏掉它不应该算错。

**规则三：删掉括号尺寸命令。** `\left(`、`\right)`、`\big(`、`\Bigg]` 这些命令让括号随内容自动变大，或者指定一个大小。删掉命令、保留括号本身。特例：`\left.` 和 `\right.` 表示"这一边不画括号"，要连同后面的点一起删掉。`\displaystyle`、`\limits` 这类只改变显示样式的命令也归在这一条里。

**数值例子**（第 3 部分）：

```
\dfrac{1}{2}               → ['\frac', '{', '1', '}', '{', '2', '}']
a\le b                     → ['a', '\leq', 'b']
\left(\frac{a}{b}\right)   → ['(', '\frac', '{', 'a', '}', '{', 'b', '}', ')']
f(x)\,dx                   → ['f', '(', 'x', ')', 'd', 'x']
\left. x \right|_{0}^{1}   → ['x', '|', '_', '{', '0', '}', '^', '{', '1', '}']
```

最后一个例子是定积分求值时常写的"竖线代入"。`\left.` 被整个删掉，`\right|` 只剩下竖线。

**每条规则都要问一句：真的等价吗？** 规则三其实有一点争议。`\left(\frac{a}{b}\right)` 排出来的括号比 `(\frac{a}{b})` 高，能把分式完整地包住；后者的括号矮一截，看起来不太好看。从"数学含义"看两者相同，从"排版效果"看两者不同。本章选择按含义判断，所以删掉尺寸命令。0.8 节的渲染后比较站在另一边，会把这一对判成不同。这是一个取舍，选了哪边都要**写进报告**。

**代码**（练习 0.2）：

```python
def apply_token_rules(tokens):
    out, i = [], 0
    while i < len(tokens):
        t = tokens[i]
        if t in SPACING:                                  # 规则二
            i += 1
        elif t in SIZING:                                 # 规则三
            if t in ("\\left", "\\right", "\\middle") and i + 1 < len(tokens) and tokens[i + 1] == ".":
                i += 2                                    # \left. 整个删掉
            else:
                i += 1                                    # 只删命令，括号留给下一轮
        else:
            out.append(SYNONYMS.get(t, t))                # 规则一：查不到就原样保留
            i += 1
    return out
```

注意它返回一个新列表，不修改输入。测试会检查这一点：在评测脚本里，同一份 token 列表可能还要被别的函数用到，悄悄改掉输入是很难查的错误。

### 0.4.4 第三步：解析成语法树

剩下的写法差异和**结构**有关，只看单个 token 处理不了：

- `x^2` 和 `x^{2}`：花括号有没有，要知道 `^` 的参数是什么。
- `\frac12` 和 `\frac{1}{2}`：要知道 `\frac` 有两个参数，`1` 是第一个、`2` 是第二个。
- `x^{2}_{i}` 和 `x_{i}^{2}`：上下标的先后顺序不影响排版，要知道这两个都是 `x` 的脚标。
- `{a}^{2}` 和 `a^2`：多余的花括号。

**一个容易犯的错误是"删掉所有花括号"。** 看起来很省事：`x^{2}` 和 `x^2` 删完都是 `x^2`。但 `x^{ab}` 删完变成 `x^ab`，而在 LaTeX 里 `x^ab` 的意思是"x 的 a 次方，再乘以 b"，只有 a 在上标里。这个"太松"的规范化器会把两个不同的公式判成相同（第 3 部分）：

```
x^{ab} vs x^ab   删花括号后相等：是   本章的规范化后相等：否
x^{2}  vs x^2    删花括号后相等：是   本章的规范化后相等：是
x^ab 的规范写法：x ^ { a } b
```

花括号有时是可有可无的写法，有时决定了结构。要分清这两种情况，就得真的去理解结构。办法是把 token 列表**解析**成一棵语法树。

**语法树的节点**只有四种，都用元组表示：

| 节点 | 含义 | 例子 |
|---|---|---|
| `("tok", t)` | 一个普通 token | `("tok", "x")` |
| `("group", [节点, ...])` | 一对花括号括起来的一组 | `{a+b}` |
| `("cmd", 名字, 可选参数, [参数])` | 带参数的命令 | `\frac{a}{b}`、`\sqrt[3]{x}` |
| `("script", 底, 下标, 上标)` | 带上下标的东西 | `x_{i}^{2}` |

**解析的规则**，核心是"原子"（atom）这个概念：一个原子是一个分组、一个带参数的命令（连同参数），或者一个普通 token。

1. 遇到 `{`，一直读到配对的 `}`，得到一个分组。
2. 遇到 `ARITY` 表里的命令（例如 `\frac` 有 2 个参数，`\sqrt` 有 1 个），接着读那么多个原子作为参数。`\sqrt` 后面如果紧跟 `[`，先把方括号里的内容读成可选参数。
3. 每读完一个原子，看后面有没有 `^` 或 `_`。有的话，这个原子就是"底"，`^` 后面读一个原子作上标，`_` 后面读一个原子作下标，两种各最多一次，顺序随意。
4. 出错就报错：花括号不配对、命令缺参数、同一个底有两个上标（例如 `x^1^2`，LaTeX 本身也会报"Double superscript"）。

**为什么 `^` 后面只读一个原子？** LaTeX 就是这样规定的，所以 `x^ab` 里只有 a 是上标。用"原子"这个概念，`x^2`、`x^{2}`、`x^{ab}`、`x^ab` 都能按 LaTeX 本来的意思解析出来。

**数值例子**（第 3 部分）：

```
x^2          → [('script', ('tok', 'x'), None, ('tok', '2'))]
x^2_i        → [('script', ('tok', 'x'), ('tok', 'i'), ('tok', '2'))]
\frac12      → [('cmd', '\frac', None, [('tok', '1'), ('tok', '2')])]
x^ab         → [('script', ('tok', 'x'), None, ('tok', 'a')), ('tok', 'b')]
{a}^{2}      → [('script', ('group', [('tok', 'a')]), None, ('group', [('tok', '2')]))]
\sqrt[3]{x}  → [('cmd', '\sqrt', [('tok', '3')], [('group', [('tok', 'x')])])]
```

手推一遍 `x^2_i`：

1. 读一个原子：`x` 是普通 token，得到 `("tok", "x")`。
2. 后面是 `^`：读一个原子 `2`，作为上标。
3. 后面是 `_`：读一个原子 `i`，作为下标。
4. 后面没有 `^`、`_` 了，打包成 `("script", ("tok","x"), ("tok","i"), ("tok","2"))`。注意元组里下标在前、上标在后，和输入里的顺序无关。

**代码**（练习 0.3）。解析器用三个互相调用的小函数，`pos` 记录读到了第几个 token：

```python
def parse_latex(tokens):
    pos = 0

    def atom():                                  # 读一个原子
        nonlocal pos
        if pos >= len(tokens) or tokens[pos] in ("}", "^", "_"):
            raise LatexSyntaxError(...)          # 需要原子却没有
        t = tokens[pos]
        if t == "{":
            pos += 1
            items = seq(inside_group=True)       # 读到配对的 } 为止
            pos += 1                             # 跳过 }
            return ("group", items)
        pos += 1
        if t in ARITY:                           # 带参数的命令
            opt = ...                            # \sqrt 的 [可选参数]
            return ("cmd", t, opt, [atom() for _ in range(ARITY[t])])
        return ("tok", t)

    def with_scripts(base):                      # 读底后面的上下标
        ...

    def seq(inside_group):                       # 读一串原子，直到 } 或结尾
        ...

    return seq(inside_group=False)
```

这种写法叫**递归下降解析**（recursive descent parsing）：`atom` 遇到 `{` 就调用 `seq`，`seq` 又调用 `atom`，嵌套多少层花括号，就递归多少层。`nonlocal pos` 让内层函数能修改外层的 `pos` 变量。

### 0.4.5 第四步：按规范写法写回

有了语法树，就可以按一套固定的规矩把它写回 token 列表。规矩只有三条：

1. **参数一律带花括号。** 上下标、`\frac` 的两个参数、`\sqrt` 的参数，都写成 `{ … }`。参数本身就是一个分组时，只保留一层花括号：`\frac{{a+b}}{c}` 的第一个参数写成 `{ a + b }`。
2. **先下标、后上标。**
3. **多余的花括号去掉。** 一个分组里只有一个元素时，直接写这个元素（这是本章实现的简化，并非总是等价，见 0.4.7 节的作用域反例）：`{a}` 写成 `a`，`{{a+b}}` 写成 `{ a + b }`。**例外：** 这个元素自己带上下标、又被拿来当底时，花括号必须留着。`{x^2}^3` 是合法的（x 的平方再整体三次方）；如果把花括号去掉，就成了 `x^{2}^{3}`，这是一个底挂了两个上标的非法写法。

最后用空格把 token 连起来，得到规范写法的字符串。

```
x^2          规范写法  x ^ { 2 }
x^2_i        规范写法  x _ { i } ^ { 2 }
\frac12      规范写法  \frac { 1 } { 2 }
x^ab         规范写法  x ^ { a } b
{a}^{2}      规范写法  a ^ { 2 }
\sqrt[3]{x}  规范写法  \sqrt [ 3 ] { x }
{{a+b}}^{2}  规范写法  { a + b } ^ { 2 }
\frac{{a+b}}{c}  规范写法  \frac { a + b } { c }
{x^2}^3      规范写法  { x ^ { 2 } } ^ { 3 }
```

（第 3 部分）

第 3 部分还检查了例外那一条：合法的参考 `{x^2}^3` 规范成 `{ x ^ { 2 } } ^ { 3 }`；非法的预测 `x^{2}^{3}` 解析失败，退回到只做逐 token 规则，得到 `x ^ { 2 } ^ { 3 }`。两者不相等，非法预测不会被判成对的。

**为什么用空格连起来？** 规范写法本身也是一段合法的 LaTeX，空格在数学模式里不起作用。`\text{…}` 这类文字盒子里面是例外：那里是文字模式，空格会排出来，所以 `\text { i f }` 和原来的 `\text{if}` 排出来并不一样。规范写法是拿来比较的，不是拿来排版的，选做练习 0.9 会碰到这个问题。用空格隔开以后，`text.split()` 就能还原出 token 列表，方便后面按 token 计算编辑距离。im2latex 数据集发布的"规范化公式"也是这种用空格隔开 token 的格式。

**代码**（练习 0.4）：

```python
def serialize(nodes):
    def unwrap(node):                                    # 剥掉单元素分组：{{a}} → a，{{a+b}} → {a+b}
        while node[0] == "group" and len(node[1]) == 1:
            node = node[1][0]
        return node

    def ser(node):
        node = unwrap(node)
        kind = node[0]
        if kind == "tok":
            return [node[1]]
        if kind == "group":                              # 剥完以后只剩多元素或空分组
            return ["{"] + serialize(node[1]) + ["}"]
        if kind == "cmd":
            _, name, opt, args = node
            out = [name]
            if opt is not None:
                out += ["["] + serialize(opt) + ["]"]
            for a in args:
                out += braced(a)
            return out
        _, base, sub, sup = node                         # script
        base = unwrap(base)
        out = ["{"] + ser(base) + ["}"] if base[0] == "script" else ser(base)
        if sub is not None:
            out += ["_"] + braced(sub)                   # 先下标
        if sup is not None:
            out += ["^"] + braced(sup)                   # 后上标
        return out

    def braced(node):
        node = unwrap(node)
        if node[0] == "group":
            return ["{"] + serialize(node[1]) + ["}"]    # 已经是分组：只要一层
        return ["{"] + ser(node) + ["}"]

    out = []
    for node in nodes:
        out.extend(ser(node))
    return out
```

几个细节：

- `unwrap` 先把"只套着一个元素的分组"一层层剥掉，`ser` 和 `braced` 都先调用它。剥完以后还是分组的，一定是多元素分组（或空分组），花括号要保留。所以 `{a}^{2}` 的底 `{a}` 写成 `a`，而 `{a+b}^{2}` 的底保留花括号。后者必须保留：去掉就成了 `a+b^{2}`，只有 b 是平方。
- 底剥完以后如果本身是一个带上下标的节点（`{x^2}^3` 的底 `x^2`），也要套回一对花括号，这就是规则 3 的例外。
- `braced` 处理参数。剥完以后是分组的，把分组里的内容放进一对新花括号；否则用 `ser` 写出这个节点，再套一对花括号。`\frac{{a+b}}{c}` 的第一个参数是"分组里套一个多元素分组"，剥掉外层后只剩 `{a+b}`，最后得到 `\frac { a + b } { c }`。

**把四步串起来：**

```python
def normalized_tokens(s):
    toks = apply_token_rules(tokenize_latex(s))
    try:
        return serialize(parse_latex(toks))
    except LatexSyntaxError:
        return toks                                  # 解析失败：只做逐 token 规则

def normalize_latex(s):
    return " ".join(normalized_tokens(s))
```

**解析失败时怎么办？** 模型的输出不一定合法，比如 P15 的 `x^{2` 少了右花括号。这时没法建语法树，我们退一步，只做分词和逐 token 规则，返回 `x ^ { 2`。这样它仍然能参与编辑距离的计算，和参考答案的距离是 1（少一个 `}`），而不是让整个评测脚本崩溃。

| 编号 | 说明 | 原样相等 | 规范化后相等 | 含义相同 |
|---|---|---|---|---|
| P1 | 写法不同 | 否 | 是 | 是 |
| P2 | 上下标顺序 | 否 | 是 | 是 |
| P3 | 省略花括号 | 否 | 是 | 是 |
| P4 | 同义命令 | 否 | 是 | 是 |
| P5 | 括号尺寸 | 否 | 是 | 是 |
| P6 | 间距命令 | 否 | 是 | 是 |
| P7 | 撇号 | 否 | **否** | 是 |

完全匹配率从 0/16 变成 6/16 = 0.3750（第 3 部分）。含义相同的 7 对里，规范化救回了 6 对；9 对真错的，一对也没有被误放过去。

**P7 为什么没救回来？** `f'` 里的撇号 `'` 在 LaTeX 里就是 `^{\prime}` 的简写，两者排出来一样。本章的规范化器没有这条规则。这条是故意留下的：任何规范化器都只覆盖一部分写法差异。选做练习 0.8 让你把它补上。

### 0.4.7 规范化器的盲区和原则

规范化器可能犯两种错误：

- **太松**：把含义不同的两个公式规范成同一个写法。例如"删掉所有花括号"会把 `x^{ab}` 和 `x^ab` 当成一样。本章的规范化器也有一处太松：`\text{…}` 里是文字模式，空格是有意义的，`\text{if x}` 和 `\text{ifx}` 是两段不同的文字，但本章的分词器把空格丢掉了，两者规范化后相同（选做练习 0.9）。还有一处：规则 3 去掉单元素分组时不检查元素是不是 `\bf`、`\rm` 这类字体声明。分组同时决定声明的作用范围：`{\bf}x` 里粗体只作用于空分组，x 不变；`\bf x` 里 x 变粗。两者含义不同，本章的实现却都规范成 `\bf x`。用本章同一个 mathtext 渲染器比较，两者都能解析，但渲染结果并不一致。更稳妥的做法是只剥去不含声明类命令的分组，遇到声明就保留花括号（选做练习 0.11）。规范键后面还用于分组划分和去重（第 12、31 章），这里太松也会把两条不同的公式并成一组；它在真实语料里出现得多频繁，尚未统计。太松的规范化器会**高估**模型：错的被判成对的。
- **太紧**：没能把含义相同的写法统一起来。例如本章的规范化器处理不了 P7 的撇号，也处理不了下面这些：
  - `\left(\begin{matrix}a&b\\c&d\end{matrix}\right)` 和 `\begin{pmatrix}a&b\\c&d\end{pmatrix}`：都是圆括号矩阵。
  - `\mathrm{d}x` 和 `dx`：微分号用不用正体，各有各的习惯。

  太紧的规范化器会**低估**模型：对的被判成错的。

两种错误哪个更危险？**太松更危险。** 太紧只是让分数偏低，而且你在错例分析时会看到"明明是对的却被判错"，会去修规范化器。太松会让分数虚高，错例表里根本不会出现这些例子，你也就永远发现不了。所以原则是：

1. **只合并你确信等价的写法。** 拿不准的就不合并，宁可在错例表里多看到几条"写法差异"。
2. **不要合并"数学上等价、但识别结果不同"的写法。** 比如 `a+b` 和 `b+a`，数学上相等，但图上写的是 `a+b`，模型输出 `b+a` 就是识别错了。我们评的是"有没有照着图写对"，不是"算出来对不对"。测试 `test_normalize_different` 专门检查这一点。
3. **规范化规则是评测协议的一部分。** 规则一改，所有数字都变。所以规则要写进报告，要有版本号；比较两个模型时，必须用同一版规则。什么时候可以改规则，见 0.10.5 节。
4. **两边都要规范化**，用同一个函数。

## 0.5 指标一：完全匹配

### 0.5.1 定义

**完全匹配率**（exact match，简称 EM）：规范化以后，预测和参考完全相同的样本所占的比例。

$$
\mathrm{EM} = \frac{\text{规范化后完全相同的样本数}}{\text{样本总数}}
$$

演示集上，不规范化时 EM = 0.0000，规范化后 EM = 0.3750（第 3 部分）。今后本书说"完全匹配"，默认都指规范化以后的。

### 0.5.2 长处

- **简单，好解释。** "100 个公式里完全对了 62 个"，谁都听得懂。
- **严格。** 只要规范化器不太松，被判对的就真的对了。对于要直接拿去用的结果（比如把公式粘贴进论文），用户关心的就是这一点："我要不要手动改？"

### 0.5.3 盲区：全对或全错，分不出轻重

完全匹配只有 0 和 1 两个值。P12 只把 `n+1` 认成了 `n-1`，P16 把 `x^{2}` 复读了四遍，它们的 EM 都是 0；什么都不输出的空预测，EM 也是 0（第 3 部分）。

这带来一个实际问题：**模型在进步，EM 却可能纹丝不动。** 假设你改进了模型，原来错得一塌糊涂的长公式，现在只错一个符号了。对使用者来说这是很大的进步（只要改一个字符），但 EM 一点都没变。特别是对长公式，完全做对很难，EM 会长期接近 0，失去分辨能力。

所以我们还需要一个能给部分分的指标。

## 0.6 指标二：编辑距离与错误率

### 0.6.1 直觉：改作文要动几笔

老师批改作文，错一个字划一下、漏一个字补一下、多一个字删一下。改得越少，说明写得越接近。**编辑距离**就是把这个想法精确化：

> 把预测变成参考答案，最少需要多少次"插入一个、删除一个、替换一个"？

这个定义来自 Levenshtein（1965 年，待验证），所以也叫 Levenshtein 距离。每种操作的代价都是 1。

几个简单的例子：

- `x^{2}` → `x_{2}`：把 `^` 换成 `_`，替换 1 次，距离 1。
- `kitten` → `sitting`：k 换成 s，e 换成 i，末尾插入 g，距离 3（第 4 部分）。
- 空字符串 → `abc`：插入 3 次，距离 3。

"最少"两个字很要紧。把 `kitten` 全删掉再一个个写出 `sitting`，要 6 + 7 = 13 步，但这不是最少的。怎样保证找到最少的？试遍所有改法显然不行，改法的数量是指数级的。下面用动态规划来算。

### 0.6.2 推导：一张表填出最少步数

设参考答案是 a，预测是 b。这里先按字符讲，按 token 算完全一样，只是把字符换成 token。记 `D[i][j]` 为"把 a 的前 i 个字符变成 b 的前 j 个字符"的最少操作数。我们要的答案是 `D[len(a)][len(b)]`。

> 方向说明：编辑距离是对称的，"a 变成 b"和"b 变成 a"的最少步数相同（插入和删除互换）。代码里按 a 变成 b 写，讲解时说"把预测改成参考"也行，结果一样。

**边界：**

- `D[i][0] = i`：把 a 的前 i 个字符变成空串，只能删掉 i 个。
- `D[0][j] = j`：把空串变成 b 的前 j 个字符，只能插入 j 个。

**递推：** 想一想，把 a 的前 i 个字符变成 b 的前 j 个字符，**最后一步**只有三种可能：

1. **删除 a 的第 i 个字符。** 那么之前要先把 a 的前 i−1 个变成 b 的前 j 个，代价 `D[i-1][j]`，再加这次删除的 1。
2. **插入 b 的第 j 个字符。** 之前要先把 a 的前 i 个变成 b 的前 j−1 个，代价 `D[i][j-1]`，再加 1。
3. **把 a 的第 i 个字符对应到 b 的第 j 个字符。** 之前要把 a 的前 i−1 个变成 b 的前 j−1 个，代价 `D[i-1][j-1]`；如果这两个字符相同，不用改，加 0；不同就替换，加 1。

最少的那个就是答案：

```
D[i][j] = min( D[i-1][j]   + 1,                    删除
               D[i][j-1]   + 1,                    插入
               D[i-1][j-1] + (a[i-1] != b[j-1]) )  相同或替换
```

Python 下标从 0 开始，所以"第 i 个字符"是 `a[i-1]`。

为什么这样一定能找到最少的？因为任何一种改法，它的最后一步都必然是这三种之一；而去掉最后一步之后，剩下的部分本身也必须是那个子问题的最优改法，否则把它换成更优的，整体就能更少。这种"大问题的最优解由小问题的最优解拼成"的性质，就是动态规划能用的前提。这是数学结论。

### 0.6.3 数值例子

参考 a = `x^{2}`（5 个字符），预测 b = `x_2`（3 个字符）。表 D 的形状是 (6, 4)：行对应 a 的前 0 到 5 个字符，列对应 b 的前 0 到 3 个字符，ε 表示空串（实验脚本第 4 部分）：

```
         ε   x   _   2
     ε   0   1   2   3
     x   1   0   1   2
     ^   2   1   1   2
     {   3   2   2   2
     2   4   3   3   2
     }   5   4   4   3
```

挑几个格子手算一遍：

- `D[1][1]`（`x` 变成 `x`）：两个字符相同，取左上角 `D[0][0] + 0 = 0`。另外两个候选 `D[0][1]+1 = 2`、`D[1][0]+1 = 2` 都更大。结果 0。
- `D[2][2]`（`x^` 变成 `x_`）：`^` 和 `_` 不同，左上角 `D[1][1] + 1 = 1`；上方 `D[1][2] + 1 = 2`；左方 `D[2][1] + 1 = 2`。结果 1，对应"把 `^` 换成 `_`"。
- `D[4][3]`（`x^{2` 变成 `x_2`）：最后两个字符都是 `2`，相同，左上角 `D[3][2] + 0 = 2`。结果 2。
- `D[5][3]`（`x^{2}` 变成 `x_2`）：`}` 和 `2` 不同。左上角 `D[4][2] + 1 = 4`；上方 `D[4][3] + 1 = 3`；左方 `D[5][2] + 1 = 5`。结果 3，来自上方，对应"删掉 `}`"。

编辑距离 = `D[5][3]` = 3。

**回溯：找出具体是哪几步。** 从右下角出发，每一步看当前格子是从哪个邻居算来的，倒着走回左上角，就得到一组最少操作。脚本里的 `align` 函数做的就是这件事（第 4 部分）：

```
[('=', 'x', 'x'), ('D', '^', ''), ('S', '{', '_'), ('=', '2', '2'), ('D', '}', '')]
```

意思是：`x` 相同；删掉 `^`；把 `{` 换成 `_`；`2` 相同；删掉 `}`。三步。读起来有点怪：人会说"把 `^` 换成 `_`，删掉两个花括号"，也是三步。**最少操作可能不止一组**，回溯只找出其中一组，具体是哪组取决于平局时优先走哪个方向。所以用 `align` 统计"哪个符号被认成了哪个"时，要记得它只是一种合理的对齐，不是唯一的真相。

这个例子还说明了为什么要先规范化：`x^{2}` 和 `x_2` 只差"上标还是下标"一处，但不规范化时距离是 3；规范化以后两边都有花括号，距离是 1。

**代码**（`miniocr/eval/metrics.py`，练习 0.5）：

```python
def edit_distance(a, b):
    prev = list(range(len(b) + 1))                 # 第 0 行：D[0][j] = j
    for i in range(1, len(a) + 1):
        cur = [i] + [0] * len(b)                   # D[i][0] = i
        for j in range(1, len(b) + 1):
            cur[j] = min(prev[j] + 1,              # 删除：上方
                         cur[j - 1] + 1,           # 插入：左方
                         prev[j - 1] + (a[i - 1] != b[j - 1]))   # 左上
        prev = cur
    return prev[-1]
```

填第 i 行只用到第 i−1 行，所以只保留两行，内存从 O(len(a) × len(b)) 降到 O(len(b))；时间仍然是 O(len(a) × len(b))。a、b 可以是字符串，也可以是列表：`a[i-1] != b[j-1]` 对两者都成立。传入 token 列表，算出来的就是按 token 的编辑距离。

### 0.6.4 从编辑距离到错误率

编辑距离是一个绝对数。同样差 3，对一个 5 个字符的公式是大错，对一个 300 个字符的公式是小错。所以要除以长度，变成**错误率**。

**按字符的错误率**就是 OCR 领域最常用的 **CER**（character error rate）。按 token 计算的，本书叫**按 token 的错误率**，记作 CER_token（有的文献叫 TER 或 token error rate）。

**一个样本的错误率：**

$$
\text{错误率} = \frac{\text{编辑距离}(\text{参考},\text{预测})}{\text{参考答案的长度}}
$$

**为什么分母是参考答案的长度，而不是预测的长度？** 因为参考答案是固定的，所有模型都除以同一个数，才能互相比较。如果除以预测的长度，一个疯狂复读的模型输出越长，分母越大，错误率反而被"稀释"了（0.11 节有数字）。

**错误率可以大于 1。** P16 的参考答案 `x^{2}` 规范化后有 5 个 token，预测复读了四遍有 20 个 token，要删掉 15 个，单样本错误率 = 15 / 5 = 3.0000（第 5 部分）。看到 CER 大于 1 不要以为算错了，这通常说明模型在胡乱生成。

**语料级错误率。** 一个数据集有很多样本，怎样合成一个数？标准做法是**先把编辑距离和长度分别加起来，再相除**：

$$
\mathrm{CER} = \frac{\sum \text{编辑距离}}{\sum \text{参考答案的长度}}
$$

而不是"每个样本先算错误率，再求平均"。两者差别有多大？看两个样本（第 5 部分）：

| 参考 | 预测 | token 编辑距离 | 参考长度 | 单样本错误率 |
|---|---|---|---|---|
| `\pi` | `n` | 1 | 1 | 1.0000 |
| `\sum_{k=1}^{n}k=\frac{n(n+1)}{2}` | `\sum_{k=1}^{n}k=\frac{n(n-1)}{2}` | 1 | 25 | 0.0400 |

- 语料级：(1 + 1) / (1 + 25) = 0.0769。
- 逐样本平均：(1.0000 + 0.0400) / 2 = 0.5200。

差了将近 7 倍。语料级的含义是"平均每个参考 token 要改多少次"，长样本的权重大；逐样本平均的含义是"平均每个样本错了百分之几"，短样本的一次错误被放大。两个都有道理，但 CER 的惯例是语料级。**报告时一定要写清楚用的是哪种。** 本书默认语料级。

### 0.6.5 按字符还是按 token

演示集上，规范化以后（第 5 部分）：

| | 按字符（CER） | 按 token（CER_token） |
|---|---|---|
| 全部 16 对 | 0.1724 | 0.1962 |
| 只看真错的 9 对 | 0.2138 | 0.3068 |

两种算法对单个错误轻重的判断不一样（第 4、5 部分）：

| 编号 | 错误 | 按字符 | 按 token |
|---|---|---|---|
| P10 | `\alpha` 认成 `a` | 5 / 12 = 0.4167 | 1 / 3 = 0.3333 |
| P13 | `积` 认成 `枳` | 1 / 22 = 0.0455 | 1 / 16 = 0.0625 |
| P14 | 矩阵里 c、d 对调 | 2 / 36 = 0.0556 | 2 / 9 = 0.2222 |

- **P10：** 按字符，`\alpha` 变成 `a` 要删掉 5 个字符，看起来是一个大错；按 token，只是换了一个符号，编辑距离 1。人看来这就是"认错了一个符号"，按 token 更贴近直觉。
- **P13：** 汉字一个字就是一个字符、一个 token，两种算法的编辑距离都是 1。错误率的差别只来自分母：参考答案里 `\text`、`\pi` 这些命令按字符被拆开，分母变大。
- **P14：** 矩阵的 `\begin{pmatrix}` 和 `\end{pmatrix}` 按字符有 28 个字符，把分母撑得很大，两个元素对调只算 5.56%；按 token 它们各算 1 个，同样的错误算 22.22%。

**规律：按字符计算时，命令越长，它在分子和分母里的分量越重。** 一个公式里长命令越多，分母越大，同样的符号错误显得越轻；而把一个长命令认错，又显得越重。按 token 计算把每个符号同等看待，更接近"错了几个符号"。

只报按 token 的也不够，因为按 token 的结果依赖分词规则：换一种分词（比如把 `\begin{pmatrix}` 拆开），数字就变了；而按字符的结果只依赖规范化，和别的论文更容易对比。所以 OCR 主任务面板（0.9.3 节）两个都报，并写清楚分词和规范化的版本。

### 0.6.6 盲区：距离小不等于错得轻

编辑距离把每一次修改都看作代价 1，它不知道哪个符号重要：

- **P8：** `x^{2}` 认成 `x_{2}`，编辑距离 1，CER_token 只有 1 / 11 = 0.0909（第 5 部分）。可是 x 的平方变成了 x 带下标 2，含义完全变了。
- **P9：** `\frac{a}{b}` 认成 `\frac{b}{a}`，编辑距离 2，单样本错误率 0.2857（第 5 部分）。分数整个颠倒了，但错误率看起来不到三成。
- **P12：** `n+1` 认成 `n-1`，编辑距离 1，单样本错误率 0.0400。在长公式里，一个改变结果的符号错误显得微不足道。
- **命令边界：** 字符 CER 的实现把规范 token 无分隔地拼成字符串再比较。`\sin h(x)`（正弦作用于 h(x)）和 `\sinh(x)`（双曲正弦）的 token 不同，完全匹配为 0、CER_token 为 0.4，按字符拼接后却一模一样，字符 CER 为 0；`\alpha b` 和 `\alphab` 也一样。所以本书的字符 CER 是一个会碰撞的代理距离：字符距离为 0 不保证规范化完全匹配。后面用字符距离排序偏好候选或计算奖励的章节（第 18、23、25、34 章）都继承了这个口径；修正它（例如在 token 之间保留分隔）要升级评测版本、所有候选重算，旧数字保留旧协议标签。

另一方面，编辑距离也不知道结构。它把公式当作一串符号，看不出 `x^{2}` 里的 `2` 和 `x_{2}` 里的 `2` 位置完全不同。要从"排出来是什么样子"的角度判断，得看后面的渲染比较。

还要提醒一点：编辑距离的**定位**能力很有限。0.6.3 节说过，最少操作可能不止一组，`align` 给出的只是其中一组。拿它统计"哪个符号最常被认错"做参考可以，但不能当作精确结论。

## 0.7 指标三：可编译率

### 0.7.1 定义

**可编译率**：预测能被 LaTeX 成功编译（排版）的比例。

$$
\text{可编译率} = \frac{\text{能编译的预测数}}{\text{样本总数}}
$$

它和前两个指标性质不同：**它不看参考答案**，只检查预测"是不是一段合法的 LaTeX"。

### 0.7.2 为什么还需要它

前两个指标都会给 P15 的 `x^{2`（少一个右花括号）一个很小的错误：编辑距离只有 1。但这段 LaTeX 排不出来，拿到手完全没法用。对生成模型来说，"输出不合法"是一类单独的故障，往往说明模型在长序列上失去了对结构的控制。可编译率专门盯着这类故障。

第二部分训练 LaTeX 语言模型时（里程碑 M1），可编译率也是衡量"生成的公式像不像样"的主要指标。

### 0.7.3 本章怎样近似：mathtext 能不能解析

要测可编译率，需要一个 LaTeX 引擎。本机没有装 LaTeX，正式渲染器的选型也还没定。所以本章用 matplotlib 自带的 mathtext 代替：**能被 mathtext 解析，就算"能编译"。**

mathtext 是 matplotlib 为了在图表里写公式而实现的一个小排版器，只支持 LaTeX 数学模式的一个子集。用它来近似，会在两个方向上出错。我们在演示集上看看（第 6 部分）：

| 编号 | 参考能解析 | 预测能解析 | 说明 |
|---|---|---|---|
| P1、P2、P5 到 P13、P16 | 是 | 是 | |
| P3 | 是 | **否** | mathtext 不接受 `\frac12` 这种省略花括号的写法 |
| P4 | 是 | **否** | mathtext 不认识 `\le` |
| P14 | **否** | **否** | mathtext 不支持 `\begin{pmatrix}` 环境 |
| P15 | 是 | 否 | 真的不合法 |

预测的可解析率是 12/16 = 0.7500，参考答案的可解析率是 15/16 = 0.9375（第 6 部分，本项目观察）。

16 对里只有 P15 是真的不合法。P3、P4、P14 在完整的 LaTeX 里都能编译，却被 mathtext 判成了"不能编译"。这是近似带来的**假阴性**。再多看几个例子（第 6 部分，本项目观察）：

```
\frac12                                mathtext 能解析 否   先规范化再解析 是
a\le b                                 mathtext 能解析 否   先规范化再解析 是
\tfrac{1}{2}                           mathtext 能解析 否   先规范化再解析 是
\begin{pmatrix}a&b\\c&d\end{pmatrix}   mathtext 能解析 否   先规范化再解析 否
```

前三个先规范化再交给 mathtext 就能通过，因为规范化把 `\frac12` 写成了 `\frac { 1 } { 2 }`、把 `\le` 换成了 `\leq`、把 `\tfrac` 换成了 `\frac`。但矩阵无论如何都通不过。**用 mathtext 评测，矩阵类公式的可编译率和渲染一致率都没法算。** 这是一个必须写进报告的局限。

反方向也可能出错：mathtext 接受一些完整的 LaTeX 会报错的写法（**假阳性**）。本章没有系统地测这个方向，因为手头没有 LaTeX 可以对照（待验证）。

所以本章的"可编译率"只是近似，数字只对 mathtext 成立。正式评测用哪个渲染器，要在选型时实测它和完整的 LaTeX 有多一致（待验证）。选型时至少要看三件事：支持的命令和环境够不够（矩阵、`\text` 里的中文）；速度够不够（要是把渲染比较放进奖励函数，训练时会反复调用它；第 25、34 章的奖励用的是 mathtext 可解析性、规范化字符串和编辑距离，没有比较渲染图）；同一个公式在不同机器上渲染出来是否一致。

**一个不依赖渲染器的补充检查：结构合法率。** `latex_norm.is_well_formed` 只检查我们自己的解析器能不能解析：花括号配不配对、上下标和命令有没有参数。它比真正的编译弱得多，不认识的命令也照样放行，但它不依赖任何渲染器，任何机器上结果都一样。演示集上预测的结构合法率是 15/16 = 0.9375，只有 P15 不合法（第 6 部分）。

### 0.7.4 盲区：能编译不代表对

可编译率只看预测本身，所以它对"排得出来但错了"的预测完全看不见。P8 的 `x_{2}+y^{2}`、P16 的复读四遍，都能被解析（第 6 部分）。如果一个模型永远输出 `x`，它的可编译率是 100%。

所以可编译率从来不单独报告。它的作用是补上编辑距离的一个盲点：区分"错了一点但能用"和"错了一点而且不能用"。

## 0.8 指标四：渲染后图片一致率

### 0.8.1 直觉：把两张图叠在一起对着光看

前面的指标都在比较字符串。可我们常常关心的是"排出来的公式是不是一样"。既然如此，干脆把参考答案和预测都渲染成图片，直接比较图片。

这就像检查两张复印件是否一致：把它们叠在一起，对着光看，有没有对不上的笔画。

这个想法正好能处理规范化器漏掉的写法差异。P7 的 `f'(x)` 和 `f^{\prime}(x)`，规范化器认为不同，但渲染出来一模一样。

**渲染后图片一致率**：渲染以后，两张图一致的样本占可比较样本的比例。

### 0.8.2 比较两张图的步骤

渲染得到的是灰度图，用一个形状为 `(高, 宽)` 的 uint8 数组表示，本章约定 0 是白、255 是墨迹。`compare_images` 分四步：

1. **二值化**：像素值 ≥ 128 的算墨迹（True），其余算空白。抗锯齿会让笔画边缘出现灰色像素，二值化把它们归到一边。
2. **裁剪**：各自裁到"包住所有墨迹的最小矩形"。这样，公式在画布上整体偏左还是偏右、上下留白多少，都不会影响比较。
3. **补齐**：两张图都在右边和下边补空白，补到同样的大小，左上角对齐。
4. **数差异**：

$$
\begin{aligned}
\mathrm{diff} &= \frac{\text{只在一张图里是墨迹的像素数}}{\text{至少在一张图里是墨迹的像素数}} \\
&= \frac{\text{A 异或 B 的个数}}{\text{A 或 B 的个数}}
\end{aligned}
$$

diff = 0 表示逐像素一致，diff = 1 表示没有一个墨迹像素重合。本章默认 diff = 0 才算"渲染一致"。

1 − diff 就是两张图墨迹区域的交并比（intersection over union，IoU）。分母用"或"而不用整张图的像素数，是为了不让大片空白把差异稀释掉。

**手算例子 1**（第 7 部分）。A 和 B 都是 3 × 4 的图，`#` 表示墨迹：

```
A           B
. # # .     . # # .
. # . .     . # # .
. # . .     . # . .
```

1. 二值化后就是上面的样子。
2. 裁剪：两张图的墨迹都在第 1、2 列，第 0 到 2 行，各裁成 3 × 2：

   ```
   A'      B'
   # #     # #
   # .     # #
   # .     # .
   ```

3. 大小已经相同，不用补齐。
4. 异或：只有第 2 行第 2 列不同，1 个。或：A' 有 4 个墨迹，B' 有 5 个，并起来 5 个。diff = 1 / 5 = 0.2000。

**手算例子 2**（第 7 部分）。两张 1 × 4 的图：

```
C = [# . # .]
E = [# . . #]
```

E 的第二笔比 C 右移了一格。

1. 裁剪：C 的墨迹在第 0 到 2 列，裁成 `[# . #]`，宽 3；E 的墨迹在第 0 到 3 列，宽 4。
2. 补齐：C 补成 `[# . # .]`。
3. 异或：第 2 列（C 有 E 没有）、第 3 列（E 有 C 没有），2 个。或：第 0、2、3 列，3 个。diff = 2 / 3 = 0.6667。

只是一笔挪了一个像素，diff 就到了 0.67。0.8.3 节解释 P5 的结果时还会用到这个例子。

**代码**（`miniocr/eval/render.py`，练习 0.7）：

```python
def compare_images(a, b, threshold=128):
    def crop(img):
        ink = img >= threshold                                  # 1. 二值化
        rows = np.flatnonzero(ink.any(1))                       #    有墨迹的行
        cols = np.flatnonzero(ink.any(0))                       #    有墨迹的列
        if len(rows) == 0:
            return np.zeros((0, 0), dtype=bool)
        return ink[rows[0]:rows[-1] + 1, cols[0]:cols[-1] + 1]  # 2. 裁剪

    A, B = crop(a), crop(b)
    H, W = max(A.shape[0], B.shape[0]), max(A.shape[1], B.shape[1])
    PA = np.zeros((H, W), dtype=bool)                           # 3. 补齐
    PB = np.zeros((H, W), dtype=bool)
    PA[:A.shape[0], :A.shape[1]] = A
    PB[:B.shape[0], :B.shape[1]] = B
    union = (PA | PB).sum()
    return float((PA ^ PB).sum() / union) if union else 0.0     # 4. 异或 / 或
```

`ink.any(1)` 沿第 1 维（列方向）求"有没有 True"，得到每一行是否有墨迹，形状 `(高,)`；`np.flatnonzero` 返回 True 的下标，第一个和最后一个就是墨迹的上下边界。两张图都没有墨迹时分母为 0，约定 diff = 0。

渲染本身由 `render(latex)` 完成：调用 mathtext 把 `$latex$` 画成灰度图。`x^{2}` 在 100 dpi 下渲染成形状 (18, 17) 的图；同一个公式渲染两次，diff = 0.0000（第 7 部分，本项目观察）。渲染是确定的，这是比较的前提。

`compare_render(ref, pred)` 把渲染和比较包在一起：参考和预测**都能解析**时才比较；只要有一个不能解析，结果记作"无法判断"（None），而不是"不一致"。

### 0.8.4 盲区

渲染比较看起来最接近"人眼判断"，但它有四个盲区：

1. **无法判断的样本。** 渲染器解析不了的公式没法比较。用 mathtext 时，16 对里有 4 对无法判断（第 7 部分）。这些样本**不能算作"不一致"**：如果那样算，渲染一致率会从 3/12 = 0.2500 变成 3/16 = 0.1875（第 7 部分），而 P3、P4 其实是对的。正确的做法是分开报告"一致率"和"能判断的样本数"。
2. **对排版细节过于敏感。** 间距、括号大小这类不影响含义的差别，都会让结果变成"不一致"（P5、P6）。可以设一个容忍度 `tol`，允许 diff 小于某个值也算一致；但 P12 的 diff 只有 0.018，容忍度一放宽，真错也会被放过去。
3. **依赖渲染器和字体。** 换一个渲染器、换一种字体、换一个 dpi，像素就会变。本章在渲染含汉字的公式时用的是 Noto Sans CJK SC 字体；另一台机器上没有这个字体，结果就可能不同。所以渲染一致率**必须注明用的是哪个渲染器、哪组字体设置**。
4. **只有一个"是/否"，不能定位。** 它告诉你图不一样，但不告诉你哪个符号错了。

有一类更精细的方法，先在渲染图上找出每个字符和它的位置，再把两边的字符一一配对，按配上了多少个打分，这样既不怕整体错位，又能给部分分、能定位。代表是 CDM（Character Detection Matching，Wang 等，2024，待验证）。它是本章精读的选读材料。

| 改坏（改坏率） | 在输入本来正确的样本里，预测规范化后和目标不同的比例 |
| fix_rate | 在输入有错的样本里，预测规范化后和目标相同的比例 |

改坏和 fix_rate 是这版面板特有的，因为只有后纠错才分"输入本来正确"和"输入有错"。这版面板没有 CER_token 和渲染一致率：第三部分的评分脚本 `score_postcorrect` 只按字符算 CER，也不比较渲染图。脚本还会算可解析率（`parse_rate`），但它不是必报项：它只说明语法，不说明对错，连标准答案的可解析率也到不了 1（第 18 章 18.2.1 节）。需要诊断时可以另外列出（第 18、19 章的表里就有），并且要和标准答案的可解析率一起读。但两个比例接近不说明预测忠实：标准答案的可解析率只反映解析器的支持范围和数据分布，不含逐题对错。两道题里一题参考可解析、一题不可解析，模型把两题的可解析状态对调，比例不变，却可能两题都错。

**OCR 面板的精简版**用于第 31 到 35 章：报告 EM_norm、CER、parse_rate，有的章另列 EM_raw 和截断条数。parse_rate 就是 mathtext 近似的可编译率，它的局限见 0.7.3 节。有两项没有报告：

- **CER_token。** 这几章复用第 18 章的 `score_postcorrect`，这个脚本只按字符算 CER。
- **渲染一致率。** 同一个脚本只判断预测能不能解析，不比较渲染图。这个指标还受 mathtext 限制：参考答案解析不了的样本，只能记作"无法判断"，而这几章的 val 里这样的参考答案不少（第 33 章 33.7.3 节有实测比例）。第 32 章的渲染图对照换的是输入图片，第 35 章的渲染比对只用来筛选训练用的伪标签，它们都不是这个指标。

不管用哪一版，都不要只看一个数。两个模型比较时，如果 EM 涨了而 CER 也涨了，说明一个模型"对的更多，但错的时候错得更离谱"，这本身就是一个值得去错例表里看的现象。第 22 章还会给这些数字加上置信区间，判断差别是不是运气。

## 0.10 评测协议与里程碑 M0

有了尺子，还要规定怎样用尺子。这一节讲原则，具体步骤在实验手册的 M0 部分。

### 0.10.1 验证集和测试集

**验证集**（validation set，也叫开发集）和**测试集**（test set）都是模型训练时没见过的数据，但用途完全不同：

- **验证集用来做决定。** 选哪个提示词、学习率取多少、要不要加这批数据、看错例、提出下一步的假设，都只看验证集。可以反复用。
- **测试集是留出集**（held-out set），也就是一直放在一边、不参与开发决定的数据。选型冻结以后，预先登记的候选可以各评一次，只报告数字（和置信区间），不根据结果改任何设置。开发期间不看它的错例；最终报告定稿以后，才可以解封做错例分析。

**类比：模拟考和高考。** 模拟考可以考很多次，考完对答案、分析错题、调整复习重点，这就是验证集。高考只考一次，用来衡量你的真实水平，这就是测试集。如果你提前看到了高考题，并且针对它复习，高考分数就不再代表你的真实水平了。

和高考不同的是，测试集可以评多次：预先登记的几个候选各评一次，选择已经在验证集上定了，只要**不根据测试集做决定**，偏乐观的风险就很小。危险的是"看一次测试集，改一点设置，再看一次"。这样反复几轮，你其实是在测试集上调参，它就变成了第二个验证集，报告出来的数字会系统性地偏高。

**如果发现自己已经根据测试集改了设置怎么办？** 不要掩盖。在报告里写明，然后补一份新的、从来没看过的测试集。

### 0.10.2 每张图片的来源和使用权

验证集和测试集里的每张图片，都要记下它从哪里来、你凭什么能用。建议的清单字段（实验手册里有模板）：

- `id`：唯一编号。
- `file`：图片文件名。
- `sha256`：图片内容的哈希，用来发现重复和意外的改动。
- `source`：来源，例如"TexPixel 某某批次"。
- `license`：使用权依据，例如"作者本人拍摄""某某授权""某某许可证"。说不清楚的，不放进来。
- `split`：validation 或 test。
- `ref`：参考 LaTeX，以及是谁标注、谁校对的。

这件事看起来是行政工作，但项目做到后面要写报告、可能要公开，到那时再追溯每张图的来历会非常痛苦。TexPixel 数据的使用权现在还没有确认，**在确认之前，不要把任何真实数据放进仓库。**

### 0.10.3 按公式分组划分，防止泄漏

如果同一个公式（哪怕是不同的图片、不同的写法）同时出现在验证集和测试集里，或者同时出现在训练集和测试集里，测试集的分数就会偏高：模型可能只是背下了这个公式。这叫**泄漏**（leakage）。

一个简单有效的办法：**按规范化后的参考答案分组**，同一组的样本必须落在同一个集合里。具体做法是对规范化后的参考答案取哈希，用哈希值决定它进哪个集合（第 10 部分）：

```
P1   x ^ { 2 } + y ^ { 2 }   sha1 前 8 位 557c3c98
P8   x ^ { 2 } + y ^ { 2 }   sha1 前 8 位 557c3c98
```

P1 和 P8 的参考答案相同，哈希也相同，所以必定在同一个集合里。即使参考答案的写法不同（`x^2+y^2` 和 `x^{2}+y^{2}`），规范化以后也一样，同样会被分到一起。

但要说准确：这个办法保证的是**规范化结果相同的样本**落在同一边，不是"同一个公式的所有写法"。规范化器没覆盖的等价写法照样会被分开。P7 就是现成的反例（第 10 部分）：

```
f'(x)           f ' ( x )              sha1 模 100 = 20  → test
f^{\prime}(x)   f ^ { \prime } ( x )   sha1 模 100 = 57  → validation
```

两种写法含义相同，却一个进了测试集、一个进了验证集。所以冻结划分之前还要补两件事：用错例分析里发现的等价写法和图片的 `sha256`（以及近重复检查）把该在一起的样本合并成一组，给每组一个明确的分组编号；然后按分组编号划分，而不是直接按规范化字符串划分。

这也只能挡住"完全相同的公式"。"几乎相同"的公式（例如只差一个下标）怎样检查，在项目报告 R1 和第 22 章再细讲。

### 0.10.4 基线

**基线**（baseline）是一个现成的、不经过你改进的系统在验证集和测试集上的成绩。它回答一个问题："什么都不做，能得多少分？"后面所有的改进都要和它比。

M0 的基线定为 TexPixel 当前的模型或 GLM-OCR 服务。跑基线时要记下：模型和版本、图片怎样预处理、提示词、生成参数、日期。少记一项，以后就复现不出来。

### 0.10.5 错例表

只看汇总数字，你知道模型"错了多少"，但不知道"错在哪里"。**错例表**就是把验证集上判错的样本一条条列出来，人工标上错误类型。一个初始的分类可以是：

| 错误类型 | 例子 |
|---|---|
| 结构错误 | 上下标认反（P8）、分子分母颠倒（P9）、根号次数丢失（P11）、矩阵行列错乱（P14） |
| 符号认错 | 形近字母（α/a，P10）、形近汉字（积/枳，P13）、运算符（+/−，P12） |
| 漏识别 / 多识别 | 少了一项、多了一项 |
| 重复输出 | 复读（P16） |
| 语法错误 | 不能编译（P15） |
| 写法差异（其实是对的） | 规范化器没覆盖（P7） |
| 标注错误 | 参考答案本身就错了 |

最后两类是**尺子的错**，不是模型的错。"写法差异"说明要改进规范化器；"标注错误"说明要修正参考答案（修正要记录，而且只能在验证集上发现和修正，测试集的修正要单独说明）。真实项目里，这两类往往不少。

改进规范化器时，要把两件事分开。第 32 章说，看完结果再改口径就是在调评分，第 33 章也坚持官方数字不改，那说的是**已经冻结的结果**：它们按事先定好的协议算出，不改，诊断数字单独列出。而根据验证集错例**开发新版协议**是可以的：规则要升级版本号，所有候选都要用新版重算，最终测试另行安排，不和旧协议下的数字混比。

`formula_tags` 会根据参考答案自动打上"分式""上下标""矩阵""中文""根号""长公式"等结构标签（第 10 部分），帮你按结构分桶看错误分布。错误类型那一栏则要你人工填。

## 0.11 常见错误

| 错误 | 现象 | 原因 | 怎样发现 |
|---|---|---|---|
| 只规范化预测 | EM 低得离谱 | 参考答案仍是原来的写法 | 规范化后 EM 应该 ≥ 原样 EM；检查参考答案是否也经过同一个函数 |
| CER 的分母用预测长度 | 复读的惩罚被压缩，原样复读再多遍，CER 也到不了 1 | 输出越长分母越大 | 构造一个复读样本，看 CER 是否大于 1 |
| 逐样本错误率再平均 | 和别人报告的 CER 对不上 | 短样本被放大 | 写清楚是语料级还是逐样本平均 |
| 不规范化就算 CER | CER 明显偏高 | 写法差异被算成错误 | 用 P1 这类样本检查，距离应该是 0 |
| 规范化器太松 | 分数虚高，错例表里看不到某类错误 | 合并了不等价的写法（例如删掉所有花括号） | 为规范化器写"应该不同"的测试，如 `x^{ab}` 与 `x^ab` |
| 把"无法判断"当作"不一致" | 渲染一致率偏低 | 渲染器解析不了的样本被记成 0 | 单独报告能判断的样本数 |
| 看测试集的错例做决定 | 测试分数偏乐观 | 测试集变成了第二个验证集 | 记录每次看测试集的时间和目的 |
| 换了规范化规则还拿旧数字比 | 改进或退步其实来自尺子 | 评测协议变了 | 规则加版本号，比较前核对 |

下面展开其中三个。

**只规范化预测。** 假设你写评测脚本时，想着"模型的输出写法不统一，规范化一下"，只处理了预测。规范化后的预测是 `x ^ { 2 } + y ^ { 2 }` 这种带空格的格式，参考答案仍是 `x^{2}+y^{2}`，两边永远对不上。演示集上 EM 从 0.3750 变成 0.0000（第 9 部分）。现象很明显，但如果真实数据上 EM 本来就低，你可能以为是模型不行。

**CER 的分母用预测长度。** 演示集上按 token 的总编辑距离是 31，参考总长度 158，预测总长度 172。用参考长度，CER_token = 31/158 = 0.1962；用预测长度，变成 31/172 = 0.1802（第 9 部分）。差别看起来不大，因为演示集里只有一个复读样本。如果一个模型经常复读，它的预测总长度会远大于参考，这个错误会让它的 CER 被严重低估。

具体看一个样本（**数学结论**，第 9 部分有数值）：参考长度为 L，预测把参考原样复读 k 遍，编辑距离是 (k−1)L。原因是每次插入或删除只让长度变 1、替换不改长度，所以编辑距离至少等于两边的长度差 (k−1)L；而预测的前 L 个 token 和参考一模一样，删掉后面多出来的 (k−1)L 个正好做到。分母用预测长度，得到 (k−1)L / (kL) = 1 − 1/k；k = 1、2、3、4 时分别是 0、0.5000、0.6667、0.7500。它随复读次数**上升**，只是被压缩在 1 以下，再怎么复读也趋近于 1 而到不了 1。正确的算法（分母用参考长度）得到 k − 1，即 0、1、2、3，复读越多惩罚越重。所以这个错误把复读的惩罚压扁了：复读十遍只有 0.9000，正确值是 9.0000（第 9 部分）。

**逐样本错误率再平均。** 演示集上，逐样本平均的 CER_token 是 0.3415，语料级是 0.1962（第 9 部分）。差这么多，主要是 P16 的单样本错误率 3.0 把平均值拉高了。两种算法没有对错，但和别人比较时必须用同一种。不规范化直接算按字符的错误率是 0.3130，规范化后是 0.1724（第 9 部分），所以每个数字都要带着它的计算方法一起报告。

## 0.13 小结

- **公式识别**把一张公式图片变成一段 LaTeX。难点是二维结构、形近符号、长序列，以及同一个公式有很多种正确写法。
- **规范化**把等价的写法统一起来：分词 → 逐 token 规则（同义命令、间距、括号尺寸）→ 解析成语法树 → 按规范写法写回（参数带花括号、先下标后上标、去掉多余花括号）。太松比太紧更危险。两边都要规范化。
- **编辑距离用动态规划算**：边界 `D[i][0] = i`、`D[0][j] = j`；`D[i][j]` 取删除 `D[i-1][j] + 1`、插入 `D[i][j-1] + 1`、相同或替换 `D[i-1][j-1] + (a[i-1] != b[j-1])` 三者中最小的。语料级错误率 = Σ 编辑距离 / Σ 参考答案长度，按字符算是 CER，按 token 算是 CER_token。分母用参考长度，所有模型才除以同一个数，复读时错误率可以大于 1。
- **渲染比较**：二值化、裁剪、补齐以后算 diff = (A 异或 B) 的个数 / (A 或 B) 的个数，也就是 1 − IoU。diff 的大小不代表错误的严重程度。
- **五个指标各管一面**：完全匹配严格但不分轻重；编辑距离和错误率能给部分分，但不知道哪个符号重要，按字符和按 token 的结果不同，而且可以大于 1；可编译率只看预测本身；渲染一致率能发现规范化器漏掉的等价写法，但依赖渲染器、对排版细节过于敏感、有些样本无法判断。所以总是报告一组指标：图片识别用 OCR 主任务面板（第 31 到 35 章用它的精简版），第三部分用文本后纠错面板。
- **本章的可编译率和渲染一致率用 mathtext 近似**，只对 mathtext 成立；它不支持矩阵，还会冤枉 `\frac12`、`\le` 这类合法写法。正式渲染器待选型。
- **验证集用来做决定，测试集是留出集。** 选型冻结后预先登记的候选各评一次，不据此改设置；开发期不看测试集错例。按规范化后的公式分组划分，记录每张图的来源和使用权。
- **最常见的两个错误**：只规范化预测，参考答案还是原来的写法，EM 低得离谱；CER 的分母用预测长度，复读的惩罚被压在 1 以下。防法是两边用同一个函数规范化，并构造一个复读样本，检查 CER 能不能大于 1。

**术语表：** 公式识别（formula recognition）、LaTeX、token（词元）、规范化（normalization）、语法树（syntax tree）、递归下降解析（recursive descent parsing）、完全匹配（exact match）、编辑距离（edit distance / Levenshtein distance）、字符错误率（CER）、按 token 的错误率、语料级（corpus-level）、可编译率、渲染后图片一致率、交并比（IoU）、验证集（validation set）、测试集（test set）、留出集（held-out set）、泄漏（leakage）、基线（baseline）、错例表。
